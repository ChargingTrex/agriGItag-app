# D-030: Batch attribution and grading loss are two separate checks

**Date:** 2026-10-31  
**Status:** Accepted (Architect-Gate ruling on B08 review P2-4; implemented by B15)

## Context

B08 shipped one batch rule, `batch_quantity_unattributed`, comparing the batch's output kilograms (packed, else
graded, else received) with the sum of `batch_shares.kg_contributed`, at 5 %. Shares are built from the lots'
received kilograms, so the rule really measured grading loss: every normal batch that loses more than 5 % in
sorting raised a warn. It reproduced backend-design §5 only because the reference batch loses 93.75 %
(320 kg procured, 20 kg graded, PRD §12.2).

The sources describe two different things:
- Dataflow Stage 7: "sums component-lot quantities against total procured quantity; … flags variance beyond
  threshold, e.g. >5 %". That is attribution: is every received kilogram owned by a farmer's share?
- PRD §12.2: "the 20 kg batch is never attributed back to the three farmers". FR60 answers it with each
  farmer's share (%) on the public page. Once shares exist (B09 `shares.py`, Σ share_pct = 100), every output
  kilogram is attributed in proportion. What stays suspicious in the sample is the 320 → 20 kg drop.

## Decision

`quantity_reconciliation._batch` raises two warn-severity codes:
1. `batch_quantity_unattributed`: the batch has `total_received_kg` and either no shares, or Σ
   `kg_contributed` differs from `total_received_kg` by more than 5 % (the existing `TOLERANCE`).
2. `grading_loss_high`: the output (packed, else graded) is more than `grading_loss_warn_pct` below
   `total_received_kg`, or more than 5 % above it. `grading_loss_warn_pct` lives in `features.yaml`
   (default 15, tenant override per D-017). Details carry received kg, output kg, loss %, limit % and `"unit": "kg"`.

Neither code is a hold, so neither blocks a gate. B09 gates block on `severity == hold` only (lot, batch,
plot and reading holds from `run_gate_checks`), as already agreed in TODO.

## Advantages

- Each code means what its name says; an FPO Admin no longer sees a warn on every normal batch.
- Attribution follows Dataflow Stage 7 literally; loss follows the PRD §12.2 symptom.
- The reference batch still fails visibly (`grading_loss_high`, 93.75 % against 15 %).
- The loss limit is tunable per FPO without a release (D-017).

## Compromises

- One more flag code and one more feature key (Features schema, OpenAPI, regenerated clients).
- Grading loss really depends on the crop, not the FPO; a per-crop limit belongs in the Standards Profile
  next to the yield margins (D-015), which costs a profile schema change and a new profile version. The
  15 % default is a guess to calibrate after season 1.
- `batch_quantity_unattributed` can rarely fire once B09 always creates shares from intakes; it stays as a
  cheap safety net for hand-edited or partly attributed batches.

## Revisit when

- Season 1 shows loss differs by crop: move `grading_loss_warn_pct` into the Standards Profile.
- Product decides a batch losing more than X % must be held, not warned.
