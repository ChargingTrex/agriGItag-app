# D-048: The demo seed writes the reference history by direct model inserts; only the batch goes through `create_batch`

**Date:** 2026-10-31  
**Status:** Accepted (B12)

## Context

`make seed` must reproduce the PRD §12 reference batch `FGP8T4033HM7` *with its known problems*
(backend-design §5): lots with no quality readings, dates in 2025–26, intakes of lots that never passed the
moisture ready gate, and a grading of grade "A" without readings. The API now refuses most of that on purpose
(`moisture_gate_failed`, `unknown_grade_for_profile`), so the seed cannot replay the record through the
public routes. The B12 brief asks for one consistent write path, documented, and for the batch to be created
by the real `create_batch` with a `client_id`.

## Decision

1. Everything that is *history* (FPO, processor, GI 883 and its non-official fixture region, crop and
   profile, inputs, staff and farmer users, memberships, consents, plots, lots, farm events with their
   versions, intakes) is written by **direct ORM inserts** in `apps/api/agritrace/seed/demo.py`. The ORM
   listener writes audit rows (system actor) for the audited models; `event_versions` is not audited, and the
   seed does not add the explicit per-version rows the events API writes (demo history only).
2. The batch is made by `lots_batches.service.create_batch` with the fixed client id `BATCH_ID`: shares
   (31.250 / 62.500 / 6.250 %), `total_received_kg` (320 kg), the intake approval, the rule run and the GI
   re-check all come from production code. The seed then sets the reference codes (`FGP8T4033HM7`,
   `COMBO_LOT_6C1DCCFE`), adds the legacy grading event (grade "A", 20 kg, 2026-07-30), sets `graded_kg = 20`
   with the batch still `created` (no grade computation exists, so the grading gate stays closed) and re-runs
   `run_gate_checks` so the stored flags are what the rules say.
3. Idempotency: the marker is the reference batch (`BATCH_ID`), the last row written. If it exists, a re-run
   returns without writing. An FPO with the demo code but no batch (made by an admin, or by
   `tests/integration/test_config_imports.py`) is reused and given the reference values. The shared rows
   (GI tag, region, crop, profile) are get-or-create and committed first. Caveat: if `create_batch` refuses a
   gate it commits the history before raising (`_refuse`, D-033), so a re-run then fails on the seeded
   phones; recover by deleting that FPO's rows and re-running (review B12-r1 P2-2).

## Consequences

- **ADV:** the reference record is reproduced as captured, including what the API now rejects; the parts
  B09/B15 own (shares, received total, flags, GI) are not re-implemented in the seed.
- **COMPROMISE:** direct inserts skip request validation. Mitigations: `tests/unit/test_seed_demo.py` runs the
  real lot and batch rule modules on the seed's own data and asserts the exact flag set, and
  `tests/e2e/test_reference_batch.py` runs the gates, the fixes and the publish on the seeded rows. The
  reference codes and `graded_kg` are written after `create_batch`, which a real batch never does.
- The fixture region is labelled NON-OFFICIAL; production outlines are built with
  `infra/scripts/gi_boundary/build_virudhunagar.py` and uploaded with `POST /v1/gi-tags/{id}/region-versions`
  (D-019).
