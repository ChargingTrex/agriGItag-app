# D-065: DPDP erasure anonymises in place with Core statements and fixed placeholders; a repeat is a no-op

**Date:** 2026-11-04  
**Status:** Proposed (WP-B24; Architect-Gate review pending)

## Context

`POST /v1/farmers/{id}/erase` replaces the manual erasure transaction of `docs/ops/dpdp-data-subject-runbook.md` §2.
The traceability record (events, event versions, lots, batches, consents, audit trail) is append-only (D-005) and
must stay readable, so rows cannot be deleted: the personal fields are overwritten. `users`, `farmers` and `plots`
are `Audited`: an ORM attribute change makes the flush listener write `{column: [old, new]}` into `audit_log`, which
is itself append-only. Erasing through the ORM would copy the name, phone, address and survey number into a table
that can never be cleaned.

## Decision

1. Erasure writes Core `UPDATE`/`DELETE` statements (no ORM attribute changes on audited rows) in one transaction
   and records a single `audit_log` row `farmer.erase` with the admin's reason and row counts only.
2. Placeholders, as in the runbook: `farmers.name = 'Erased <farmer code>'`; `users.name = 'Erased farmer'`;
   `users.phone = 'erased:<user id>'` (keeps NOT NULL and the unique index, never matches an E.164 sign-in);
   `name_local`, `photo_key`, `gi_authorised_user_no`, `pin_hash`, `plots.land_record_ref` (also in
   `plot_revisions.snapshot`) become NULL; farmer and user `suspended`. Unlike the runbook SQL, `farmers.address`
   keeps its village-level parts (village, block, taluk, district, state) and loses only `pin`: the public page
   requires a village-level `place`, so a NULL address made the rebuild fail and left the old page, with the
   name, online (found by the B24 test). Earlier `page_builds` snapshots lose
   `farmer_name` and `gi_authorised_user_no` on the farmer's own lots (matched by lot code, not by name).
3. Every open consent gets `revoked_at` (the only column the `consent_records` trigger allows), so rebuilt pages
   show "Farmer N" (W01/B10). The farmer membership is removed and devices revoked with the B14 helper
   `_end_farmer_access`. The `users` row, its OTP challenges and notifications are erased only when no other
   membership is left: an account that is also an officer, or a farmer of another FPO, is not this FPO's to erase.
4. ID-document rows are deleted; their `id-docs` objects (every version) are deleted before the commit, so an S3
   failure commits nothing and the call can be repeated.
5. A second call finds the `farmer.erase` audit row and answers 204 doing nothing (no new error code).

## Advantages

- No new copy of the erased data lands in an append-only table; the old audit rows are untouched (D-005 holds).
- Lots, batches and pages keep working: the farmer row and its ids exist, names read "Erased F-007" / "Farmer N".
- Idempotent without a status column or migration; retries after a failure are safe.

## Compromises

- The erasure itself has no per-column audit trail, only counts; who did it, when and why is recorded.
- PII already in old `audit_log.diff` rows and in `event_versions` free text stays until the Architect-Gate rules
  on a D-005 exception (runbook §2 "Residual").
- The farmer's village stays on the farmer row and on the page; with "Farmer N" and the farm area it can still
  narrow down a person in a small village. This was already public before the erasure.
- An account shared with another FPO or an office role keeps its phone and name; the data officer handles that
  person's other memberships by hand.
- Old `public-pages` object versions still hold the name until someone deletes them (runbook §2 step 4); the
  route only queues the rebuild.
