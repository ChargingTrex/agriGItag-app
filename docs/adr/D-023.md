# D-023: Enum columns as VARCHAR(32) with CHECK constraints, not PostgreSQL ENUM types

**Date:** 2026-10-29  
**Status:** Accepted (Architect-Gate, B01 review)

## Context

The schema has 31 enumerated columns (roles, statuses, event types, categories). PostgreSQL offers native ENUM types; adding a value to one needs `ALTER TYPE … ADD VALUE`, which cannot run inside a transaction on older versions and cannot remove or reorder values.

## Decision

Enum columns are `VARCHAR(32)` with a named `CHECK (col IN (…))` constraint generated from the Python `StrEnum` in `core/enums.py`. The Python enum is the source of truth; a unit test pins each column to its enum values and an integration test (B01 r2, R3) compares the live `pg_get_constraintdef` output with the enum.

## Advantages

- Adding a value is an ordinary, transactional migration that only replaces a CHECK
- No type dependency ordering in migrations; downgrade is trivial
- Reflects cleanly in SQLAlchemy and Alembic autogenerate (as VARCHAR)

## Compromises

- `alembic check` does not compare CHECK constraints, so a value added to the Python enum without a migration is not reported as drift; the live-constraint integration test closes that gap and must stay in CI
- Slightly larger storage than a native enum (irrelevant at pilot scale)
- The CHECK name convention must be stable so migrations can replace it by name

## Revisit when

- If a column needs ordering semantics that a native enum would give for free
