# D-035: The Sell QR `sig` is an unkeyed checksum; authenticity comes from the server's lot record

**Date:** 2026-10-31  
**Status:** Accepted (M08)

## Context

At the collection centre the farmer shows a QR for the lot that is ready to sell and the QC app (M11) scans it
(UserFlows §Selling to the FPO). The plan fixes the payload as `{lotId, farmerId, packedKg, sig}`. A keyed signature
(HMAC-SHA256 with a per-device secret) needs a key the verifier also holds. None exists: M06 keeps only per-install
tokens and a device id in the keystore (D-027), the server never sees a device secret, and two phones share nothing.
A per-device HMAC would therefore be unverifiable by M11 and by the server.

## Decision

1. The QR text is compact JSON `{"lotId": "<uuid>", "farmerId": "<uuid>", "packedKg": 300.0, "sig": "<11 chars>"}`,
   packedKg in kilograms rounded to 0.1 kg.
2. `sig` = base64url without padding of the first 8 bytes of SHA-256 over the UTF-8 string
   `lotId|farmerId|packedKg` with packedKg written with one decimal (`300.0`).
3. `SellQr.decode` (`apps/mobile/lib/features/sell/sell_qr.dart`) returns null for anything that is not this shape
   or whose `sig` does not match, and returns packedKg at the one decimal the `sig` covers. It is importable by the QC
   screens of the same app; M11 r1 still parses the JSON itself and must switch to it (review M08-r1 H-1).
4. Trust comes from the lookup, not from the QR: M11 opens `lotId` from its pulled data or the API, checks that it
   belongs to `farmerId` and that `packedKg` matches the server's packed kg (B09 intake already checks weight vs
   packed kg).

## Advantages

- No secret to provision, rotate or leak; works offline on both phones
- Catches a garbled, truncated or hand-built payload before the QC officer acts on it
- Three lines on each side; the same rule is easy to port to Python if the server ever reads the QR

## Compromises

- Anyone can compute the checksum, so it proves nothing about who made the QR; a forged QR naming a real lot is caught
  only by the server lookup and the weighing
- The field is named `sig` although it is not a signature (kept because the plan fixed the payload)
- A keyed or server-signed QR would not stop the bigger risk either: someone showing a screenshot of another farmer's
  genuine QR. The real controls are the QC officer checking the person against the farmer name M11 shows, and B09's
  server-side FPO scope, lot status and weight-vs-packed check
- B10's `GET /v1/lots/{id}/qr` encodes only the unsigned lot code, so it is not a signed alternative today

## Revisit when

- Forged QRs become a real problem, or the QR must work without any lookup: the server signs `lots.qr_payload` with an
  FPO key at pull time (B07 + M02 mirror), the phone shows it as is and M11 verifies with the public key. The slot exists: the unused `Lots.qrPayload`
  column
