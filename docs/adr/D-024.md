# D-024: Phone + OTP + PIN session model

**Date:** 2026-10-29  
**Status:** Accepted (B02; Architect-Gate review pending)

## Context

Farmers "log in once" with a phone number and an SMS code and stay signed in on a phone that is often
shared with the family (User Flows §Log in once). Field officers, QC officers and admins add a 4-digit PIN
(System Architecture §Security, privacy and consent). The P00 portal codes against a discriminated
OTP-verify response and requires that no refresh token, role or FPO id is released before the PIN passes.
Every API call must be scoped to the caller's FPO and role, and a session is tied to one device.

## Decision

- **OTP.** `POST /v1/auth/otp/request` stores a challenge (HMAC-SHA256 of `phone:code` keyed with
  `JWT_SECRET`; never the code): 6 digits, 5-minute expiry, one request per phone per 60 s (429
  `rate_limited`), 5 wrong attempts lock the challenge (409 `otp_locked`). Unknown numbers get a challenge
  but no SMS, and verify answers `otp_invalid` exactly like a wrong code. With `OTP_DEV_CODE` set (never in
  prod) that code is the challenge's code and no SMS is enqueued.
- **Verify.** Farmers get `{kind: "session", access_token, refresh_token, expires_in, roles[], fpo_id}`.
  Office roles get `{kind: "pin_required", pin_token, expires_in, pin_set}`; the device is bound but stays
  signed out until the PIN passes.
- **pin_token.** HS256 JWT, `typ=pin`, 5 minutes, claims `sub` (user) and `dev` (device) only. It is
  accepted only by `POST /v1/auth/pin/verify`; `get_current_user` refuses it.
- **PIN.** Argon2id hash on `users.pin_hash` (one PIN per person across FPOs and devices; migration 0002).
  5 wrong PINs lock it for 5 minutes (409 `pin_locked`; `pin_invalid` 422 before that). An office user's
  first PIN is chosen at the PIN step (`pin_set: false`); `POST /v1/auth/pin` changes it with a session.
- **Access token.** HS256 JWT, `typ=access`, 15 minutes: `sub`, `fpo`, `role`, `dev`, `sa` (super-admin
  flag), `jti`. `get_current_user` decodes it and does one indexed read: is `dev` still signed in for
  `sub`. Multi-FPO users are scoped to their oldest membership for now.
- **Refresh token.** Opaque `<device_id>.<256 random bits>`; only its SHA-256 is stored on
  `devices.refresh_token_hash`, one per device. Every refresh rotates it. Presenting any other token of
  that device (an already-rotated one) is reuse: the device is revoked and the answer is 401
  `refresh_reused`. Logout revokes the device. Refresh tokens do not expire on their own (the farmer
  stays signed in for the season).
- **Web.** With `X-Client: web` the refresh token travels only as an httpOnly, Secure, SameSite=Strict
  cookie on path `/v1/auth` (browser-session lifetime) and the body field is null (D-022).

## Advantages

- No password anywhere; farmers never re-enter anything after the first SMS
- Stolen access tokens die within 15 minutes; logout and reuse detection take effect on the next request
  because of the device check
- Office sessions need phone possession plus a PIN; no role, FPO or refresh token leaks before the PIN
- A leaked `otp_challenges` table reveals nothing without the server secret
- One `devices` row per installation gives operators a "sign this phone out" lever

## Compromises

- One indexed DB read per request for the revocation check (cacheable later)
- One refresh hash per device: two refreshes racing from the same app look like reuse and sign the device
  out, so clients must serialise refresh calls
- A 4-digit PIN hash is brute-forceable offline by anyone who can read `users` or `audit_log` (users is
  audited, so PIN changes appear in diffs); the PIN's protection is the online lockout after an OTP
- Whoever passes an office user's first OTP chooses the PIN (same trust as the OTP itself)
- The OTP lock is per challenge: an attacker gets 5 guesses per minute per phone (1 in 200,000 per try)
- Rotating `JWT_SECRET` signs everyone out and voids codes in flight
- Refresh tokens never expire by time; a lost phone stays signed in until someone revokes the device

## Revisit when

- When a security review asks for idle expiry of refresh tokens (e.g. 90 days via `last_seen_at`) or a
  PIN prompt on each app open for office roles
- When the first user with memberships in two FPOs needs to switch between them
- If the revocation read shows up in request latency (move it to a Valkey set)
- If SMS abuse appears (add per-IP limits in front of `otp/request`)
