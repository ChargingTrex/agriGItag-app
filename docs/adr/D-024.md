# D-024: Phone + OTP + PIN session model

**Date:** 2026-10-29  
**Status:** Accepted (B02; amended in review round 2, 2026-10-30; amended 2026-11-02 by B23; Architect-Gate
review pending; the 30 d staff / 90 d farmer session lifetimes and the SMS-only sign-in risk (ASVS 2.7.1) accepted by the Architect-Gate at G5, 2026-11-02, farmer figure pending user/FPO confirmation)

## Context

Farmers "log in once" with a phone number and an SMS code and stay signed in on a phone that is often
shared with the family (User Flows §Log in once). Field officers, QC officers and admins add a 4-digit PIN
(System Architecture §Security, privacy and consent). The P00 portal codes against a discriminated
OTP-verify response and requires that no refresh token, role or FPO id is released before the PIN passes.
Every API call must be scoped to the caller's FPO and role, and a session is tied to one device.

## Decision

- **OTP.** `POST /v1/auth/otp/request` stores a challenge: HMAC-SHA256 of `phone:code`, keyed with a key
  derived from `JWT_SECRET` for OTP use only. The code itself is never stored.
  - The code has 6 digits and expires after 5 minutes.
  - Each phone may request one code per 60 s and at most `OTP_DAILY_CAP` codes (default 10) in any
    24 hours; beyond either limit the answer is 429 `rate_limited` with `retry_after_s`.
  - 5 wrong attempts lock the challenge (409 `otp_locked`).
  - Unknown numbers get a challenge but no SMS, and verify answers `otp_invalid` exactly like a wrong code.
  - With `OTP_DEV_CODE` set (never in prod), that code is the challenge's code and no SMS is enqueued.
- **Verify.** Farmers get `{kind: "session", access_token, refresh_token, expires_in, roles[], fpo_id}`.
  Office roles, and every super-admin whatever their membership, get
  `{kind: "pin_required", pin_token, expires_in, pin_set}`. The device is bound but stays signed out until
  the PIN passes. A device id that is signed in for another user is refused (409 `device_in_use`).
- **pin_token.** HS256 JWT, `typ=pin`, 5 minutes, claims `sub` (user) and `dev` (device) only.
  - Only `POST /v1/auth/pin/verify` accepts it; `get_current_user` refuses it.
  - Once a sign-in on its device succeeds, an earlier pin token is spent (`iat < signed_in_at`).
- **PIN.** An Argon2id hash on `users.pin_hash`: one PIN per person across FPOs and devices (migration
  0002).
  - Lockout: `pin_invalid` (422) for a wrong PIN, then the 5th wrong PIN locks it for 5 minutes (409
    `pin_locked`).
  - An office user's first PIN is chosen at the PIN step (`pin_set: false`).
  - `POST /v1/auth/pin` changes it with a session plus the current PIN, under the same lockout.
  - The audit trail records PIN changes as `"[redacted]"`. Every `*_hash` / `*_secret` column is
    redacted in `audit_log` diffs (`core.audit.is_secret_column`).
- **Access token.** HS256 JWT, `typ=access`, 15 minutes, with 30 s leeway for clock differences between
  containers. Claims: `sub`, `fpo`, `role`, `dev`, `sa` (super-admin flag), `jti`.
  - `get_current_user` decodes it and does one indexed read: is `dev` still signed in for `sub`, and was
    the token issued at or after the device's last OTP/PIN sign-in (`devices.signed_in_at`)?
  - A token killed by logout or by reuse detection therefore stays dead after the device signs in again.
  - Multi-FPO users are scoped to their oldest membership for now.
- **Refresh token.** Opaque `<device_id>.<256 random bits>`.
  - Only its SHA-256 is stored, on `devices.refresh_token_hash`.
  - Every refresh rotates it and keeps the rotated-out hash in `devices.previous_refresh_token_hash`.
  - Presenting that previous token again is reuse: the device is revoked and the answer is 401
    `refresh_reused`.
  - Any other unknown token is a plain 401 and changes nothing, so knowing a device id is not enough to
    sign a device out.
  - Logout revokes the device.
  - ~~Refresh tokens do not expire on their own: the farmer stays signed in for the season.~~ Superseded
    on 2026-11-02, see "Amendment 2026-11-02" below.
- **Web.** The refresh token travels only as an httpOnly, Secure, SameSite=Strict cookie on path
  `/v1/auth`, with browser-session lifetime (D-022). This applies with `X-Client: web` and whenever the
  token arrived in the cookie. The body field is then null, so page scripts never see the token.
- **Responses.** Device ids appear only in the caller's own `GET /v1/me`. Consent and other responses
  that farmers or viewers can read never carry them.

### Amendment 2026-11-02 (B23, SEC ASVS L1 review P1-1, ASVS 3.3.2)

- **Absolute session lifetime.** `POST /v1/auth/refresh` with the device's current refresh token refuses
  with 401 `session_expired` and revokes the device when its last OTP/PIN sign-in (`devices.signed_in_at`)
  is older than the limit for the session's role: `SESSION_MAX_DAYS` (default 30) for every staff role and
  for super-admins, `SESSION_MAX_DAYS_FARMER` (default 90) for farmer sessions. The role is the one of the
  membership the refresh already loads. A device never stamped with `signed_in_at` counts
  as expired (fail closed). A guessed or rotated-out token keeps its earlier answer (`unauthorized` /
  `refresh_reused`), so a guess still cannot sign a device out. Access tokens need no change: they live
  15 minutes and cannot be renewed without a refresh. The phone (`session.dart` `_doRefresh`) and the
  portal (`AuthProvider.tsx` `endIfRejected`) already end the session on any 401 from refresh.
- **Device revocation.** `POST /v1/devices/{device_id}/revoke` (optional body `{reason}`) signs a lost or
  stolen phone out. The device's own user may call it for their own device; an FPO admin may call it for
  any device whose user holds a membership in the admin's FPO. Other roles get 403; a device outside the
  caller's FPO gets 404. It uses the same sign-out as logout (`revoked_at` set, refresh hashes cleared) and
  writes an `audit_log` row `device.revoke` with the actor and the reason. The device's next request and
  refresh then answer 401.
- **Finding the device.** `GET /v1/users/{user_id}/devices` lists a user's devices, newest first, with
  `signed_in_at` and `revoked_at`. The same check as the revoke route applies: the user themself, or an
  FPO admin of the user's FPO; 404 outside the FPO, 403 for other roles. The admin picks the lost phone
  there, then revokes it.
- **Accepted deviation for farmers (ASVS 3.3.2), pending FPO/user confirmation.** ASVS L1 asks for
  re-authentication at least every 30 days. Farmer sessions get 90 days instead, following UserFlows
  §Design rules ("log in once"). 30 days would mean four to six SMS codes a chilli season, often during
  harvest, in the field and offline. A farmer token can write only that farmer's own records. A lost phone
  can be revoked at once by the farmer or the FPO office. The phone's outbox survives the sign-out, so
  nothing is lost. Staff keep 30 days, because they hold FPO-wide powers and use shared PCs. If the FPO or
  the user rejects the deviation, set `SESSION_MAX_DAYS_FARMER=30`; no code change is needed.
- **Consequences.** A farmer types an SMS code again every 90 days and an office user every 30 days.

## Advantages

- No password anywhere; farmers re-enter only an SMS code, once every `SESSION_MAX_DAYS_FARMER` (90 days)
- Stolen access tokens die within 15 minutes. Logout and reuse detection take effect on the next request,
  and survive a later sign-in on the same device.
- Office and super-admin sessions need phone possession plus a PIN. No role, FPO or refresh token leaks
  before the PIN.
- A leaked `otp_challenges` table reveals nothing without the server secret, and the audit trail holds no
  credential material
- One `devices` row per installation gives operators a "sign this phone out" lever

## Compromises

- (G5, 2026-11-02) Sessions now end after 30 days for staff and 90 days for farmers; a farmer re-enters an SMS code up to four times a chilli season, and a lost phone stays usable until the admin revokes it via `POST /v1/devices/{id}/revoke` or the lifetime runs out.


- One indexed DB read per request for the revocation check (cacheable later)
- Reuse detection remembers only the last rotated-out token, so an older stolen token is a plain 401
  rather than a revocation. Two refreshes racing from the same app look like reuse and sign the device out,
  so clients must serialise refresh calls.
- A 4-digit PIN hash is brute-forceable offline by anyone who can read the `users` table. The PIN's
  protection is the online lockout after an OTP. The hash never reaches `audit_log`.
- Whoever passes an office user's first OTP chooses the PIN (same trust as the OTP itself). Accepted for
  the pilot (B02-r1 P2-6).
- The OTP lock is per challenge. With the daily cap, an attacker gets at most 50 guesses a day per phone:
  10 challenges × 5 tries, or 1 in 20,000 a day.
- A shared phone must be signed out by its current user before another user can sign in on it
- Rotating `JWT_SECRET` signs everyone out and voids codes in flight
- ~~Refresh tokens never expire by time; a lost phone stays signed in until someone revokes the device~~
  (2026-11-02: a sign-in now lasts at most `SESSION_MAX_DAYS` / `SESSION_MAX_DAYS_FARMER`, and
  `POST /v1/devices/{id}/revoke` exists)
- Farmers repeat the SMS code every 90 days and staff every 30 days (amendment 2026-11-02). The farmer
  limit deviates from ASVS 3.3.2 (accepted, pending FPO/user confirmation).

## Revisit when

- When a security review asks for idle expiry of refresh tokens (e.g. 12 h for web via `last_seen_at`,
  SEC review 3-7) or a PIN prompt on each app open for office roles
- When B03/P01 can issue an admin-set initial PIN for office users, retire first-OTP-sets-PIN
- When the first user with memberships in two FPOs needs to switch between them, and when B03/B10 define
  what a super-admin may see across FPOs
- If the revocation read shows up in request latency (move it to a Valkey set)
- If SMS abuse appears (add per-IP limits in front of `otp/request`)
