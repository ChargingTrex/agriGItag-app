# D-034: QC mode records intake on the lot (offline) and grading / final packing on the batch (batch list online)

**Date:** 2026-10-31  
**Status:** Accepted (M11)

## Context

The M11 brief describes one linear QC flow on a scanned lot: lot card → intake → grading form → final packing.
The data model splits it in two subjects:

- **Intake** (Dataflow Stage 7) is a lot event; the intake moisture reading is a lot reading (`lot_id`, stage
  `intake`).
- **Grading and final packing** (Stages 8–9) happen after the FPO admin has merged received lots into a batch on
  the portal (UserFlows §Create a batch, §Grade a batch: "Scan the batch QR"). The grade engine computes a batch's
  grade from readings with that `batch_id` (`quality.service.compute_grade_for_batch`), the grading approval and the
  "packed ≤ graded" gate are batch gates (D-033), and `GradingPayload` / `FinalPackingPayload` carry no subject of
  their own: the event version's subject is the batch.

Grading readings saved against a lot would be stored but never graded. The phone, however, has no batch table and no
batch pull entity (M01/M02), and its Lots table holds no lot code (the pull drops `code`; `lib/core/db` and
`lib/core/sync` are outside M11's paths).

## Decision

1. **Two entries on the QC home:** "Receive lot" (scan → lot card → intake check) and "Grade batch" (batch list →
   grading form → final packing).
2. **Lot side, fully offline.** A scanned code is M08's QR `{lotId, farmerId, packedKg, sig}` or a bare lot id,
   looked up in the local Lots table; a lot not pulled yet is shown from the QR's own fields. The fallback when the
   camera cannot read the QR is a list of the lots on the phone that are `ready_for_sale` (tap to pick), not a typed
   lot code: no typing, and nothing to match a typed code against locally.
3. **Batch side, list online, saving offline.** The batch list comes from `GET /v1/batches` (generated client,
   D-003), keeping `created` (to grade) and `graded` (to pack). The readings (`quality_reading`, `batch_id`, stage
   `grading`) and the `grading` / `final_packing` events (payload key `batch_id`, lifted onto the event version as
   its subject by M02) are saved through `EntriesDao.save` in one transaction and pushed by the outbox, exactly like
   every other entry. Entries for a batch have `lotId` null and `farmerId` `''` (the column is NOT NULL).
4. The phone only previews (D-006): the weight check, moisture limit, plausibility, grade, declared-vs-computed and
   packed-vs-graded checks all run again on the server.

## Consequences

- **ADV:** grading readings land on the subject the grade engine reads; no new Drift table, migration or pull entity;
  every save works without signal; payloads match the server schemas field for field (tested against
  `packages/openapi/openapi.json`).
- **COMPROMISE:** opening the batch list needs signal (one sentence and "Try again"); only the first page (50
  batches) is listed; a lot not yet pulled to the phone cannot be picked from the fallback list (its QR still works);
  batch QR scanning waits for B10's batch QR content.

## Revisit

When B10 defines the batch QR, scan it on the "Grade batch" path. If QC officers need to grade without signal, add a
`batch` pull entity and table (M02/M13, schema v3) and drop the online list. If typed lot codes are needed, store the
pulled `code` in Lots (schema v3) and add a code keypad.
