# D-033: Lifecycle gates answer one 409 listing every unmet reason; gate records are append-only

**Date:** 2026-10-31  
**Status:** Accepted (B09)

## Context

The batch lifecycle has human gates (Dataflow §4): ready for sale (automatic moisture gate), intake,
batch merge with a second sign-off above a threshold, grading approval (FR49), final packing (≤ graded kg)
and publish. The portal greys the action buttons and must show *why* (P04 "grey-button reasons"), often
several reasons at once (not graded, not packed, an open hold flag). The approvals, intakes and lot shares
those gates write are commercial records that end up on public pages and labels.

## Decision

1. Every gate raises the existing registered error `gate_not_met` (409) with
   `details.reasons = [{code, message, ...context}]`, listing **all** unmet conditions, not the first.
   Reason codes (data, not API error codes): `lot_status`, `moisture_gate_failed`, `lot_not_ready`,
   `lot_already_batched`, `intake_not_current`,
   `lot_not_received`, `lot_not_received_by_processor`, `mixed_crops`, `lot_quantity_zero`,
   `same_approver`, `batch_status`, `not_graded`, `grade_incomplete`, `declared_above_computed`,
   `grading_not_approved`, `packed_above_graded`, `final_packing_missing`, `already_published`,
   `second_signoff_missing`, `open_hold_flag` (any active hold on the batch, its lots, their plots,
   events or readings, from `rules_flags.run_gate_checks`).
2. Before raising, the gate commits what it has already refreshed: the flags of its synchronous rule run
   (so `/v1/flags` shows the same holds the reasons name) and, on publish, the GI re-check
   (`gi_verified`, `gi_block_reasons`). The change the gate guards (state, approval, build) is not made.
3. `batch_approvals`, `lot_intakes` and `batch_shares` get the 0001 `forbid_change()` trigger
   (migration 0004): rows are added, never updated or deleted (D-005).
   **Corrections add rows (CLAUDE.md §6):** until the lot is batched, a wrong intake is corrected by a new
   `lot_intakes` row with `supersedes_intake_id` (UNIQUE: each intake corrected once) and a mandatory
   `correction_reason`; the lot's current intake is the row nothing supersedes
   (`lots_batches.models.current_intake()`), and the batch merge and the B08 reconciliation read only
   current rows. Once the lot is in a batch the correction is refused with reason `lot_already_batched`.
4. GI is never a publish blocker: a batch whose GI re-check fails is published without the GI badge
   (`gi_verified=false`, `gi_block_reasons`, FR29).

### Ops procedure: a wrong intake after batching (interim, until a void endpoint exists)

Shares are printed on the public page, so a batched quantity is never edited in place. The FPO admin
asks the operator to (1) record why in the batch's audit trail (a support ticket referenced in the
batch approval note), (2) void the batch: do not publish it, or if published, rebuild its page with a
visible "withdrawn" notice (B10), (3) once a void path exists (owner B10/B11, TODO.md), return the
lots to `received`, correct the intake through the API and merge them into a new batch with a new code.
Until then the trigger is never disabled for this; the batch stays unpublished and the lots are
re-merged only after the void path ships.

## Advantages

- One error code for clients; new gate conditions are additive data (D-020), not new API codes
- The admin sees every blocker at once instead of fixing them one round trip at a time
- Gate records are tamper-evident for GI and certification audits

## Compromises

- OpenAPI does not enumerate reason codes; this ADR and the route descriptions are the list
- A wrong intake is corrected only before batching; after it, the batch must be voided (no endpoint yet)
- A failed gate still commits the refreshed flags (a write on a refused request)

## Revisit when

- Product asks for intake corrections or batch splits: add correction rows rather than relaxing the trigger
