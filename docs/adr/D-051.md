# D-051: Portal CSV exports are written in the browser with a BOM and a formula guard; a lot's share of the final packed kg is derived (batch packed kg × share %) and labelled as derived

**Date:** 2026-10-31 (amended in P05 round 2)  
**Status:** Accepted (WP-P05)

## Context

P05 adds CSV downloads to the FPO admin portal (plan §7.3 P05, FR21, FR58): the batch's lots and shares, and the
dashboard farmer table. The audit trail CSV already comes from the API (B11 `GET /v1/batches/{id}/audit-export.csv`,
formula guard in `reporting.service.csv_cell`, no BOM). The other two hold only data the portal has already loaded
(`BatchOut.shares`, `LotOut`, farmer names, `FarmerRow`), so no new route is needed. Farmer and village names are
often Tamil; Excel opens a UTF-8 CSV without a BOM as the system code page and shows garbage. Final packing is recorded
per batch (`BatchOut.packed`); `LotOut.packed` is on-farm packing (Stage 6), a different figure. The Orchestrator's P05
brief asks for a packed kg per lot.

## Decision

1. The portal writes these CSVs itself (`features/exports/exportModel.ts`, ~15 lines, no library): RFC 4180 quoting,
   CRLF line ends, a UTF-8 BOM at the start. The saved audit CSV gets the same BOM prepended to B11's bytes (nothing
   else is changed or re-escaped).
2. Every cell starting with `=`, `+`, `-`, `@`, tab or CR gets a `'` prefix, the same rule as B11 `csv_cell`.
3. Every quantity is two columns, value and unit (`received`, `received_unit`), FR58.
4. The lots CSV carries the recorded lot quantities (`harvested`, `farm_packed` from `LotOut`, `received` from the
   share) and, separately, `final_packed_share_derived` = `batch packed kg × share % ÷ 100`, rounded to the gram. The
   column name says it is derived.
5. The farmers CSV writes only an allow-list of `FarmerRow` columns (the dashboard's), whatever else a row holds, so a
   phone, survey number or coordinate cannot reach the file (CLAUDE.md §6).

## Advantages

- Excel opens Tamil names correctly on a double-click; a malicious name stays text.
- No new route, no library, no server load for data the page already holds.
- The derived column answers "how much of the final packed output came from this farmer" (FR60) without a schema
  change, and an auditor can still reconcile harvested ≥ on-farm packed ≥ received from the recorded columns.

## Compromises

- The CSV rules exist twice (B11 Python, portal TypeScript); both are pinned by tests on all six triggers.
- A cell that really starts with `-` gains a `'` (none today: exported quantities are not negative).
- The final packed share is derived, not recorded; share rounding can make the column sum differ from the packed kg by
  a few grams.
- If B11 ever writes its own BOM, the portal must stop prepending one.

## Alternatives rejected

- papaparse or another CSV library: a dependency for 15 lines (Ponytail; D-047 made the same call for reading).
- New `lots.csv` / `farmers.csv` API routes: more contract and server code for data the portal already has.
- Leaving the per-lot packed figure out: the Orchestrator's P05 brief asks for it (the PLAN P05 row asks only for a
  unit on every quantity).
- Calling the derived figure `packed_share`: reads as recorded and is easily confused with `LotOut.packed` (P05-r1 P2-1).
