# D-040: A QC phone receives a lot with a `lot_intake` push kind; `lot_intakes` stays the one intake record

**Date:** 2026-10-31  
**Status:** Accepted (Architect-Gate ruling 2026-10-31b §1 on M11 review P2-2; implemented by B16 and M11 r2)

## Context

User Flows §Selling has FPO staff scan the farmer's QR with the QC app, weigh the bags and run the checks on the
spot; the farmer then hears "200 kg received". The portal's "Ready lots" lists *received* lots (User Flows §Create a
batch step 1). On the server only `POST /v1/intakes` (lots_batches, FPO admin only, `processor_id` required)
writes `lot_intakes` and moves the lot to `received`. Batch shares, `total_received_kg`, the reconciliation snapshot,
the pull's `intake` change and the public page's "Sale to Processor" row all read `lot_intakes`
(`publishing/builder.py`: "intake ... come from the intake rows, not from events"). M11 pushes an `intake`
**event version** instead, which only lands on the lot timeline: the lot is never received, and the admin must
re-enter it on the portal, so two records can disagree.

There is also no server path from the phone to `ready_for_sale`: only `POST /v1/lots/{id}/ready`, which no phone
calls. A first intake requires `ready_for_sale`, so every phone intake would be refused `lot_not_ready`.

## Decision

1. **Push kind `lot_intake`.** `data` = `IntakeIn` without `client_id`; the entry's `client_id` is the intake id.
   The handler calls a dict-accepting `lots_batches.service.create_intake_from_sync` (the house twin pattern of
   `create_plot_from_sync` / `create_farmer_from_sync`), then commits. Idempotent on the id like `POST /v1/intakes`.
   The name is `lot_intake`, not `intake`, because `intake` is an event type and the phone maps entry types named
   like an event type to `event_version` (`outbox_processor.entryToWire`).
2. **Who.** `create_intake` itself checks the role: QC officer or FPO admin; a correction
   (`supersedes_intake_id`) stays FPO admin only. `POST /v1/intakes` opens to the same two roles.
3. **Processor.** `IntakeIn.processor_id` becomes optional (D-020 additive). When absent, the server uses the
   FPO's only own processor (`processors.fpo_id` = caller's FPO); zero or several → `field_required`
   (`processor_id`). Shared processors (`fpo_id` null) are never picked by default.
4. **Readiness at the gate.** A first intake of an `open` or `drying` lot runs `mark_ready` (the moisture gate,
   `lot_gates.ready_for_sale`) in the same transaction; a failing gate refuses the intake with
   `moisture_gate_failed`. Every check runs before any row changes.
5. **The `intake` event type stays accepted** (D-020) but is documented as a timeline note that receives nothing.
   M11 stops writing it.

## Advantages

- One intake record. Shares, reconciliation, pull, page and the portal see the QC officer's weight with no re-entry.
- Uses the existing push pattern and service; the phone needs one enum value and a different entry type, no
  outbox change, no Drift schema change.
- The phone's offline intake works even when the farmer's phone never told the server the lot was ready.

## Compromises

- One more push kind in the server, the spec and both clients.
- The processor default is right only while an FPO registers one processor; an FPO with two gets
  `field_required` until M11 gets a processor picker (mirror `GET /v1/processors`).
- The lot timeline (`GET /v1/lots/{id}/events`) has no intake entry for phone or portal intakes; the intake lives
  in `lot_intakes` only.
- The server shows a packed lot as `open` until intake; readiness is enforced at the point it matters
  (intake), not when the farmer packs.

## Revisit when

- A tenant registers more than one processor: processor picker in QC mode.
- The portal must show "ready" lots before intake: run the ready gate on the server when a packing event lands.
