# D-031: Farmers registered offline sync as a `farmer` push kind with a client id

**Date:** 2026-10-31  
**Status:** Accepted (Architect-Gate ruling on the M09 report; implemented by B15, consumed by M02)

## Context

The onboarding wizard (M09) must work in the field without signal. A farmer saved offline gets a phone UUIDv7
and an Entries row of type `farmer`; the consent and plot entries that follow already carry that id as
`farmer_id`. But `POST /v1/sync/push` accepts only `event_version`, `quality_reading`, `plot`, `consent` and
`flag_resolution`, and `FarmerIn` has no `client_id`, so the server would mint a different id. M09 offered:
(a) a `farmer` push kind, idempotent on `client_id`; or (b) `client_id` on `FarmerIn`, with M02 calling
`POST /v1/farmers` first and rewriting `farmer_id` in the consent and plot payloads.

There is also an online-path hazard: M09 falls back to the offline path when `POST /v1/farmers` returns no
response. If the server did commit, the queued copy creates a second farmer, or fails with
`farmer_phone_taken`, and the consent and plot entries then point at an id the server does not know.

## Decision

(a), plus the client id on the REST body:
- `FarmerIn.client_id` (UUID, optional on REST, D-020 additive). When given it becomes `farmers.id`.
  `create_farmer` looks the id up first: same FPO → returns the stored farmer (duplicate, no phone check, no
  second `users` or `memberships` row); another FPO → `client_id_conflict`. That is the same rule as plots (D-005).
- `SyncEntry.kind` gains `farmer`; `data` is `FarmerIn` and the entry's `client_id` is the farmer id. The
  handler copies `_push_plot`: field officer or FPO admin only, one transaction per entry, commit, result
  `accepted` / `duplicate` / `rejected`. The farmer is stored `pending` (Stage 0 admin approval), with the
  `users` and `memberships` rows `create_farmer` already writes.
- The phone generates the UUIDv7 *before* the online attempt and sends it as `client_id` on
  `POST /v1/farmers`. If there is no response, the same id is queued as a `farmer` entry. M02 sends the entry
  ahead of that farmer's `consent` and `plot` entries, so in-order processing (backend-design §3) satisfies
  the foreign keys and no payload is rewritten.
- Attribution: onboarding is the officer's own Stage 0 task, not assist mode for an existing farmer (an
  assist session needs a `farmer_id` that does not exist yet). The `audit_log` row carries the officer as
  actor plus the device. The `farmer` kind ignores `X-Assist-Session` and the per-entry `assist_session_id`
  (D-032) and requires neither. The consent and plot entries that follow carry the wizard's assist session
  (D-032), which makes the officer the consent witness.

## Advantages

- One outbox path for every offline write: same batching, retry, per-entry result and metrics.
- No id mapping on the phone and no rewriting of append-only payloads.
- Retries are idempotent online and offline, which removes the duplicate-farmer hazard.

## Compromises

- One more push kind on the server, the Dart and TS clients, and the spec.
- A farmer whose entry is rejected (e.g. `farmer_phone_taken` against a different farmer) leaves its consent
  and plot entries rejected too (`validation_error` / not found). M02 shows them for the officer to fix; they
  are never retried blindly.
- The farmer is visible to the admin only after the officer's phone syncs.

## Revisit when

- Farmers self-register offline (not in the pilot flows): extend the role check.
