# D-039: The audit log viewer scopes rows to an FPO by the ownership of the row they describe

**Date:** 2026-10-31  
**Status:** Accepted (B11)

## Context

P06 needs a searchable audit log (actor, entity, date) for the FPO admin, and CLAUDE.md §6 requires
every API call to be scoped to the caller's FPO. `audit_log` (B01) has no `fpo_id`: the flush listener in
`core.audit` does not know the tenant, and a user may belong to several FPOs (memberships), so the actor
does not identify the FPO either.

## Decision

`GET /v1/audit-log` returns a row only when the entity it describes belongs to the caller's FPO:
`entity_type = 'fpos'` and `entity_id` = the FPO; or `entity_type = 'event_versions'` and the version's
event is the FPO's; or `entity_type` is any table with `id` and `fpo_id` columns (found from the
SQLAlchemy metadata, so new tenant tables are covered without code) and that row's `fpo_id` is the FPO.
Diffs are returned as stored (secrets are already `[redacted]`, D-024), except that location, boundary
and land-record values (`pin`, `walked_boundary`, `land_record_ref`, `exif_gps`, `gps`, `started_gps`,
`boundary`, at any depth) read `[hidden]` (B11-r1 P2-1); the row's device id and GPS columns are left out.
FPO admin only. No migration.

## Advantages

- Exact tenant isolation even for users in several FPOs; no schema change, no listener change.
- New tenant-scoped tables are included automatically.

## Compromises

- Rows about deleted records, and about untenanted tables (`users`, `devices`, `consent_records`,
  `batch_approvals`, `batch_shares`), are not visible in the viewer.
- One `IN (SELECT id ...)` per tenant table; fine for the pilot. When the log grows, add
  `audit_log.fpo_id` stamped by the listener from the audit context (a migration plus a context field).
