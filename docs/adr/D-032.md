# D-032: Assist context travels with each sync entry, not with the request

**Date:** 2026-10-31  
**Status:** Accepted (Architect-Gate ruling on M09 review P2-1; implemented by B15, M02, M09, M10)

## Context

The server knows about assist mode only from the request: the `X-Assist-Session` header, resolved by
`core.auth.get_current_user` to an *open* session of the caller. Assist sessions come from `POST /assist/start`.
`identity.service._check_writer` and the events path read `assist_session_id` / `on_behalf_of_farmer_id` only from
that context. An officer working offline (M09 onboarding, M10 assist mode) captures entries hours before M02 pushes
them. One push carries entries for many farmers, and M02 sends no header. The effect: every wizard consent is
refused (403), and every assisted event is stored without assist mode, which breaks CLAUDE.md §6 ("assist mode is
recorded on every entry it creates"). `assist_sessions.id` is already a client id, and `start_assist` is already
idempotent and takes `started_at` / `started_gps` from the phone (D-005).

## Decision

1. **Push kind `assist_session`.** `data` = `AssistStartIn` without `client_id` (`farmer_id`, `started_at`,
   `started_gps`). The entry's `client_id` is the session id. The handler calls `identity.service.start_assist`
   unchanged: the officer is the caller, the farmer must be in the officer's FPO, and an id owned by another officer
   or farmer is refused (409 `conflict`). Field officers only.
2. **Per-entry `SyncEntry.assist_session_id`** (optional, on the envelope entry, never inside `data`). When set, the
   server loads that session for the caller (`officer_user_id` = caller). An ended session is accepted, because the
   entry was captured during it. For that entry only, it applies `on_behalf_of_farmer_id` = the session's farmer and
   `assist_session_id`, both to the caller and to the audit context. An unknown session, or another officer's →
   that entry `rejected` `assist_session_invalid`. An entry whose farmer is not the session's farmer → `forbidden`,
   on every kind that names a farmer: consent (existing `_check_writer`), event_version (existing check), plot (new
   check). When it is absent, the request header applies as today (portal and REST unchanged). The `farmer` kind
   ignores it (D-031).
3. **Phone storage, without a Drift schema change.** The phone keeps the session id in the entry's `payloadJson`
   under the reserved key `assist_session_id`. M02's `entryToWire` removes it from `data` and sets it on the envelope
   entry, for every kind, the same way it already lifts `occurred_on` / `batch_id`. The phone's `assistMode` bool stays.
4. **Order.** The `assist_session` entry is queued before the entries that use it (and after the `farmer` entry
   when the farmer is new). In-order push processing does the rest.
5. Offline sessions need not be ended. M10 calls `POST /assist/end` when it is online (best effort). An open session
   grants nothing an officer could not get by starting a new one.

## Advantages

- §6 holds offline: every assisted entry carries its session; consent gets its witness; FR69 `entered_remotely`
  works unchanged.
- One push can mix farmers; no header juggling or one-request-per-farmer.
- Reuses `start_assist`, `_check_writer` and the events farmer check; no consent rule is relaxed.
- No Drift migration; M09 can write the key today.

## Compromises

- A transport field lives inside `payloadJson` on the phone. M02 must lift it, or event versions (`extra="forbid"`)
  are rejected. Registry and identity bodies ignore unknown keys, so plot and consent entries are safe before M02 r2.
- Sessions minted offline stay open on the server unless the phone ends them online.
- The per-entry path accepts an ended session, so entries can be attributed to a session after it closed. The audit
  row keeps both times.

## Revisit when

- An Entries schema change is due anyway: move the key to a nullable `assistSessionId` column.
- Audit needs session durations: add `ended_at` to the `assist_session` kind.
