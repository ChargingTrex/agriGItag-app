# D-046: Reminders are scheduled on the phone from the Tasks table; push waits for Firebase

**Date:** 2026-10-31  
**Status:** Accepted (WP-M12)

## Context

FR7 and User Flows §Alerts ask for reminders ("Time to log your harvest") from the crop calendar, with one tap
opening the right event. PLAN §7.2 M12 adds: an offline reminder is scheduled, a tap lands on F04 with harvest
preselected, and the payload has no phone number or ID. The project has no Firebase project yet (google-services.json,
GoogleService-Info.plist, APNs key: a human step, PLAN §12), and PLAN §13 caps the APK size. B04 sends SMS through a
console provider and has no push channel or device-token endpoint. The phone already holds the farmer's next tasks
in the Drift Tasks table (M01), which the farmer home card reads (M07) and the drying start writes (M07).

## Decision

1. The phone schedules local notifications with flutter_local_notifications, one per open task in the Tasks table,
   at its due time (07:00 for a due day without a time), in the app language. Title "Time to log: <event>", body the
   farmer's field ("Field 2"), payload the route `/log/<event>?lot=<lot id>` (D-043). Nothing else.
2. On every change of the open tasks, the session (role, language) or the Settings "Reminders" switch, all pending
   reminders are cancelled and the open tasks scheduled again. Only the farmer role gets reminders.
3. A tap (warm start) or the launch details (cold start) open the route on top of the farmer home.
4. The phone asks once with its own sentence before the Android 13+/iOS permission prompt, when the first reminder
   is scheduled. The answer and the switch live in SyncState key/values (no schema change).
5. Push (FCM/APNs) is a `PushProvider` interface with a console provider that gives no token; registration is behind
   the `push_notifications` feature flag of the `fields` bundle (absent, so off). No Firebase dependency is added.

## Advantages

- Reminders work with no signal and no server scheduler; the same Tasks rows drive the home card and the reminder.
- Cancel-all-and-reschedule needs no notification-id bookkeeping: completion, undo, language and the switch are all
  just "tasks changed".
- No phone number, name or ID document can reach a notification: the text is built from the event and the field
  number only, and a test scans every scheduled payload.

## Compromises

- Reminders only exist for tasks the phone holds. Crop-calendar tasks need the `calendar` bundle (empty today, B07)
  or pulled `notification` entities mirrored into Tasks (the pull ignores them today, M02); both are TODO.
- A pull in the background isolate does not reschedule until the app opens (the reschedule listener lives in the app).
- Inexact alarms: a reminder can arrive minutes late; no exact-alarm permission is asked.
- Reminder state (switch, rationale answered) sits in the sync key/value table, shared by every user of the phone.
- No server-sent push until a human creates the Firebase project and the API gets a device-token endpoint.
