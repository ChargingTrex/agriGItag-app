# D-005: Append-only events with client-generated UUIDs as primary and idempotency keys

**Date:** 2026-10-29  
**Status:** Accepted

## Context

Phones create entries offline and retry sends; two devices may correct the same event.

## Decision

Every entry gets a UUID on the phone; the server inserts with ON CONFLICT DO NOTHING and re-reads, so a retry returns the original result. Events are never updated in place; undo and corrections add `event_versions` rows. DB triggers forbid UPDATE/DELETE on `event_versions`, `evidence_photos`, `audit_log`.

## Advantages

- Idempotent sync without a separate idempotency table
- Nothing a farmer records is lost or duplicated
- Full history for audits

## Compromises

- Storage grows; the current version needs a view or denormalised pointer
- A foreign-owned id must be rejected (`client_id_conflict`)
- Concurrent corrections resolve by `stale_version` rejection, not merge

## Revisit when

If storage cost or query complexity becomes a problem at scale (partitioning first).
