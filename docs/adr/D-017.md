# D-017: YAML-driven field and feature configuration with per-tenant overrides

**Date:** 2026-10-29  
**Status:** Accepted

## Context

Customers will want to enable or disable data fields (Aadhaar, soil type, price, boundary walk, PIN login, SHG groups) without code changes.

## Decision

`apps/api/config/fields/<entity>.yaml` lists each field: name, type, required, enabled, visibility (public/partner/internal), en/ta label keys, capture stage. `features.yaml` holds feature flags; `tenants/<fpo_code>.yaml` overrides. The API validates the YAML against a schema at start-up, builds dynamic Pydantic validators, serves `GET /v1/config/fields` and `/features` (also in the sync bundle), and the page builder honours `visibility`.

## Advantages

- Fields on/off without deploys
- One source for three clients
- Privacy visibility enforced centrally

## Compromises

- Dynamic validation is harder to type-check (mitigated by YAML schema and table-driven tests)
- Disabling a required field needs a migration story
- Tenant overrides are reviewed like code

## Revisit when

If per-tenant configuration needs a UI; then move the files to a table with the same schema.
