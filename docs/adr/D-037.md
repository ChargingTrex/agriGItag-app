# D-037: Dashboard completeness and stage progress are derived from live events and the crop's `event_schema`

**Date:** 2026-10-31  
**Status:** Accepted (B11)

## Context

B11's acceptance line is "completeness = lots with all mandatory events ÷ lots", and P06 needs
stage-progress tiles (Land prep, Nursery, Sowing, Inputs, Harvest, Drying, Packing) with done /
in-progress / not-started counts. No table stores a lot's stage: lots have a coarse `status`
(open, drying, ready_for_sale, received, batched, closed), events carry an `event_type`, and each crop's
`event_schema` lists `mandatory` types and date-ordered `tracks` (FR22, FR55). Undone and superseded
events must not count (FR25).

## Decision

1. **Live events** are events whose `status` is not `undone` or `superseded` (`rules_flags.service.DEAD_EVENTS`,
   the same set the rules use).
2. **Complete lot** = for every type in its crop's `event_schema.mandatory`, the lot has a live event of
   that type. A crop with no `mandatory` list makes its lots complete. Computed in SQL
   (`reporting.service.lot_complete`: `NOT EXISTS` over `jsonb_array_elements_text`), so the dashboard and
   the per-farmer table use one definition. Completeness % = complete lots ÷ lots in scope, one decimal;
   null when there are no lots.
3. **Stage tiles.** A lot's *furthest stage* is the last P06 stage (in P06 order) with a live event.
   For each stage: **not started** = no live event of it; **in progress** = it is the lot's furthest stage
   and the lot is still in the field (`open` or `drying`); **done** = recorded and either a later stage is
   recorded or the lot has passed the ready-for-sale gate. The three counts add up to the lots in scope.
   One SQL query (per-lot `bool_or` and `max` over a CASE, then `count(*) FILTER`).
4. **Filters** (crop → district → block → village) apply to completeness, tiles, land area (place
   filters only, plots carry no crop) and the per-farmer table. Place comes from the farmer's village in
   the villages master (B13). Flags, batches, finished goods, scans and sync health stay FPO-wide.

## Advantages

- No new column, table or migration; the numbers follow the same live-event rule as the server rules.
- A crop's schema change (more mandatory types) is reflected at once.
- One definition of "complete" in SQL, reused by both endpoints.

## Compromises

- "In progress" is inferred, not recorded: a lot that skipped a stage shows that stage as not started even
  though later stages are done (completeness and the `event_out_of_order` rule surface the gap).
- Nursery and input application are not strictly sequential with the main track; they still get a place in
  the P06 order for the furthest-stage test.
- Correlated subqueries per lot; fine for pilot sizes (hundreds of lots). If an FPO reaches tens of
  thousands of lots, store a per-lot stage summary updated by the events service.
