# D-044: The portal reads import CSVs with a small in-house reader numbered like the server's; no CSV library

**Date:** 2026-10-31  
**Status:** Accepted (P08)

## Context

P08 shows a dry-run preview of a master data CSV (farmers, villages, inputs): every row of the file with its
cells, and the rejected rows in red with the code B13's dry run returns. B13's `ImportReport` carries only
`accepted` and `rejected: [{row, code, field}]`, where `row` is Python `csv.DictReader.line_num`: the physical
line the record ends on (header = 1; a quoted line break and a blank line each count). The portal therefore
has to split the file itself and number its rows exactly the same way, or the red mark lands on the wrong row.
D-018 says to prefer a widely used library (the brief suggested `papaparse`, MIT).

## Decision

`apps/portal/src/features/imports/csvFile.ts` `parseCsv` is a ~30-line RFC 4180 reader (quotes, doubled quotes,
quoted line breaks, CRLF) that records the line each record ends on and drops all-blank rows, as
`imports.parse_csv` does. It is used for display only: the server re-parses the uploaded bytes and decides.
A Vitest case pins its numbers to the output of Python's `csv` for the same text.

## Advantages

- Row numbers match the server's report by construction, including quoted line breaks and blank lines.
- No dependency, no ledger row, nothing added to the 400 KB bundle budget.
- The server stays the single judge of the file (D-006 pattern: the client view is a preview).

## Compromises

- In-house parsing code to maintain. It is small, pure and covered by a test against Python's numbers.
- Exotic files (bare `\r` line endings, a quote inside an unquoted cell) may display differently from how the
  server reads them; the server's verdict and counts are still the ones shown and enforced.

## Alternatives rejected

- `papaparse` (MIT): reports rows and character offsets, not physical end lines; mapping back to `line_num`
  needs the same line counting this reader already does.
- Asking B13 to return the parsed rows in the dry run: outside P08's paths, larger responses for 5,000-row
  files, and the farmer phone numbers would travel back unmasked.
