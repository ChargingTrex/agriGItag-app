## 1. B08 P2-4: `batch_quantity_unattributed` vs grading loss

**Decision: (b).** Split it into two warns (D-030):
- `batch_quantity_unattributed`: Σ `batch_shares.kg_contributed` vs `batches.total_received_kg`, 5 %; also fires when
  received kg exists and there are no shares. This is Dataflow Stage 7 word for word ("sums component-lot quantities
  against total procured quantity … >5 %").
- `grading_loss_high`: the output (packed, else graded) is more than `grading_loss_warn_pct` below received kg, or more
  than 5 % above it. The limit is in `features.yaml`, default **15**, tenant-overridable (D-017).

Why not (a): a tolerance on the old comparison keeps a name that says "attribution" on a check that measures loss.
Raising it to 15 % is (b) with a misleading code. Once B09 builds shares (Σ share_pct = 100), FR60 attributes every
output kilogram in proportion. PRD §12.2's "never attributed back" is fixed by the share % on the page (B10). The
320 → 20 kg drop is the part that still deserves a flag.

- **ADV:** codes mean what they say; no warn on every normal batch; the reference batch still shows its problem
  (93.75 % loss against 15 %); the limit is tunable without a release.
- **COMPROMISE:** one more code and feature key (OpenAPI and clients change). Grading loss really depends on the
  crop, and its proper home is the Standards Profile next to the yield margins (D-015). 15 % is a guess to calibrate
  after season 1.
- **Implements:** **B15** (new, docs/agents/acceptance/B15.md, item 1).
- **B12 seed expectation:** `grading_loss_high` ×1 and **no** `batch_quantity_unattributed`. The seed's shares
  (100 + 200 + 20 = 320 kg) equal received 320 kg. B12.md and backend-design §5 are updated.
- **B09 batch gate:** unchanged in kind. Gates block on `severity == hold` only (lot, batch, plot and reading holds
  returned by `run_gate_checks`; TODO "B08 → B09" line). Neither code blocks approve or publish; both show on the
  batch for the FPO Admin. B09 must set `batches.total_received_kg` = Σ the component lots' intake `received_kg` at
  batch creation and build shares from the same intakes, or both checks have nothing to compare. **No B09 acceptance
  line change.** The B09 line "intake 100 vs packed 69 → `quantity_mismatch`" still holds.
- **Acceptance line changes:** B12.md flag-set line (done, see §2). B15.md written.

## 2. B08 P2-5: `yield_check_unavailable` ×2 vs ×3

**Decision: the spec is wrong; the rule and the seed are right.** PRD §12.1 (Harvest row: "no harvest quantity")
and §12.2 ("No harvest quantity, so yield per acre can't be sanity-checked") apply to all three reference lots. The
seed "mirrors PRD §12 with its known problems", so no lot gets a harvest quantity, and the per-lot rule gives **×3**.
The ×2 has no source. It most likely came from backend-design §3's example harvest payload (195 kg, which matches
LOT0EF81415's second packing), and that payload is an illustration, not seed data.

- **ADV:** the seed stays faithful to the sample; no special data to make a count come out.
- **COMPROMISE:** the seed never exercises `yield_over_ceiling`. The unit cases (1,150 / 1,250 / 1,350 kg) and the
  B08 integration test cover it. B12 may enter harvest quantities as part of "after fixes" (optional, not asserted).
- **Implements:** B12 (seed and e2e).
- **Acceptance line change (done):** backend-design §5 and B12.md now read `yield_check_unavailable`×3, and replace
  `batch_quantity_unattributed` with `grading_loss_high`×1 plus "no `batch_quantity_unattributed`". B12 now depends on B15.

## 3. M09: offline farmer registration and the step 1 phone check

### 3a. Sync contract

**Decision: (a), with `client_id` on `FarmerIn` as well** (D-031). Push kind `farmer` (`data` = `FarmerIn`, the
entry's `client_id` = the farmer id). It is idempotent on the id like plots (same FPO → `duplicate`, another FPO →
`client_id_conflict`), committed per entry, field officer / FPO admin only, and the farmer is stored `pending` with the
`users`/`memberships` rows `create_farmer` already writes. `FarmerIn.client_id` is optional on `POST /v1/farmers`
(D-020 additive). The phone creates the UUIDv7 *before* trying online and reuses it in the queued entry. That closes
the hole in M09's current fallback: a request that committed but returned no response no longer produces a second
farmer or a `farmer_phone_taken` rejection. M02 sends the `farmer` entry ahead of that farmer's `consent`/`plot`
entries; in-order processing satisfies the foreign keys and nothing is rewritten.

Assist attribution: onboarding is the officer's own Stage 0 task. An assist session needs a `farmer_id` that does
not exist yet, so the `farmer` kind ignores `X-Assist-Session`. The audit row (officer actor, device, request id) is
the record. The consent and plot entries that follow carry the wizard's assist session (§4), which also makes the
officer the consent witness.

Why not (b): M02 would special-case one entry type onto a separate REST call outside the outbox's batching, retry,
per-entry result and metrics. Without a client id, it would also have to rewrite append-only payloads.

- **ADV:** one offline write path; no id mapping; retries idempotent online and offline.
- **COMPROMISE:** one more push kind in the server, both clients and the spec. A rejected farmer entry leaves its
  consent/plot entries rejected; M02 shows them to the officer instead of retrying.
- **Implements:** **B15** item 2 (server). **M02** (round 2 or follow-up): map Entries `farmer` → push kind `farmer`,
  order it first, and generate the UUIDv7 before the online call (M09's `farmerCreatorProvider` sends it as
  `client_id`). That is an M02/M09 acceptance-line addition for the Orchestrator; I do not edit those files.

### 3b. Officer-only phone check at step 1

**Decision: not pilot scope.** UserFlows step 1 assumes the code is "read automatically". The SMS goes to the
*farmer's* phone, so the officer's app cannot auto-read it (D-028 reads only the device's own SMS). Step 1 is also
often offline, which is why 3a exists. The route would add an SMS-sending surface that officers can point at any
number, plus a `phone_verified_at` column to give it meaning. Smartphone farmers prove the number at step 9 when they
sign in with the OTP on their own phone (FR1, D-024). Feature-phone farmers are confirmed by read-back at step 9
(the number shown in large type) and by the admin's Stage 0 approval.

- **ADV:** no new SMS endpoint or abuse surface; onboarding works fully offline.
- **COMPROMISE:** a feature-phone farmer's number is not proved, so reminders can go to a mistyped number until the
  first missed call-back is noticed. That is a deviation from UserFlows step 1, recorded here.
- **Implements:** none now. TODO line "M09 → B02/B03 (phone check at step 1)" stays open, re-labelled "deferred
  post-pilot by Architect-Gate 2026-10-31". Revisit if pilot SMS delivery reports show wrong-number rates above a few
  percent.

## 4. Offline assist context in sync push (M09 review P2-1, M10)

**Decision: (a), D-032.** The smaller options fail:
- The reviewer's P2-1(a) lets officers record consent without assist. That fixes consent only. Assisted events
  from M10 would still be stored without assist mode, and the CLAUDE.md §6 invariant stays broken.
- One header per push cannot work: a batch mixes farmers, and offline sessions do not exist on the server yet.

The contract:
- **Push kind `assist_session`.** `data` = `AssistStartIn` minus `client_id`; the entry `client_id` is the session
  id. It is handled by the existing idempotent `identity.service.start_assist`: officer = caller, farmer in the
  officer's FPO, `started_at`/`started_gps` from the phone, an id owned by another officer or farmer gives `conflict`.
- **Per-entry `SyncEntry.assist_session_id`** on the envelope entry. The server loads it for the caller and accepts
  an ended session (the entry was captured during it). For that entry only, it sets `on_behalf_of_farmer_id` /
  `assist_session_id` on the caller and in the audit context. Unknown session or another officer's →
  `assist_session_invalid`. An entry farmer that is not the session's farmer → `forbidden`, for consent and events
  (existing checks) and plots (new check). With no field, the header behaves as today, so the portal is unchanged.
- **Order:** `farmer` (if new) → `assist_session` → the entries that use it.
- **On the phone, no Drift schema change.** The session id lives in `payloadJson` under the reserved key
  `assist_session_id`. M02's `entryToWire` lifts it onto the envelope for every kind (as it already lifts
  `occurred_on`/`batch_id`). `assistMode` stays.
- Offline sessions need not be ended; M10 calls `POST /assist/end` online, best effort.

- **ADV:** §6 holds offline and online; consent gets its witness without relaxing `_check_writer`; FR69
  `entered_remotely` works unchanged; one push can carry many farmers; it reuses `start_assist`.
- **COMPROMISE:** a transport key inside `payloadJson`. M02 must lift it before any assisted *event* is pushed:
  `EventVersionIn` forbids extra keys, while plot and consent bodies ignore them. Sessions minted offline may stay
  open. Entries can be attributed to an ended session (the audit keeps both times).
- **Implements:**
  - **B15 item 3** (backend; B15.md updated: declared paths, output 3, 5 acceptance lines).
  - **M02** (r2): map Entries types `farmer` and `assist_session` to those kinds instead of the `event_version`
    fallback, and lift `assist_session_id` from the payload onto the entry for every kind. Acceptance line: "push of
    `[farmer, assist_session, consent, plot]` built from Entries carries kinds in that order and `assist_session_id`
    on consent and plot, not inside `data`".
  - **M09** (r2): mint and attach the session; the minimum is below.
  - **M10:** start assist mode by minting a UUIDv7 session id and queueing an `assist_session` entry (online or
    offline, one path; no `X-Assist-Session` from the phone). Put `assist_session_id` in the payload of every entry
    made while assisting, and call `POST /assist/end` online at exit. Acceptance line: "an event logged in assist
    mode offline reaches the server with `assist_session_id` and the farmer as `on_behalf_of_farmer_id`".
- **What M09 round 2 does now** (forward-compatible, no backend wait; this is an acceptance-line addition for the
  Orchestrator):
  1. At wizard start, mint the farmer id F and the session id S (UUIDv7) and keep both in the draft. F is also sent
     as `client_id` on the online `POST /v1/farmers` (D-031).
  2. In the save transaction, write in this order: the `farmer` entry (offline only; no session key), an
     `assist_session` entry (`farmerId` F, payload `{farmer_id: F, started_at: <wizard start, ISO 8601>,
     started_gps: <first fix or null>}`, `assistMode` true), then `consent` and `plot` with `"assist_session_id": S`
     added to their payloads. "Another plot" reuses S. Write the `assist_session` entry online too.
  3. Fix the two wrong comments about the witness (review P2-1) to cite D-032.
  4. Test: the flow test asserts the four entries, their order, and S in the consent and plot payloads.
  Until B15 and M02 r2 merge, these entries end `rejected` on a real server, as the `farmer` entry already does. No
  field device may run M09 before **B15 + M02 r2 + M09 r2** are all merged (make it a G5 pilot-candidate condition).
