## 1. Intake from the QC phone (M11 review P2-2)

**Decision: (b), shaped to fit; D-040.** New push kind **`lot_intake`**: `data` = `IntakeIn` without `client_id`, the
entry's `client_id` = the intake id, handled by `lots_batches.service.create_intake` through a dict-accepting
`create_intake_from_sync` twin, committed per entry. `create_intake` checks the role itself (QC officer or FPO admin;
corrections stay FPO admin only), and `POST /v1/intakes` opens to the same two roles. `IntakeIn.processor_id` becomes
optional: absent → the FPO's only own processor, zero or several → `field_required`. A first intake of an `open` or
`drying` lot runs `mark_ready` (the moisture gate) in the same transaction. The `intake` *event type* stays accepted,
documented as a timeline note that receives nothing; M11 stops writing it.

Why not (a), the intake event calling `create_intake`: `lot_intakes` is already the one source for shares,
`total_received_kg`, reconciliation, the pull's `intake` change and the public page ("intake … come from the intake
rows, not from events", `publishing/builder.py`). (a) keeps two records and makes the events module special-case
one event type inside `write_version`'s transaction. Event corrections (field officer/admin) and undo would then need
intake corrections too, or the two records drift apart. (b) reuses the existing service and the house push-kind
pattern, so the phone sends one record.
Why not (c), a check only: User Flows §Selling ends with "200 kg received" to the farmer, and §Create a batch starts
from *received* lots. (c) makes the admin re-type every weighing, so the two records can disagree. That is the defect.
Why `lot_intake` and not `intake`: the phone sends any entry whose type is an event type as an `event_version`
(`entryToWire` checks `eventTypes` first, and `intake` is one). A distinct name needs no outbox change.
Why the ready gate at intake: nothing on the server sets `ready_for_sale` except `POST /v1/lots/{id}/ready`, and no
phone calls it (M07's D-006 comment says "the server re-runs the gate on the packing entry". It does not). Without
this, every phone intake would be refused `lot_not_ready`. Running the same gate at the moment it matters is one
call to existing code.

- **ADV:** one intake record, no portal re-entry; offline intake at the collection centre works; no Drift or outbox
  change; the server stays the authority (D-006): weight checks, the moisture gate and B08 rules run on intake.
- **COMPROMISE:** one more push kind in the server, the spec and both clients. The processor default only works
  while an FPO has one processor. An FPO with two gets `field_required` until QC mode has a processor picker. The lot
  timeline shows no intake entry. The server shows a packed lot as `open` until it is received.
- **Implements:** **B16** item 1 (new, docs/agents/acceptance/B16.md). **M11 r2**, phone side:
  1. In `intake_screen.dart`, replace the `intake` event entry with an entry of type `lot_intake`. Its id is the
     intake id. Payload: `{lot_id, sale_date: <local date YYYY-MM-DD>, received: {value, unit: "kg"},
     intake_moisture_reading_id: <the reading entry's id, when taken>, price_per_kg?}`, with no `processor_id`.
     Save it in the same `saveQcEntries` transaction, after the reading entry, so the server finds the reading first.
  2. Add `SyncKind.lotIntake` (wire `lot_intake`) in `enum_wire_names.dart`. In `contract_test.dart`, leave it out of
     the `unorderedEquals` against openapi.json until B16 merges, and assert it against backend-design.md §3 (the
     same interim pattern used for D-031/D-032 before B15). After B16 and `make clients`, compare it in full.
  3. Replace the false `shortcut:` comment with a `DECISION D-040` note: the server picks the FPO's only processor,
     and a processor picker comes when a tenant has more than one.
  4. Report and TODO: until B16 merges, `lot_intake` entries end `rejected` on a real server. No field device runs
     QC intake before **B16 + M11 r2** are merged.
- **Acceptance line changes (done):** M11.md gets the intake-save line. B16.md is written. backend-design §3 has the
  `lot_intake` paragraph. **B09.md is unchanged:** its lines still hold, and the new behaviour is asserted in B16.

## 2. Non-GI batches vs holds (P03 review P3-4)

**Decision: D-041.** The pilot raises holds with two codes, and the sources make both of them GI holds:
`plot_outside_gi_region` (FR29: "can still be traced as a normal, non-GI batch") and `yield_over_ceiling` above the
hold margin (FR68 / Stage 7: "held out of the GI-labelled batch until reviewed"). In a batch with
`gi_label_requested = false`:
- these two codes (`GI_ONLY_HOLD_CODES`) **do not block** approve grading, final packing or publish. They stay
  open flags, and each approval row records them in `blocked_reasons` as approved-over;
- **every other hold still blocks**: batch, reading and event holds, and any future code (fail closed);
- the GI re-check is **skipped**, as `_gi_check` already does (`gi_verified = false`, no reasons, no badge). No
  change there.

A GI-requested batch is unchanged: every hold blocks. The admin asked for the badge, and FR70 wants the review. I
considered letting GI-only holds never block and only deny the badge on GI batches too. I rejected it because a
batch the admin asked to label would then quietly publish without the badge.

- **ADV:** P03's non-GI switch becomes true. FR29's non-GI trace path exists. The hold stays visible and is
  recorded on every approval. Unclassified holds fail closed.
- **COMPROMISE:** a two-code list in code. A new GI-only rule must be added to it on purpose, and a unit test ties
  the list to the rules' `CODES`. A lot over the yield ceiling can reach a non-GI public page while its review is
  open. The page makes no GI claim, and the admin still sees the flag.
- **Implements:** **B16** item 2. **P04** (in progress; it owns `apps/portal/**`, including P03's Ready lots page):
  - The batch page lists GI-only holds of a non-GI batch under warnings, as "<rule text>: allowed in a non-GI
    batch". They do not grey Approve or Publish.
  - The batch chip reads "Non-GI batch: no GI badge on the public page".
  - The Ready lots switch label reads "Non-GI batch: lots outside the GI region or above the yield ceiling can join.
    The public page shows no GI badge." This replaces P03 review P3-4's interim "held lots block publishing" text.
  - Until B16 merges, the MSW handlers model the new server rule, and the live check waits for B16.
- **Acceptance line changes (done):** P04.md gets the non-GI line. P03.md is unchanged (merged; P04 carries the
  label). B09.md is unchanged.

## 3. `assist_session_id` on kinds that never check the farmer (B15 review P3-1)

**Decision: per kind, D-042.** Assist applies to entries about one farmer's records:

| Entry | `assist_session_id` |
|---|---|
| `consent`, `plot`, lot `event_version` | must be the entry's farmer, else `forbidden` (B15, unchanged) |
| `quality_reading` on a lot | **verify**: must be the lot's farmer, else `forbidden` (`quality.service.create_reading`) |
| `quality_reading` on a batch, batch `event_version` | **reject** `forbidden`: a batch belongs to many farmers |
| `farmer`, `flag_resolution`, `assist_session`, `lot_intake` | **ignore**: no session lookup, no assist fields; the officer's own task (extends D-031's `farmer` rule in `_entry_caller`) |

Why not reject everywhere: M10 attaches the session to *every* entry made while assisting (rulings 2026-10-31 §4). A
flag cleared or a reading taken on the farmer's screen would then be rejected offline for no data fault. Why not
ignore everywhere: a field officer's drying-end reading taken while assisting farmer A is exactly what §6 wants
recorded as on behalf of A, and on another farmer's lot it is a real error. The two new checks sit in shared code
(`create_reading`, `events._check_subject`), so the header path gets them too.

- **ADV:** audit rows never name a farmer the record does not belong to. Assisted readings are attributed. No
  spurious offline rejections. No new error code.
- **COMPROMISE:** the field is silently ignored on four kinds, so a phone bug there goes unnoticed (harm is low: the
  field only adds attribution). REST `POST /v1/flags/{id}/resolve` with `X-Assist-Session` still stamps the header's
  farmer, and no client sends that.
- **Implements:** **B16** item 3. Nothing changes on the phone: M10's rule stays "the session on every assisted
  entry".
- **Acceptance line changes:** B16.md (written). The B15 lines stand.

## 4. Tap count for farmer events (M07 review P2-1, M08 proposal)

**Decision: accept the M08 proposal, with one fix to the card path; D-043.** The three taps ("choose the event, take
the photo, confirm") are counted from choosing the event. "Log" is navigation: the home rule says "everything else is
one tap away", and one job per screen keeps the grid off the home card. Log → grid → event = 4 (+1) is accepted. The
routine path is the next-task card, and it must be 3 (+1) from home **also for a farmer with two or more active
lots**. Today the card opens `/log/<event>` without its lot, so the field picker adds a tap. When the task names a lot
(`Tasks.lotId`), the card passes it (for example `/log/<event>?lot=<id>`). `EventFlowScreen` then starts on that lot
when it is active, and it falls back to the picker otherwise. That is about 5 lines plus one test with two lots that
asserts `h.taps == 4` (card, Next, shutter, tick for harvest). Out-of-order Yes/No and weak-GPS "Save anyway" stay
exception paths.

- **ADV:** no home redesign; the promise holds on the reminder-driven path for every farmer; the test counting
  matches M07's report table.
- **COMPROMISE:** browsing to an unprompted event costs 4 (+1). That follows User Flows' intent but not its letter,
  and it is recorded here. A task with no lot still asks for the field.
- **Implements:** M07 is merged. The card-lot fix is an M07 follow-up. The Orchestrator routes it to **M08 r2** (same
  app, already editing the farmer home and its harness) or makes it a micro-patch on main.
- **Acceptance line change (done):** M07.md, line 1 now states the D-043 counting and the 2+-lot card case.
