## What was done, and why

### P2-A, finding 4 (B06): a phone could upload a multi-GB "photo"

1. **The PUT is signed for the declared length** (`core/storage.py` `presign_put`, new optional `size_bytes`).
   boto3 signs `Content-Length` when `ContentLength` is in `Params` (`X-Amz-SignedHeaders` now lists
   `content-length`), so S3 and LocalStack refuse a body of any other length. `evidence.upload_instruction` and
   `service.PendingPhoto` carry `size_bytes` from the push row (new entries and duplicates). The phone already sends
   `Content-Length` from the bytes (`photo_uploader.dart:88`), so the returned `headers` are unchanged.
2. **Ceiling 2 MiB** (`events/schemas.py` `MAX_PHOTO_BYTES = 2 * 1024 * 1024`, was 5 MB), with a two-line why.
   It is enforced by the existing `PhotoIn.size_bytes` `le=` check. In a push that rejects only that entry, with
   the registered `validation_error` (422, `details` names `photos.N.size_bytes`); other entries go through.
   No new `photo_too_large` code was added: the registered code already refuses at the boundary, and a new one
   would need en/ta keys and client mappings for a case the M04 compressor (≤ 350 KB) never produces.
   Not in YAML: it is a security ceiling and a schema bound, not a tenant setting, so it has no `shortcut:`.
3. **Verify reads at most size + 1 bytes** (`evidence._read_object(key, size_bytes)` uses `body.read(size + 1)`;
   `verify` and `make_variants` pass `photo.size_bytes`). A length other than declared is `checksum_mismatch`,
   so it takes the existing path: no variants, `rules.check_event` with the `checksum_mismatch` hint. This
   also covers an S3-compatible store that ignores the signed length, and a second version written under the
   same key. Worker memory per photo is bounded by 2 MiB + 1.
4. `confirm_photos` is unchanged: once the length is signed, a stored object always has the declared size.
   That is why TODO §6's version of the fix (refuse in confirm) was not needed.

### P2-B, finding 3 (B10/W03): published pages never went through the privacy linter

1. **One linter, importable by the API.** `infra/scripts/privacy-lint.py` was moved, byte for byte, to
   `apps/public-page/agritrace_page/privacy_lint.py`. Only the header changed: one location note and the new
   caller. The API image ships `agritrace_page` but not `infra/`. `infra/scripts/privacy-lint.py` is now a
   **symlink** to it, so CI, `qa/tests`, `qa/robot/public/page.robot`, `tools/check_output.sh` and the API tests
   run the same file with no edits. There is no parallel mechanism.
2. **`build_page` lints before writing** (`publishing/builder.py` `privacy_hits`, `publishing/service.py`
   `build_page`). After `render`, `scan_text` runs over `index.html` (text rules) and `data.json` (text and JSON
   rules), with no canaries. On any hit:
   - the `page_builds` row becomes `failed`, and `snapshot.error` holds `public_record_invalid` with details
     `{loc: [file, line], msg, type: rule}`, never the matched text;
   - `PublicRecordInvalidError` is raised (409; registered; the task does not retry it);
   - nothing is written to S3: no page, QR or photo copies.

   The schema `ValidationError` branch and the lint branch share one failure block.
3. **Patterns: no change needed.** All four formats the audit lists are already caught by the linter (they
   were only missing from the renderer's schema patterns, `schema.py`):
   - `R.S. No. 112/3`, `T.S. No. 45`;
   - `புல எண் 123/4`, `சர்வே எண் 45`, `பட்டா எண் 452`;
   - `9.559806 78.133521`;
   - `98765.43210`, `(98765) 43210`.

   Four probe rows were added to the existing probe set (`qa/tests/test_privacy_lint.py` `LEAKS`, as free-text
   village forms) to pin this. The schema stopgap was skipped because the full linter now runs on every build.
4. `apps/public-page/pyproject.toml`: a per-file `E501` ignore for the moved file, which was linted in `infra/`
   without a line limit. Without it the public-page `ruff check` CI step fails, and a file-level `noqa` trips
   root ruff's RUF100.

## Risks

- A linter false positive now **fails a build** instead of passing silently. The clean fixtures and the
  existing built-page lint tests pass. If a real batch trips it, the officer sees `public_record_invalid` with
  the file, line and rule.
- The symlink needs a checkout that keeps symlinks (git on Linux/macOS does; Windows without
  `core.symlinks` would get a text file).
- Phones on an old build that declares a wrong `size_bytes` would now get a 403 on upload. M04 sends
  `bytes.length` of the same file, so this is not expected.
