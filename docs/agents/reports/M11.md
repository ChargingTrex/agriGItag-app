## Design call first (D-036, new ADR)

The brief's linear flow (lot → intake → grading → packing) does not match the data model: intake is a **lot** event,
but grading and final packing are **batch** events (the grade engine reads readings with `batch_id`; approval and
"packed ≤ graded" are batch gates, D-033; UserFlows: "Scan the batch QR"). Readings saved on a lot would never be
graded. The phone has no batch table and the Lots table has no lot code (the pull drops it; `core/db` and `core/sync`
are outside M11). So:

- **"Receive lot"** (offline): scan → lot card → intake check. The fallback when the camera fails is a tap list of the
  lots on the phone that are `ready_for_sale` (no typed code: nothing local to match it against, and no typing).
- **"Grade batch"**: the batch list comes from `GET /v1/batches` (generated client) → grading form → final packing.
  All readings and events are still saved offline through `EntriesDao.save` and pushed by M02.

**Save path.** `saveQcEntries` writes every entry of a step in one `db.transaction` through `EntriesDao.save`
(M02 pushes them in that order): ids are UUIDv7 made once per screen (D-005, a retry rewrites the same ids),
`enteredByUserId` = signed-in QC user, `deviceTime` = `createdAt` = now, `gpsTime` null (no fix taken at the
processing unit; the server adds its clock), `undoDeadline` = now (QC records are corrected by a new version, not
undone, as M09), `assistMode` false. Batch entries have `lotId` null and `farmerId` `''` (`shortcut:`, column is
NOT NULL). There is no EventLogNotifier on main (M07 not merged), so the DAO is used directly like M09.
