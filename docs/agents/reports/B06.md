## What was done

- **Payload schemas** (`modules/events/payloads/farm.py`, `processing.py`): one model per event type
  (land_preparation, nursery, sowing, input_application, harvest, drying with `phase` start/end, packing,
  problem, intake, grading, final_packing). Every field has a description and every amount is a `Quantity`.
  Every field is optional (tenant requiredness is B13 field config, D-017). Unknown keys are rejected.
- **Event version union** (`schemas.py`): `EventVersionBase` plus 11 variants, combined as
  `EventVersionIn = Annotated[..., Field(discriminator="event_type")]`. OpenAPI renders it as `oneOf` with
  a discriminator mapping all 11 types (unit-tested). A validator checks that subject, dates and change kind
  agree: version 1 ⇔ `create`.
- **`POST /v1/sync/push`** (`sync_router.py`, `service.push`):
  - Envelope as §3. More than 50 entries → 422 (`max_length`). Body over 256 KB → 413
    `payload_too_large` (a dependency that runs before body validation).
  - Entries run in order, one transaction each. Dispatch is one dict, `HANDLERS`:
    - `event_version` → own path.
    - `quality_reading` → `quality.service.create_reading`.
    - `plot` → new `registry.service.create_plot_from_sync`, then commit and `enqueue_plot_check`.
    - `consent` → `identity.service.record_consent`.
    - `flag_resolution` → `rejected` with `not_implemented_pilot` (`TODO(B08)`).
  - An `AppError` or SQLSTATE 23001 rejects only its own entry.
  - `metrics[]` → `sync_metrics`, recorded against the token's device. `sync_cursors.last_push_at` is
    upserted.
- **Event version write path** (`service._add_version` / `write_version`): one path for sync, REST
  correction and REST undo.
  - Pre-read by client id. Same user → `duplicate`, with upload URLs re-issued only for photos still
    `pending_upload` (their expiry is moved forward). Another user or FPO → `client_id_conflict`.
  - Scope checks: lot or batch in the FPO, farmer only on own lots, assist session for the lot's farmer,
    plot in the FPO.
  - Version 1 creates `events` (ORM, so it is audited by the listener). Later versions lock the event
    row, require `version_no = max + 1` (else `stale_version`), forbid a change of type or subject, and
    apply `check_change`:
    - `correct`: field officer or FPO admin only, `reason_code` required.
    - `undo`: only the farmer who entered the event, within 24 h of version 1's device time, else 409
      `undo_window_closed`.
  - `INSERT … ON CONFLICT (id) DO NOTHING RETURNING id`. If no row comes back, or an IntegrityError is
    raised, the write rolls back and re-reads the version: `duplicate` if it exists, otherwise
    `stale_version`.
  - `entered_by`, the assist fields and the device come from `CurrentUser`. `server_received_at` is set
    by the server.
  - `entered_remotely` uses `registry.service.event_within_plot` in assist mode (radius 100 m, buffer
    50 m).
  - `events.current_version_id`, `occurred_on` and `status` are updated (`undone` on undo).
  - Photos become `evidence_photos` rows in `pending_upload`, with key
    `evidence/{fpo}/{occurred_on.yyyy}/{event_id}/{photo_id}.jpg`. A reused photo id →
    `client_id_conflict`.
  - An explicit `audit_log` row is written (action `sync.push`, `event.correct` or `event.undo`; entity
    `event_versions`).
  - After commit: one presigned PUT per photo (15 min, SHA-256 + Content-Type bound, public endpoint,
    with the exact headers). An entry without photos enqueues `rules.check_event` with hints
    (`clock_skew` when the device time is in the future vs the server, or off from GPS time, beyond 1 h).
- **`POST /v1/sync/photos/confirm`**: checks the photo belongs to the caller's FPO (key prefix), HEADs
  the object, stores `s3_version_id`, sets `uploaded` and `uploaded_at`, and enqueues
  `events.verify_photo`. The answer is `received`; a missing object, unknown id or another FPO's photo
  answers `missing`. The response is a bare list, as in §3.
- **Tasks** (`tasks.py`, logic in `evidence.py`):
  - Each task runs `asyncio.run` on its own NullPool engine (D-009).
  - `events.verify_photo`: reads the object and computes the SHA-256. A mismatch → `checksum_mismatch`
    (no variants). Otherwise it reads the EXIF DateTimeOriginal (+ OffsetTimeOriginal, else IST) and GPS
    with Pillow and compares them with the entry's device time (±30 min) and GPS (±250 m, geodesic via
    pyproj) → `verified` or `exif_mismatch`. It then enqueues `events.make_variants` and
    `rules.check_event` (hint = status when not verified).
  - `events.make_variants`: EXIF-transposes the image and writes a WebP thumbnail (≤ 480 px, ≤ 60 KB)
    and a medium (≤ 1280 px, ≤ 150 KB) next to the original. Quality steps down, then the image shrinks if
    needed. The result is recorded as `variants {thumb_url, medium_url, jpeg_url, width, height,
    medium_width, medium_height}` (width/height = thumbnail, as the public page schema expects).
- **`GET /v1/lots/{id}/events`**: latest versions ordered `occurred_on, instance_no`, with photo statuses
  and variants, returned as one `Page`. **`POST /v1/events/{id}/versions`** (field officer / FPO admin,
  body `{client_id, data: EventVersionIn}`) and **`POST /v1/events/{id}/undo`** (farmer) go through the
  same write path.
- **Errors**: new codes `stale_version` (409) and `undo_window_closed` (409). Reused:
  `client_id_conflict`, `payload_too_large`, `not_implemented_pilot`, `append_only_violation`. SQLSTATE
  23001 is mapped in two places: `core.errors.append_only_error()` for the per-entry sync path, and a
  global `DBAPIError` handler for REST (other DB errors still render as `internal_error`).
  `photo_missing` was not registered: confirm reports `missing` per photo, and nothing raises it.
- **Registry** (declared exception): `create_plot_from_sync(session, current_user, data)` validates the
  dict as `PlotIn` (→ `validation_error`) and calls `create_plot`; it is added to `__all__`.
- Docs: conventions.md "Sync" section, error-codes.md regenerated (39 codes), OpenAPI regenerated, Pillow
  ledger row (pyproj and shapely rows extended), CHANGELOG line, and TODO items closed or added.

## Risks

- **Not run on a live stack.** Things only the live stack can confirm:
  - ORM-enabled `pg_insert(...).on_conflict_do_nothing().returning()` and the bulk `insert(EvidencePhoto)`
    with geography values on asyncpg;
  - `with_for_update` on `session.get`;
  - LocalStack accepting `put_object` with `ChecksumAlgorithm="SHA256"` on the object-locked bucket;
  - the presigned PUT headers end to end.
- **Privacy (B10):** `variants.jpeg_url` is the original JPEG, which keeps the phone's exact EXIF GPS
  (M04 keeps GPS on purpose). The public page should use the WebP variants (no EXIF) or a GPS-stripped
  copy. Recorded in TODO.md.
- The 256 KB check measures a body that is already read. Production must cap request size at the load
  balancer.
- Undo is judged on phone clocks (undo device time minus capture device time). A phone with a wrong
  clock can stretch the window; the `clock_skew` hint lets B08 flag it.
- A broker outage after commit loses the `rules.check_event` / `verify_photo` enqueue (logged only, no
  retries in the request path). Confirm can be resent; the B08 sweep should cover rules.
