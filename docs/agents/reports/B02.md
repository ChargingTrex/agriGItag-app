## What was done

- **`core/auth.py`** (placeholder body replaced, signatures kept): HS256 JWTs with PyJWT. Access token
  lasts 15 min and carries `sub`, `fpo`, `role`, `dev`, `sa`, `jti`, `typ=access`. The `pin_token` lasts
  5 min and carries `sub`, `dev`, `typ=pin`, with no role or FPO. `decode_token(token, typ)` refuses a token
  of the wrong type, so a pin token never works as a session token. `get_current_user`:
  - reads the Bearer token (`HTTPBearer`, scheme `AccessToken`);
  - does one indexed read to check that the device is still signed in for that user (TODO for a Valkey
    cache);
  - validates `X-Assist-Session` against `assist_sessions` (the session must be the officer's own and still
    open), then sets `on_behalf_of_farmer_id` and `assist_session_id`;
  - calls `set_audit_context` with the actor, on-behalf-of farmer, assist session, device and request id
    (`X-Request-Id`, or a new UUIDv7).

  `require_role(*roles)` also accepts `"super_admin"` (`SUPER_ADMIN`), which admits users with
  `is_super_admin`. That flag opens no other route. `assert_same_fpo` raises 404 for another FPO's data.
  `CurrentUser` gains `is_super_admin`. core reads `devices` and `assist_sessions` through lightweight
  table handles, so it never imports a module (D-004).
- **`modules/identity/`**:
  - `schemas.py`: every field has a `description`. `OtpVerifyOut` is a discriminated union on `kind`.
  - `service.py`: has `__all__`. Pure helpers come first, then the DB functions.
  - `router.py`: 12 routes under `/v1` (listed below).
  - `__init__.py` is unchanged (`__all__ = []`). The public names are in `service.__all__` (D-004).
    Re-exporting them from `__init__` would create an import cycle with `registry.models`.

  The routes are:
  - `POST /auth/otp/request`, `POST /auth/otp/verify`, `POST /auth/pin/verify` (bearer pin_token),
    `POST /auth/pin` (office roles), `POST /auth/refresh`, `POST /auth/logout`;
  - `GET /me`;
  - `POST /assist/start` (field_officer, idempotent by `client_id`), `POST /assist/end`;
  - `POST /consents` (the farmer, or an officer in assist mode; idempotent by `client_id`),
    `GET /farmers/{id}/consents` (same FPO; a farmer sees only their own),
    `POST /consents/{id}/revoke` (writes `revoked_at` only).
- **OTP:**
  - Only the code hash is stored: HMAC-SHA256 of `phone:code`, keyed with `JWT_SECRET`.
  - Codes are 6 digits and expire after 5 min. A second request within 60 s returns 429 `rate_limited`.
  - The 5th wrong code returns 409 `otp_locked`, and so does every later attempt on that challenge.
  - Unknown phones get a challenge but no SMS, and verify returns `otp_invalid` exactly like a wrong
    code. The account lookup runs on every attempt, so known and unknown phones take the same time.
  - `OTP_DEV_CODE` set: that code becomes the challenge's code and no SMS is enqueued. When it is unset,
    `notifications.send` is enqueued by task name (template `otp`) through `agritrace.worker.app.send_task`.
    The import is lazy, because the worker reads settings when it is imported.
- **Office PIN** (migration `0002_identity_pin` adds `users.pin_hash`, `pin_attempts` and
  `pin_locked_until`):
  - The hash is Argon2id (argon2-cffi), run in a worker thread.
  - Wrong PIN: 422 `pin_invalid`, with `details.attempts_left`.
  - The 5th wrong PIN locks the PIN for 5 min: 409 `pin_locked`, with `details.locked_until`.
  - **First sign-in:** the response carries `pin_set: false`, and the PIN sent to `/pin/verify` becomes
    the user's PIN. This keeps the contract that no session is released before a PIN. `POST /auth/pin`
    changes the PIN.
  - Choice recorded: the PIN lives on the user, not on the membership. It is one PIN per person, and the
    lockout follows the person.
- **Refresh:**
  - The refresh token is `<device_id>.<256-bit secret>`, and only its SHA-256 is stored on
    `devices.refresh_token_hash`.
  - Every refresh rotates the token.
  - Any other token of that device counts as reuse: the device is revoked and the answer is 401
    `refresh_reused`.
  - Logout revokes the device, so its refresh token gets 401 and its access tokens get 401 on the next
    request.
  - At the OTP step, office devices are bound but stay signed out until the PIN passes.
- **Web (D-022):** with `X-Client: web` the refresh token is set as an httpOnly, Secure, SameSite=Strict
  cookie `agritrace_refresh` on path `/v1/auth`, and the body field is `null`. Refresh reads the cookie
  when the body has no token. Mobile keeps the body token.
- **Errors** (registered in `core/errors.py`): `otp_invalid` 422, `otp_expired` 422, `otp_locked` 409,
  `pin_invalid` 422, `pin_locked` 409, `refresh_reused` 401, `assist_session_invalid` 403,
  `consent_conflict` 409. A conflicting assist `client_id` uses the existing `conflict` code.

### Differences from the P00 contract (Orchestrator please note; documented in conventions.md)

All are additive or tighten the contract; P01 adapts the portal:
1. `otp/verify` also requires `device_id` (UUID) and `platform`; `app_version` is optional. The task
   contract asked for these.
2. `pin_required` adds `pin_set: bool`, needed for the first-PIN flow.
3. For web, `SessionOut.refresh_token` is `null` (typed `string | null`), because the cookie carries it.
4. P00's mock for `otp/request` returned `{expires_in_s}`; the contract says 204, and 204 is what ships.

## Ponytail

Skipped:
- an FPO switch for multi-FPO users (oldest membership wins);
- idle expiry for refresh tokens, and a PIN prompt on each app open;
- `X-Device-Id` (the device comes from the token);
- cursor paging on consents (one page);
- `Retry-After` header (`details.retry_after_s` instead);
- a race-proof OTP rate limit;
- user creation (B03).

Risks:
- Integration tests and `alembic check` for 0002 have not run on PostGIS.
- Migration `0002_identity_pin` revises `0001`. If B03 or B05 also add a revision on `0001`, the merge
  has two heads and someone must rebase `down_revision`.
- Two refreshes racing from one app sign that device out, by design.
