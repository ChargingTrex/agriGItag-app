## What was done

**Bundles** (`events/bundle_service.py`, routes in `events/sync_router.py`)
- `GET /v1/sync/bundle` returns `{parts: {<part>: {version, etag}}}` for 11 parts: plots, crops, inputs,
  standards, gi_region, farmer_profile, villages, fields, prompts, images, calendar.
- `GET /v1/sync/bundle/{part}` returns the part body with a strong `ETag`. The ETag is `fieldconfig.etag`,
  the SHA-256 of the canonical JSON. `If-None-Match` handles a single tag, a list, `W/` and `*`, and answers
  304 with no body. An unknown part answers 422 (enum path parameter). `gi_region` answers 404
  `gi_region_missing` while no region is in effect.
- `GET /v1/sync/reference?since=<part>:<version>,...` compares each part on its own (TODO F1). It returns a
  part when its version **differs** from the one the phone holds, or when the phone did not list it. It
  answers 304 when nothing changed. A bare number or a malformed item answers 422 `validation_error`.
  - Why "differs" and not "greater": the versions of database-fed parts only grow, and fingerprints have no
    order.
- Versions:
  - **Database-fed parts** (plots, crops, inputs, standards, gi_region, villages): the version comes from
    `reference_versions`, as the global row + the FPO row summed. A max would hide a late-committing global
    bump, for example on inputs. Each row grows in commit order because it is bumped under its row lock, so
    the sum grows with every visible change.
  - **Other parts**: the version is the first 48 bits of the ETag hash.
- Part bodies follow M03's contract exactly. The golden fixture `apps/mobile/test/fixtures/reference_bundle.json`
  is asserted in unit tests. Additive keys: `plots.code`, `plots.gi_tag_id` and `crops.gi_tag_id`.
  - `standards`: `{profiles: {crop_id: <full rules JSON>}}`, carrying the full rules (DECISION D-006 comment).
  - `gi_region`: `simplify_region` at 50 m, then 100/200/400 m until the outline is ≤ 50 KB. It also carries
    the buffer, `version_no` and provenance.
  - `fields`: `fieldconfig.bundle_part` (D-017 comment).
  - `farmer_profile`: lean `{farmers: [...]}`, with no phone, address or IDs. It holds the farmer themself,
    or the FPO's farmers for officers (assist mode).
  - `villages`: the villages of the FPO's district.
  - `images`: input product pictures as plain URLs into the `public-pages` bucket (D-016 comment: stable URLs
    keep the ETag stable).
  - `prompts` and `calendar`: empty lists with a documented item shape.
- Scope:
  - A farmer gets their own plots and their own farmer row. Every other role gets the FPO.
  - Crops, standards and gi_region are global.
  - Inputs are global + the FPO's own.

**Pull** (`events/pull_service.py`)
- `GET /v1/sync/pull?cursor=&limit=200` returns `{changes: [{entity, op: upsert, data}], next_cursor,
  has_more}`. Changes come from `lot`, `intake`, `flag`, `notification` (own) and `event` (current version
  through `service.event_outs`, plus `subject_type` and `lot_id`).
- Ordering and paging:
  - Changes are merged in `(updated_at, id)` order. Each table returns `limit+1` rows, so the merge is exact.
  - The cursor is opaque: base64 of `[iso, id]`. A bad cursor answers 422.
- Farmer scope:
  - Lots, intakes and events: the farmer's own lots.
  - Flags: lot, plot and event flags on the farmer's own rows.
- `photo_pending` lists the caller's photos still `pending_upload` 24 h after the entry arrived. They come
  on the last page, and the rule lives in one function, `is_photo_pending`.
- `sync_cursors` is upserted for the token's device.
- Rows newer than `PULL_SETTLE` = 30 s wait for the next pull. `updated_at` is the transaction start time,
  not the commit time; there is a `shortcut:` comment for this.

**Presigned GETs**
- Added `core/storage.presign_get(key, expires=900, bucket=None)`.
- `evidence.signed_variants` presigns every `*_url` for 1 h. It is used by the lot timeline and pull through
  the new `service.event_outs`, which was extracted from `list_lot_events` with no behaviour change apart
  from the URLs.

**Docs**

- openapi.json was regenerated, every new route has descriptions, and error-codes.md was regenerated.
- No new error codes: the routes reuse `validation_error` and `gi_region_missing`.

## Risks

- Strong ETags are computed before Brotli/gzip compression, the same as the config routes. A cache that
  stores compressed bytes per tag could mix encodings; phones send the same `Accept-Encoding`, so this is low risk.
- The `standards_profiles` (crop link) and `fpos.address` (district) tables have no version trigger. A change
  there alters the body and ETag (the manifest catches it), but not `version`, so `?since=` misses it until
  the part's own table changes. The same applies to a region version whose `effective_from` is in the
  future: it becomes active on that date with no version bump.
