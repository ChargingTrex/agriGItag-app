## What was done

- **Auth on the final B02 contract** (`src/auth/*`):
  - `authApi.ts` now uses the generated `openapi-fetch` client (no hand-typed shapes or zod).
  - Every auth call sends `X-Client: web`. Verify sends `device_id` (a UUID kept in localStorage) and `platform: "web"`.
  - The `kind` discriminator picks the next step: `session` signs in, `pin_required` goes to the PIN step with `pin_token` as the Bearer.
  - When `pin_set: false` the user chooses a PIN, types it twice, and it is checked on the client.
  - `otp/request` expects 204.
  - `refreshSession()` sends `{}` and the cookie comes along on the same origin. It shares one in-flight promise, because two refreshes at once count as reuse.
  - Sign-out calls `POST /v1/auth/logout`.
  - `AuthProvider` keeps the `SessionOut` in React state only (`DECISION D-024` at the storage point; `DECISION D-022` at the transport). sessionStorage is gone.
  - On mount it restores the session through the refresh cookie, and `RequireAuth`/`LoginPage` show a progress bar meanwhile. It refreshes 60 s before `expires_in` runs out.
  - Any API 401 signs out.
  - Error text comes from the generated `ERROR_MESSAGES` plus details: `pin_invalid` "N attempts left", `pin_locked` "You can try again at HH:MM" (from `locked_until`), `rate_limited` "Try again in N seconds".
  - Note: the contract names `details.locked_until`. The brief's "retry_after" exists only on `rate_limited` (`retry_after_s`).
- **Members** (`src/features/members/`):

  - `PlotPage`: location_status chip, method label, declared vs walked area with units, gap % with a >20 % warning, and the review outcome.
  - `PlotMap` is loaded with `React.lazy`:
    - MapLibre GL 6.16 shows an OSM raster style. The source `bounds` and the map's `maxBounds` are the GI region bbox padded by 0.1°, so tile requests and the browser cache stay in the FPO area (D3).

  - Routes: `/members`, `/members/:farmerId`, `/members/plots/:plotId`, `/processors`. Nav: "Processors" added after Members.

How the P2-2 fix works:
- A 401 from a data call tries the refresh cookie once. All concurrent 401s for the same token share that one attempt.
- On success the new session is stored and every query is invalidated.
- The session ends only in two cases: the server refuses the refresh (`ApiError`), or a token obtained by a recovery less than 10 s ago gets a 401 again. The second case is the loop guard.
- A network error during a scheduled or recovery refresh keeps the session.
- 401s carrying a token that is no longer current are ignored.

While doing P2-2 I found a real stale-token bug, and the existing Dashboard test caught it:
- Queries that `invalidateQueries` refetched still sent the old token, because each client captured the token when it was created.
- Now one client reads the token per request from a ref, which `store()` keeps in step with React state. The token is still only in memory (D-024 comment updated).
- `react-hooks/refs` flags passing the getter to `createApiClient`, so there is one `eslint-disable-next-line` with its reason.
- The 401 handler receives the rejected token from the request's `Authorization` header.
- The mock refresh now issues a new token each time (`mock-access-token-<n>`), like the real API.
