## What was done

- **39 models, one per table in backend-design.md §2**, each in its owning module's `models.py`:
  identity 7, registry 12 (includes the flag-gated `id_documents` and `producer_groups`), events 6
  (includes `reference_versions` and `sync_metrics`), lots_batches 5, quality 5, rules_flags 1,
  publishing 1, reporting 1, notifications 1. Every column has `comment=`, every class has a docstring
  that cites FR numbers or a Dataflow stage. No ORM relationships (services join explicitly) and no
  columns beyond §2.
- **`core/db.py`**: `Base.type_annotation_map` (str → TEXT, Decimal → NUMERIC(12,3), datetime →
  timestamptz, dict → JSONB, StrEnum → VARCHAR(32) + CHECK). There are two mixins: `IdTimestamps` (UUIDv7 `id`
  default from `core.ids.uuid7`, `created_at`/`updated_at` with `now()`) and `TenantScoped` (`fpo_id` NOT
  NULL, indexed FK to `fpos`). `sync_cursors` (PK `device_id`) and `batch_shares` (PK `batch_id, lot_id`)
  declare their own timestamps.
- **`core/enums.py`**: 31 `StrEnum`s: one per `a | b | c` value set in §2, plus `PracticeTag` for the JSONB shapes.
  The CHECK-versus-PG-ENUM choice is recorded in `core/db.py`, as `DECISION D-014` in round 1 and as `DECISION D-023` since round 2.
- **Spatial**: `plots.pin` POINT, `plots.walked_boundary` POLYGON, `gi_region_versions.geom` MULTIPOLYGON,
  `event_versions.gps` POINT, all SRID 4326 with GiST indexes (`idx_<table>_<col>`). The other five point
  columns have no index. `event_versions.payload` has a GIN index (D-014 compromise).
- **Keys and checks**: events `ck_events_one_subject` (exactly one of lot_id / batch_id); UNIQUE
  (event_id, version_no), (gi_tag_id, version_no), (profile_id, version_no), (user_id, fpo_id),
  (plot_id, revision_no), (batch_id, build_no), (fpo_id, code) on farmers; unique lot/batch/super-lot
  codes, phone, dedupe_key, object_key; batch_shares PK(batch_id, lot_id) + `0 ≤ share_pct ≤ 100`;
  `reference_versions` UNIQUE (part, fpo_id) NULLS NOT DISTINCT (Postgres 15+). Two circular FKs
  (`events.current_version_id`, `evidence_photos.quality_reading_id`) use `use_alter`.
- **`alembic/versions/0001_initial.py`**: `CREATE EXTENSION IF NOT EXISTS postgis`, then every table and
  index. The table and index calls were rendered from the metadata with Alembic's own renderer, so they
  match the models exactly. Geography columns are created with `spatial_index=False` and their GiST
  indexes explicitly, so each index is created once. Raw SQL:
  - `forbid_change()` trigger function: DELETE is always refused. An UPDATE is refused unless only the
    columns passed as trigger arguments change. The error is `append_only_violation` with SQLSTATE
    23001 `restrict_violation`. It is installed on `event_versions` and `audit_log` (no columns
    allowed), on `evidence_photos` (sha256_server, exif_taken_at, exif_gps, status, variants,
    s3_version_id, upload_url_expires_at, uploaded_at, verified_at, updated_at) and on `consent_records`
    (revoked_at, updated_at).
  - `bump_reference_version(part)` AFTER INSERT/UPDATE/DELETE on plots, crops, inputs_master,
    standards_profile_versions, gi_region_versions and villages. It upserts
    `reference_versions(part, fpo_id)` to `nextval('reference_version_seq')`, so a single `since` number
    covers every bundle part (§3).
  - `downgrade()` drops everything except the shared postgis extension.
  - `alembic/env.py` now imports every `modules/*/models.py`, which B00's env.py docstring asked B01 to do.
    `search_path` is still pinned to `public`.
- **`core/audit.py`**: `Audited` marker mixin; `AuditContext` with `set_audit_context` /
  `reset_audit_context` (a ContextVar; B02 sets it per request); an `after_flush` listener on `Session`
  that writes one `audit_log` row per created, changed or deleted `Audited` object in the same
  transaction. The row holds actor, on_behalf_of, assist_session, device, gps, action, entity_type,
  entity_id and request_id. `diff` holds the column values on create and delete, and `{column: [old, new]}` on update.
  core may not import modules (D-004), so the listener writes through a lightweight
  `table("audit_log", ...)`, and a unit test keeps it in step with `AuditLog`. Audited models: users,
  memberships, consent_records, fpos, processors, farmers, plots, events, lots, lot_intakes, batches,
  batch_shares, batch_approvals, standards_profiles, standards_profile_versions, instruments,
  quality_readings, flags.
- **`core/auth.py`**: `CurrentUser` dataclass, `get_current_user()` placeholder that always raises
  `unauthorized` (B02 replaces its body; documented in the module header), and `require_role(*roles)`.
  `require_role` returns a dependency that raises `forbidden` when the caller's role is not listed.
- **`core/schemas.py`**: `Address`, `PracticeTags`, `Reconciliation`, `YieldCheck` (every field has a
  description). These are the shapes of the address / practice_tags / reconciliation / yield_check JSONB
  columns.
- **Tests**:
  - `tests/unit/test_models.py` (40 tests):
    - the table set equals §2 exactly;
    - every model has a docstring citing a requirement and every column has a comment;
    - constraint and index names are unique;
    - each of the 32 enum columns stores its StrEnum values and round-trips;
    - the mixin defaults produce UUIDv7 ids and fpo_id is NOT NULL with an FK to fpos;
    - SRID, geometry types and the GiST/GIN index sets are as specified;
    - the §2 keys and checks are declared;
    - the migration's trigger lists, drop order and late FKs name real tables and columns.
  - `tests/unit/test_audit.py` (5 tests): context stamping, update diffs, unaudited models skipped,
    nested contexts.
  - `tests/unit/test_auth.py` (2 tests).
  - `test_schemas.py` gained 1 test for the JSONB shapes.
  - `tests/integration/test_schema.py` (7 tests, marker `integration`):
    - `alembic upgrade head` then `alembic check` reports no drift; downgrade to base and re-upgrade
      also work;
    - UPDATE and DELETE on `event_versions` raise `append_only_violation`;
    - `ST_SRID(pin::geometry) = 4326`;
    - inserting a plot bumps the FPO's `plots` reference version;
    - evidence photos accept a verification update but refuse an `object_key` change;
    - an audited insert writes an audit row with the context, and that row cannot be deleted.

## Risks

- `alembic check` false positives that cannot be ruled out without PostGIS:
  - how GeoAlchemy2 reflects `geography(...)` types and the `idx_*` GiST indexes;
  - non-native Enum (VARCHAR(32)) versus reflected VARCHAR;
  - `postgresql_nulls_not_distinct` reflection.

  All three are handled by Alembic 1.20 / GeoAlchemy2 0.20 code paths I read, but none was observed
  running. If drift shows, the fix is in the model or the migration, not the env.
- `alembic check` does not compare CHECK constraints, so an enum value added without a migration is not
  flagged by drift. The database still rejects the value, and `test_models.py` pins each column to its
  StrEnum.
- Append-only triggers block DELETE-based test clean-up (TRUNCATE still works). Tests must use fresh rows (as
  `test_schema.py` does) or drop and recreate the schema.
- `evidence_photos` allows `upload_url_expires_at` to change, which is not in the brief's list. A URL
  re-issued for an expired presigned PUT on the same object key is not an evidence change; drop it
  from `APPEND_ONLY` if the reviewer disagrees.

## Round 2 (review docs/agents/reviews/B01-r1.md)

- **R1**: `bump_reference_version` now draws the number under the row lock with
  `DO UPDATE SET version = nextval('reference_version_seq')`, so a part's version cannot go backwards.
  The comment above it now says the sequence orders transaction *starts*, not commits, so B06 must
  compare parts one by one rather than trust a single `since` across parts (F1). No test inspected the
  old SQL, so no test changed. I re-ran the PL/pgSQL check in a rolled-back transaction on the local

  COMPROMISE lines. `test_models.py` and the migration header cite D-023.
- **R3**: added `test_live_enum_checks_match_the_strenums` (marker `integration`) to
  `tests/integration/test_schema.py`. It reads `pg_get_constraintdef` for each of the 32 `ck_<table>_<enum>`
  constraints after `upgrade head` and checks two things: the constraint tests the right column, and
  its quoted values equal the StrEnum's value set. I checked the regex against the real
  `pg_get_constraintdef` output for a VARCHAR `IN (...)` CHECK on Postgres 14:
