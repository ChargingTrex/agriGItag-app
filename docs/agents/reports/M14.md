# WP-M14 worker report — Sync engine audit P1 fixes

**Branch:** `worktree-agent-a97f169273e8f5afb` (from main `283b039`) · **Decision:** D-054 (docs/adr/D-054.md) ·
**Date:** 2026-11-01 · **Source:** docs/agents/audits/waves-3-6.md findings 1 and 2 (TODO.md §6, both ticked)

## P1-1: out-of-order retry after a failed push

Root cause: `_failed` drew a jittered backoff per row and `OutboxDao.nextBatch` filtered on
`nextAttemptAt <= now`, so the row with the shortest wait went alone, ahead of the farmer, assist session or
version 1 it depends on; the server rejected it (`not_found`, `assist_session_invalid`) and the phone parked it as
`needs_attention` for good. Fix: `nextBatch` (outbox_dao.dart) no longer filters on due time; it walks the owner's
`waiting` entry rows in `seq` order and stops at the first row not yet due, so a row in backoff holds back every later
row (strict FIFO; `needs_attention` rows are not `waiting` and never block). `_failed` (outbox_processor.dart) draws
one backoff for the whole batch (same 2-4-8 s jittered policy, 5 min cap, `Retry-After` hint). In `_applyResults`
the per-entry codes `not_found` and `assist_session_invalid` (picked from docs/api/error-codes.md and
`events/service.py` `push` / `_entry_caller`) are retried once, exactly like the existing `stale_version` rule
(D-005); because of FIFO every older row has been answered by the time of the retry. A second rejection with the same
code, and every other code (`validation_error`, `forbidden` …), is final. No schema change; the 50-entry/256 KB
limits, entries-before-photos and the D-031 farmer/assist-session-first ranking are unchanged. Recorded as D-054.

## P1-2: background refresh signs the farmer out

Root cause: `SessionNotifier._doRefresh` (lib/core/router/session.dart) used the in-memory `_refresh`, which the
WorkManager isolate may already have rotated in the keystore; the server saw `refresh_reused` and revoked the device.
Fix: a new private `_adoptStored()` re-reads `flutter_secure_storage` (one `readAll`) and adopts its tokens and expiry
when the stored refresh token differs from the one in memory (never after this isolate signed out; a keystore error
keeps the memory copy). `_doRefresh` calls it first and returns the stored access token without a network call when
it has not expired; otherwise it refreshes with the stored token. After a 401 on refresh it re-reads once more and,
if another isolate rotated the token meanwhile, keeps that session instead of signing out. The single-flight
`_refreshing` and the "answer after sign-out is discarded" rule are unchanged.

## Risks

- One row in backoff now delays every later row of that user until it is due (at most 5 min); an entry that keeps
  failing with 5xx holds the queue for its backoff each time.
- A truly missing dependency (e.g. a lot of another FPO) waits one backoff longer before needs_attention.
