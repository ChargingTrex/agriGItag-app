## Cause

`store_flags` closes every active flag of its subjects/codes that the current run did not raise. A run reads
its facts first and calls `store_flags` later, in one READ COMMITTED transaction. Two checks of the same lot ran
at the same time with no lock, so a `quantity_mismatch` that `create_intake` → `run_gate_checks` committed between
the task's fact read and its stale query got closed `fixed` / `rule_passed` by a `rules.check_event` task that never
saw the intake.

## Fix (option a: serialise per lot/batch)

`apps/api/agritrace/modules/rules_flags/service.py` `run_gate_checks`: the batch row, then each lot row in id
order, is loaded `with_for_update=True, populate_existing=True` before its facts are read. Every lot/batch rule
run goes through `run_gate_checks`: tasks `check_lot` and `check_event`, the B09/B16 gates and the seed. So two
checks of one lot now run one after the other. Once a check holds the lock, its READ COMMITTED reads see every
check committed before it. `populate_existing` refreshes a lot that was already loaded earlier in the same
session. Lots are locked in id order, which is the order `create_batch` uses, so two checks cannot deadlock on
lots. The order is batch first, then lots. `create_batch` locks lots and then only its own new batch, which no
one else can see yet, so that path cannot form a cycle.

### Why not option (b) (close only flags raised before the run started)

The two timestamps cannot be compared safely. `raised_at` is set by the writer before it commits (Python
`utcnow()`, or `now()` at the start of its transaction). A flag can carry a `raised_at` older than the reader's
start and still commit after the reader read its facts, which is exactly this race. So (b) would only narrow the
window. Postgres exposes no commit timestamp without `track_commit_timestamp`, which would be a config change.
Option (a) is four changed lines in one function and is correct for both orders, so no DECISION entry was
needed. An inline comment at the lock explains why it is there.

### Reopen semantics (B08-r1) unchanged

`store_flags` and `reopens` are untouched. A `rule_passed` close still reopens when the rule fires again. A flag
a reviewer resolved still reopens only when the severity increases (`test_hold_comes_back_after_auto_close`
and `test_resolve_over_http_and_sync` pass).

## Risks

- Lot checks now queue behind each other. A gate request waits while a worker check of the same lot holds the
  lock: one check, milliseconds to about a second under load.
- No deadlock path was found: lots are always locked in id order, batches before their lots, and sync push
  entries commit one at a time. If some later code path locks a lot and then a batch, or a lot and then a flag
  in one transaction, Postgres aborts one side with a deadlock error. A task fails and is logged; a push entry
  fails and the phone resends it. In both cases nothing is lost.
