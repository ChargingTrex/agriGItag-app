## 1. Q04-1: one entry Postgres refuses turns the whole push into a 500

**Root cause.** `events/service.py` `push()` caught `AppError` and only the `DBAPIError` that
`append_only_error` maps (SQLSTATE 23001); any other `DBAPIError` was re-raised, so the request ended in 500.
Two inputs passed Pydantic and failed in Postgres: a NUL (`\u0000`) in any string reaching text/jsonb, and an
int above int32 in an INTEGER column (`instance_no`, `version_no`).

**Fix (trust boundary first, DB backstop second).**
- `core/schemas.py`: `INT32_MAX`, `NoNulStr` (an `Annotated[str, AfterValidator]`) and `find_nul()` (walks
  JSON-like data, dict keys included, and returns the location of the first NUL).
- `events/schemas.py`: `le=INT32_MAX` on `EventVersionBase.version_no`, `instance_no` and `UndoIn.version_no`.
- `push()`: before an entry's handler runs, `find_nul(entry.data)` rejects that entry with `validation_error`
  and `details=[{loc: ["data", ...path], type: "string_nul"}]`. This is one check for all eight kinds, including
  the ones whose schemas live in other modules (plot, consent, farmer, reading, intake). `SyncEntry.data` stays
  `dict[str, Any]`, because an envelope-level validator would 422 the whole batch and break the per-entry contract.
- `push()` backstop: a `DBAPIError` with SQLSTATE class 22 (data exception), or a driver `ValueError` (asyncpg's
  client-side `DataError`, e.g. int32 encode), becomes that entry's `validation_error`. The session is rolled
  back and the next entry runs. Any other DB error (connection loss, deadlock) is still raised as a 500, so the
  phone retries it and never sees a false `rejected`. Each entry is already its own transaction (commit or
  rollback per entry), so there is no extra savepoint.

**Tests.**
- `tests/integration/test_sync.py::test_nul_and_int32_overflow_reject_only_their_entries`:
  [NUL in `payload.description`, clean, `instance_no=3000000000`] → rejected / accepted / rejected, 200, no row
  for the two. I also ran it once with the NUL check and the `le=` bound switched off. It passed through the DB
  backstop alone, against real PostGIS, so the backstop catches both of Q04's shapes.
- `tests/unit/test_sync_b21_unit.py`: SQLSTATE 22021 → `rejected` + next entry `accepted`; 08006 → re-raised;
  NUL nested in a list → rejected with `loc ["data","payload","tags",1]`.

## 2. Q04-2: telemetry 500 after the entries committed

**Root cause.** `SyncPushIn.app_version` and `SyncMetricIn.network_type` accepted NUL, and `failures` and
`photo_upload_ms` had no upper bound. `_store_metrics` runs after the entries have committed.

**Fix.** `app_version: NoNulStr`, `network_type: NoNulStr | None`, `le=INT32_MAX` on `failures` and
`photo_upload_ms`. A bad envelope is now a 422 at request validation, before any entry is written, so nothing
commits and the phone gets a clear error. There is no 500 after commit.

**Test.** `tests/unit/test_sync_b21_unit.py::test_telemetry_postgres_cannot_store_is_refused_at_the_envelope`
(4 cases: NUL in `app_version` and in `network_type`, `failures` = 2^31, `photo_upload_ms` = 2^31).

Not done: plausibility of `saved_at`/`acked_at` (years 0001/5383 are stored; not a 5xx, listed in TODO).

## 3. Q04-3 / BM-07: p95 1.9–3.1 s at 50 users

**What one push costs (py-spy, 40 s at 50 Hz on the single uvicorn process during the 50-user run,
summary `docs/agents/qa/B21/logs/pyspy-before-1proc-summary.txt`).** The process was busy in 1627 of 1698
samples (about 96 %), so it is CPU-bound and is not waiting on the DB or the pool. No single hot spot: about 21 %
is SQLAlchemy ORM `session.execute` (compile, cache key, row loading), 13 % `session.get`, 7 % Celery
`send_task` (kombu publish in a thread), 5 % `get_current_user`/`_device_active`, 3 % `pool_pre_ping`, and the
rest is the FastAPI/Starlette stack and asyncio. The push itself is 16 % of samples (`_add_version` about 8
round trips per entry). One Python process saturates one core at about 25 RPS, as Q04 diagnosed.
Postgres (130–460 %) and the Celery worker (300–560 % on `rules.check_event`) compete for the same 12 vCPUs.

**Fix.** `apps/api/Dockerfile`: `ENV WEB_CONCURRENCY=4`. uvicorn reads this as its `--workers` default, so
a deploy can size it to its vCPUs without a new image, and the celery container ignores it. Each process has
its own pool (5 + 10), 60 connections at most, under Postgres' default 100. **Pool not changed.** The profile
shows CPU saturation, not checkout waits, and the run had 0 failures and no pool timeouts. Compose needs no
change (the api service uses the image CMD).

**Numbers** (locust 2.47.0, Q04 profile unchanged: 30 farmer sync + 20 staff batch-read users, spawn 5/s, 60 s;
host i7-8850H, 12 vCPU to Docker, host load average 5–13 at the start of each run). Each B21-stack run started
from a fresh `down -v` + seed. The rules work grows with events per lot (about 3 s per check at 1,000 events),
so runs on a growing DB are not comparable.
