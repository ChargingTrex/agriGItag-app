## What was done

1. **Models** (`lib/core/refdata/models/`):
   - `standards.dart` is the Dart mirror of `StandardsProfileRules` (Range, Parameter, LabCertifiedRequires, LotGate,
     TrailRule, YieldRule). Defaults are the Pydantic ones, so a trimmed bundle entry parses to what the server
     assumes. No validation: the server already accepted the profile. `toDecimal(x)` is `Decimal.parse(x.toString())`,
     which is the same thing as Pydantic's `Decimal(str(x))`.
   - `reference.dart` holds Crop + EventSchema (`mandatory`, ordered `tracks`), InputItem (FR56 category), RefPlot
     (pin and declared area in acre or cent), GiRegion (polygons → rings → `(lon, lat)` plus `bufferM`; it reads the
     bundle form or the seed FeatureCollection) and CalendarEntry.
2. **`bundle_repository.dart`**: `BundleRepository(db.refBundlesDao)` with `crops()`, `inputs()`, `plots()`,
   `calendar()`, `standards(cropId)` and `giRegion()`. Before the first download it returns empty lists or null. A
   malformed part throws `FormatException`/`TypeError`. It is the only Drift reader; the rules never touch the DB.
3. **Rules** (`lib/core/rules/`, one pure file per rule, no engine abstraction):
   - `grade_calculator.dart` is a line-by-line port of `grade_engine.py`: `compute`, `rank`, `declaredVsComputed`,
     `checkPlausibility`, `checkTrail`, `lotGate` and `yieldOutcome`. It keeps the private helpers `_latest`
     (sorts by `(measuredAt, id)`, null first, UUID as lower-case hex = Python `uuid.UUID` order) and `_countsAsLab`.
     The header carries `DECISION D-006` and `DECISION D-015`.
   - `gi_check.dart` uses an even-odd ray test over every ring, so holes count as outside. Distance in metres to the
     nearest edge comes from an equirectangular projection centred on the pin. A pin within 1 mm of the outline
     counts as `inside` (ST_Covers), a pin within the buffer is `nearEdge`, anything farther is `outside`. It
     returns `(status, distanceM)`, as `locate_point` does.
   - `yield_check.dart` converts the plot's area to acres (exactly: 100 cents = 1 acre) and calls `yieldOutcome`.
   - `moisture_limit.dart`: `moistureVerdict(rules, value)` → `ready` / `continueDrying` through
     `lotGate('ready_for_sale')`. A profile with no gate never blocks.
   - `event_order.dart`: `orderGaps(schema, recorded, newType, on)` lists the earlier steps, in every track that
     contains `newType`, that have no event dated on or before `on`. Tracks are independent of each other.
   - `practice_tags.dart`: `derivedPracticeTags` (any chemical input → inorganic; inputs present and none chemical →
     organic; no inputs → nothing) and `practiceFlags` → `practice_tag_contradiction`, `ipm_without_pest_event`.
     These are the B08 flag codes from backend-design.md §5.
4. **Fixtures** (`test/fixtures/`): byte-identical copies of `grade_cases.json`, `dry_chilli_agmark_v1.json` and
   `gi_region_fixture.geojson`. A JSON file cannot carry a header, so `README.md` there names the source of each. Also
   added a phone-only `reference_bundle.json` (crops with nursery/main-field tracks, the 5 seed inputs plus Urea,
   plots in acre and cent, calendar).
5. **Identity check**: `tool/check_shared_fixtures.sh` runs `cmp` on the three pairs. It is a new step in the CI
   `mobile` job (the only change to ci.yml).
6. **Dependency**: `decimal ^3.2.6` (Apache-2.0; transitive `rational` 2.2.3, Apache-2.0), with a ledger row.
   `libraries-check.py` PASS (121 rows).

## Float or Decimal (judged as asked)

A double port of `yield_outcome` gives the wrong answer on fixture cases. In IEEE doubles, the same arithmetic that
Dart uses:
`(1950/(1000*1.5)-1)*100 = 30.000000000000004` → `hold`, but the fixture expects `warn` (exactly 30 % over).
`1300 kg / 1 acre` gives the same failure, and `1200` gives `19.999999999999996`. So the port uses `Decimal`
everywhere the Python engine does. `yieldOutcome` divides exactly with `Rational`. Python rounds the quotient to 28
significant digits, so the two can differ only when the excess is within about 1e-26 % of a margin.

## Contract for B07 (B07 is not merged; these are the shapes the phone parses)

- `crops` `{"crops": [{id, code, name_en, name_local?, event_schema: {mandatory: [type], tracks: {name: [type in date order]}}}]}`.
  An event type may sit in several tracks (`sowing` ends `nursery` and follows `land_preparation`).
- `inputs` `{"inputs": [{id, name_en, name_local?, manufacturer?, category, unit}]}`.
- `plots` `{"plots": [{id, farmer_id, pin: {lat, lon}, declared_area, area_unit: acre|cent}]}`.
- `standards` `{"profiles": {"<crop_id>": <rules JSON>}}`.
- `gi_region` `{"geometry": <Polygon|MultiPolygon>, "tolerance_buffer_m": n, ...}`.
- `calendar` `{"calendar": [{event_type, due_on: "YYYY-MM-DD", prompt_id, lot_id?}]}`.

**Conflict to resolve before M11:** the B07 acceptance says the `standards` part has *only* `lot_gates`, `yield`,
`plausible` and `limits`. The grade preview also needs `grades`, `fail_grade` and, per parameter, `code`, `unit`,
`required`, `grading_stage`, `role`, `sources_allowed`, `max_grade_for_source` and `exception_flags`, plus
`trail_rules` and `lab_certified_requires`. With the trimmed part, the moisture gate and yield preview work, but
`compute` would see no grades. B07 should either ship the full rules or the list above.

## Risks

- **Float vs Decimal**: resolved by using `decimal`. The remaining divergence is the 28-digit quotient rounding
  described above (theoretical).
- The GI distance uses a sphere and an equirectangular projection, while PostGIS uses the spheroid. Within a few km
  of the edge the difference is under 1 m, so a pin within about 1 m of the buffer line may get a different
  near_edge/outside answer on the phone than on the server. That is acceptable for a preview; the server decides.
