## 1. P06 / B11: the `event.correct` audit row has no reason

**Cause.** `events/service.py` `_add_version` writes the `audit_log` row by hand (Core insert, D-005). Its
`diff` held `event_id, event_type, version_no, change_kind, photos`, not the reason the version stores.

so the portal shows no "reason code: null" line on `sync.push` rows. The portal already reads these exact keys:

present, so no portal change is needed. The audit search goes through `reporting.service.scrub`, which hides only
location and land-record keys. The audit CSV (B11 `audit_csv`) already read `reason_code` / `reason_text` from

## 2. B10-1: a plot without `farming_type` fails the page build

**Cause.** `builder.assemble` already sends `farming_type: None` for a plot without one. W01's
`agritrace_page/schema.py` `Lot.farming_type` was `Literal["irrigated", "rainfed"]` with no `None`, but
`config/fields/plot.yaml` has `farming_type` `required: false`. So the page refused data the YAML allows.

**Fix (root, page schema).** `Lot.farming_type` is `Literal[...] | None = None`, with a `DECISION D-017` comment
(the YAML decides requiredness). The template prints the farming-type row only when it is set, the same way it
handles `irrigation_source`. Without that guard, `t("farming_type.None")` would raise `KeyError`. The YAML field
stays optional. `PAGE_REQUIRED_FIELDS` still lists `plot.farming_type`, so a tenant still cannot hide or disable
it. That keeps D-034's start-up check: always public when recorded, never narrowed. Only its comment changed.

**D-034 note.** D-034 §Decision 1 lists "farming type" among the fields that are always sent and whose empty
value fails the build. The brief says it is not page-required, and the YAML agrees. The ADR text now disagrees
with the code. I logged a TODO for the Orchestrator to amend it, because `docs/adr/` is not a declared path.

**Test.** `tests/unit/test_publishing_builder.py`: the old
`test_missing_farming_type_is_refused_with_its_path` (which encoded the bug) is now
`test_plot_without_farming_type_builds_without_the_line`. All lots have no farming type, the build succeeds,
`data.json` has `farming_type: null` for each lot, and the HTML has no "Farming type" row and no "Irrigated".
The test first checks that the row is there when the type is recorded, so the check is not vacuous.
Fail-closed validation of the page's required fields is still covered by `apps/public-page/tests/test_render.py`.
That suite has 76 tests and all pass.

## 3. B08-2: `POST /v1/intakes` 500 on a deadlock with the rules worker

**Lock order now (main with B19).**
- Intake: `create_intake` locks the lot `FOR UPDATE` (`_lot_in_scope(lock=True)`), may run `mark_ready`,
  inserts the intake, then calls `run_gate_checks(lot_id=…)`. There is no `batch_id`, so it takes no batch lock.
  The lot lock is then a no-op re-lock, and it writes lot-rule flags and updates the lot.
- Worker `check_event`: locks the event `FOR NO KEY UPDATE`, then `store_flags` writes the event-rule flags.
  The subject is the event and the codes are `event_off_plot, gps_poor_accuracy, clock_skew,
  photo_checksum_mismatch, exif_mismatch`. Then `run_gate_checks` locks the lot `FOR NO KEY UPDATE` before any
  lot flag or `UPDATE lots`.
- The event-rule codes and the lot-rule codes are disjoint (`rules/__init__.py` groups, each module's `CODES`).
  So the worker's event phase never holds a flag row or `uq_flags_dedupe_key` entry that the intake's
  `store_flags` inserts or closes. The intake never waits on the worker, and the worker waits on the lot. There
  is no cycle, so the lot-then-batch concern does not apply at intake.
- Before B19, the worker inserted lot flags with no lock and then ran `UPDATE lots`. That was the observed cycle
  (`INSERT INTO flags` vs `UPDATE lots … gi_eligible`). B19 removed it.

**Live reproduction: not reproduced, 0 of 20 runs.** Stack: compose `agritrace` on localhost:8000. The api and
worker image contains B19's `key_share` locks: checked in both containers with
`grep key_share /app/agritrace/modules/rules_flags/service.py`, which gives 5 hits. Script:
`docs/agents/qa/B20/logs/live_b20_deadlock.py`. It reuses `docs/agents/qa/B09/logs/qa_live.py` with the shared `QA_WORLD`.
The run had 20 iterations with no pause. In each, the officer pushes harvest 220 kg and packing 200 kg on a new
lot (two `rules.check_event` tasks). Then, straight away, the admin posts a drying-end moisture of 10.0 %,
`POST /lots/{id}/ready` and `POST /v1/intakes` (200 kg, processor named).
- The intakes all succeeded: **20/20 HTTP 201**.
- `docker logs --since 18:59:20Z` for api, worker and db: **0** `deadlock` lines and 0 HTTP 500. The worker logged
  80 `check_event` lines.
- The race window was really open. For example, the run-1 task arrived at 19:00:00.56 and ran 3.8 s, and the
  run-1 intake answered at 19:00:02.10, while that task was still running.

Not reproduced in 20 live runs (logs in `docs/agents/qa/B20/logs/`: the script `live_b20_deadlock.py`, the run log `01-live-b20-deadlock.log` and the api/worker/db greps `02-log-greps.txt` from `greps.sh`). B08-2 is closed on the lock-order analysis plus the 503 `retry_later` backstop; the Verifier confirms it live at G2. 0 of 20 at the observed rate of 1 in 11 is weak evidence on its own (review B20-r1 P2-2). The lock order was left alone, and the resolution is appended to the issue file.

**Backstop (a few lines, as the brief allows).** `core/errors.py` has a new registered `RetryLaterError`
(`retry_later`, 503, `error.retry_later`, with a fix line). `_db_error` now maps SQLSTATE `40P01`
(deadlock_detected) and `40001` (serialization_failure) to 503 `retry_later` with `Retry-After: 1` and logs one
WARNING. Before, both became a 500 `internal_error` with a traceback. The transaction has already rolled back
and intakes and pushes are idempotent by client id, so the client can resend the same request unchanged.
Unit test: `tests/unit/test_errors.py::test_deadlock_is_retryable_503`.
