## 1. Export: `GET /v1/farmers/{farmer_id}/export`

- `fpo_admin` only (`Admin` dependency, 403 otherwise, farmer role included). Outside the caller's FPO, or
  a missing farmer, answers 404 (`_farmer_in_scope`, FR24).
- `service.export_farmer` runs the runbook §1 query as one SQL statement (`_EXPORT_SQL`). Empty sections
  are `[]`, not null. Sections: `farmer`, `user` (full phone, no `pin_hash`), `plots` (pin and walked
  boundary as GeoJSON, land record ref included), `consents`, `id_documents`, `lots`, `intakes`,
  `batch_shares`, `event_versions` (payload as stored, `gps` as GeoJSON), `evidence_photos`,
  `assist_sessions` (no GPS), `audit_log` (no GPS), `links_expire_at`.
- Each ID document and evidence photo gets `url`, a presigned GET valid for 15 min (`ID_DOC_URL_TTL_S`).
  `core/storage.presign_get` gained a `bucket=` argument for this (2 lines, outside the declared paths).
- Response schema `FarmerExport`: each section has a `description=`. Sent with `Cache-Control: no-store`.
- It writes the audit row `farmer.export`. Its diff holds only the row count per section, no values. After
  merging main (B25), both audit rows go through `core.audit.write_audit(..., "farmers", ...)`.

## 2. Erase: `POST /v1/farmers/{farmer_id}/erase`

- `fpo_admin` only, FPO-scoped (403/404 as above). Body `FarmerErase`: `reason` (1-500 chars, a request
  reference and no personal data, since the audit trail keeps it for good) and `confirm: Literal[True]`.
  If either is missing or wrong, the answer is 422 `validation_error`. The route answers 204.
- **Idempotency: 204 again, no-op** (the smaller option, so no new error code). The service locks the farmer
  row. If a `farmer.erase` audit row already exists for the farmer, it does nothing.
- One transaction (`service.erase_farmer`), runbook §2 steps 2-4:
  - Earlier `page_builds` snapshots: `farmer_name` and `gi_authorised_user_no` are set to null on the
    farmer's own lots. Lots are matched by lot code, not by name as in the runbook SQL, so a namesake keeps
    theirs. An empty `lots` array no longer turns the snapshot into NULL.
  - Every open consent gets `revoked_at` (the only column the trigger allows). The page then falls back to
    "Farmer N".
  - B14 helper `_end_farmer_access` removes the farmer membership. If the user has no other membership, it
    also revokes the devices. B23's `revoke_device` is not used because it commits and audits per device.
  - If the account has **no other membership**: its `otp_challenges` and `notifications` rows are deleted,
    and the `users` row gets `phone = erased:<id>`, `name = Erased farmer`, `name_local`/`pin_hash` NULL and
    `suspended`. An account that is also an officer, or a farmer of another FPO, is kept, because it is not
    this FPO's to erase (FR24). D-065 records this, and TODO asks the Architect-Gate to rule on it.
  - `farmers`: `name = Erased <code>`, `name_local`/`photo_key`/`gi_authorised_user_no` NULL, `suspended`.
    **`address` keeps village/block/taluk/district/state and loses only `pin`.** The runbook SQL sets it to
    NULL, but then the rebuilt page fails its `place` check (`public_record_invalid`) and the old page,
    which shows the name, stays online. The first test run caught this. The runbook now gives the SQL
    fallback the same rule.
  - `plots.land_record_ref` NULL; `plot_revisions.snapshot - 'land_record_ref'`; `id_documents` rows deleted.
  - Each published batch with the farmer's lots gets a queued `page_builds` row with `trigger = 'erase'`.
    These are the same steps as publishing `rebuild`, which is not exported (D-004). After the commit, the
    router enqueues them with `lots_batches.service.enqueue_page_build`, the existing build task.
  - S3: every object version and delete marker under `id-docs/<fpo_id>/<farmer_id>/` is deleted. This runs
    last, before the commit. A database error deletes nothing. An S3 error (or a partial refusal, which
    raises `RuntimeError`) commits nothing, and the call can be repeated.
  - Audit row `farmer.erase`: `{reason, page_builds_scrubbed, consents_revoked, membership_removed,
    devices_revoked, user_erased, otp_challenges_deleted, notifications_deleted, plots_scrubbed,
    plot_revisions_scrubbed, id_documents_deleted, page_rebuilds, id_doc_objects_deleted}`.
- **D-065**: every write uses Core `update()`/`delete()`. ORM attribute changes would make the flush
  listener copy `[old, new]` name, phone and address into the append-only `audit_log`. The test checks that
  no new audit row holds the phone, name, survey number, GI number or PIN code.
- The route never writes `events`, `event_versions`, existing `audit_log` rows, or any `consent_records`
  column other than `revoked_at`. The test compares these tables row for row.

## 3. OTP purge

- There was no periodic mechanism. `agritrace/worker/__init__.py` now has `app.conf.beat_schedule` with
  `registry.purge_otp_challenges` daily at 02:30 UTC. The name constant is `PURGE_OTP_CHALLENGES` in the
  worker, because `core/task_names.py` is not in the declared paths.
- `registry/tasks.py` runs `service.purge_otp_challenges`. It deletes rows whose `expires_at` is older than
  `OTP_RETENTION_DAYS` (new setting, default 30, `ge=1`, `description=`, also in `.env.example`).

  outside B24's paths, so this is a TODO follow-up.
