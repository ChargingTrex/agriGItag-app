## What was done

- **`StandardsProfileRules`** (`modules/quality/schemas.py`) validates the §4 JSON with `extra="forbid"`.
  Every field has a description. It covers `schema_version` (literal 1), `standard{name, schedule, edition,
  clause_ref}`, `grades`, `fail_grade`, `parameters[]` (all §4 keys, plus an optional `exception_flags`
  for coffee), `lab_certified_requires`, `lot_gates`, `trail_rules[]`, `yield` (Python attribute
  `yield_`), and `public_note`.
  Cross-checks:
  - grades are unique and do not include `fail_grade`;
  - parameter codes are unique;
  - the keys of `limits`, `max_grade_for_source` and `declare_for_grades` are all in `grades`;
  - `grading_stage` is one of `capture_stages`;
  - a `load_from_standard` parameter has `limits: null`;
  - gates and trail rules name parameters that exist;
  - `min ≤ max`, and `hold_margin ≥ warn_margin`.

  Limits are exact `Decimal` in Python and are serialised as JSON numbers, so the Dart side reads
  numbers, not strings.
- **`grade_engine.py`** is pure: it imports only Pydantic, core enums and the rules model. It provides:
  - `compute(rules, readings, exception_flags=())` → `GradeResult`. It follows §4 steps 1–6. Grading
    parameters with `limits: null` are reported as `profile_incomplete`. Label and contract parameters are
    reported as `not_graded`.
  - `rank`, `declared_vs_computed`, `check_plausibility` (unknown parameter, unit, range, source) and
    `check_trail` (`non_increasing` + tolerance, `overridable`).
  - `lot_gate` and `yield_outcome` (pass ≤ 20 % over the ceiling, warn ≤ 30 %, hold above that).

  `DECISION D-015` and `DECISION D-006` markers, with ADV and COMPROMISE, are in the module header.
- **`tests/fixtures/grade_cases.json`** has 51 table-driven cases in the sections compute, declared,
  plausibility, trail, yield and lot_gate. They are written so M03 can run them verbatim. Chilli cases
  point to the real profile file. Turmeric (moisture + curcuminoid min, lead chromate pending), saffron
  (lowest category across crocin, picrocrocin and safranal, with placeholder thresholds and edition
  `LOAD_FROM_STANDARD`) and coffee (8–12.5 %, the `monsooned` flag gives a warning, not a fail) are inline
  fixtures. They prove the one engine handles four crops with no crop-specific code.
- **`profiles/dry_chilli_agmark_v1.json`** is copied verbatim from §4.
- **`profiles/loader.py`**: `load_profile(session, crop_id, name="dry_chilli_agmark_v1")` is what B12's
  seed calls. It is idempotent. It upserts the profile (keyed by crop and standard name) and publishes
  version 1 with `allow_incomplete`. Because grading parameters are still pending, it stamps
  `public_note: "Graded on moisture only — full schedule pending"`.
- **Service and router.** These 10 routes are under `/v1`, tag `quality`, and each has a summary,
  description and documented error responses:
  - `GET /standards-profiles`
  - `GET /standards-profiles/{id}/versions/{n}`
  - `POST /standards-profiles/{id}/versions`: super-admin only, checked through `users.is_super_admin`.
    Publishing needs `allow_incomplete` while any parameter is `load_from_standard`. The previous
    published version is retired through the ORM, so the change is audited.
  - `GET` and `POST /instruments`: scoped to the caller's FPO.
  - `POST /quality-readings`:
    - `client_id` is the primary key. A resend returns the stored row with 200. Another owner's id gives
      409 `client_id_conflict`.
    - Checks run in this order: plausibility (422), then calibration (judged on the measuring day; no due
      date counts as expired), then the trail rule. A trail rule with a `reason_code` is accepted, and
      after the commit `rules.check_lot` is sent by name with kwargs
      `{lot_id, batch_id, reading_id, hint: "moisture_trail_override"}`.
    - Stores `calibration_due_on_at_time` and `profile_version_id`.
  - `GET /lots/{id}/readings` and `GET /batches/{id}/readings`: cursor pages.
  - `POST /batches/{id}/grading`: the declared grade is checked first; then inline readings are
    recorded, then the engine runs and a `grade_computations` row is stored with status `ok`,
    `incomplete` or `declared_above_computed`.
  - `GET /batches/{id}/grade`.

  Batch trail checks compare against intake readings of the component lots through `batch_shares`.
  Lots and batches are only read; B05 never writes them.
- **`service.__all__`**: `create_reading` accepts the API model or the raw sync `data` dict, for B06.

## Decisions made inside the WP (documented in code, no new ADR)

- A grade missing from a parameter's `limits` cannot be reached through that parameter. A range of `{}`
  means unconstrained. This choice never over-grades.
- Trail baseline: the highest value at the latest earlier stage that has readings. With several component
  lots this is the most lenient value, so a genuine mix never fails.
- Calibration is judged on the date of `measured_at`, not the sync date. An instrument with no due date
  counts as expired.
- `lot_gate`: a profile without that gate passes. `lot_gate_passes` with no published profile or an
  unknown lot returns False.
- An exception flag such as `monsooned` stops that parameter from limiting the grade, and the result
  carries a warning.
- `create_reading` commits per reading, as sync push does. Inline grading readings are therefore stored
  even if a later one fails; a retry is idempotent.
