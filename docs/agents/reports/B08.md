## What was done

- **Service** (`service.py`, `__all__ = ["resolve_from_sync", "run_gate_checks"]`):
  - `store_flags` upserts by `dedupe_key = rule_code:subject_id:sha256(discriminator)[:12]`. A re-check
    refreshes an active flag; it never adds a second one. A concurrent insert is caught by a savepoint.
    Active flags in the run's scope that are no longer raised are closed as `fixed` / `rule_passed`.
    Resolved flags are never reopened. Everything goes through the ORM, so `audit_log` rows are written.
  - Assignee: hold → `fpo_admin`, warn/info → `field_officer`.
  - `_sync_lot_hold`: an active hold on a lot sets `gi_eligible=false` and
    `gi_hold_reason="flags: <codes>"`. When the last hold is cleared, only a reason with that prefix is
    removed.
  - `check_event` runs the event rules and then the rules of the event's lot or batch. An undone event
    closes its own flags. `check_plot` runs the plot rules. `check_lot` runs the lot and/or batch rules.
  - `run_gate_checks(session, lot_id|batch_id)` runs synchronously for B09. It flushes without committing
    and returns the active flags on the lot(s), the batch, their plot, events and readings.
- **Tasks** (`tasks.py`): `rules.check_event(event_id, version_id, photo_id, hints)`, `rules.check_plot(plot_id)`
  and `rules.check_lot(lot_id, batch_id, reading_id, hint)` all go through `worker.run_db_task`. The kwargs
  are exactly what the existing enqueuers send (events push and verify_photo, registry, quality).
  `DECISION D-009` is marked there.
- **API** (`router.py`, `schemas.py`):
  - `GET /v1/flags` filters by `fpo_id` (super-admin only for another FPO), `assignee`, `status` and
    `severity`, with a keyset cursor.
  - `GET /v1/flags/{id}`.
  - `POST /v1/flags/{id}/resolve` takes `{resolution: looks_fine|fixed|escalated, reason_code, note}` and
    sets status cleared, fixed or escalated. `escalated` reassigns the flag to `fpo_admin`. Errors:
    - 422 `reason_required` when there is no reason;
    - 403 `resolution_forbidden` when an officer resolves a hold or an escalated flag;
    - 409 `flag_not_open` when the flag is already resolved;
    - 403 `forbidden` when the role is neither field_officer nor fpo_admin.
- **Sync push `flag_resolution`:** the handler in `events/service.py` calls
  `rules_flags_service.resolve_from_sync`. The result is `accepted`, or `duplicate` for a resend of the
  same resolution, with the flag id as `server_id`. The unused `NotImplementedPilotError` import was
  removed. The push descriptions in `events/sync_router.py` and `events/schemas.py` (`SyncEntry.data`)
  were updated.
- **Errors** appended to `core/errors.py`: `flag_not_open` (409) and `resolution_forbidden` (403).
  `reason_required` is reused.
- **Shared fixture** `tests/fixtures/rule_cases.json`: 5 event_order cases, 9 practice_tags cases and 7

## Risks

- `batch_quantity_unattributed` (5 % between the batch's packed/graded/received kg and the share total) is
  my reading of PRD §12.2. Real grading loss over 5 % will warn. It is not a hold, so it does not block
  publish unless B09 decides it should.
- `quantity_mismatch` treats a shortfall after packing (packed 272.6 → used 20) as a mismatch, which is how
  the seed expects ×3. A farmer who sells part of a lot will see a warn.
- Auto-close (`rule_passed`) changes status without a human. The audit log records it as a system action.
