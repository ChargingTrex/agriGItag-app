## What dominated
I profiled one `check_event` on a lot of 1,500 live events (cProfile, testcontainers PostGIS 16). The lot rules took about 80 % of the time:

1. **`event_order.run` was O(events²).** For every event, `order_gaps` filtered all events of the lot by date and then scanned them again for each earlier step. At 1,500 events that was 4,500 `order_gaps` calls and about 1/3 of the total time (257 ms of 813 ms over 3 profiled runs). It is pure Python, so under worker concurrency it costs CPU directly.
2. **`_lot_context` loaded full ORM `Event` rows plus each version's payload JSON** (1,500 entity loads + 1,500 JSON decodes, about 1/4 of the time). It only needed the type, the date, the input id and two kg sums.
3. The SQL was not the problem. `EXPLAIN ANALYZE` on the real queries gives 1.6 ms for the lot join and 1.6 ms for the aggregate. `events.lot_id` has an index, the join goes through the `event_versions` pk, and `event_versions (event_id, version_no)` is already unique. No index gap was found, so there is no migration 0005.

## What changed
- `rules/event_order.py` `run`: passes `order_gaps` only the earliest event of each type. A step is done by date D exactly when its earliest event is on or before D, so the answer is the same, and the cost drops to O(events × types). `order_gaps` and the shared Dart/Python fixture contract are unchanged.
- `service.py` `_lot_context`: selects `(Event.id, event_type, occurred_on, payload->>'input_id')` as plain rows. Harvest and packing kilograms come from a single SQL aggregate, `sum((payload->'quantity'->>'value')::numeric) FILTER (event_type = … AND unit = 'kg')`. `_kg` is now that column expression, and the kg-only `shortcut:` is kept. Behaviour is the same as before: NULL when no kg quantity exists, falling back to `lots.harvested_kg`/`packed_kg`, and dead events (undone/superseded) are excluded.
- Unchanged: all rules, flag codes, `store_flags` dedupe/reopen/auto-close, the hold sync, the lock order (event → batch → lots by id, `FOR NO KEY UPDATE`) and the task contracts.
- **Add-on (audit wave-7 #3):** `rules.check_event`, `check_plot` and `check_lot` now use `autoretry_for=(DBAPIError,)`, `max_retries=3`, `retry_backoff=True`, `retry_jitter=True` (`tasks.py` `RETRY`; `acks_late` is unchanged). `DBAPIError` covers `OperationalError`, deadlock 40P01, serialization 40001 and a dropped connection. Retrying is safe:
  - a failed run rolls back as a whole, and the retry is a full re-run;
  - `store_flags` upserts by `dedupe_key`, and a concurrent insert of the same key is caught in a savepoint;
  - a flag a reviewer closed reopens only if it was `rule_passed` or the severity got worse, which is the same as any re-check.

  I corrected the B19 report sentence "Rules tasks never retry" and ticked TODO §8 (finding 3).

## Timings (`apps/api/tests/integration/bench_check_event.py`)
Run it with: `uv run pytest tests/integration/bench_check_event.py -q -s -p no:cacheprovider`. The script seeds 1,500 events with one version each and a GPS fix: about 1,400 problem events with a QA-sized payload, 29 harvests, 60 input applications and the crop track. Each figure is the median of 15 runs after 1 warm-up. Every run uses a fresh session, and the checked event is a problem event in the middle of the lot. The host was noisy (load average 6–9 from other stacks), so each row lists every separate run. CPU is the Python process only (Python + driver), and that is what saturates the Celery worker.

| Path (1,500 events) | Before (pre-B22) wall median per run | After wall median per run | Before CPU | After CPU |
|---|---|---|---|---|
| `check_event` (whole task body) | 507, 203, 169, 525, 163 ms | 129, 105, 70, 68 ms | 319, 142 ms | 61, 47, 44 ms |
| `check_lot` (gate / full-lot path) | 322, 484, 189, 354, 153 ms | 113, 66, 142, 59 ms | 262, 135 ms | 44, 83, 40 ms |
| `_lot_context` + `LOT_RULES` | 249, 187, 241, 142, 136 ms | 59, 30, 42, 29 ms | 128, 128 ms | 18, 25, 17 ms |

**Result:** one `check_event` at 1,500 events now takes **68–129 ms** (median of medians about 88 ms), down from 163–525 ms. The target was under 300 ms, so it is met. Per-check CPU fell about 3×, and lot-rule CPU about 6×. The ~3 s per check on the shared stack was this CPU cost multiplied by 12 concurrent worker processes and Postgres sharing the same vCPUs. The live BM-07 rerun with a seeded backlog is not done: it is optional, and the shared stack is reserved for gate evidence. The verifier owns that rerun.

## Risks
- `ix_flags_subject` is `(subject_type, subject_id)`, but the stale-flag and `_active` queries filter on `subject_id` alone. That is fine at today's 151 flags, but once the flags table grows to tens of thousands of rows, check whether an index on `subject_id` is needed (B22 did not add one, because no EXPLAIN showed a gap at this size).
- A payload whose `quantity.value` is not numeric now fails the task inside SQL (a `DataError` cast error) instead of in Python. The outcome is the same: the task fails, and now it is retried 3 times first. The sync push already validates payloads.
