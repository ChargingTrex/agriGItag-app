## What was done

1. **D-030, batch reconciliation split.** `quantity_reconciliation._batch` now raises two warns:
   `batch_quantity_unattributed` (received kg exists and the shares are missing or Σ `kg_contributed` is more
   than 5 % off received kg) and `grading_loss_high` (output = packed, else graded, more than
   `grading_loss_warn_pct` below received kg or more than 5 % above it; details carry received/output kg,
   `loss_pct`, `limit_pct` and `unit`). If received kg is missing, nothing is raised. `CODES` lists both, so
   `rules.codes(BATCH_RULES)` closes old flags `rule_passed`. `BatchContext` gains `received_kg` and
   `grading_loss_warn_pct`. `batch_kg` is kept and now means the output (packed, else graded). `_check_batch` reads
   the limit from `fieldconfig.features_for(registry_service.fpo_code(...))`. `Features.grading_loss_warn_pct`
   (0–100) and `features.yaml: grading_loss_warn_pct: 15` were added with a reader comment. The `shortcut:` comment
   was replaced by a `DECISION D-030` block. `rule_cases.json` is unchanged: batch rules do not run on the phone,
   so M03's schema is untouched.
2. **D-031, offline farmers.** `FarmerIn.client_id: UUID | None` (with `description=`). `create_farmer` checks it
   first. If the id belongs to the same FPO, it returns the stored farmer (no phone check, no second user or
   membership). If it belongs to another FPO, it raises `client_id_conflict`. Otherwise the id becomes
   `farmers.id`. `client_id` is excluded from `validate_payload` because `fields/farmer.yaml` is `extra: forbid`.
   `POST /v1/farmers` answers **201 both times**, documented in the field description and conventions; the router
   is not in the declared paths. `registry.service.create_farmer_from_sync` is the twin of
   `create_plot_from_sync`: it allows field officers and FPO admins only (others get `forbidden`), validates, and
   returns `(out, created)`. The push kind `farmer` (`_push_farmer`) commits per entry. `push` clears the assist
   context for this kind (caller and audit), so neither `X-Assist-Session` nor `assist_session_id` applies.
3. **D-032, per-entry assist.** The push kind `assist_session` goes through
   `identity.service.start_assist_from_sync`. This is a new dict-accepting entry in `__all__` that checks the
   field officer role, validates `AssistStartIn` and calls the unchanged `start_assist`. `SyncEntry.assist_session_id`
   is new (with `description=`). For each entry, `push` resolves the caller via the new
   `core.auth.assist_session_farmer`, which ignores `ended_at`; `_assist_farmer` and the header path are unchanged.
   The resolved caller is used for that entry only, and the audit context is restamped (actor, device and request
   id are kept) and then restored. An unknown session or another officer's session rejects that entry with
   `assist_session_invalid`, and the next entry still runs. `create_plot` refuses with `forbidden` when the plot's
   `farmer_id` differs from the caller's `on_behalf_of_farmer_id`. Consent (`_check_writer`) and events
   (`_check_subject`) already did this. The `DECISION D-032` comment is in `push` and in `assist_session_farmer`.
4. No migration (`alembic heads` = `0003_masters`), no new error code, no new library. OpenAPI and error-codes.md
   were regenerated. Updated: `docs/api/conventions.md` (Sync), the sync router description, CHANGELOG, and TODO.
