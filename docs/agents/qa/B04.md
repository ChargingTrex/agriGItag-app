## Observation (P3, not filed): unacked tasks wait about an hour after a hard worker stop

D-009 says a task message is acknowledged only after the task finishes, and that a worker crash or a deploy restart "loses no photo check, rule run or SMS". This held on the stack. My first two live tasks were handed to the old worker at 16:13:09.7Z, and that worker was then stopped by the stack recreate. Both messages stayed in Valkey's `unacked` hash ([04](B04/logs/04-unacked-after-worker-recreate.log)). The new worker re-ran them at **17:13:53Z, 3643 s later**, and wrote the expected `sent` and `failed` rows ([05](B04/logs/05-redelivery-after-visibility-timeout.log)). So nothing was lost, but a task stranded this way waits about an hour, because the repo sets no `broker_transport_options.visibility_timeout` and kombu's Redis default of 3600 s applies.

For an OTP SMS this means the code arrives about an hour after a sign-in attempt, long after it expires. D-009's COMPROMISE line names the duplicate-send risk but not this delay. I am not filing it as a P2: no acceptance line fails, no data is lost, and a warm shutdown should re-queue at once (I did not test that). It is a note for the D-009 owner, either to set a shorter `visibility_timeout` (longer than the slowest task) or to add the delay to D-009's COMPROMISE line.

Reproduction (what I saw, not yet repeated on purpose): with the stack up, enqueue `notifications.send` ([live_send.py](B04/logs/live_send.py)) and recreate the worker within a second or two (`docker compose up -d --force-recreate worker`). Then `valkey-cli HLEN unacked` stays at 2, and the rows appear about 3600 s later.
