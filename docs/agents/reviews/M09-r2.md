## Checks the coordinator asked for

**1. Does the crossing test reject walks that end at the start point?** No, not wrongly. I traced each case
against the server's `shapely.is_valid` (`registry/geo.py:_checked`):
- **The last fix equals the first.** Repeated points are removed and the closing duplicate is dropped. Simple. OK.
- **The last fix stops just short of the start, or off to the side.** The closing edge Z→A only meets edge
  A→B at A, and that pair is skipped as neighbours (`i == 0 && j == n-1`). Simple. OK.
- **The last fix overshoots past the start along the first edge** (Z on or across A→B). D→Z crosses or touches
  A→B, so the shape is rejected. The server's `is_valid` rejects that shape too (Self-intersection / Ring
  Self-intersection), so the phone matches the server and drops nothing the server would accept.
- **A spike at the closing corner** (i = n-1 and i = n-2 wrap around) is covered. A walk where every point lies on
  one line fails the spike check. Touching needs exact collinearity (`== 0`), as shapely does, so there are no
  false positives from rounding.

Overshooting is common in the field. Those walks are dropped and the officer is asked to walk again (P3-R2-2).

**2. Location-off path.** `GpsFix.fixes()` yields an empty, completed stream on refusal or location off.
`_ended` resets `_sub`, sets `_off`, and the button returns with a sentence and a clip. A stream that ends
*after* a fix keeps the ring and "Save anyway" (`_best != null`), which is right. Tested.

**3. Entry order and payload keys vs ruling §4 "What M09 round 2 does now".**
- (1) F and S are minted when the wizard opens. ✔ F is **not** sent as `client_id` on the online POST: the
  generated `FarmerIn` has no such field until B15. This is marked `TODO(B15)` and asserted in the online test.
  Acceptable. The r2 acceptance line does not require it.

- Online, F is replaced by the server id *before* the transaction, so the session, consent and plot all name the

**4. Voice-player change: callers and waiting screens.**
- I grepped every `play(` and `ClipPlayer` use. `VoicePlayer.play` gained an optional named `onEnd`. Its only other
  caller is `playPrompt` (M05/M06 kit, all farmer screens), which passes none. The no-op default applies, so there
  is no behaviour change.
- The `ClipPlayer` typedef change breaks implementers, but only three exist: the provider, `test/auth/harness.dart`
  and `test/widget/kit_harness.dart`. All three are updated. Main and M02 (f039ae4) have no other implementers. M07
  is not on main. Other worktrees carry only the same two fakes, so a parallel WP that adds a new fake will fail to
  compile and must add `onEnd` (P3-R2-3).
- Only the consent step waits on `onEnd`. A missing or failing clip calls `onEnd` at once (`voice_player.dart:58`),
  and so does an interrupted load (`:79`). No screen can hang.

**5. Is the shared-code edit justified?** Yes, in principle. `clipLocale` and `onEnd` are the smallest seam for

production half does not do what it says: see P2-R2-1.

## Findings

### P2

**P2-R2-1. `onEnd` fires at once for every clip after the first, so "I agree" does not wait on a device.**
`apps/mobile/lib/core/voice/voice_player.dart:74-84`.
- just_audio 0.10.6 `play()` starts with `if (playing) return;`. Its doc says `playing` "will remain true until
  pause or stop is called", even after the clip completes. The provider never pauses or stops.
- So once any clip has played (step 1's `onboardPhonePrompt` autoplays just before consent), every later
  `audio.play()` returns at once. `.whenComplete(onEnd)` then fires immediately and `_heard` becomes true as the
  consent clip starts.
- It fails open (the r1 behaviour), so no one is stuck. But the report, the consent header and the shared seam's
  doc ("called once the clip stops") claim something the device will not do. No test can catch it: both fakes call
  `onEnd` at once, and no test checks that "I agree" is disabled before the end.
- **Fix:** in `playClip`, add `if (audio.playing) await audio.pause();` before `setAsset`. `play()` then waits for
  the real end, and the replaced clip's pending `play()` completes, which fires its `onEnd` (that is the
  documented "replaced"). Add one widget test with a fake `ClipPlayer` that keeps `onEnd`: "I agree" is disabled,
  then enabled after `onEnd()`. The other option is to withdraw the claim and go back to r1 (P3-4 was optional).

### P3

- **P3-R2-1.** Tapping any other speaker while the consent clip plays (for example the "I agree" speaker) replaces
  the clip. `onEnd` fires and enables "I agree" before the message ends. That fits the documented "replaced"
  meaning. If it matters, ignore `onEnd` from replacements on the consent step.
- **P3-R2-2.** A walk that ends just past the start point is dropped as crossing, as the server requires, and that
  will be common. Trimming the tail after the point closest to the start (before `ringIsSimple`) would save most of
  these walks. Leave it to Q01 with real walks; the shortcut comment at `boundary_step.dart:48` already sends
  tuning there.
- **P3-R2-3.** The `ClipPlayer` signature change will break any in-flight WP that adds its own fake (`(path) async`
  → `(path, onEnd) async`). The Orchestrator should mention it in the merge note.
