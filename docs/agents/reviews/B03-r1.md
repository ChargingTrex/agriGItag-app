### P2 (fix in round 2 / at merge)

- **P2-1: the boundary output does not carry the ODbL attribution or share-alike notice that D-019
  (amended) requires.**
  - D-019 says: "the derived `gi_region_v*.geojson` files are published under ODbL with attribution in the
    file properties".
  - `build_virudhunagar.py` writes `licence` (whatever `--licence` says) and `source_ref`. The attribution
    line ("Boundaries © geoBoundaries / Pathways Data, ODbL") appears only in the README.
  - Fix: add to `common` in `build()`:
    - `attribution` (default the geoBoundaries line; override with `--attribution` for a census-style source)
    - `licence_terms` / `share_alike`: "derived database offered under ODbL-1.0"
  - Assert both in `test_builds_v0_district_and_v1_taluk_union_with_provenance`.
  - The API side (attribution on the public map) is already a main TODO for W03/B10.
- **P2-2: the plot review outcome is free text, so the status logic treats any review as an
  acceptance.**
  - `PlotCorrection.review_outcome: str | None`. In `correct_plot`, `reviewed = plot.reviewed_at is not None`.
  - A map pin reviewed with a negative outcome ("farmer not on this land") becomes `confirmed` when the pin
    lies inside the region.
  - A near_edge or outside plot can record a positive review, but nothing machine-readable says so for
    B08/B09 (FR70: "records the outcome").
  - `reviewed_at` also stays set when a later correction moves the pin or switches it to `map_pin`
    without a new review.
  - Fix (schema only, no migration):
    - `review_outcome: Literal["accepted", "rejected"]`, required when `review_method` is sent, plus a
      `review_note`
    - `rejected` keeps `needs_review`
    - clear `reviewed_at`/`review_*` when `pin`/`pin_method` changes without a review in the same request
  - Add a unit case to `test_location_status_mapping`.
- **P2-3: two region provenance fields are not required.** `GiRegionVersionIn.taluks` is optional and
  `confidence` defaults to `district_derived` as free text.
  - D-019: "Every version stores `source_ref`, `licence`, `confidence`, `taluks[]`."
  - The model column is nullable (B01), but the API can still require it.
  - Fix:
    - `taluks: list[str] = Field(min_length=1, …)`
    - `confidence: Literal["district_derived", "taluk_derived", "official", "surveyed", "test_fixture"]`
      with no default
    - update `_region()` in the integration test to send them
- **P2-4 (Orchestrator, merge integration; not the worker's fault):**
  1. `git merge-tree main wp/B03` gives **CONFLICT in CHANGELOG.md and TODO.md**. Main already folded B03's
     TODO rows (commit `8ec48ac`), so take main's TODO and re-add the B03 CHANGELOG line.
  2. B03 changes `packages/openapi/openapi.json`, so after the merge CI's portal `npm run gen:check` and
     mobile `tool/gen_api.sh && git diff --exit-code` will fail. Regenerate both clients and
     `apps/portal/src/api/generated/error-messages.ts` in the merge commit; those paths are outside B03's
     declared paths.
  3. B03 registers `client_id_conflict`. If B05 or B06 also register it, `AppError` registration raises at
     import, so the second package to merge must reuse B03's class (already a main TODO).

### P3 (follow-ups; may land in round 2 or TODO)

- **P3-1:** a crafted cursor with a non-UUID id causes an unhandled `ValueError`, which returns 500
  instead of 422 (`list_villages`, `list_farmers`). Parse the UUID inside `decode_cursor` (or catch
  `ValueError` there).
- **P3-2:** `to_acres` checks `value > 0` *before* quantizing. A size of 0.04 cent (or 0.0004 acre)
  is stored as 0.000.
  - `area_gap` then divides by zero, so create-with-walked-boundary returns 500, and so does every later
    read of that plot.
  - Fix: check after quantizing.
- **P3-3:** an idempotent resend compares only pin and declared size. Changed `pin_method`, walked
  boundary or times give 200 with the stored plot. This errs on the safe side, but say so in the
  `PlotIn.client_id` description.
  - D-005 names `ON CONFLICT DO NOTHING` + re-read, whereas this code uses get-then-insert. A concurrent
    first insert gives 500 (in TODO).
- **P3-4:** FR67 says "the pin (or walked boundary)", but only the pin is checked against the region.
  A walked boundary that crosses the edge goes unchecked. Note it for B08.
- **P3-5:** OpenAPI operation descriptions contain the whole Google-style docstring, including
  `Args: session: database session …` and Python exception names. That text leaks into the generated
  Dart/TS docs. Put `\f` before `Args:` in the router docstrings (FastAPI cuts there).
- **P3-6:** `simplify_region` docstring: at 9° N a degree tolerance is slightly *finer* east-west
  (≈ 49.4 m), not coarser.
- **P3-7:** the D-019 DECISION comment in `geo.py` says "2011-era admin boundaries". After the
  amendment the source is LGD-derived geoBoundaries, so update the COMPROMISE line.
- **P3-8:** integration test gaps:
  - no `client_id_conflict` case (other FPO, other farmer)
  - no cross-FPO `GET /v1/plots/{id}` → 404
  - the ≤ 50 KB check runs on the 1 KB fixture, so it does not exercise the bound
- **P3-9:** `POST /v1/inputs` requires `FPO_ADMIN` before the super-admin check, so a super-admin
  acting under another role cannot add a global entry. Fold this into the B02/B03 super-admin
  reconciliation.
- **P3-10:** two `create_farmer` edge cases:
  - A phone whose user already has a non-farmer membership in this FPO gets a farmer row linked to that
    user but no farmer membership (UNIQUE(user_id, fpo_id)).
  - Two concurrent creates with the same new phone give 500.
- **P3-11:** `gi_region_versions` is not `Audited` (B01 model), so a super-admin upload leaves only
  `created_by`. FR31 treats the region as a legal fact, so consider the mixin. Also, the `max + 1`
  version race gives 500 (super-admin only; rare).
- **P3-12:** cosmetic:
  - the report says "19 operations on 13 paths"; the registry has 18 operations on 13 paths, and the
    19th is `/v1/healthz`
  - v0's `taluks_confirmed: true` reads as if the GI list were confirmed; it is only the district's
    sub-district list
  - a geometry with the wrong `type` gets `validation_error` rather than `invalid_geometry` (both 422)
