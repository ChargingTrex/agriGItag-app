## What this change does

The phone's outbox (its queue of entries waiting for the server) is now strict first in, first out per user. A row in
backoff (waiting before its retry) holds back every later row, and a failed push gives the whole batch one backoff.
So a consent, assisted entry or undo can no longer go ahead of its farmer, assist session or version 1 after a failed
push. The rejection codes `not_found` and `assist_session_invalid` now get one retry, like `stale_version`. Token
refresh now reads the keystore (the phone's secure token store) first, and uses the background isolate's newer tokens
instead of sending the old refresh token, which made the server sign the phone out.

Both audit P1 cases are fixed and tested. The 4 new tests fail on the old code (checked by reading: old per-row jitter
plus the `nextAttemptAt <= now` filter sends the forced-due consent alone; old `_doRefresh` posts r1 without reading
the keystore).

Run here: `flutter analyze --fatal-infos`: no issues. `flutter test test/sync test/auth -j 1`: 70 passed.

## Should fix (P2, exact fixes for an Orchestrator micro-patch)

1. **A row still `sending` does not hold the queue, so the retry-once can expire before its dependency is answered**
   (`apps/mobile/lib/core/db/daos/outbox_dao.dart:46-57`; claim in `docs/adr/D-054.md` "Advantages" bullet 2 and
   the D-054 comment at `outbox_processor.dart:235-236`)
   - **What this is:** `nextBatch` reads only `waiting` rows. A row is `sending` while its push is in flight in the
     other isolate. It also stays `sending` after the app was killed mid-push, until `resetStaleSending` finds it
     older than 5 min.
   - **Problem:** A newer row is still sent ahead of an older `sending` row. Concrete case: a Go phone saves harvest
     v1, the push is in flight, and Android kills the app. The farmer reopens within 5 min and taps Undo (the server
     allows undo for 24 h). v1 is still `sending`, so the undo goes alone and gets `not_found`. Its single retry comes
     2 s later (`backoff(1)`), v1 is still `sending`, and the second `not_found` parks the undo as `needs_attention`.
     The server keeps the event live while the phone shows it undone: the audit's M07/M08 case, by another route. The
     same happens when the WorkManager run is pushing v1 on 2G (a 256 KB batch takes over 10 s) while the foreground
     sends the undo. The ADR says "by the retry every older row has been answered". That is not true for these rows.
   - **Fix:** Let an older `sending` entry row block, like a row in backoff. Two lines in `nextBatch`:
     ```dart
                 outbox.status.isInValues([OutboxStatus.waiting, OutboxStatus.sending]),
     ...
           if (item.row.status != OutboxStatus.waiting || item.row.nextAttemptAt.isAfter(now)) break;
     ```
     Change the doc line "`needs_attention` rows are not `waiting`, so they never block" to also say that a `sending`
     row (in flight in another isolate, or left by a kill until `resetStaleSending`) blocks. Add one DAO test: two
     rows, `markSending` on the first, `nextBatch` is empty. That also gives the "DAO test" the ticked TODO §6 line
     promises. In the ADR, replace Advantages bullet 2 with: "an older row still `sending` (other isolate, killed app)
     also holds the queue; the retry-once covers a dependency the server answered late". The cost: after a kill,
     later rows wait until the next run after the 5 min reset (save, resume, network change or the 15 min job).
     Within one run nothing changes, because `_pushBatch` settles every row it marked `sending`. A side benefit: the
     two isolates stop pushing the same rows in parallel.
   - **If we skip it:** After a kill or an overlapping background run, undos, consents and assisted entries can still
     be lost on the server, and the officer cannot repair them.

2. **After a user switch on a shared phone, the background isolate takes the new user's tokens and pushes the old
   user's entries with them** (`apps/mobile/lib/core/router/session.dart:287-300` `_adoptStored`)
   - **What this is:** `_adoptStored` takes the keystore tokens whenever the stored refresh token differs from the one
     in memory. Its guard (`_refresh == null`) only covers "this isolate signed out".
   - **Problem:** A WorkManager run for user A is pushing on 2G (with photos it can take minutes). In the foreground, A
     signs out and B signs in with an OTP. The server revokes A's tokens on logout, so the background run's next
     request gets a 401. The interceptor calls `refreshAccessToken`, `_adoptStored` sees B's refresh token, takes
     B's tokens and returns B's valid access token. The interceptor then re-sends A's push (`c.userId` is still A)
     with B's token. The server books A's farm events as entered by B, or rejects them as `forbidden`, which parks A's
     rows as `needs_attention`. That breaks D-029 ("never sends them under another user's session"). The old code
     failed differently in this window (its `_endLocally` wiped B's fresh session). The new adoption opens this path.
   - **Fix:** Adopt only tokens of the same user. If the stored session belongs to someone else, drop this isolate's
     tokens without signing out, so the run stops with 401s, A's rows keep waiting for A, and B's keystore and Session
     row are not touched:
     ```dart
         if (_refresh == null || refresh == null || refresh == _refresh) return false;
         final mine = _subOf(_access);
         if (mine != null && _subOf(stored[_kAccess]) != mine) {
           // Another user signed in on this shared phone meanwhile (D-029): forget ours, never send with theirs.
           _access = _refresh = _expiresAt = null;
           return true;
         }
     ```
     Add `/// The `sub` claim (user id) of [jwt], or null when missing or malformed. Throws nothing.` on a
     `static String? _subOf(String? jwt)` that does what `openSession` already does at line 223
     (`jsonDecode(utf8.decode(base64Url.decode(base64Url.normalize(jwt.split('.')[1]))))['sub']`), with
     `FormatException`/`TypeError`/`RangeError` mapped to null. Let `openSession` use it too, so the decode exists only
     once. With `_refresh` null, both callers in `_doRefresh` return null without a POST and without `_endLocally`.
     One test in the M14 group: `b`'s keystore gets `fakeJwt(sub: 'user-2')` and `r9`. Then `a.refreshAccessToken()`
     returns null, `foreground.to(refresh)` is empty, and `storedValues()` still holds `r9`.
   - **If we skip it:** On shared family phones a sign-out and sign-in during a background run puts one farmer's
     events under another farmer's name, or parks them where nobody can fix them from the phone.

3. **The two-isolate refresh collision is untracked, and it has a common trigger** (`TODO.md`; `session.dart:258-260`;
   `sync_service.dart:116`, `background_scheduler.dart:34`)
   - **What this is:** The worker names the residual risk "two refreshes at the very same moment". No TODO line tracks
     it. The TODO §6 line that tracked the issue is now ticked, and M02-r1 P2-6 covers the outbox, not tokens.
   - **Problem:** The two refreshes are not independent. A farmer has the app open in a no-signal field for more than
     15 min, so the access token expires and the periodic job is overdue. When signal comes back, both start at once.
     The foreground's connectivity listener runs a sync, which gets a 401 and refreshes. The overdue WorkManager job
     (constraint `NetworkType.connected`) starts too, and its `restore()` refreshes with the same r1. The second one
     to reach the server gets `refresh_reused`, and the server revokes the device (`identity/service.py` `refresh` →
     `_sign_out(device)`). The phone is signed out. This is rarer than the audit case, and signal is present for the
     OTP. So it is P2, not P1.
   - **Fix:** Add under TODO §6: `- [ ] **P2 M02/M14**: the foreground and WorkManager isolates can refresh with the
     same token at the same moment (both fire when signal returns: connectivity listener + overdue periodic job with
     NetworkType.connected); the server answers refresh_reused and revokes the device. Needs the cross-isolate lease
     M02-r1 P2-6 proposed (SyncState row taken in a transaction around refresh and push). Before the Q01 device run.`
   - **If we skip it:** The lease is never scheduled, and field phones get "You were signed out" when signal comes
     back.

## Focus questions, answered

- **Ordering vs batch rules.** Entries-before-photos holds: `nextBatch` reads entry rows only, and photos wait for the
  entry's confirmation in `MediaDao.pendingUploads`, so a photo's backoff never blocks entries. The 50-row limit and
  the 256 KB cut only drop newer rows. The D-031 rank sort followed by the `n--` trim drops rank-2 rows, never a
  farmer. A trimmed older row going next is safe, because dependencies always point to older rows. D-029: the query
  is per owner, so another user's rows neither block nor jump ahead, and are never sent. Residual hole: `sending` rows
  (finding 1).
- **"Retried once" timing.** A consent whose farmer the same isolate sends in the same or an earlier batch is
  answered in order, because the server processes entries in sequence. The retry matters only when the dependency is
  answered late, and that is finding 1. The server rolls back a rejected entry and caches nothing (`push`), so the
  retry is a real second try.
- **True 404s.** They are not retried forever. A foreign or deleted id gets `not_found` twice and is parked. The
  `lastError != code` check resets when a network failure comes in between, so such a row gets one more try per
  failed push. That is bounded and the same as D-005 today. `client_id_conflict`, `forbidden` and `validation_error`
  are not in `_retriedOnce` and stay final. No tenant-scoping error is hidden; it only waits one backoff longer.
- **"Newer" token.** The code checks for a *different* refresh token string, not a timestamp, so no clock is involved.
  The expiry is an absolute time from the same device clock, read by both isolates. A torn three-key write (new
  refresh, old expiry) only costs one extra rotation, and the next pre-read fixes it. No token is logged, and memory
  holds the same three fields as before. Skipping the POST while the stored access token is valid keeps D-024 (15 min
  access, rotating per-device refresh). Server-side nothing changes.
- **401 → re-read → sign-out.** No loop. The interceptor retries once (`_retriedKey`), and the refresh POST carries no
  bearer token, so it never re-enters the interceptor. Single-flight within an isolate is unchanged.
- **Cross-isolate collision.** It is realistic when signal comes back (finding 3). P2 with a TODO line, not blocking:
  it is rarer than the fixed case and leaves signal for the OTP.
- **Ponytail.** `_retriedOnce`, the one-wait `_failed` and the `break` are minimal. Lean: finding 4 removes about 4
  lines plus one test. Nothing else should be deleted.
