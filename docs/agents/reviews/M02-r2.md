**Is the P2-6 guard safe? Could it mark a photo confirmed that never reached the server?** No.
- `purgedAt` is written only by `MediaDao.purgeFullSize`, which throws unless `uploadStatus == done`
  (`media_dao.dart:80`).
- `done` is written only in three places:
  - `_received`, after the server answered `received` to `/sync/photos/confirm`;
  - `markUploaded`, which only tests call;
  - this guard, which itself requires `purgedAt`.
- So `purgedAt != null` means that some isolate saw the server confirm the photo. The guard only puts back the
  `done`/`confirmed` state that the foreground run's `markSending` and `uploading` had just overwritten.
- A file deleted any other way (OS, user, storage cleaner) leaves `purgedAt` null and still becomes
  `file_missing`.
- `pendingUploads` excludes purged rows. The guard can therefore only fire when a run listed the photo before
  the other isolate purged it, which is exactly the race in r1.
- `_reopenPhoto` (`photo_pending`) skips purged rows, so the two paths never disagree.

## New findings (all P3)

- **P3-a. A late duplicate confirm can blank `objectKey`** (`photo_uploader.dart:190-193`).
  - Now that `uploadUrl` is cleared on `done`, a run whose PUT finishes after the other isolate confirmed the
    photo confirms it again. `_received` then computes `key = null` and writes `objectKey: Value(null)` over the
    good key.
  - Nothing reads `objectKey` today.
  - Fix: `objectKey: key == null ? const Value.absent() : Value(key)`.
- **P3-b. A confirm that keeps failing re-uploads the photo every run** (`sync_service.dart` `_run` →
  `resetStaleSending`).
  - The per-run reset also turns media rows that are `sent` (PUT done, confirm owed) for over 5 min back to
    `waiting`.
  - While `/sync/photos/confirm` keeps failing, each run re-asks for a URL and uploads the ~300 KB again on
    mobile data. It converges once the confirm succeeds, and at start-up it behaved like this before r2 too.
  - Fix: reset only `sending` in `_run`, and keep the `sent` reset in `resetAfterKill`.
- **P3-c. `test/sync` failed twice at load average ~100** ("pull pages" and "airplane", run 1 above).
  - It did not happen again in three clean runs.
  - If the Verifier sees it, raise the per-file timeout (`@Timeout(Duration(minutes: 2))`) rather than
    change the code.
