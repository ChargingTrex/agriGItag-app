## Findings

### Should fix

1. **P2-1: the full number outlives the page by 5 minutes** (`apps/portal/src/features/members/FarmerPage.tsx:44-49`)
   - **What this is:** the revealed number is the `data` of a TanStack `useMutation`. The comment and the report
     say it is "never in the query cache" and "gone once the page is left".
   - **Problem:** TanStack keeps every mutation, with its `data`, in the client's `MutationCache` until `gcTime`
     runs out after the last observer leaves. The default is 5 minutes
     (`node_modules/@tanstack/query-core/build/modern/removable.js:35`; `Mutation.removeObserver` calls
     `scheduleGc`). Case: an admin reveals farmer A and goes to Members. For 5 minutes `+91…` still sits in
     `queryClient.getMutationCache().getAll()[n].state.data`. The same happens to A's number when the admin then
     reveals farmer B on the same mounted page. Nothing reads it today, and sign-out clears it. But the stated
     guarantee is wrong, and any future `useMutationState()` or devtools would show it.
   - **Fix:** one option on the mutation, then the comment is true:
     ```ts
     const reveal = useMutation({
       gcTime: 0, // drop the number from the mutation cache as soon as this page stops observing it
       mutationFn: () => unwrap(api.GET('/v1/farmers/{farmer_id}/phone', { params: { path: { farmer_id: farmerId } } })),
     });
     ```
     Change the comment at `:43` to say "held only in this mutation, removed from TanStack's mutation cache
     (`gcTime: 0`) once the page is left". Change the P10 report sentence the same way.
   - **If we skip it:** the number sits in tab memory for 5 minutes after every reveal, contrary to what the
     code and the report promise. A later screen that lists mutations would expose it.

### Nice to have

2. **P3-1: back to a farmer shows the number again without a new audit row**
   (`FarmerPage.tsx:73`, `:107`)
   - **What this is:** the page stays mounted when the route changes from one farmer to another, and
     `reveal.data` is never reset.
   - **Problem:** reveal A, then edit the URL to farmer B (no reveal), then press Back. A shows the full number
     at once and no request is made. Also, a 403 alert from A stays on B's page. The admin did see it once and
     that is audited, so this is minor.
   - **Fix:** reset the mutation when the farmer changes (`reset` is a stable bound method):
     ```ts
     const { reset } = reveal;
     useEffect(() => { reset(); }, [farmerId, reset]);
     ```
     The `farmer_id === f.id` check can stay as it is.
   - **If we skip it:** a rare re-show of a number the same admin already revealed, and a stale error alert.

3. **P3-2: no test for "gone when the page is left"** (`apps/portal/src/features/members/members.test.tsx:135`)
   - **What this is:** the three tests cover masked → revealed, no button for an officer, and a 403.
   - **Problem:** none fails if the number survives leaving the page, which is the privacy claim of part A.
   - **Fix:** in the first test, after the reveal, click the "Members" nav link, open the same farmer again and

     client.
   - **If we skip it:** a later refactor (for example moving the reveal into a `useQuery`) could cache the
