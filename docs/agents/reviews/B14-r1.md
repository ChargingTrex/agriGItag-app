### P2

**P2-R — A rejected farmer can still sign in and push entries (Orchestrator ruling; required in round 2).**
`reject_farmer` changes only `farmers.status`. The farmer's `memberships` row and devices stay as they
were. Concrete case: a pending farmer was created with a phone (`create_farmer` adds a `farmer`
membership) and has signed in. An admin rejects them. Their refresh token keeps working, because
`refresh` → `_account` finds the membership. Their access token keeps passing `current_user`, because it
checks the device row, not farmer status. So the sync push still accepts their entries. The worker
flagged this risk in the report.
Required change, the smallest that fits the schema:
1. `Membership` has no status or active column (`identity/models.py`, unique `(user_id, fpo_id)`).
   So **delete** the farmer's membership for that FPO in `reject_farmer` with an ORM delete:
   `user_id = farmer.user_id`, `fpo_id = farmer.fpo_id`, `role = farmer`. `Membership` is `Audited`, so the
   listener writes the `delete` row. No migration.
2. To stop pushes now rather than when the token expires (up to 15 min later): if the user has no
   membership left, set `devices.revoked_at = now()` and clear `refresh_token_hash` on that user's
   devices, as logout does. `current_user` reads the device row on every request, so the next push gets
   401 `device_revoked`.
3. Identity, the declared exception: add `AccountInactiveError` (`account_inactive`, 403, en/ta message
   key, fix line e.g. "Your FPO has not approved this account; contact the FPO office") to
   `core/errors.py`. Raise it in `verify_otp` when a `users` row exists for the phone but `_account`
   returns None (no membership, or user `suspended`).
   - **Raise it only after the code has matched.** Otherwise anyone could type a phone number and learn
     that it belongs to a rejected member. That would break D-024's rule that a wrong code and an unknown
     phone give the same answer.
   - Note: `request_otp` sends the SMS only when `_account` is not None. A rejected farmer therefore never
     gets a code, and `account_inactive` could never be reached outside `OTP_DEV_CODE`. Round 2 must send
     the code to any known `users` row (look it up by phone, not through `_account`) for the new code to
     be reachable. The alternative is to keep `otp_invalid`, which already blocks sign-in today once the
     membership is deleted. The Orchestrator's ruling asks for the dedicated code, so do the former.
   - `refresh` keeps answering 401.
4. Tests:
   - unit: reject deletes the membership and revokes devices;
   - unit: `verify_otp` gives `account_inactive` with the right code and `otp_invalid` with a wrong code,
     for a user with no membership;
   - integration: one line in `test_registry_b14.py` (rejected farmer: OTP → 403 `account_inactive`;
     push with the old token → 401).
   - Regenerate `error-codes.md` and `openapi.json`. Update the `reject_farmer` docstring's
     `Side effects:` and the D-020 DECISION text.

Accepted for the pilot (Orchestrator): suspended and rejected share one status, and the audit action
(`farmer.reject`) tells them apart.

### P3

- **P3-1 — A tenant-disabled field can still be reached through its computed sibling in `?fields=`.**
  - `farmer_fields` removes only the configured names.
  - A tenant that disables `address` can still request `?fields=address_line`, which is computed from
    `address`.
  - A tenant that disables `phone` still gets `phone_masked`.
  - Fix: also drop `address_line` when `address` is disabled, and `phone_masked` when `phone` is
    disabled. That is a two-entry map in `farmer_fields`. The data is not secret: D-017 "disabled =
    hidden" is not about privacy.
- **P3-2 — The reveal response has no `Cache-Control: no-store`.** The full number is in a GET body. Add
  `response.headers["Cache-Control"] = "no-store"` (one line, `Response` parameter) so shared office
  browsers and proxies do not keep it.
- **P3-3 — `GET /v1/fpos/{id}` is `AnyRole`, so farmers and viewers get the plot-derived `bbox`.**
  - In an FPO with 2–3 plots, the corners of the box come from other farmers' walked boundaries.
  - It is internal, not a public or partner payload (CLAUDE.md §6 is not broken).
  - Either restrict the route to `Staff`, or accept and record the choice in TODO.
- **P3-4 — Trimmed `?fields=` rows do not match the OpenAPI schema.** The generated TS client types
  them as full `FarmerOut`.
  - Accepted for the pilot: it is documented in the query description and in conventions.md.
  - P02 must type the trimmed call as `Pick<FarmerOut, …>` / `Partial`.
  - Record a TODO for a per-endpoint lean schema if more lists add `?fields=`.
- **P3-5 — The super-admin branch of `get_fpo` has no test.** Add one unit case: a super-admin reads
  another FPO and gets 200; a plain admin gets 404.
- **P3-6 — A rejection is terminal.** `approve_farmer` refuses `suspended`, so a farmer rejected by
  mistake cannot be re-admitted except by a new farmer record. A new record with the same phone hits
  `farmer_phone_taken` only if the old farmer still holds that phone. Put this in TODO for P02/B-next.
- **P3-7 — The report says the `error-codes.md` diff is "line numbers only".** It also adds two new
  reference sites (`farmer_not_pending` at service.py:1598, `not_found` at :1681). This is cosmetic; the
  check passes.
- **P3-8 — Pass-through `sqlalchemy.exc.SQLAlchemyError` is not listed under `Raises:`.** Missing on
  `_audit`, `reveal_phone`, `reject_farmer`, `list_farmer_plots` and `get_fpo`; it is listed only on
  `fpo_bbox`. Most of registry does the same, so this is not a reject. Fix it while touching these
  functions in round 2.

## ponytail-review (skill run on `git diff main...HEAD -- apps/api`, trimmed)

What this change does: adds what the portal's Members screens need from the registry: a masked phone on
every farmer, an audited admin-only "show full number" route, reject with a reason, a per-farmer plot
list, server-side village/text search with lean `?fields=` lists, and a map frame (`bbox`) on one FPO.
Assumed load: pilot, one FPO, a few thousand farmers, a handful of portal users. At that size the
unindexed `ILIKE '%q%'` and the outer join are fine.

**Must fix**

1. **A rejected farmer keeps working** (`registry/service.py` `reject_farmer`)
   - **What this is:** Reject marks the farmer `suspended`.
   - **Problem:** The sign-in membership and devices are untouched. The farmer can refresh tokens and
     push entries.
   - **Fix:** Delete the FPO membership and revoke the user's devices when no membership is left. Add
     `account_inactive` at OTP verify, after the code matches (see P2-R).
   - **If we skip it:** Rejected people keep adding farm records that look genuine.

**Should fix**

2. **The super-admin path of `get_fpo` is untested** (`service.py` `get_fpo`)
   - **What this is:** This branch decides who may read another FPO.
   - **Problem:** If it breaks, either super-admins lose the map or admins read other FPOs. No test would
     catch either.
   - **Fix:** One unit case (P3-5).
   - **If we skip it:** A silent regression in access control.

**Nice to have**

3. **`no-store` on the phone reveal** (P3-2). One header line.
4. **Disabled field reachable via its sibling in `?fields=`** (P3-1). A two-entry map.

Verdict: fix 1 first.
Lean: nothing to cut. Each helper (`mask_phone`, `farmer_out`, `_account_phone`, `_box`) has more than
one caller or a test, and there is no new abstraction.
Not checked: PostGIS execution of the two bbox queries and the explicit audit inserts (Docker down;
Verifier).
