## What this change does

Two FPO-admin routes. `GET /v1/farmers/{id}/export` returns one JSON document built by a single SQL statement
(the runbook §1 query), with 15-minute presigned links to the ID documents and evidence photos, writes an
audit row `farmer.export` with counts only, and sends `Cache-Control: no-store`. `POST /v1/farmers/{id}/erase`
(`reason`, `confirm: true`) anonymises the farmer, the account and the plots with Core statements, withdraws
consents, ends sign-in, deletes the id-docs objects and queues a page rebuild per published batch. A daily
Celery beat job deletes OTP challenges 30 days after expiry.

## Focus checks (what holds)

1. **Audit listener really is bypassed.** `core/audit.py` hooks only `Session` `after_flush` (line 155); its
   docstring says Core `insert/update/delete` are not seen. The ORM writes left in `erase_farmer` (membership
   delete, device revoke, `batch.current_build_no += 1`, the new `PageBuild`) carry no PII. The integration test
   checks that no new audit row holds the phone, name, survey number, GI number or PIN code. Good.
2. **Rebuild runs after the commit.** The router commits (`router.py:525-528`) and only then calls
   `enqueue_page_build` per build. The build task renders from the database at run time, so it cannot
   republish the old name. No race. `test_erasure_rebuilds_the_page_as_farmer_n` proves "Farmer 1" and no "Muthu".
3. **S3 before commit is the safe direction.** If the commit fails after `_delete_id_doc_objects`, the
   documents are gone and the rows still say "not erased". The retry finishes the job (S3 then deletes 0). The
   person asked for deletion, so losing the files early loses nothing we may keep. The reverse order (commit,
   then S3) could leave ID images behind with the audit row saying "erased". The chosen order is right.
4. **Idempotent without re-running side effects.** The farmer row is locked (`service.py:1974`), then the
   `farmer.erase` audit row is checked (`:1978`) *before* `_end_farmer_access`, so a second call touches
   nothing. Under READ COMMITTED the second of two parallel calls waits on the lock and then sees the first
   call's committed audit row.
5. **Phone placeholder.** `erased:<user uuid>` is unique per user, `users.phone` is unbounded `text` with a
   plain unique constraint, so two erased farmers never collide. It never matches an E.164 sign-in.
6. **OTP rows.** Erasure deletes the challenges for the old phone (only when the account itself is erased).
   The purge deletes `expires_at < now - OTP_RETENTION_DAYS`, so it can never touch a challenge still inside
   its validity window, nor the 24-hour `OTP_DAILY_CAP` window. `otp_retention_days` has `ge=1` and a
   `description=`; `.env.example` documents it.
7. **Authorisation.** Both routes use `Admin` (`require_role(Role.FPO_ADMIN)`) plus `_farmer_in_scope`
   (another FPO's farmer is 404, FR24). Tested: officer 403, farmer 403, FPO B 404, `confirm: false` 422.
   A self-serve path for the farmer is out of scope (the runbook routes requests through the data officer).
   No rate limit is needed: admin-only, audited, one farmer per call.
8. **Links.** 900 s (`ID_DOC_URL_TTL_S`). ID documents are signed against `S3_BUCKET_IDDOCS`; evidence photos
   against the row's `bucket`, which the events service always sets to `s3_bucket_evidence`
   (`events/service.py:517`). No `temp_uploads` path exists. `links_expire_at` is returned.
9. **Export audit row** holds `{"rows": {section: count}}` only; the test checks the phone is absent.
10. **Documentation.** Every new function has Args/Returns/Raises/Side effects; every `FarmerExport` and
    `FarmerErase` field has `description=`; `DECISION D-065` exists in `DECISIONS.md` and `docs/adr/D-065.md`,
    and the ADR matches the code (placeholders, address keeps village-level parts, counts-only audit, account
    kept with another membership, S3 before commit, 204 repeat). CHANGELOG and TODO lines are present; the
    runbook calls the routes. No new error code.

## Must fix

1. **P1. The export hands over other people's data when the farmer's account also has another role or FPO**
   (`apps/api/agritrace/modules/registry/service.py:1804`, same clause in the runbook SQL at
   `docs/ops/dpdp-data-subject-runbook.md:47`)
   - **What this is:** The `my_versions` part of the export query picks every event version on the farmer's
     plots and lots, made for the farmer, **or entered by the farmer's user account**
     (`OR v.entered_by_user_id = (SELECT user_id FROM f)`), with no FPO or subject filter.
   - **Problem:** `create_farmer` links a farmer to an existing account by phone (`service.py:784-798`). So a
     field officer of FPO A who registers his own farm has `farmers.user_id` = his officer account. The export
     of *his* farmer record then contains every event version he entered for every other farmer he assisted:
     their payloads, their exact capture GPS and 15-minute links to their evidence photos. The same clause, for
     a farmer who is also a member of FPO B, gives FPO A's admin FPO B's events and photos (breaks FR24).
     Nothing real is lost by dropping it: event subjects are only plot, lot or batch, so a farmer's own entries
     are already caught by the plot and lot clauses, and assisted entries by `on_behalf_of_farmer_id`.
   - **Fix:** Delete `OR v.entered_by_user_id = (SELECT user_id FROM f)` in `_EXPORT_SQL` and in the runbook §1
     SQL. Add one case to `test_export_shape_scope_and_audit`: create a farmer with `officer_a`'s phone, insert
     one event version (with one `evidence_photos` row) entered by `officer_a` on behalf of a *different*
     farmer, and one on the officer-farmer's own plot; assert the export holds only the own-plot version, its
     photo has a URL containing `/evidence/`, and the other farmer's version and photo are absent. This also
     covers the export's event and photo sections, which today are only ever asserted empty.
   - **If we skip it:** The first DPDP access request from an officer-farmer leaks other farmers' records and
     farm locations to him, which is exactly the harm the export exists to avoid.

   - **Problem:** The compose `worker` runs `celery ... worker` only. The runbook §3 promises the 30-day purge.
     Plain `--beat` is not enough either: the image runs as user `app` with `WORKDIR /app` owned by root

     worker's command with
     `command: celery -A agritrace.worker worker --beat --schedule /tmp/celerybeat-schedule --loglevel=INFO`.

   - **If we skip it:** Phone numbers in `otp_challenges` stay forever, against the retention the runbook states.
