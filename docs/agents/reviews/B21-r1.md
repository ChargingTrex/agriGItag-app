- **Verdict: PASS.** P1: 0, P2: 1, P3: 4.
  - P2-1: `find_nul` is recursive, so an entry whose `data` is nested about 1,000 levels deep (a 2 KB body) raises

## What this change does

Sync push now refuses, per entry and before any database work, a NUL anywhere in `entries[].data`. It also caps
`version_no`/`instance_no` at int32. A Postgres data error (SQLSTATE class 22) during an entry rejects only that
entry as `validation_error`, and the batch goes on. Telemetry with a NUL or an int32 overflow is a 422 for the whole
envelope. The api image runs 4 uvicorn processes (`ENV WEB_CONCURRENCY=4`).

## Findings

### Should fix

1. **P2-1: Deeply nested `data` turns the NUL check into a 500** (`apps/api/agritrace/core/schemas.py`
   `find_nul`; called from `modules/events/service.py` `push`)
   - **What this is:** `find_nul` walks `entry.data` by calling itself once per level of nesting.
   - **Problem:** Python stops at about 1,000 nested calls. `{"a": [[[ … ]]]}` with 1,000 levels is 2 KB, well
     under the 256 KB cap, and `json.loads` and pydantic (`dict[str, Any]`) accept it. `RecursionError` is not an
     `AppError` or `DBAPIError`, so it escapes `push`: the response is a 500, and the entries after the bad one are
     never processed. A retry fails the same way. Under uvicorn the call stack is already deeper, so the limit is
     lower than 995. On `main` the same entry is a per-entry `rejected`. A real phone never sends this, so it is
     not a P1. But it is a 5xx at the trust boundary this WP hardens.
   - **Fix:** walk with a list instead of recursion, and drop the path. A per-level path would cost
     O(depth²) memory on the same input, and the phone never sends a NUL, so the location only helps debugging:
     ```python
     def has_nul(value: Any) -> bool:
         """…Args/Returns as today…"""
         stack = [value]
         while stack:
             item = stack.pop()
             if isinstance(item, str):
                 if "\x00" in item:
                     return True
             elif isinstance(item, dict):  # JSON keys are always str
                 if any("\x00" in key for key in item):
                     return True
                 stack.extend(item.values())
             elif isinstance(item, list):
                 stack.extend(item)
         return False
     ```
     In `push`: `if has_nul(entry.data): raise ValidationFailedError(details=[{"loc": ["data"], "msg": msg,
     "type": "string_nul"}])`. In `test_nul_in_entry_data_rejects_that_entry`: assert `loc == ["data"]`, and add
     one entry nested 5,000 deep that must come back `rejected` (or `accepted`), not raise.
   - **If we skip it:** any authenticated caller can still get a 500 from `/v1/sync/push` with a 2 KB body.
     Schemathesis or a fuzzing QA run will report Q04-1 again.

### Nice to have

2. **P3-1: The `ValueError` branch in `_data_error` is never reached** (`modules/events/service.py` `_data_error`)
   - **What this is:** the backstop maps SQLSTATE class 22, "or" a driver error whose `__cause__` is a
     `ValueError`.
   - **Problem:** asyncpg 0.32 wraps every bind-time encode failure in `asyncpg.exceptions.DataError`. That class
     is the server-side class-22 error, with `sqlstate = "22000"`, and it is not a `ValueError`. Only
     `asyncpg.exceptions._base.DataError` is a `ValueError`. Probed on real Postgres: int32 and int64 overflow and
     `'abc'` into an int column all arrive as `22000` and are mapped by the SQLSTATE test alone. The
     `__cause__` clause is dead, and the docstring credits it with the int32 case.
   - **Fix:** delete `and not isinstance(exc.orig.__cause__, ValueError)`. Reword the docstring: "SQLSTATE class 22
     (data exception, including asyncpg's own encode errors, reported as 22000)". -1 line.
   - **If we skip it:** a reader trusts a branch that does nothing, and keeps it through an asyncpg upgrade
     without a test.

3. **P3-2: No committed test drives the backstop on real Postgres** (`tests/integration/test_sync.py`
   `test_nul_and_int32_overflow_reject_only_their_entries`)
   - **What this is:** the integration test sends [NUL, clean, `instance_no` 3e9].
   - **Problem:** both bad entries are now stopped before the database (the NUL pre-check, pydantic `le=`), so
     `_data_error` plus the rollback-and-continue path is covered only by the unit test with a fake SQLSTATE. The
     worker's "validators off" run was by hand and is not committed.
   - **Fix:** one more case in the same test: `monkeypatch.setattr(service, "has_nul", lambda _: False)` (or
     `find_nul` → None), then the same [NUL, clean] push → `rejected`/`accepted`, 200. Three lines.
   - **If we skip it:** a future change to the error mapping (or SQLAlchemy's asyncpg adapter) can bring back the
     batch-wide 500 with every test green.

4. **P3-3: Telemetry 422 refuses the whole push. Accepted, but say why where the choice is made**
   (`modules/events/schemas.py` `SyncPushIn` / `SyncMetricIn`)
   - **What this is:** a bad `metrics[]` row or `app_version` now fails validation of the whole envelope.
   - **Problem:** `apps/mobile/lib/core/sync/outbox_processor.dart` `_failed` marks every entry of the batch
     `needs_attention` on any 4xx other than 401/403/429. So one bad telemetry row would park up to 50 good
     entries. I checked the phone: `app_version` comes from the package, `network_type` from a fixed mapping,
     `failures` is the attempt count, and `photo_upload_ms` comes from a `Stopwatch` (monotonic, no clock jumps).
     A real phone cannot produce these values. The same rule already applied before B21 (`network_type` over 16
     characters, a negative counter). So this is not a P1. On `main` the same input was worse: a 500 after the
     entries committed, retried forever.
   - **Fix:** one line in the `SyncPushIn` docstring: "a telemetry value Postgres cannot store is a 422 for the
     envelope; the phone drops its metrics and only a non-app client can send one (B21)". No code change.
   - **If we skip it:** the next reviewer reopens the same question.

5. **P3-4: The connection budget leaves out the Celery worker** (`apps/api/Dockerfile` comment; `TODO.md` B21 →
   deploy line)
   - **What this is:** the comment says 4 × 15 = 60 connections, "under Postgres' default 100".
   - **Problem:** the `worker` container runs Celery at its default concurrency (vCPU count: 12 on the Q04 host).
     Each child process has its own engine. That adds roughly 12 to 24 connections, plus QA and Robot sessions.
     It is still under 100 today, but the deploy line ("size to vCPUs") can push a bigger host over.
   - **Fix:** in both places say "api processes × 15 + worker concurrency (+ headroom) ≤ `max_connections`".
   - **If we skip it:** a 16-vCPU deploy (16 × 15 + 16 > 100) fails with `too many clients` under load.

## Checked and fine

- **NUL walk scope:** covers all 8 kinds (every kind's content is in `data`). The other `SyncEntry` fields are
  UUID or a literal. It covers dict keys and list items. Bytes cannot come out of JSON. It runs before
  `_entry_caller`, so no DB read or write for that entry. The rejection goes through `except AppError` → rollback.
  The response is the registered `validation_error`.
- **Lone surrogates:** pydantic rejects them in typed strings (`app_version`, `network_type`, typed payload fields)
  as `string_unicode` 422. In free `data` the backstop catches them (jsonb 22P02/22P05).
- **int32 caps:** the only push-reachable INTEGER columns written from client values are
  `event_versions.version_no` / `events.instance_no` and `sync_metrics.failures` / `photo_upload_ms`. All are
  capped now. `bags` and `packs` live in the JSONB payload. Kg and price columns are unbounded `Numeric`, and
  `share_pct Numeric(6,3)` is server-computed. `quality_readings.version_no` and the registry
  `version_no`/`revision_no` are set by the server.
- **Backstop:** maps only class 22. 23xxx stays `IntegrityError` and is re-raised (probed). The handlers' own
  `IntegrityError` race paths are untouched. 08xxx and other errors are re-raised → 500 → the phone retries
  (unit-tested). The message is a constant with `loc: ["data"]`: no SQL, no value, no driver text (the asyncpg
  message holds `repr(value)`, and it is not echoed). Every handler commits only at its end, after all DB writes,
  so a class-22 rollback never leaves half an entry. Enqueue and presign happen after the commit. A class-22 error
  is deterministic for the same input, so making it final rather than retried is what ends the Q04-1 poison loop.
- **B06 contract:** per-entry transactions, mixed batch, `duplicate`, `client_id_conflict`, B15/B16 kinds: the 37
  integration tests pass unchanged.
- **Multiple processes:** uvicorn reads `WEB_CONCURRENCY` (`uvicorn/config.py:358`). Compose does not override the
  api command, and Celery ignores the variable. The lifespan only validates config. The `lru_cache` singletons
  (settings, fieldconfig, engine, S3 client) are per process and read-only. The scan limiter is a Valkey INCR. OTP
  and PIN limits are DB rows. The audit context is a contextvar. The pull cursor is `(updated_at, id)` with a
  settle window, so it does not depend on per-process `uuid7` order. I found no module-level mutable state.
- **OpenAPI / clients:** the 25 `maximum: 2147483647.0` values follow the existing `minimum: 1.0` style. dart-dio
  (built_value) emits no range checks (the existing `minimum` values produce none in `sync_metric_in.dart` /
  `undo_in.dart`), so regenerating the Dart client only changes doc comments. The portal `schema.d.ts` has no
  range types.
- **Docs and tracking:** headers and docstrings on the new helpers and tests (interrogate 100 %). No DECISION
  needed beyond P3-3 (D-062 unused, as the report says). The CHANGELOG line and the four TODO lines are accurate.
- **Ponytail:** small diff. It reuses `ValidationFailedError`, `_rejected` and the `append_only_error` pattern.
  Nothing to delete beyond P3-1.
