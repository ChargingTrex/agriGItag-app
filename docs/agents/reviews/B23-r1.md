## What this change does

`refresh` now refuses the device's *current* refresh token with 401 `session_expired`, and signs the device out,
when the device's last OTP/PIN sign-in (`devices.signed_in_at`) is more than `SESSION_MAX_DAYS` (default 30)
old. A new route `POST /v1/devices/{id}/revoke` lets a user sign out one of their own devices, or an FPO admin
sign out a member's device, with an audit row. The sync push's "class 22 data error → 422" mapping moved to
`core.errors.data_error`, and the global DB error handler now uses it too, so a NUL or an out-of-range number in
any REST body answers 422 `validation_error` instead of 500.

## Focus questions, answered

1. **Deploy-time impact of "no `signed_in_at` = expired": none in practice.** A device row gets a refresh token
   only through `_open_session`, and its two sign-in callers (`verify_otp` `service.py:584`, `verify_pin`
   `service.py:669`) both pass `sign_in=True`, which stamps `signed_in_at`. `_bind_device` creates rows signed
   out (`revoked_at` set, no hash). Refresh passes `sign_in=False`. So only a row signed in under the original
   B02 code, before migration `0002_identity_pin` (2026-10-29 → 10-30, dev only), can hold a live refresh token
   with NULL `signed_in_at`. The seed (`agritrace/seed/`) writes no devices, and the pilot is not deployed yet
   (G5 unsigned, deployment checklist just written). The worst case, a dev phone from 29 Oct, gets one re-OTP.
   No backfill needed. Fail-closed is the right default.
2. **Clock basis: server only.** Both ends of the comparison are server time. `signed_in_at` is set from
   `utcnow()` in `_open_session`, and the check uses `utcnow()` in `refresh`. The phone's clock never enters.
   `signed_in_at` moves only on a successful OTP/PIN sign-in, never on refresh (`if sign_in:` at
   `service.py:505`). So the limit is absolute and refreshing cannot extend it. The 31-day test proves it: the
   OTP was refreshed nowhere, but nothing in the code path could move the stamp anyway.
3. **Product impact:** see "Recommendation for the Orchestrator" at the end.
4. **Revoke route.**
   - Scope goes through the target user's `Membership` in `caller.fpo_id` (`revoke_device`), not a device FPO
     field. Devices have none, so this is correct.
   - The order is right. An outside-FPO device is 404 *before* the role check, so no other-tenant id is
     confirmed. A non-admin gets 403 for a same-FPO member's device.
   - The access token dies at once, not after 15 minutes. `get_current_user` → `_device_active`
     (`core/auth.py:228-251`) requires `revoked_at IS NULL` on every request.
   - Only the `session_expired` path leaves a ≤15 min tail: the lifetime is checked at refresh, so an access
     token issued on day 29.99 works until it expires. That is acceptable under D-024 (15-minute access TTL).
   - The audit row's `diff` is `{user_id, reason}`. It holds no phone number. An admin could type one into
     `reason`, but `audit_log` is internal and not shown on any public or partner payload.
   - Double revoke answers 204 again and writes a second audit row. That is idempotent and the right answer for
     a "make sure it is gone" action (409 would only make the portal handle a non-error).
   - A user with memberships in two FPOs can have a device revoked by an admin of either one. That is fine for
     a security action.
5. **Class-22 → 422 globally.**
   - The push still catches `DBAPIError` per entry inside its loop (`events/service.py:1013`), before the global
     handler, so per-entry rejection is unchanged.
   - `_store_metrics` can no longer hit class 22, because B21 bounds the metric ints and `NoNulStr`s them.
   - The CSV import (`registry/imports.py:_run`) never caught `DBAPIError`. A class-22 value in a row used to be
     a 500 for the whole file and is now a 422 for the whole file. The rollback is still whole-file (atomic,
     no partial writes), so nothing broke. A per-row report would be better (P3-2).
   - No other route catches `DataError` (grep: only `IntegrityError` catches in quality, rules_flags and
     events).
   - The message is fixed text with no database text in it. `validation_error` is an existing registered code;
     `db_data_error` is a `details[].type`, not a code, so the registry rule holds.
6. **`has_nul` kept, no dead code.** `has_nul` is still used by the push (`events/service.py:1004`), so it is
   not dead. `_data_error` is gone from events. The unit test `test_sync_b21_unit.py:70` and the integration
   test `test_sync.py:643` exercise the moved function through the push.
7. **OpenAPI diff:** `DeviceRevokeIn`, the new route, and the reworded refresh 401 description. That is all;
   `error-codes.md` adds `session_expired`, and the rest is line-number churn. The Dart client and the portal
   `schema.d.ts`/`error-messages.ts` need regenerating (Orchestrator, TODO §8). The clients need no code
   change: mobile `_doRefresh` ends the session on any 401 from refresh with the generic "You were signed out"
   string. `_endLocally` clears only the keystore and the session row, so the unsynced outbox survives a
   `session_expired` sign-out and sends after the next sign-in. Portal `endIfRejected` signs out on any 401.
8. **Docs standard:** headers, docstrings (Args/Returns/Raises/Side effects), the `DECISION D-024` comment, the
   `DECISIONS.md` row note, CHANGELOG and TODO are all present. D-064 was not consumed. Two doc slips are listed
   as P2-1 (a false claim) and P3-4.

## Findings

### Should fix

1. **P2-1: the revoke route has no way to find the device id** (`docs/adr/D-024.md` amendment "Consequences";
   `identity/router.py` `device_revoke`)
   - **What this is:** to sign out a lost phone you call `POST /v1/devices/{device_id}/revoke`, which needs the
     lost phone's device id (a UUID the app made up at install).
   - **Problem:** no route returns another device's id. `GET /v1/me` returns only the *calling* session's
     device, so a farmer on a new phone sees the new phone's id, not the lost one, and an admin cannot call
     another user's `/me`. There is no audit read route. Today only someone with database access can use the
     route. Yet D-024 says "Admins find the device id in the audit trail or the user's `GET /v1/me`", which is
     wrong.
   - **Fix, smallest that makes the route usable:** add `GET /v1/users/{user_id}/devices` in the identity router.
     - Callers: the user themself, or `Admin` in the FPO. Reuse `revoke_device`'s membership check: extract
       its five-line membership/role block into one private `_check_device_owner(session, caller, user_id)`
       used by both.
     - Body: `list[DeviceOut]`, reusing the existing `DeviceOut` from `MeOut`; add `signed_in_at` and
       `revoked_at` to it if they are missing.
     - Add one integration test: an outside-FPO user gives 404, and an admin sees the member's device.
     - That is about 25 lines.
   - **Acceptable alternative if the Orchestrator defers the list route:** strike the false sentence from D-024.
     Write instead "until a device list route exists, an operator reads the id from `devices` by user", and keep
     the TODO §8 line. The 30-day lifetime already closes ASVS 3.3.2 on its own, and the SEC review rated the
     revoke route P2.
   - **If we skip it:** an FPO office cannot act on "I lost my phone" for up to 30 days, and the ADR misleads
     the next reader.

### Nice to have

2. **P3-1: data errors are no longer logged** (`core/errors.py` `_db_error`)
   - **What this is:** a class-22 error now becomes a 422 with no log line.
   - **Problem:** some class-22 errors are server bugs, not client mistakes. One example is a server-computed
     sum that overflows an INTEGER column. These now look like a client error and leave no trace. Before B23
     they were a 500 with a traceback.
   - **Fix:** in `_db_error`, before returning a mapped `ValidationFailedError`, add one line:
     `log.warning("data error %s on %s %s", sqlstate, request.method, request.url.path)` (the SQLSTATE only, no
     database text).
   - **If we skip it:** a real server overflow is blamed on the phone and never seen in the logs.
3. **P3-2: a CSV import with one bad cell rejects the whole file without a row number**
   (`registry/imports.py:_run`, outside B23's paths)
   - **Problem:** registry schemas do not use `NoNulStr`. So a NUL in one farmer name now gives a file-level 422
     `db_data_error` with `loc: ["data"]`, not a `rejected[]` row. The admin cannot tell which of 500 rows is
     at fault.
   - **Fix (follow-up WP):** in `_run`, after `except ValidationError`, add a branch that catches `DBAPIError`:
     if `data_error(e)` gives a mapped error, append `ImportRowError(row=line, code=mapped.code, field=None)`;
     otherwise re-raise. The savepoint has already rolled back.
4. **P3-3: the fail-closed branch (`signed_in_at IS NULL`) has no test** (`tests/integration/test_identity.py`)
   - **Fix:** in `test_refresh_after_session_max_days_is_session_expired`, add a third device with
     `signed_in_at = None` (set it the way `_age_sign_in` sets the date) and assert 401 `session_expired`. That
     is three lines. It keeps the security default from being "fixed" into fail-open later.
5. **P3-4: D-024 still says farmers never re-enter anything** (`docs/adr/D-024.md` "Advantages")
   - **Fix:** change "No password anywhere; farmers never re-enter anything after the first SMS" to "…farmers
     re-enter only an SMS code, once every `SESSION_MAX_DAYS`".
6. **P3-5 (lean): third hand-written `audit_log` insert** (`identity/service.py` `revoke_device`, same 15
   lines as `registry/service.py:1569 _audit` and `events/service.py:529`)
   - **Problem:** three copies must change together, for example when `request_id` gets copied. Registry's
     copy carries the `shortcut:` note about the missing `request_id`; this copy dropped it.
   - **Fix (follow-up):** move registry's `_audit` to `core.audit.write_audit(session, caller, action,
     entity_type, entity_id, diff)` and call it from the three places, for −30 lines. For now, copy the
     `shortcut:` line into `revoke_device`.

Known and already ledgered: `SESSION_MAX_DAYS` is missing from `apps/api/.env.example` (TODO §8). The default
works, but `config.py`'s header promises every variable is in that file.

## Recommendation for the Orchestrator: farmer re-OTP interval

30 days is the ASVS L1 number. For office roles it is right: they hold FPO-wide powers, sign in on shared PCs,
and already type a PIN. For farmers it costs about four to six SMS codes per chilli season. Each code needs
network coverage and an SMS, often mid-harvest when the farmer is in the field and offline for days. That
goes against UserFlows §Design rules ("log in once"). A farmer token can only write that farmer's own
records, and with B23 a lost phone can now be revoked (once P2-1 is closed). I recommend putting this to the
user: **staff 30 days, farmers 90 days**, recorded in D-024 as an accepted ASVS 3.3.2 deviation, which the
SEC review explicitly allowed ("the Architect-Gate may accept a longer farmer limit"). The code cost is small.
Add a second setting, `session_max_days_farmer` (default 90). In `refresh`, pick the limit from the
membership already loaded in `account`: `account[1].role == Role.FARMER`. Add one test at 60 days. If the
user prefers one number for everyone, 30 days works today. Nothing is lost on expiry, because the phone's
outbox survives the sign-out and sends after the new OTP.
