## What this change does

When an officer corrects or undoes a farm entry, the audit-log row now also stores the reason code and
reason text, so the portal's audit search shows why. A plot saved without the optional farming type no
longer stops the public page from being built; the page simply leaves that line out. And when Postgres
breaks a deadlock or a serialization conflict, the API now answers 503 `retry_later` with `Retry-After: 1`
instead of a generic 500.

## Focus questions

1. **Privacy of `reason_text` in the audit diff.** No new exposure. `reason_text` (max 500 chars) is already
   stored in plaintext in `event_versions.reason_text`, already exported in the batch audit CSV
   (`reporting/service.py audit_csv`, admin or viewer) and already returned to phones by pull. The audit
   search that now shows it is FPO-admin only and FPO-scoped. Neither `publishing/` nor `partner_api/` reads
   `audit_log` or `reason_text`, so no public or partner payload gains it. Both stores are append-only, so a
   phone number typed into a reason is equally hard to erase in either place; that was true before.
2. **`farming_type` None.** This is the house pattern, not a one-off: `farmer_name`, `irrigation_source`,
   `review_note`, `gi_authorised_user_no` are already `| None` in `Lot`, and the template guards each with
   `{% if %}`. Every other plot field the page needs is `required: true` in `plot.yaml` (`declared_area`).
   A generic "every optional YAML field is nullable" layer would be scope creep. The fixture page renders
   byte-identically to `main`; a page with no farming type passes `check` and `check_output.sh`
   (privacy lint 0 hits). The template edit is outside the declared paths but is needed (without it
   `t("farming_type.None")` raises `KeyError`); accepted.
3. **`retry_later`.** Mapping is in `core/errors.py _db_error`, the one `DBAPIError` handler. It matches only
   `orig.sqlstate in {"40P01", "40001"}` (the same `getattr` chain that already works live for 23001); every
   other `DBAPIError` still goes to `_unhandled` (500 with traceback), so nothing is swallowed. The original
   B08-2 traceback is `sqlalchemy.exc.DBAPIError: (…asyncpg.Error) deadlock detected`, so it hits this path.
   Rollback: Postgres already aborted the victim transaction; push calls `session.rollback()` before
   re-raising, and `get_session` closes (rolls back) the session for other routes. The code is registered
   (`RetryLaterError`, `error.retry_later`, fix line) and is in `docs/api/error-codes.md`; `Retry-After` is not
   in OpenAPI, same as the existing 429 `rate_limited`. `_http_error` maps a Starlette 503 to this code, but
   nothing raises one (`/v1/healthz` sets `response.status_code` directly).
   **Push semantics (B06):** a deadlock inside one entry is not per-entry; `push` re-raises any non-23001
   `DBAPIError`, so the whole request answers 503. Entries before it are already committed and return as
   `duplicate` on resend. This is the right choice: the phone retries every 5xx with backoff
   (`apps/mobile/lib/core/sync/retry.dart:34`), while a per-entry `rejected` would park the entry for the
   user's attention.
4. **The 0/20 reproduction.** Sequence matches the Verifier's (officer push, then moisture reading → ready →
   intake straight away), plus a harvest event, so two `check_event` tasks per run. The report cites one
   overlap (run-1 task 19:00:00.56 for 3.8 s, intake answered 19:00:02.10) and "80 `check_event` lines", and
   the image was checked for B19's `key_share` locks. My own reading of the lock order agrees there is no
   cycle: intake holds the lot first; the worker holds only its event row and event-rule flag rows (codes
   disjoint from the lot and batch rules, checked) before it waits on the lot. See P2-2 for the evidence gap.
5. **Docs standard and Ponytail.** Touched functions keep full docstrings (`_db_error`, both new test
   functions, the test route). `DECISION D-017` in `schema.py` exists in DECISIONS.md. CHANGELOG line and
   TODO entries are present. The diff is small: one line in `_add_version`, one schema line, one guard, ~20 lines
   for the error code. Nothing to delete.
