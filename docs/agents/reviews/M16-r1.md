## What this change does (M16)

Photo upload URLs carry an expiry in server time. The phone now checks that expiry against the server's clock: its
own clock minus the stored skew (the measured offset between phone and server clocks). So a phone whose clock runs
fast no longer sees every fresh URL as expired and stops uploading photos.

A running sync now re-reads the signed-in user before each push batch, before re-requesting upload URLs, before each
PUT round and before each photo confirm. If another person signed in, it stops and leaves the previous user's rows
`waiting` for them. The auth interceptor (the code that adds the token to API calls) also no longer re-sends a request
that got a 401 with a token that belongs to another user.

## Nice to have (P3)

1. **Pull and bundles still run with B's token after a switch** (`apps/mobile/lib/core/sync/sync_service.dart`
   `_run` phase loop)
   - **What this is:** After a switch, `pushEntries` and `uploadPhotos` stop, but `pullChanges` and `fetchBundles`
     still run in the same run with B's token.
   - **Problem:** This puts no wrong data on the phone, and nothing is sent in A's name. B's rows and cursor are
     stored, and the next run's D-029 reset (`syncUserKey` A → B) deletes them and downloads them again. The only cost
     is one wasted pull plus bundle download on 2G. So TODO or P3, not P2.
   - **Fix:** One line at the top of the phase loop body in `_run`: `if (await c.userChanged()) break;`. That is
     cheaper than a TODO line. It does not replace the per-batch check in `pushEntries`.
   - **If we skip it:** About one extra pull and bundle download per user switch.

2. **The skew is read once, before the URL refresh that records a new one** (`photo_uploader.dart:41-55`)
   - **What this is:** `skew` is read at the top of `uploadPhotos`. `refreshUploadUrls` goes through `_post`, which
     records a new skew, but `usable` keeps the old value.
   - **Problem:** Suppose the phone clock jumps 20 min ahead after the last push and no entry is pending. The refresh
     returns fresh URLs, records skew +20 min, and the URLs are still judged with skew 0. They look expired and nothing
     uploads in this run. The next run reads the new skew and uploads, so the cost is a delay of up to one run
     (about 15 min).
   - **Fix:** Make it `var skew = …;` and after `due = await c.db.mediaDao.pendingUploads(...)` on line 55 read it again
     with the same expression. Or pull the read into a small `_skew(c)` helper and call it at both places.
   - **If we skip it:** Photos wait one more run after a clock jump.

3. **Formatting and ledger** (`apps/mobile/lib/core/api/api_client.dart:124`; `TODO.md`)
   - **What this is:** The interceptor doc line grew to 157 characters. The file and repo keep 120. The worker also
     notes that `SessionDao.save` cannot replace an existing row: `insertOnConflictUpdate` meets a CHECK on `id = 1`,
     not a primary-key conflict.
   - **Problem:** The long line is hard to read and will reflow on the next edit. The `save` limit is latent today,
     because every sign-in path clears the row first. A future path that signs in over a live row would throw after

## Focus questions, answered

- **Sign of the skew.** `_recordSkew` stores `phone now − server_time`, so a fast phone gives a positive skew. Server
  now is phone now minus the skew, and the check `expires_at > now − skew + 1 min` is right. A slow phone (negative
  skew) is fixed too: it used to treat expired URLs as valid for up to the size of the offset.
- **No skew recorded yet.** It counts as 0, the old behaviour. That is never wrong at the moment a URL arrives:
  every URL comes from a push or a URL refresh, both go through `_post`, and `_post` records the skew from the same
  response before the photo phase uses it. Skew and `expires_at` come from the same API, so there is no cross-server
  mismatch. RTT error (seconds) is far below the 1 min margin.
- **Skew under 10 min is stored as 0** (`_recordSkew`, mobile-design §3). A phone up to 9 min fast still has ≥ 5 min
  of a 15 min URL, which is fine. A phone up to 9 min slow can still PUT once with an expired URL. The 403 path drops
  the URL and the next run re-requests it, which costs one wasted PUT. That is the existing behaviour, not a
  regression, so no finding.
- **User re-check granularity.** The check runs a few database awaits before the request goes out. A switch needs a
  full sign-out plus an OTP round trip, so the gap between the check and the send is milliseconds against tens of
  seconds. That is acceptable. A batch already in flight was authorised with A's token at request time, which is
  correct, and its results apply to A's rows. If it gets a 401 after A's logout, the new interceptor guard
  (foreground: current token is B's) or `_adoptStored` dropping A's tokens (background, from the micro-patch)
  prevents a re-send. The rows go through `_failed` as `FailureAction.wait`, so they wait and are not failed. The
  background isolate has two layers: its in-memory token never becomes B's, and `userChanged` reads the shared
  Session row.
- **A's rows are not marked failed.** The early returns leave them `waiting` and owned by A. A `_put` already running
  finishes normally (the presigned PUT carries no token), and its confirm waits for A's next run (`awaitingConfirm`
  is per owner).
- **Normal refresh path.** `current == sent` refreshes as before. A token rotated by a concurrent request has the same
  `sub`, so the retry uses it as before. A `null` current (signed out) still calls `refresh()`, which returns null
  without a POST because `_refresh` is null. The existing interceptor tests pass.
- **Docs.** File headers, `userChanged`, `jwtSub` and `clockSkewKey` are documented; the skew line has its why
  comment. D-058 is unused. That is fine: the audit prescribed the fix, and the "keep the pre-check, do not waste a
  PUT on a 403" reason is in the worker report and the code comment is enough.
- **Ponytail.** About 25 lines of code for two P1s. The PUT-round guard only saves work, but it is one line. No
  wrapper or option nobody asked for.
