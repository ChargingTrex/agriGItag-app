## Probe: does the OTP code reach Celery log records?

Throwaway script `/private/tmp/claude-501/-Users-fi-it-Documents-projects-agriGitag/1234289e-8332-4673-8beb-a187a8f85a38/scratchpad/b04_probe.py`,
run with the worktree venv. The root logger is at DEBUG with a handler that checks for the code `987654` in
`getMessage()`, in `record.data`, and in the formatted text (traceback included). Four cases, each with
`payload={"code": "987654"}`:
(1) the real `notifications.send` fails with a bad `user_id`;
(2) the real task with `service.deliver` patched to raise `RuntimeError("db down")`;
(3) the success path, where `LOG_SUCCESS` also carries args/kwargs;
(4) the `celery.worker.strategy` "received" record, built exactly as Celery 5.6.3 builds it.

```

celery.app.trace       ERROR code_in_msg=False code_in_data=False code_in_formatted=False | ...raised unexpected: RuntimeError('db down')
celery.app.trace       INFO  code_in_msg=False code_in_data=False code_in_formatted=False | ...succeeded in 0.0012s: 'sent'
celery.worker.strategy INFO  code_in_msg=False code_in_data=False code_in_formatted=False | Task notifications.send[t1] received
--- WITHOUT MaskTaskArguments (filters removed)
celery.app.trace       ERROR code_in_msg=False code_in_data=True  code_in_formatted=False | ...ValueError(...)
celery.app.trace       ERROR code_in_msg=False code_in_data=True  code_in_formatted=False | ...RuntimeError('db down')
celery.app.trace       INFO  code_in_msg=False code_in_data=True  code_in_formatted=False | ...succeeded ...: 'sent'
celery.worker.strategy INFO  code_in_msg=False code_in_data=True  code_in_formatted=False | ... received
```

**Result.** Without the filter, the code is in `record.data` / `record.args` of every trace and strategy record,
so any JSON formatter would print it. With the filter it is gone from all of them. Formatted tracebacks show
source lines, not local values. The filter does its job.

Remaining paths outside the filter's two loggers are covered in P3-3:
- the consumer's unknown/invalid-task body dump;
- the pool's DEBUG line.

The DB row stores `{"code": "***"}` (`templates.redact` runs before the insert). `ConsoleProvider` logs only the
text rendered from the redacted payload. The phone is never logged. There is no result backend and no
`result_extended`.

## Findings

### P1
None.

### P2

**P2-1. `SMS_PROVIDER=console` is not refused in prod** (`core/config.py:_refuse_dev_secrets_in_prod`).
- **Case:** with `ENV=prod`, `OTP_DEV_CODE` is already refused. If someone sets `SMS_PROVIDER=console`, for example
  by copying compose or `.env.example`, every OTP row reads `sent/console`, but nothing is sent. The code is
  redacted in the log too, so no farmer can sign in. The admin view shows "sent", which hides the cause.
- **Fix:** add `or self.sms_provider == "console"` to the existing prod guard and to its error message, plus one
  unit test next to the B00 guard test. Same pattern as B00's secret guard.

### P3 (record in TODO; none blocks merge)

**P3-1.** Make `sms_provider: Literal["console"] | None`.
- **Case:** a typo such as `SMS_PROVIDER=Console` starts fine and fails every SMS with `provider_not_configured`.
  A Literal fails at startup instead.
- **Cost:** one line.

**P3-2.** A real gateway must turn every transport error into `ProviderRefused`.
- **Case:** `deliver` catches only `(KeyError, ProviderRefused)`. An `httpx.TimeoutException` from a future gateway
  would leave the row `queued` forever. The task fails and `acks_late` acks it on failure, so the message is gone.
- **Fix:** add this to the `TODO(provider)` line, or catch `Exception` there and record `error:<ClassName>`.
- **Today:** no current provider raises anything else.

**P3-3.** Two Celery log paths are outside `MaskTaskArguments`. Neither is reachable at the compose settings
(`--loglevel=INFO`, one image for api and worker). Both print positional strings, so a filter cannot mask them.
- `celery.worker.consumer` UNKNOWN/INVALID task ERROR dumps up to 1024 chars of the message body, including
  `payload.code`. This happens during an api/worker version skew.
- `celery.concurrency.base` DEBUG `TaskPool: Apply …` prints the body.
- **Fix:** add a deploy note to TODO next to the existing `kwargsrepr` item: never run the worker at DEBUG in
  prod, and deploy the worker before the api.

**P3-4.** OTP redelivery after a hard node crash comes too late to be useful.
- **Case:** on Redis, a message reserved by a worker that dies without a clean shutdown comes back only after
  `visibility_timeout`, 1 h by default. The SMS then carries a code long past `OTP_TTL` (5 min).
- **Fix:** identity can pass `expires=OTP_TTL.total_seconds()` to `send_task`. That call site is B02's path, so
  this goes in TODO, not in B04.

**P3-5.** `task_reject_on_worker_lost` re-queues a task that kills its own child process, again and again (a
poison message).
- **Risk:** none for `notifications.send` today.
- **Fix:** add one clause to the D-009 compromise when the ADR is amended (P3-6).

**P3-6.** `docs/adr/D-009.md` still says "a fresh engine per worker process".
- The code now uses a NullPool engine per task call, plus `acks_late`, `reject_on_worker_lost`, no result backend
  and masked arguments.
- **Fix:** the Orchestrator amends the ADR. `docs/adr/` is outside B04's paths.

**P3-7.** `ProviderRefused` dodges the `raise [A-Z]\w*Error` regex in `gen-error-codes.py` through its name.
- Accepted for one internal exception, and the docstring says why.
- **Fix:** if a second internal (non-API) exception appears, add a small allow-list to the script and rename it
  `ProviderRefusedError`.

**P3-8.** Keyset paging is written twice, in a different style from registry.
- `notifications/service.list_mine` repeats the UUID-cursor keyset paging that `quality/service.py` (`cursor:
  uuid.UUID`, around L92) and the `Cursor`/`Limit` aliases in `quality/router.py:44-47` already have.
- Registry uses an opaque base64 cursor (`registry/service.py:encode_cursor`). conventions.md says "the cursor is
  opaque".
- D-004 stops modules sharing these helpers, so this is not the worker's fault.
- **Fix:** the Orchestrator moves one style into `core` when a third list endpoint appears.

**P3-9.** Every Tamil template is 92–114 chars, measured.
- UCS-2 SMS allows 70 chars per single segment, so each Tamil message costs two SMS. `payment_made` in English
  goes UCS-2 too when the amount carries `₹`.
- DLT also requires the registered template text verbatim.
- **Fix:** add this to the `TODO(provider)` gateway item, so someone decides when choosing the gateway.

**P3-10.** The unit test asserts masking only for `celery.app.trace`, not `celery.worker.strategy`.
- The probe above covers it.
- **Fix (optional):** extend the test to both loggers if B04 gets a round 2.

## Ponytail review (skill `ponytail:ponytail-review`, trimmed)

**What this change does:** Other modules can now queue a message by task name. The worker looks up the
recipient's phone, renders a Tamil or English template, stores the message with secrets replaced by `***`, and
hands it to a provider. In dev the provider is the console; elsewhere it fails cleanly. The change also lets
users list their own messages, makes Celery acknowledge tasks only after they finish, and hides task arguments
from Celery's logs.

**Load assumed:** pilot scale, with one FPO, a few thousand farmers and tens of messages a minute at peak. One
new DB connection per task (NullPool) is fine at that load.

**Should fix**

1. **The console provider can run in production** (`core/config.py:78-89`)
   - **What this is:** settings refuse dev secrets when `ENV=prod`.
   - **Problem:** `SMS_PROVIDER=console` is not refused. OTPs are then marked "sent" but never sent, so nobody
     can sign in.
   - **Fix:** add `or self.sms_provider == "console"` to the existing check, plus one test.
   - **If we skip it:** one copied env file locks every farmer out, and the logs say all is well.

**Nice to have**

2. **A typo in `SMS_PROVIDER` passes silently** (`core/config.py:56`): type it `Literal["console"] | None` so the
   process refuses to start.
3. **Paging is written a second time** (`notifications/service.py:list_mine` vs `quality/service.py`): the same
   eight lines of keyset paging. They can only merge through `core` (D-004), so wait for a third copy.

Verdict: fix 1 first.
Lean: -0 lines possible now. The paging merge saves about 8 lines later.
Not checked: the integration suite (Docker), and a real worker process (only eager `apply` and hand-built
strategy records were probed).
