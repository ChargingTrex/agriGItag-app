## Findings

### P1
None.

### P2
- **F1: reference version can go backwards, and a single global `since` is not commit-ordered.**
  - In `INSERT … VALUES (…, nextval(…)) ON CONFLICT DO UPDATE SET version = EXCLUDED.version`, the
    `nextval` is taken *before* the row lock. Suppose T1 draws 5 and T2 draws 6, but T2 locks first and
    commits 6. T1 then writes 5 and the part's version goes backwards.
  - Fix in the trigger: R1. With `SET version = nextval(…)` the value is drawn under the row lock.
  - A second problem remains even after R1. The sequence orders transaction *starts*, not commits. A
    part bumped to 7 that commits after a client saw another part at 8 is missed forever by
    `GET /sync/reference?since=8`. Phones would keep a stale GI region or standards (previews only; the
    server stays the authority).
  - **For B06 (TODO):** compare per part (the client sends the versions or ETags it holds; the manifest
    already carries per-part `version`/`etag`), or advertise only versions below the oldest in-flight
    transaction.
- **F2: D-014 is cited for a decision it does not record.** D-014 decides "one event table with typed JSON
  payloads", not how enums are stored. CLAUDE.md §5.4 requires new decisions to get the next number → R2
  (D-022; DECISIONS.md runs to D-021).
- **F3: the enum drift guard is a tautology** → R3. This is the worker's own admitted risk, and an
  integration test against `pg_constraint` closes it for every future revision.
- **F4: the audit listener misses the main write path.** `after_flush` fires only for ORM unit-of-work
  flushes. §3 prescribes `INSERT … ON CONFLICT (id) DO NOTHING` for sync push, so plots, consents,
  readings and intakes written by B06/B07 produce **no** audit row. Bulk `update()`/`delete()` statements
  are missed too.
  - R4a documents the limit.
  - **For B06/B07 (TODO):** after a non-duplicate insert, call a small public helper. Exposing
    `audit_rows`-style row building for a single entity is enough. Alternatively, re-read the row through
    the ORM.
- **F5: DPDP erasure versus append-only.**
  - Arch §Security says "nothing is hard-deleted except on a valid data-deletion request". The triggers
    make that impossible through the application, and `audit_log.diff` stores full create snapshots,
    including `users.phone`, `plots.pin` and `land_record_ref`.
  - Not a B01 code change. **Orchestrator TODO / future ADR:**
    - (a) an erasure runbook: the table owner runs `ALTER TABLE … DISABLE TRIGGER` inside one
      transaction, or uses a SECURITY DEFINER redaction function;
    - (b) the API's DB role must **not** own the tables, or any API code path could disable the
      triggers (infra/B00 follow-up);
    - (c) consider redacting phone, pin and survey number from audit diffs.

### P3
- **F6:** `test_event_versions_are_append_only` only matches the message. Also assert `IntegrityError`
  and `exc.orig.sqlstate == "23001"`, so the contract B06 relies on is pinned. One line; can be done in
  r2.
- **F7: a farmer without a user has no phone anywhere.**
  - `farmers.user_id` is nullable "for feature-phone farmers", but Dataflow Stage 0 captures a phone
    for every farmer.
  - **Architect-Gate ruling:** phone stays only on `users` (good for B10). B03 creates a login-capable
    `users` row for every farmer who has a phone; `farmers.user_id` is null only when there is no phone
    at all. TODO for B03.
- **F8:** `core.schemas.Address` has `block` but no `taluk`. FR53 wants the address used as "a second GI
  check against the taluks", and in Tamil Nadu block ≠ taluk. `villages` already has both. Adding an
  optional `taluk` field is additive; do it in B03 or in r2.
- **F9:** FR53 also asks for a structured *farm* address, which §2 does not give `plots` (a spec gap,
  not the worker's). Derive it from the farmer's village until someone asks.
- **F10: tighten the allowed updates at service level.**
  - `evidence_photos`: after `verified_at` is set, B06 should refuse further changes to
    `sha256_server`, `s3_version_id` and `exif_*`.
  - `consent_records.revoked_at`: allow only NULL → value; no un-revoke.
  - The generic trigger cannot express either rule, and a service check is enough for the pilot.
- **F11:** `event_versions.updated_at` and `audit_log.updated_at` can never change. They are harmless and
  required by §0; leave them.
- **F12:** `bump_reference_version` is a row-level trigger, so a B13 bulk import of villages or inputs
  does one upsert on the same row per input row. Measure it in B13; switch to a statement-level trigger
  with transition tables if it is slow.
- **F13:** the `event_versions.device_id` → `devices` FK means a push from an unregistered device fails
  with an FK error. B06 must turn that into a 4xx (B02 creates the device on OTP verify).
- **F14:** `quality_readings.evidence_photo_id` ↔ `evidence_photos.quality_reading_id` is a double link
  (both are in §2). Because `quality_reading_id` is frozen by the trigger, B05 must insert the reading
  first, then the photo.
