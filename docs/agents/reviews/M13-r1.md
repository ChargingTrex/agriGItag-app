## What this change does

It hardens the phone app for release. Below 100 MiB free storage (read through a three-line `StatFs` method channel
in `MainActivity.kt`) the phone deletes the photo files of server-confirmed photos and shows "Phone is full. Send
your entries now?", at app start on the farmer home and after every photo. It also clears the previous user's pulled
lots, plots, tasks and flags on a user switch (D-029; farmers are kept on purpose, see the report), keeps a lot
`ready_for_sale` on pull only while its packing entry stands, drops the empty Session token/PIN columns (Drift v3),
adds tests for the WorkManager registration and the background run, and sends uncaught errors to an `agritrace.crash`
developer log. The APK/AAB size was not measured.

## Should fix

1. **A family member's sign-in takes away a farmer's Sell QR** (`apps/mobile/lib/core/sync/sync_service.dart:L248-257`
   together with `apps/mobile/lib/core/sync/pull_service.dart:L94`)
   - **What this is:** On a user switch `_forgetPulledRows` deletes every lot except those named by an entry that is not
     yet confirmed. The pull keeps `ready_for_sale` only when the local row already says so.
   - **Problem:** Farmer A packs lot L; the phone sets L `ready_for_sale` (D-006); the packing entry is confirmed. A
     signs out, B signs in: L is deleted (its packing is confirmed, so it is not protected). B signs out, A signs in:
     the pull refills L as `open` (the server never sets ready), there is no local row to keep, so L stays `open`
     with `lastMoisture` gone too. A's Sell screen now says nothing is ready, and packing again cannot make it ready
     (no moisture on the phone). Before M13 this could not happen. No farm event is lost (the entries stay), so it is
     not a P1.
   - **Fix:** Also keep a lot that is ready on the phone while its packing stands — the one piece of lot state the
     server cannot give back. In `_forgetPulledRows`, replace the lots delete with:
     ```dart
     // A lot this phone made ready (D-006) cannot come back from a pull: keep it while its packing stands.
     final standingPacking = db.selectOnly(db.entries)
       ..addColumns([db.entries.lotId])
       ..where(
         db.entries.entryType.equals('packing') &
             db.entries.status.isNotInValues([EntryStatus.rejected, EntryStatus.undone]) &
             db.entries.lotId.isNotNull(),
       );
     await (db.delete(db.lots)
           ..where(
             (l) =>
                 l.lotId.isInQuery(namedBy(db.entries.lotId)).not() &
                 (l.status.equals('ready_for_sale') & l.lotId.isInQuery(standingPacking)).not(),
           ))
         .go();
     ```
     In the D-029 robustness test add a lot `lot-r` with status `ready_for_sale` and a packing entry set to
     `EntryStatus.confirmed`, and expect `['lot-1', 'lot-r']`. Add to the D-029 comment's COMPROMISE: "B still sees
     A's ready lots in Sell until intake (Sell/Money/Log are not scoped by farmer; TODO)". Adjust the
     `_forgetPulledRows` doc line to name the ready-lot exception.
   - **If we skip it:** On every shared family phone, one sign-in by another member silently takes away the packed
     farmer's QR. The farmer cannot sell from the app until an officer sorts it out by hand. If the Orchestrator
     prefers the stricter privacy (B never sees A's QR), record this as a known compromise in the D-029 comment and
     TODO.md instead; it must not stay silent.

2. **The photo-step purge has no test** (`apps/mobile/lib/features/event_log/camera_step.dart:L141-149`)
   - **What this is:** After each photo the camera step runs `purgeIfLow`, shows "Phone is full" when it returns true,
     and then goes on to the GPS wait or the confirm screen.
   - **Problem:** FlowHarness now answers "free space unknown" for every widget test (an honest fix: the real channel
     never answers in the fake-async zone). But no test passes a low value through the photo step, so this new branch
     (sheet, then `if (!mounted) return;`, then accept) is never run. A regression that leaves the step stuck after the
     sheet, or that skips the sheet, would pass the whole suite. The worker names this in the report's risks.
   - **Fix:** One widget test in `apps/mobile/test/features/low_storage_test.dart` (the farmer home's start check makes
     the first call, so it gets room):
     ```dart
     testWidgets('a full phone after a photo: the photo step opens "Phone is full", then the flow goes on', (tester) async {
       var calls = 0;
       final h = FlowHarness(freeBytes: () async => calls++ == 0 ? 200 * mib : 50 * mib);
       await h.start(tester);
       expect(find.text('Phone is full. Send your entries now?'), findsNothing);
       await h.tap(tester, find.text('Log'));
       await h.tap(tester, find.text('Sowing'));
       await h.tap(tester, find.text('Take photo'));
       expect(find.text('Phone is full. Send your entries now?'), findsOneWidget);
       await h.tap(tester, find.text('Send now'));
       expect(h.kicks, 1);
       await h.tap(tester, find.text('Correct'));
       expect(h.path, '/home/saved');
       await h.dispose(tester);
     });
     ```
     (`h.tap` counts and settles; the steps are those of the existing "from home through Log → grid" test in
     screens_test.dart.)
   - **If we skip it:** The acceptance line "prompt + purge" is proven only at app start; the per-photo path, where a
     farmer actually fills the phone, is proven only by Q01 on a device.

## Nice to have

3. **The purge redoes all work on every photo while the phone stays full** (`apps/mobile/lib/core/db/daos/media_dao.dart:L95-101`)
   - **What this is:** `purgeConfirmed` calls `purgeFullSize` for every `done` row: one select, one update and two file
     checks per row.
   - **Problem:** While free space stays under 100 MiB, every photo sweeps every confirmed photo again and overwrites
     its `purgedAt` (the original "deleted on confirm" time is lost; nothing reads the value today, only null or not).
     An officer phone with about 1 000 confirmed photos does about 2 000 queries before the step moves on.
   - **Fix:** Write `purgedAt` only where it is null in one statement, then delete the files of the `done` rows:
     `await (update(media)..where((m) => m.uploadStatus.equalsValue(UploadStatus.done) & m.purgedAt.isNull())).write(MediaCompanion(purgedAt: Value(now)));`
     followed by the existing file loop over `done` rows (no per-row select/update).
   - **If we skip it:** A slower photo step on a full officer phone; no wrong result.
