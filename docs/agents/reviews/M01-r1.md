## /ponytail-review output (skill `ponytail:ponytail-review`, trimmed)

**What this change does:** It adds the phone's offline database. That is 14 SQLite tables via Drift, two triggers
that stop saved entries from being edited or deleted, and small DAOs (data access objects) for saving entries,
queueing them for sync, uploading photos and reading pulled data. It also commits a schema dump and a test that
fails when the tables change without a new dump.

**Must fix**

1. **The append-only guard can be bypassed by REPLACE** (`lib/core/db/tables/append_only.drift`, `database.dart:96-98`)
   - **What this is:** Two triggers block UPDATE of an entry's facts and DELETE of an entry.
   - **Problem:** `INSERT OR REPLACE` deletes the old row and inserts a new one. SQLite fires delete triggers for
     that implicit delete only when `recursive_triggers` is on, and it is off by default. The probe overwrote a saved
     payload with no error. In Drift this is one call away: `into(entries).insert(row, mode: InsertMode.insertOrReplace)`.
   - **Fix:** In `beforeOpen`, add `await customStatement('PRAGMA recursive_triggers = ON');`. Extend the existing
     guard test with a REPLACE case. The probe shows the REPLACE then aborts and save, confirm and undo still work.
   - **If we skip it:** A future DAO or a "re-save" shortcut can silently rewrite a farmer's recorded facts before
     they reach the server.
2. **An entry left in `sent` by a killed app is never sent again** (`entries_dao.dart` `markSent`, `outbox_dao.dart` `resetStaleSending`)
   - **What this is:** `markSent` moves the entry's outbox row to `sent` while the request is in flight.
     `resetStaleSending` is the start-up kill-safety check.
   - **Problem:** `resetStaleSending` only resets `sending`, and `nextBatch` only picks `waiting`. If the app dies
     between `markSent` and the acknowledgement, the row stays `sent` forever. The probe showed reset=0 and
     nextBatch=0 one hour later and 30 days later, with pending=1. The entry never reaches the server. The same
     holds for a media row whose PUT finished before the confirm call.
   - **Fix:** Reset both states: `o.status.isInValues([OutboxStatus.sending, OutboxStatus.sent])`. `markSent` does
     not touch `nextAttemptAt`, so it still holds the attempt start that `markSending` wrote. Add one test: markSending,
     then markSent, then resetStaleSending at +6 min, then nextBatch returns the row. A resend is safe because the
     server deduplicates by client id (D-005).
   - **If we skip it:** Entries stay on the phone forever. The farmer sees a grey cloud and, after 7 days, the red
     triangle, and an officer has to intervene.

**Should fix**

3. **`nextBatch` hands out photos whose entry is not confirmed** (`outbox_dao.dart:31-50`)
   - **What this is:** It is the single "what to send next" query for M02.
   - **Problem:** Media rows come back whenever they are due. That includes a rejected entry's photo, which stays
     `waiting` forever (probe d2), and the photo of an entry that is still in backoff. Without a presigned URL the
     photo cannot actually be uploaded, so this is not an upload of rejected evidence. Still, M02 gets a row it must
     not send, and that row cycles through backoff forever.
   - **Fix:** Pick one. (a) Make `nextBatch` return entries only (`outbox.kind.equalsValue(OutboxKind.entry)`) and
     let M02 use `MediaDao.pendingUploads` for photos, which §3 already describes. (b) Add
     `entries.serverReceivedAt.isNotNull()` for media rows by joining the media row's entry. In either case,
     `markRejected` should also move that entry's media outbox rows to `needsAttention`.
   - **If we skip it:** M02 has to rediscover and re-filter this. Otherwise every sync run wastes a batch slot on
     unsendable photos.
4. **The timing test has thin headroom on CI** (`test/db/entries_dao_test.dart:20-39`): it took 1.4 s alone and
   1.72 s in the full suite against a 2 s limit, and CI runs `flutter test` on a shared ubuntu runner. Fix: tag it
   `@Tags(['perf'])` and add `-x perf` in CI, or keep the 2 s assertion only when `Platform.environment['CI'] == null`.
   The binding number is the Verifier's on the AVD.

**Nice to have**

5. **`latestVersions` scans the whole Entries table for each row** (`entries_dao.dart:83-91`): `supersedes_entry_id`
   has no index. Use `n.rootId.equalsExp(e.rootId) & n.version.isBiggerThan(e.version)`, which the unique
   (rootId, version) index serves and which gives the same result for a linear chain. Case: an officer phone with
   20k entries and a lot with 30 events gives about 600k row reads per screen open.

Verdict: fix 1 and 2 first.
Lean: about 0 lines. Nothing speculative; the small read-only DAOs each name a planned caller.

## Findings

### P1
None.

### P2
- **P2-1 The append-only triggers can be bypassed by `INSERT OR REPLACE`** (ponytail #1).
  - Fix: one line, `PRAGMA recursive_triggers = ON` in `beforeOpen`, plus a test case. Verified on the copy.
  - Why this is not P1: no code path in this WP uses REPLACE on `entries`. The server keeps its own triggers
    (D-005), and the product today has no bypass. The phone-side guard is incomplete, though, and the fix costs one
    line.
- **P2-2 Kill-safety misses `sent`**: an outbox row in `sent` is never retried (ponytail #2).
  - Fix: one predicate, plus a test.
  - Why this is not P1: the row stays on the phone and stays counted. Nothing is deleted.

### P3
- **P3-1 Perf test headroom and representativeness.** The test is 1.4 to 1.72 s against 2 s, on an in-memory
  database. Tag it `perf`, or skip it on CI (ponytail #4). Note for the Verifier: 500 separate transactions on a
  file-backed database pay a commit each. Measure with `AppDatabase.open()`-style file storage, not
  `NativeDatabase.memory()`.
- **P3-2 Linux CI and SQLite.** sqlite3 2.9.4 opens `libsqlite3.so` on Linux (`load_library.dart:60`). The
  unversioned name ships with `libsqlite3-dev`. `test/db` has never run on the ubuntu job. If the first CI run fails
  with "Failed to load dynamic library 'libsqlite3.so'", add `sudo apt-get install -y libsqlite3-dev` before
  `flutter test`.
- **P3-3 No CI freshness check for generated Drift code.** `schema_dump.sh` has no check mode.
  - Case: someone edits `tables/*.dart` without regenerating. The stale `.g.dart` and the dump then agree with each
    other, so `schema_test` stays green.
  - Fix: a CI step that mirrors the `gen_api.sh` one,
    `tool/schema_dump.sh && git diff --exit-code -- lib/core/db test/db`. It took 1 min 46 s here.
- **P3-4 `nextBatch` mixes in unconfirmed media** (ponytail #3).
  - Judgement on the brief's question: this does not break "entries first, photos second". Within one batch,
    entries sort first. A photo also cannot be PUT without the presigned URL that only an acknowledgement stores.
  - So it is **not** an upload of a rejected entry's photo, and I kept it at P3. It is a contract wart that M02
    would inherit. Fix it in round 2 together with P2-2.
- **P3-5 `latestVersions` cost** (ponytail #5).
- **P3-6 Enum names on disk are camelCase** (`needsAttention`, `lowAccuracy`, `fieldOfficer`), but the wire format
  and §2 are snake_case. That is fine for a local store. M02 must map them explicitly: sending
  `locationStatus.name` would post `lowAccuracy`, which the server rejects with 422. This is a heads-up for M02's
  brief and needs no change here.
- **P3-7 The date storage choice has no DECISION number.** ISO text with milliseconds, compared through
  `julianday()`, is justified in `build.yaml` and the README. I verified the drift source,
  `expression.dart:443` and `comparable.dart:113`, and probe f. Changing it later means migrating every date
  column. Orchestrator's call: either assign D-026 (one ADR line) or accept the `build.yaml` comment.
- **P3-8 TODO.md was not updated.** The acceptance documentation line asks for it, and §7 lets workers and
  reviewers append. Candidates for the Orchestrator to add:
  - The `AppDatabase` Riverpod provider and `SessionDao` (M06).
  - The MediaDao setter for presigned URLs and the `uploading`/`failed` setters (M02).
  - Write DAOs for the pulled tables (M02 pull).
  - Session tokens in plain SQLite versus the keystore (M06).
  - A device run of `AppDatabase.open()` with a background isolate (M02 or the Verifier).
  - The CI perf tag (P3-1).
- **P3-9 Sending media is not M02-ready yet.**
  - §3 says the acknowledgement "stores presigned URLs". No DAO method writes `uploadUrl` or `uploadUrlExpiresAt`,
    and there is no `uploading`/`failed` setter.
  - I accept this, in line with Ponytail: M02 adds them together with their caller. I list it so M02's brief says
    so.
