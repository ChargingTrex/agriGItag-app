## What this change does

It adds `/batches` (status filter in the URL, cursor paging with Load more) and grows `/batches/:id` into the full
batch page. The page shows readings with source and instrument, the latest grade computation with the standard
edition, and Approve with graded kg. It adds final packing (packed ≤ graded kg, best before ≥ pack date) and
Publish → 202 → builds polled every 2 s → public URL, QR (fetched with the token, shown as a `data:` URL), labels
download, a sandboxed preview, and the builds history with Rebuild. A new `GatedButton` puts the reasons of a greyed
button next to it and in its accessible name. `gateReasonText` labels every B09/B10 reason code. MSW handlers
model the B09/B10 gates, including D-041 until B16 merges.

## Correctness checks

- **Approve greyed from stored data + server reasons:** `approveReasons` (batchModel.ts) reads `GradeOut.status`
  (`incomplete` → `grade_incomplete` with the missing parameters sorted, `declared_above_computed` with declared and
  computed), `null` (404) → `not_graded`, plus role and holds. Same codes and context as `service.approve_grading`.
  The 409 answer is shown under the button with the same labels (`GateReasons` → `gateReasonText`). OK.
- **Final packing ≤ graded:** zod refine on grams (`toGrams(v) <= gradedGrams`), best before ≥ pack date; the server
  re-checks (`packed_above_graded`). OK.
- **Publish → 202 → polling:** `refresh` invalidates `['batches', id]`, the batch turns `published`, the builds
  query starts and re-reads every 2 s while a build is `queued`; `failed` shows the field paths; a later `built`
  shows the live block. Builds are listed oldest first (`ORDER BY id`, UUIDv7), so `items.at(-1)` is the newest. **No
  timeout, and Rebuild is greyed while any build is queued: P2-1.**
- **Rebuild admin-only:** `fpo_admin_only` reason for non-admins; tested (:448). OK.
- **D-041:** `batchHolds` filters `GI_ONLY_HOLD_CODES` only when `giRequested` is false; anything else becomes an
  `open_hold_flag` reason (fail closed for unknown codes). The MSW gates do the same. Matches D-041 §1–3. OK.
- **Per-share lot reads:** one cached `GET /v1/lots/{id}` per share for the plot id, marked `shortcut:` with its
  limit (BatchPage.tsx:446). A batch has a few dozen lots at pilot scale, so this is a decision, not a finding.
- **`/batches`:** status in `?status=`, `useCursorList` paging; the mock pages with a cursor; tested (:551). Empty
  state wording with a filter: P3-7.
- **`GatedButton`:** reasons visible beside the button (not hover-only) and in `aria-label`; index-based keys, so two
  lots with the same hold do not collide. Separator: P3-3.

## Security and privacy

- QR: fetched through the API client (bearer token from memory, D-024), turned into a `data:` URL. The cache holds
  only the image, never the token. Labels: blob → object URL → anchor click → revoked (timing: P3-6). Nothing links
  `qr.png`/`labels.pdf` directly. OK.
- Preview iframe: `sandbox=""` (no scripts, forms, popups, top navigation or same-origin), a `title`, remounted per
  build number. `src` is the dev proxy only under `import.meta.env.DEV`, else the public URL. OK.
- `VITE_PUBLIC_BASE_URL` falls back to `window.location.origin`. In a production build without it, the link and the
  preview point at `{portal}/b/<code>`, which the portal's own SPA answers: wrong URL, blank preview. The ADR names
  the mismatch risk and the CSP `frame-src` need, but TODO.md has no line for either (P3-4).
- Failed build: only `loc` and `msg` are shown; B10 stores paths, never values. OK.
- No `dangerouslySetInnerHTML`, no storage writes, no phone or ID fields; farmer names only through
  `useFarmerNames` (name only); the tests assert no Indian mobile number in the page.
- Role checks are commented as previews (BatchPage.tsx:459, JSDoc "preview; the server answers 403"). OK.

## Findings

### P2-1: A build stuck in `queued` locks Rebuild and polls forever
`apps/portal/src/features/batches/PublishSection.tsx:191-192` and `:269-276`.
- **What it does:** the builds query re-reads every 2 s while *any* build is `queued`, and Rebuild is greyed with "A
  build is running; wait until it finishes." while the newest build is `queued`.
- **What goes wrong:** B10 leaves a row `queued` for good in real cases. `enqueue_page_build` only logs a broker
  failure, and after `max_retries=5` S3 failures "the row still stays queued" (B10 report P3-3). B09/B10 name
  `POST …/rebuild` as the recovery for exactly this. The portal greys that button, so the admin cannot recover from
  the UI. The open tab also polls the API every 2 s with no end. `some(...)` also keeps polling when an *older* build
  is stuck while the newest is built.
- **Fix:** (a) delete the "A build is running" reason (`:273-275`). Rebuilding while a build is queued is safe:
  `build_page` marks older queued builds `superseded`. (b) poll on the newest build only, with a cap:
  `refetchInterval: (q) => q.state.data?.items.at(-1)?.status === 'queued' && Date.now() - Math.max(publish.submittedAt, rebuild.submittedAt) < 120_000 ? BUILD_POLL_MS : false`
  (TanStack v5 mutations carry `submittedAt`; a page opened on an already-queued build then does not poll, which
  is fine once Rebuild is enabled). When it stops, show "The build is taking longer than expected. Press Rebuild to try again." in
  place of the progress bar. (c) add one test: a mock build that stays queued (e.g. `mockState.holdBuilds = true` in
  the builds handler) leaves Rebuild enabled.
- **If skipped:** one broker blip or S3 outage at publish leaves a published batch with no page and no way to retry
  from the portal.

### P2-2: The sign-off test now depends on `/v1/me` answering within 5 s (failed in my run 1)
`apps/portal/src/features/batches/batches.test.tsx:304` (same pattern at `:269-275`, which uses `/^Sign off:/` and is fine).
- **What it does:** `findByRole('button', { name: 'Sign off' })`, then waits for it to be enabled.
- **What goes wrong:** `GatedButton` gives a greyed button the name `Sign off: Checking who you are…` until `/v1/me`
  loads. The exact-name query therefore matches only once the button is enabled, and must do so within the 5 s
  `asyncUtilTimeout`. Before P04 the name was always `Sign off`. Run 1 failed with `Unable to find role="button" and
  name "Sign off"`.
- **Fix:** `const signOff = await screen.findByRole('button', { name: /^Sign off/ });` then
  `await waitFor(() => { expect(signOff).toHaveAccessibleName('Sign off'); });`. Same pattern for any other test that
  finds a `GatedButton` by exact label before its reasons clear. The happy path already does it for Approve
  (`approveButton()` + `waitFor(toBeEnabled)`).
- **If skipped:** the portal gate fails at random under CI load.

### P3-2: The gate preview turns green while the hold list or the lot reads are still loading or cut off
`apps/portal/src/features/batches/BatchPage.tsx:445-469`.
While `useHoldFlags` is pending, or its `complete` is false (more than 200 open/escalated holds), or a lot read has
not answered yet, `holds` is empty and Approve/Pack/Publish look available. The server still refuses (409), so this
is not a safety hole. But P02/P03 fail closed in the same case (`useLotHold` doc: "an empty `holds` does not prove
the lot is free"). Fix: when `holdFlags.isPending || holdFlags.data?.complete === false || lots.some((q) => q.isPending)`,
add one reason `'Checking hold flags…'` (as `signoffBlock` does with "Checking who you are…").

### P3-3: Reasons in the accessible name run together
`apps/portal/src/features/batches/ReadyLotsPage.tsx:146`: `reasons.join(' ')`. Hold labels have no full stop, so a
screen reader reads "Open hold flag: Yield above the ceiling Open hold flag: Plot outside the GI region". Fix:
`reasons.join('; ')`, and update the expectation at `batchDetail.test.tsx:531`.

### P3-5: LIBRARIES caller columns not updated for every library P04 uses

one by one and lack `features/batches/batchDetail.test.tsx`. Add them.

### P3-6: The labels object URL is revoked in the same task as the click
`PublishSection.tsx:100-102` revokes after `setTimeout(…, 0)`. Some browsers (older Safari, Firefox in some cases)
start the download after the click handler returns and can lose the blob. FileSaver.js waits 40 s for this reason.
Fix: `setTimeout(() => URL.revokeObjectURL(href), 40_000)`.

### P3-7: The empty state ignores the filter
`BatchesPage.tsx:74-82`: with `?status=published` and no published batch, the page says "No batch yet. Create one
from Ready lots" although batches exist. Fix: when `status` is set, show `No ${BATCH_STATUS[status].toLowerCase()} batch.`
and keep the Ready lots hint for the unfiltered list only.

### P3-8: The production preview branch is untested
Tests run with `import.meta.env.DEV` true, so only the dev-proxy `src` is asserted. One unit test of `pageUrls` with
`vi.stubEnv('DEV', false)` and `vi.stubEnv('VITE_PUBLIC_BASE_URL', 'https://trace.example')` would pin the switch
(export `pageUrls`, or assert through the rendered iframe).
