## What this change does

`run_gate_checks` now locks the batch row, then each lot row in id order, before it reads any facts.
`populate_existing` re-reads rows the session already had. So two checks of one lot run one after another,
and the later one always sees the flags the earlier one committed. No caller changed.

## Lock map (focus 1)

| Transaction | Rows it locks, in order |
|---|---|
| `run_gate_checks` (tasks `check_lot`/`check_event`, gates grading/packing/publish, seed) | batch → lots by id → flag rows (`store_flags` UPDATE) → lot UPDATE (`practice_tags`, hold) |
| `create_intake` (HTTP + push kind `lot_intake`) | lot `FOR UPDATE` → `run_gate_checks(lot)` (same lot) |
| `create_batch` | lots by id `FOR UPDATE` → new batch (nobody else can see it) → `run_gate_checks(new batch)` |
| `publishing.rebuild` / `build_page` | batch only |
| sync push event entry (`_add_version`) | event `FOR UPDATE` (v2+); FK `KEY SHARE` on lot/batch (v1). Never a lot lock |
| **`resolve_flag` (HTTP + push kind `flag_resolution`)** | **flag row (autoflush) → lot row (`_sync_lot_hold` UPDATE)** |

Every row is consistent with batch → lots-by-id except the last one. That is P1-1.
Push semantics (B06): push never calls `run_gate_checks`, each entry still commits on its own, and
`test_sync.py` passes. The mixed-batch case (#2 rejected, #1/#3 accepted) holds.

## Must fix

1. **A reviewer and a running check deadlock** (`rules_flags/service.py:699-732` `resolve_flag`, against
   `run_gate_checks` L533-543)
   - **What this is:** An admin marks a lot hold "fixed" in the portal or from the phone. In the same moment,
     the check started by the farmer's correction finds the rule no longer fires and closes the same flag.
   - **Problem:** The check holds the lot lock and waits for the flag row. The reviewer has already written
     the flag row (autoflush in `session.get(Lot)`) and waits for the lot row (`gi_eligible` restored).
     Postgres kills one after 1 s. If it kills the reviewer, the request gets a 500, or the whole push answers
     500. If it kills the task, the check is lost: rules tasks have no retry (`tasks.py`: "the task fails and
     is logged"). So any new flag that run would have raised stays missing until the lot's next event. The
     worker report says "task/push fails and is retried"; that is not true for tasks. On `main` both took the
     flag first, then the lot, so this deadlock is new. A correction and a reviewer's "fixed" usually happen
     together, so this sequence is a normal one.
   - **Fix:** In `resolve_flag`, take the lot lock before touching the flag, then re-read the flag:
     ```python
     flag = await _scoped_flag(session, user, flag_id)
     # Lot row, then flag rows, as `run_gate_checks`: the reverse order deadlocks with a running check.
     lot = None
     if flag.subject_type == FlagSubject.LOT:
         lot = await session.get(Lot, flag.subject_id, with_for_update=True, populate_existing=True)
         await session.refresh(flag)  # a check may have closed it before we got the lock
     check_resolution(user.role, flag, body)
     ...
     if lot is not None:
         await _sync_lot_hold(session, lot)
     ```
     Mention the lock in `Side effects:`. A check that closed the flag first now makes the reviewer get 409
     `flag_not_open`. That is the truth, and better than overwriting `rule_passed`. Flags on events, readings
     and batches never touch a lot or batch row in the reviewer's transaction, so they need nothing. Add the
     test (it is the probe I ran; it failed with `deadlock detected` and passes with the fix):
     ```python
     async def test_reviewer_and_check_of_one_lot_do_not_deadlock(world, monkeypatch):
         # hold at 1,350 kg; correct to 1,150 kg; check A pauses after _lot_context (holding the lot lock);
         # reviewer R resolves the hold "fixed" in its own session; release A after 0.5 s;
         # gather(A, R, return_exceptions=True): no DBAPIError; flag ends FIXED (A's rule_passed or R's).
     ```
   - **If we skip it:** Now and then, a reviewer action returns 500, or a rules run is lost without any sign.
     Nobody reports either one, because the next action works.

## Should fix

2. **Sync push waits for every running check of the same lot** (`rules_flags/service.py:535,542`)
   - **What this is:** `FOR UPDATE` is the strongest row lock. When you insert a row whose foreign key points
     at the lot, Postgres takes a `KEY SHARE` lock on the lot row, and `FOR UPDATE` blocks it.
   - **Problem:** A push with several new events on one lot commits entry 1 and enqueues `check_event`. While
     that check runs, entry 2's `INSERT INTO events (lot_id=…)` waits for it. My probe: the insert ran into a
     500 ms lock timeout while a check held the lot. The same goes for intakes, quality readings, batch shares
     and page builds on a locked batch. Every following entry can wait a full check. That eats into BM-07
     (p95 ≤ 300 ms). Nothing in the fix needs to block these inserts: only other checks must wait.
   - **Fix:** On both `session.get` calls, use `with_for_update={"key_share": True}` (that gives
     `FOR NO KEY UPDATE`). It still conflicts with itself and with the `FOR UPDATE` that `create_intake` and
     `create_batch` take, so B16-1 stays closed. With it, the rules + lots_batches + sync suites pass (41,
     including the new stale test). Use it in the P1-1 fix too, and for P2-2.
   - **If we skip it:** Under load the push gets slower. The more events per lot in one push, the worse.

3. **`check_event` can still close an event flag it could not see** (`rules_flags/service.py:594-603`)
   - **What this is:** Each `events.verify_photo` enqueues `rules.check_event` for the event, even when the
     photo checks out. So an event with two photos always gets two runs at about the same time.
   - **Problem:** Run 1 reads the photos before photo 2's `checksum_mismatch` is committed. Run 2 raises the
     photo flag and commits. Then run 1's `store_flags` closes it `rule_passed`. This is the same bug as
     B16-1, for event codes (photos, GPS, clock skew). TODO says it only happens for "two runs of the same
     event (D-009)". In fact it is the normal path for every event with more than one photo.
   - **Fix:** One line: `event = await session.get(Event, event_id, with_for_update={"key_share": True})`.
     The lock order becomes event → batch → lots. No other transaction holds a lot or batch and then waits for
     an event: push v2 holds only the event, and the reviewer of an event flag holds only the flag. A
     correction push on the same event waits for the running check (short). Then delete the TODO line.
     Test: the same pause pattern on `_event_context`, with a second session that marks a photo
     `checksum_mismatch` and runs `check_event`. The photo flag must end open.
   - **If we skip it:** The system marks a bad evidence photo flag as fixed, and no reviewer ever sees it.

## Other checks (no finding)

- `with_for_update` + `populate_existing` on `session.get` gives `SELECT … FOR UPDATE`, and the lock refreshes
  the batch that grading, packing and publish had already loaded. So their status checks now see the
  committed status: a side win against a double publish. The select autoflushes first, so the caller's
  pending lot changes (intake, batch) are not lost.
- A lot with no batch: the path is unchanged. A missing lot: `session.get` returns None and the loop skips
  it. `NoResultFound` cannot happen.
- Deadlock between two checks: each transaction locks at most one existing batch, and locks it first. Lots
  always go in id order, as in `create_batch`. So there is no cycle, even when a lot is shared by two batches.
- Seed (`seed/demo.py:400`): one transaction, one batch, nothing runs alongside it. Still idempotent, and
  only one lock per row more.
- Docs: `run_gate_checks` `Side effects:` names the lock; the callers say "as `run_gate_checks`". The
  CHANGELOG line is present. Ponytail: the diff is 14 lines of code for the fix, nothing extra.
