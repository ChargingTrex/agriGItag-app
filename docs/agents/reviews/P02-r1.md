## What this change does

It adds `/flags` (a filtered, cursor-paged list), `/flags/:id` (rule details per family, lot GI state, evidence thumbnails, and a resolve form
gated by role) and `/lots/:id` (hold state, the lot's flags, photos). It adds a plot review form under the P01 plot map that calls
`POST /v1/plots/{id}/correct`, plus the farmer's plot list with a link to their flags. MSW handlers cover the B08/B14 endpoints.

## Review points checked

- **Filters:** status, severity and assignee go to the server (B08 query params). Rule and subject are filtered in the browser over the
  loaded pages, marked `shortcut:` (`FlagsPage.tsx:208`), with a TODO line to B08 and an info alert. B08 has no `subject_id`/`rule_code`
  param, so this is acceptable. The only gap is the empty-state wording (P3-2).
- **Cursor paging:** reuses `useCursorList` (`has_more` → `next_cursor`), per conventions. Tested with 60 flags (50 + "Load more" → 60).
- **Severity:** glyph (■ ▲ ●, `aria-hidden`) + MUI colour + word ("Hold"/"Warning"/"Info"). Colour is never the only cue.
- **en/ta labels:** every B08 rule code (20 codes match `rules/*.py`), `lang="ta"` on the Tamil line, readable fallback for unknown codes.
  The Tamil text is the worker's own (`shortcut:` + TODO for a native-speaker review).
- **Dates:** "14 Feb" via `dayMonth` (tested), but the result depends on the browser's time zone (P3-1).
- **Resolve form:** zod requires `resolution` and `reason_code`. The note is trimmed and sent as `null` when empty. Reason codes are a portal
  list: no reason registry exists (`apps/api/config/*.yaml` has none, and the API takes any ≤ 64-char code). The role gate in `resolveBlock`
  matches `rules_flags/service.py:check_resolution` exactly: only field_officer/fpo_admin may resolve, and an officer may not resolve a hold
  or an escalated flag. The officer sees the button disabled with the reason (tested). Server 403/409/422 codes are mapped through
  the generated `error-messages.ts` (`flag_not_open`, `resolution_forbidden`, `reason_required` are in error-codes.md).
- **Refresh without reload:** a resolve invalidates `['flags']` + `['lots']` and a plot review invalidates `['plots']` + `['flags']`, so the
  list, the detail, `useLotHold` (`['flags','holds']`) and the lot table (`['flags','all']`) all refetch. Tested.
- **Plot review:** shown for every `location_status !== 'confirmed'` (needs_review, near_edge, outside). Requires outcome, method and reason.
  The pin is optional, with both-or-neither and range checks (`Number('abc')` → NaN → rejected). The form is admin-only on the client and
  the server (B14 correct is FPO admin only). Body fields match `PlotCorrection` (`review_outcome`, `review_method`, `pin`,

- **Held state fallback:** see P2-1.

## Findings

### P2 (fix before P03 relies on it)

**P2-1. A held lot can show as "GI eligible … can be ticked" when the FPO has more than 200 hold flags** (`apps/portal/src/features/flags/LotPage.tsx:36-43`, `:56-62`)
- **What it does:** `useLotHold` reads one page of `GET /v1/flags?severity=hold&limit=200` and keeps the open/escalated holds on this lot.
- **Problem:** the request has no status filter, so cleared and fixed holds use up the 200 slots. The API sorts by `Flag.id desc` (newest
  first). Concrete case: a season with more than 200 lot holds, most of them cleared, and one early hold on lot X still open. That flag is on
  page 2, so the page says "GI eligible: no hold flag, so this lot can be ticked for a GI-labelled batch". The `shortcut:` comment names the
  200 limit, but not that the failure is silent and fails open on a compliance claim. P03 will copy this behaviour.
- **Fix (about 3 lines):** fail closed when the page is truncated. In `select`, return `{ holds: activeHolds(page.items, lotId), complete: !page.has_more }`.
  In `LotHoldState`, when `!complete && holds.length === 0`, show a warning: "GI state unknown: too many hold flags to check here; open
  this lot's flags". Optionally pass `status: 'open'` to cut most closed holds; escalated holds are rare and the `has_more` guard covers
  them. Also say "no hold flag on this lot" instead of claiming it "can be ticked", because B09's own reasons and plot holds are not visible
  here (already in TODO).
- **If skipped:** an admin is told that a held lot is GI-eligible. B09 then creates the batch with `gi_verified=false`, which surprises the
  admin, and the label and export flow sees a batch the admin thought was GI.

### P3 (cheap; fix in r2 if touching the files)

**P3-1. Dates depend on the browser time zone** (`flagModel.ts:170-171`). Date-only `occurred_on` values (`'2026-02-12'`) parse as UTC
midnight. Reviewer check: `TZ=America/New_York` prints "11 Feb" for `2026-02-12`, and `2026-02-14T20:00Z` prints "15 Feb" in IST. The
tests `flags.test.tsx:159,338` therefore fail on any runner west of UTC. Fix: add `timeZone: 'Asia/Kolkata'` to the
`toLocaleDateString` options (pilot FPO, D-017 can make it a setting later). One line, and the tests become deterministic.

**P3-2. A browser-side filter with no match on the loaded pages reads "No flags to show."** (`FlagsPage.tsx:271-288`). The flags exist on
a later page. Also, the alert says "one farmer or lot" when the link came from a plot, and the farmer link (`FarmerPage.tsx`) includes only
plot flags, not the farmer's lot/event flags. Fix: when `rule || subjects.length` and `rows.length === 0 && list.hasNextPage`, show "No
match in the flags loaded so far; Load more to search further". Change the alert to "Showing flags of the selected plots or lot only".

**P3-3. The plot review note allows 1000 characters, but `PlotCorrection.reason_text` has `maxLength: 500`** (`PlotReview.tsx:58`). A
note of 501 to 1000 characters passes the client check and gets a 422 `validation_error`. Fix: `.max(500, 'Keep the note under 500
characters.')`. (`FlagResolveIn.note` allows 2000, so the resolve form's 1000 is fine.)

**P3-4. An FPO admin is offered "Escalate to the FPO admin"** (`FlagPage.tsx:213-217`). On an escalated flag the server records it and
the flag stays escalated, so nothing happens. Fix: omit the `escalated` option when `session.roles` includes `fpo_admin`
(`Object.entries(RESOLUTIONS).filter(([v]) => v !== 'escalated' || !isAdmin)`).

**P3-5. `DECISION D-006` is a loose fit** (`flagModel.ts:188-191`). D-006 is about rule evaluation (the phone previews, the server is the
authority), not authorization UI. A disabled button that mirrors a server role check is ordinary UI and needs no ADR. Either keep it
(the "client preview, server authority" spirit matches and doc-coverage passes) or turn it into a plain `// Mirrors check_resolution in
rules_flags/service.py; the server re-checks (403 resolution_forbidden).` comment. Reviewer preference: plain comment. **No new DECISION
is needed.**

**P3-6. The `required fields block submit` test removes MSW listeners only on success** (`flags.test.tsx:178-186`). If an assertion fails,
the `request:start` listener leaks into later tests. Fix: move `server.events.removeAllListeners()` into a `try/finally` or an
`afterEach`.
