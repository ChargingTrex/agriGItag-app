# M10 review, round 1: Officer home, assist mode, flags, moisture reading

Reviewer: MOB + SEC Reviewer (Opus), 2026-10-31. Branch `worktree-agent-ab5f84b433e902efe` at 1f1c583, diffed against
`git merge-base main HEAD` = bd1af16. I did not change any code or tests.

## Verdict: **FAIL** (1 P1, 1 P2, 9 P3)

The design is sound. It is one guarded `/assist/:farmerId` scope over the M07 screens. The guard checks the running
session, the bar is drawn once at app level, a new UUIDv7 session id is minted on every start, and that id is put on
every assisted entry. Every gate is green on a full run: 663 tests, no reruns. The PASS is blocked by two things:

- **P1:** the assist session survives sign-out and session expiry. The next user on a shared phone inherits it.
- **P2:** after the server reopens a flag, the officer's phone hides it forever.

## Findings

### P1

**P1-1: Assist mode survives sign-out and session expiry. The next user on the phone inherits another farmer's
session.** `lib/features/officer_assist/assist_controller.dart:56-59`. Other places affected: `lib/app.dart:30,50`,
`event_log_controller.dart:81-84,220-226,487`.

- **Cause:** `AssistNotifier.build()` returns `null` and depends on nothing. `SessionNotifier.signOut()` / `_endLocally()`
  (`core/router/session.dart:289-297`, also the 401 refresh path at :271) never touch `assistProvider`. Grep confirms
  that only `start`/`end` change it.
- **How it happens:** The officer assists Murugan and opens Settings from the assisted home. The bar is shown there, as
  the test at `officer_test.dart:158` asserts. The officer taps **Sign out**.
- **What follows:**
  1. The "Logging for: Murugan" bar stays on `/auth`.
  2. A farmer then signs in on the same shared phone. The farmer's home shows Murugan's bar and Murugan's next task
     (`nextTaskProvider` prefers `assistFarmerProvider`), which leaks one farmer's data to another.
  3. Every farmer button goes through `farmerPath` to `/assist/farmer-1/...`, and the role redirect sends it back to
     `/home`. The farmer cannot log anything.
  4. An F17 deep link `/log/harvest` loads **Murugan's** lots (`activeLots` filters by the assisted farmer). It saves
     with `assistMode=true` and the officer's `assist_session_id`. The server rejects that entry with
     `assist_session_invalid`, because the session belongs to another caller. The farmer's entry is lost to
     needs-attention.
  5. If a second officer signs in, all of their entries carry officer 1's session and are rejected the same way.
- **Rules broken:** CLAUDE.md §6 (assist mode is recorded only on the entries it creates) and §6 privacy.
- **Fix (one line, plus one test):** reset the session whenever the signed-in role changes. Sign-out always passes
  through `null`.
  ```dart
  @override
  AssistSession? build() {
    ref.watch(sessionProvider.select((s) => s.role)); // sign-out / expiry / new user → no assist session
    return null;
  }
  ```
  (D-032 §5 allows the server session to stay open.) Test in `officer_test.dart`:
  1. Assist Murugan, then `/settings`.
  2. `runAsync(session.signOut)`.
  3. Expect `assistProvider` to be null and no `_bar` on `/auth`.
  4. Sign in as a farmer, tap Log, expect path `/log`.

### P2

**P2-1: A reopened flag stays hidden on the officer's phone forever.**
`lib/features/officer_flags/flag_actions.dart:62-68`.

- **Cause:** `officerFlagsProvider` leaves out every flag that has a `flag_resolution` entry in any status except
  `rejected`. That includes `confirmed` entries, kept forever.
- **Why it matters:** B08 reopens the **same flag id**. `rules_flags/service.py:115-128` `reopens()` does so when the
  rule fired again after `rule_passed`, or with a **higher severity** than the one the reviewer closed. Example: the
  officer marks a `warn` "Looks fine", later evidence makes it a `hold`, and the pull mirrors it as `open`/`hold`.
- **Effect:** the local confirmed resolution still matches, so the new hold never shows in the list or in "Flags to
  clear: n". The worker's own description is "hidden until the pull", and that is only true for unsent resolutions.
  After the pull, the server status must win.
- **Fix:** hide only while the resolution has not been acknowledged:
  ```dart
  ..where(db.entries.entryType.equals(flagResolutionEntryType) &
      db.entries.status.isInValues([EntryStatus.saved, EntryStatus.sent]))
  ```
  Add a test: a `confirmed` `flag_resolution` for `warnFlag` while the mirrored flag is `open` → the flag is listed.
  This is also more honest: a `confirmed` resolution means the pull will bring the server's status.

### P3

1. **Decision number collision.** D-034 belongs to B10 on main. The brief said to renumber to D-043, but the main
   working tree now has an uncommitted **D-043** from the Architect-Gate ("Farmer tap counts…", `docs/adr/D-043.md`,
   DECISIONS.md row). So M10 needs the **next free number, D-044**, unless the Orchestrator assigns another. Places to
   change:
   - `lib/app.dart:46`
   - `lib/core/router/app_router.dart:182`
   - `docs/adr/D-034.md`: rename the file, change the title and the grep line 49
   - `DECISIONS.md:41`
   - `TODO.md:143`
   - `docs/LIBRARIES.md:95` (go_router row)
   - `docs/agents/reports/M10.md:4,13,14`
2. **Leaving the assist scope without "End assist" keeps the session running.** The bar then shows over the officer's
   own screens.
   - **How:** `NotFoundScreen`'s Home button calls `context.go('/')`, which goes to `/officer`. The same happens with
     any hard-coded `/home…` push, for example M08's `history_screen.dart:100,154`, because the role redirect sends it
     to `/officer`. The session is not ended and no `/assist/end` is sent.
   - **Fix:** in `_OfficerHomeScreenState.initState` add
     `WidgetsBinding.instance.addPostFrameCallback((_) => ref.read(assistProvider.notifier).end());`. Assist is
     entered with `context.go`, so the officer home is never under a running session.
3. **"Fix it" writes the resolution after the correction, which can race the rule re-run.**
   `flag_actions.dart:118-178`.
   - **The race:** the correction commit enqueues `rules.check_event`. If the corrected value passes, `store_flags`
     marks the flag `fixed`/`rule_passed`. If that runs before the `flag_resolution` entry is processed (both are in
     one push, or the batch is split), the entry answers 409 `flag_not_open` and becomes `rejected`, "needs an
     officer", after a fix that worked.
   - **Fix option a:** write the `flag_resolution` first, then the correction. The officer-closed flag is not
     reopened at the same severity (`reopens()`), and the stale sweep only touches active flags. Update
     `officer_test.dart:227`.
   - **Fix option b:** write no resolution on Fix and let the rule close the flag. Rule which one at r2.
4. **A hold after "Fix it" looks untouched.** The flag stays in the list unchanged, and nothing says it was corrected,
   so the officer may correct it again and write version 3. Fix: on the detail screen, show one line ("Corrected, the
   FPO admin clears it") when `flaggedEntryProvider`'s latest version was entered by this officer and is not yet
   `confirmed`.
5. **Deactivated meters stay on the phone.** `moisture_screen.dart:57-71` only upserts. A meter deactivated on the
   server stays a choice, and its reading is rejected with `validation_failed` ("instrument is inactive"). Fix: when
   the fetch succeeds, also run
   `b.deleteWhere(db.instruments, (i) => i.kind.equals(_moistureMeter) & i.instrumentId.isNotIn(fetchedIds))` in the
   same batch. M11's `qcInstrumentsProvider` reads the same table (see the merge notes and TODO item 3).
6. **"Today" is fixed when the provider is built.** `officer_home_screen.dart:35-36` computes `tomorrow` once. If the
   app stays open past midnight, "Today's visits" keeps yesterday's cut-off. Fix: rebuild it on resume, or accept it
   with a `shortcut:` line.
7. **`started_gps` can be stale.** `officer_home_screen.dart:67,84` uses the last fix of a stream that may be minutes
   old and from another village. It is audit-only, so either drop fixes older than about 2 minutes or note it as a
   `shortcut:`.
8. **Stale comment that M10 now depends on.** `core/sync/enum_wire_names.dart:45` still says `flagResolution` is
   "rejected by the pilot server with `not_implemented_pilot`". B08/B15 handle it now (`events/service.py:747`). This
   is an M02 file outside M10's diff, so add a TODO line or fix it in passing.
9. **For the backend, not M10.** The server's FR69 `entered_remotely` (`events/service.py:86-87,360-362`) uses fixed
   values, 100 m + 50 m. The `event_location` flag rule (`rules_flags/service.py:322-327`) uses the GI region's
   `tolerance_buffer_m`. The phone matches `entered_remotely` exactly (150 m, `Geolocator.distanceBetween`, test at
   140 m / 160 m), so the phone is right. The bundle's `tolerance_buffer_m` is the flag rule's value, not FR69's.
   Raise a TODO for B06/B08 to use one buffer.
