## What this change does

FPO admins now see a "Devices" section on a farmer's page when the farmer has an app login. It lists the
login's devices from `GET /v1/users/{id}/devices` (platform, app version, sign-in date, "active" or "signed out
<date>"). Each active device has a "Revoke" button. It opens an MUI dialog with an optional reason; "Sign out
device" calls `POST /v1/devices/{id}/revoke` and then reloads the list. The mock API gets both routes and two
seed devices on farmer #10.

## Focus checks (what holds)

1. **Role gate matches the server exactly.** The server's `_check_device_owner`
   (`apps/api/agritrace/modules/identity/service.py:786`) allows the user themself, else needs a membership in
   the caller's FPO (404 otherwise), else `caller.role == Role.FPO_ADMIN` (403 otherwise). `caller.role` is the
   session's single membership role from the JWT `role` claim, and the portal's `session.roles` is that same
   role plus `super_admin` when the flag is set (`TokenPairOut.roles`, `roles_of`). So
   `session.roles.includes('fpo_admin')` is true exactly when the server's role check passes. A super-admin who
   is not an FPO admin sees no section, and the server would 403 them too. The page only loads farmers of the
   caller's FPO, so the membership check passes for a normal farmer login. No role the server refuses ever sees
   "Revoke". Same gate variable as the P10 Reveal (`FarmerPage.tsx:158`).
2. **Privacy.** The row shows `platform`, `app_version` and two dates. `DeviceOut` has no phone, no model, no
   push token, no IP. The device UUID is used only as the React `key`; it is never in the page text. Nothing is
   logged. The list sits in the query cache under `['devices', userId]`; it holds nothing sensitive, and sign-out
   runs `queryClient.clear()` (checked in P10-r1), so no `gcTime: 0` is needed. The revoke mutation caches only
   `undefined` (204). OK.
3. **Dialog accessibility.** MUI 9.5 `Dialog` traps focus, closes on Escape and backdrop click (`onClose`), and
   sets `aria-labelledby` to the `DialogTitle` id automatically (`Dialog.js:274`, `DialogTitle.js:57`), so the
   dialog is announced as "Sign this device out?". The reason field has a real label (`getByLabelText` finds it).
   Errors use MUI `Alert`, whose default `role` is `alert`. The confirm button "Sign out device" names the action
   plainly; the row button is "Revoke". No restyle of the farmer page; the section copies the Plots section's
   `section` + `h2` + `Stack` shape. See P3-2 for focus after success.
4. **Mutation hygiene.** "Sign out device" is `disabled={revoke.isPending}`, so no double submit. `onSuccess`
   closes the dialog, clears the reason and returns `invalidateQueries`, so the list refetches after the 204.
   `unwrap` returns `undefined` on a 2xx with no body (`api/client.ts:70`). `revoke.reset()` on each Revoke
   click drops an old error. The reason is read at call time, trimmed, blank sent as `null`
   (`DeviceRevokeIn.reason` is `string | null`). OK.
5. **MSW mirrors the contract.** Seed rows are typed `Schemas['DeviceOut']` and carry every field
   (`id`, `platform`, `app_version`, `signed_in_at`, `last_seen_at`, `revoked_at`); typecheck would fail on
   drift. GET: 401 / 403 for a non-admin on another user / list; POST: 401 / 403 non-admin / 404 unknown / 204,
   `revoked_at ??=` keeps the first sign-out date like the server's `if device.revoked_at is None`. Known gap,
   disclosed by the worker: the mock POST refuses self-revoke, the server allows it. Unreachable from the
   portal (only admins get the button, on farmers' logins), so not a finding.
6. **Tests, docs, tracking.** Two of three new tests fail on main (above). JSDoc on `DevicesSection` with
   `@param` / `@returns`; on `seedDevices`; new constants and `mockState` fields documented; file headers updated

## Findings

### Nice to have

1. **P3-1: a reason typed for one device carries over to the next** (`apps/portal/src/features/members/FarmerPage.tsx:94-97`, `:108-111`)
   - **What this is:** the reason text is kept in `reason` state; only a successful revoke clears it.
   - **Problem:** an admin types "phone lost" for device A, presses Cancel, then presses Revoke on device B. The
     dialog opens with "phone lost" already filled in. If they confirm, B's `device.revoke` audit row says
     "phone lost". The text is visible, so this is a slip, not a silent bug.
   - **Fix:** in the row's Revoke `onClick`, next to `revoke.reset();`, add `setReason('');`. One line.
   - **If we skip it:** an occasional wrong reason in the audit trail.

2. **P3-2: keyboard focus is lost after a successful revoke** (`FarmerPage.tsx:66-71`, `:92-101`)
   - **What this is:** on close, MUI returns focus to the button that opened the dialog.
   - **Problem:** after a 204 that row's "Revoke" button is gone (the device is now signed out), so focus falls
     to `<body>`. A keyboard or screen-reader user is sent to the top of the page with no word that it worked.
     The page's "Approve as member" button has the same pattern, so this is a house habit, not new to P12.
   - **Fix:** give the `Devices` `Typography` `tabIndex={-1}` and a `ref`, and in `onSuccess` call
     `headingRef.current?.focus()` before `invalidateQueries`. About 3 lines.
   - **If we skip it:** a WCAG 2.4.3 (focus order) nit; axe does not flag it.

3. **P3-3: the reason field has no 500-character limit** (`FarmerPage.tsx:114-122`)
   - **What this is:** `DeviceRevokeIn.reason` is `maxLength: 500` on the server.
   - **Problem:** a 501-character reason gets a 422; the dialog shows the generic validation alert and the admin
     has to guess why.
   - **Fix:** add `slotProps={{ htmlInput: { maxLength: 500 } }}` to the `TextField` (MUI 9 form; `inputProps`
     is deprecated). One line.
   - **If we skip it:** a confusing error in a case nobody will hit often.
