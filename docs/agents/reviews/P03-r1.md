## Verdict: FAIL

One P1, one P2, seven P3s. All gates pass. The share rounding matches `shares.py` exactly: 20 007 cases, 0 mismatches.

The P1 is the acceptance line "out-of-GI greyed with tooltip". It passes only because the MSW seed holds a lot state that the real API
never produces. Against B08/B09 a lot whose plot lies outside the GI region stays `gi_eligible = true`, so it can be ticked into a GI
batch. Once created, that batch can never be published while the plot hold stays open. The fix is small. It costs no extra request: the
hold-flag list the page already loads holds the plot flags.

## What this change does

It adds `/ready-lots`. The page lists received lots (tickable) and ready-for-sale lots (greyed) with farmer name, packed kg and a GI chip.
Ticking shows a running total and a live share % for each lot. Greyed rows give the reason in a tooltip and in the checkbox's accessible
name. A non-GI switch, a processor select and "Create batch" (`client_id` made once per form) complete the form. A 409 lists every
`gate_not_met` reason. The change also adds `/batches/:id`: batch code, a QR placeholder until B10, the GI verdict, the final shares, and
second sign-off (waiting, disabled for the creator or a non-admin with the reason, enabled for another admin). MSW handlers cover lots,
batches, sign-off, features and `/v1/me`.

## Findings

### P1

**P1-1. Out-of-GI lots are not greyed against the real API. The acceptance test uses a lot state the server never produces.**
(`apps/portal/src/features/batches/batchModel.ts:73-83`, `ReadyLotsPage.tsx:231`, `apps/portal/src/mocks/handlers.ts:175-178`, `batches.test.tsx:136-143`)
- What happens: `lotBlock` greys a lot only when `gi_eligible` is false. Only B08 (`rules_flags/service.py:230-232`) ever sets it to false,
  and always with `gi_hold_reason = "flags: <codes>"`. B09 never writes `gi_hold_reason` (`lots_batches/service.py:9`). A plot outside
  the GI region raises a **plot** hold flag, `plot_outside_gi_region` (`rules/plot_checks.py:49`), and per B08 review P3-3 that flag
  "does not change the lot's `gi_eligible`". So the "Outside the GI region (…)" branch of `lotBlock` is dead against the real API. The
  real out-of-GI lot shows "GI eligible" and can be ticked into a GI batch. The seed lot at handlers.ts:175 (`gi_eligible: false`,
  `gi_hold_reason: 'plot outside the GI region'`) is a state no server path produces, so the acceptance test passes falsely.
- Why it matters: `create_batch` does not refuse it. The batch is created "GI not verified" and its lots become `batched`. The publish
  gate then refuses on every hold, plot holds included (`hold_reasons(flags)`, service.py:1162). The lots are locked in a batch that cannot
  be published while the plot hold stays open. This is FR29, the case the acceptance line names.
- Fix (no new request): `useLotHold` already loads every open and escalated hold flag of the FPO under `['flags', 'holds']`, and
  `activeHolds` compares only `subject_id`. Split the query out of `useLotHold` into `useHoldFlags()` in `features/flags/LotPage.tsx`
  (same key and fetch; `useLotHold` keeps its `select`). In `ReadyLotsPage`, build
  `heldPlots: Map<plot_id, rule_code[]>` from the active hold flags with `subject_type === 'plot'`. Pass `heldPlots.get(lot.plot_id)` to
  `lotBlock(lot, nonGi, plotHolds)`. Return "Outside the GI region. It can only go into a non-GI batch." for `plot_outside_gi_region` and
  "Plot on hold: <ruleText>." for any other plot hold. When `complete === false`, show one warning line ("Not every hold flag was loaded;
  the server re-checks GI when you create the batch"). Re-seed the mock out-of-GI lot as it really is: `gi_eligible: true`,
  `gi_hold_reason: null`, its own plot id, and an open `plot_outside_gi_region` hold flag (`subject_type: 'plot'`) in `seedFlags()`. Then
  keep the test at batches.test.tsx:136 as it is. Keep the non-prefixed branch only as a fallback for a future B09 reason, or delete it.
  Note in TODO that `plot_location_*` GI reasons (service.py:780) are still caught only after create.

### P2

**P2-1. A received lot without a packing event cannot be batched from the portal, although the server accepts it.**
(`batchModel.ts:71-72`, `ReadyLotsPage.tsx:162-165`)
- What happens: `lotBlock` returns "No packed weight recorded for this lot yet." when `lot.packed` is null. Packing is an optional farm
  event: `record_intake` sets the lot `received` with `packed_kg = farm.get(EventType.PACKING, lot.packed_kg)` (service.py:719), which
  may be None, and `create_batch` takes shares from intake kg only. A farmer who sells loose produce, or who logged no packing event,
  has a lot the admin can never tick. The portal is the only place batches are made, so there is no way round it. The worker names
  this as a risk, but it blocks a valid server path.
- Fix: delete lines 71-72. In `selected`, keep lots without a packed weight (send them in `lot_ids`). When any ticked lot has no
  `packed`, show "—" in its share cell, hide the other shares, and replace the preview line with "Shares are computed from the weight
  received at intake when you create the batch." One test: a received lot with `packed: null` can be ticked and its id is sent. The B09
  TODO line (`received` on `LotOut`) stays the real fix.

### P3

1. **Create is not greyed for non-admins.** (`ReadyLotsPage.tsx:191-196`) `POST /v1/batches` is `Admin` only (router.py:259). Office
   roles (field officer, QC, viewer) can sign in to the portal. They see an enabled "Create batch" and get the fallback "forbidden" text
   after the click. Fix: add `!session?.roles.includes('fpo_admin') ? 'Only an FPO admin can create a batch.'` first in `createBlock`,
   with a one-line comment that the server re-checks (the same pattern as `signoffBlock`).
2. **Sighted keyboard users cannot see why a row is greyed.** (`ReadyLotsPage.tsx:236-248`) The tooltip sits on a `<span>` that cannot
   take focus, and a disabled input cannot take focus either. The reason is in the accessible name, so screen readers get it, but a
   sighted user on the keyboard only sees a grey row (WCAG 1.4.13 / 2.1.1). Fix: show `block` as a `Typography variant="caption"` under
   the lot code in the same row. Keep the tooltip.
3. **The share test on the batch page proves nothing on its own.** (`mocks/handlers.ts` POST `/v1/batches` imports `splitShares`) The
   mock computes the "server" shares with the client function, so "31.250 %" on the batch page always agrees with the client. Parity
   with `shares.py` rests on the three unit cases. Fix: add the reviewer cases to the `splitShares` unit test, which pin the negative
   residual and the middle tie: {1×7} → 14.284 / 14.286×6 and {3,7,7,1} → 16.667 / 38.888 / 38.889 / 5.556.
4. **The non-GI switch promises more than B09 delivers for held lots.** (`ReadyLotsPage.tsx:316`, `batchModel.ts:73`) In non-GI mode,
   lots held by B08 can be ticked. FR68 allows this ("a hold keeps the lot out of GI batches"). But B09's publish gate refuses on every
   hold flag whatever `gi_label_requested` says (service.py:1162), so such a batch cannot be published until the hold is resolved. The
   same is true for an out-of-GI plot hold. Fix: add a TODO line → Architect-Gate: should B09 skip GI-only holds (`plot_outside_gi_region`,
   GI-hold rules) for non-GI batches? Until then, extend the switch label with "held lots block publishing until their hold is resolved".
5. **GI block reasons show raw codes.** (`BatchPage.tsx:123-127`) A row reads "lot on hold: flags: yield_over_ceiling". Fix: for a
   `flags: ` detail, map the codes through `ruleText(code).en`, as `lotBlock` does (move that 5-line mapping into a `holdText(reason)`
   helper in batchModel.ts and call it from both places).
6. **A `DECISION D-006` label marks a plain UI mirror of a role check.** (`batchModel.ts:98-101`) P02 r1 P3-5 raised the same pattern
   on `resolveBlock`. D-006 covers rule results previewed on the phone. Fix: make it a plain comment ("server re-checks: 403 role, 409
   `same_approver`"), or settle both places with the Orchestrator. The D-006 use on `splitShares` (a computed preview, the server
   recomputes it) is fine.
7. **A 409 that arrives after the response was lost and the processor was changed shows a message the admin cannot act on.**
   (`ReadyLotsPage.tsx:159`, D-005) A resend with the same `client_id` but another processor answers `client_id_conflict`, and
   error-codes.md tells the user to "generate a new UUID on the device". Rare. Fix: on `client_id_conflict`, show "This batch was already
   created; reload the page" and invalidate `['lots']` (already done in `onError`).

## Checks that passed

- **Status reading:** `create_batch` refuses any lot whose status is not `RECEIVED` (`lot_not_received`, service.py:876). So listing
  `ready_for_sale` lots greyed as "Not ready: record the intake at the processor first." is right, not a P2. "Ready lots" in the
  acceptance is the screen name, and the server only batches received lots.
- **Greyed reasons:** already batched, not ready, held (rule names through `ruleText`), and outside GI (dead branch, see P1-1) are all
  present. The no-packed-weight reason is the P2.
- **Non-GI semantics:** sends `gi_label_requested: !nonGi` (B09 `BatchIn`). The batch page shows "Non-GI batch". The test checks the
  stored flag is false.
- **`client_id`:** `useState(() => crypto.randomUUID())` makes it once per mount and reuses it on retry and after a refusal (D-005
  comment). The button is disabled while the request is pending. A double click makes one batch (test). Navigating back remounts the
  page and makes a new id.
- **Second sign-off:** threshold from `GET /v1/config/features`, compared with `>` in grams, as `_needs_second_signoff` does
  (service.py:412). The hint before create is a preview from packed kg. The batch page uses the server's `second_signoff_required`. The
  creator sees the button disabled with the reason, another admin sees it enabled, and the server's `same_approver` refusal is listed.
- **409 reasons:** `GateReasons` lists `details.reasons[]` with the server message, falling back to the code with spaces. The headline
  comes from the generated error table (`errorMessage`).
- **Packed vs intake preview:** honest. "Shares are a preview from packed weight; the batch keeps the shares of the weight received at
  intake." sits under the total, and the batch page shows the server's shares and received kg. Not a finding (apart from P2-1).
- **N+1 farmer names:** one cached `GET /v1/farmers/{id}` per distinct farmer, with a `shortcut:` comment naming its limit. That is
  fine at pilot load (one FPO, a few dozen lots). The hold hint reuses the single shared `['flags','holds']` query, so there is no
  request per row.
- **Privacy:** only `name` is rendered from the farmer read. `/v1/me` phone is fetched but never rendered. The page test asserts no
  10-digit number. No `dangerouslySetInnerHTML`. No public URL beyond the `/b/<code>` path.
- **Accessibility:** axe 0 violations on Ready lots and on the batch page (colour contrast off in jsdom, as in P02). The disabled
  checkbox's accessible name carries the reason. The total line is `aria-live="polite"`. Sections are labelled by headings. No dates
  are shown, so `dayMonth` does not apply.
- **Documentation:** every new file has a header with FR9/FR29/FR60, User Flows §, plan §7.3 P03 and its callers. JSDoc is on every
  function (doc-coverage PASS). D-005, D-006 and D-033 exist in DECISIONS.md. LIBRARIES "used in" columns are extended (react-router,
  react-query, MUI, axe-core, user-event); msw is listed by glob, as for the earlier test files. CHANGELOG has a line under
  [Unreleased]. TODO lines cover the B09 intake kg and processor on `LotOut`, B10 QR, P04 hand-off (BatchPage seam, exported
  `GateReasons` / `useFarmerNames`), crop filter, plot-hold greying (now P1-1), Tamil reasons, and the live-API run. The P02 TODO lines
  are closed with a note.
