## What this change does

`verifyOtp` now retries once with a fresh device id when the server says the stored id is still bound to another
user. "Sign out" now waits for the server, swaps a dead access token for a live one through the refresh cookie,
and keeps the session with an error banner when the server cannot be reached. A refresh that fails with a 5xx or
429 no longer signs the user out.

## Focus answers

1. **Retry security (server read: `identity/service.py` `verify_otp`, `_bind_device`, `otp_outcome`).**
   - `device_in_use` is raised in `_bind_device`, after the code check passed. `challenge.consumed_at` is set but
     not committed, and `get_session` rolls back on the exception (`core/db.py:135-148`), so the second verify
     finds the same unconsumed challenge and the right code. The worker's comment is accurate.
   - The OTP lock is per challenge (newest challenge of the phone, `attempts >= OTP_MAX_ATTEMPTS`), not per
     device. A wrong code is answered `otp_invalid`/`otp_locked` before `_bind_device` runs, so it never reaches the
     retry. Cycling device ids cannot reset or skip the 5-wrong-codes lock.
   - A fresh id creates a new device row for B; A's row stays bound and un-revoked (B02 rule "knowing a device id
     must not let someone sign its owner out" holds). Row growth: one row per successful OTP after a stale
     binding, so at most `OTP_DAILY_CAP` (10) per phone per day. Not unbounded.
2. **Sign-out path.** Single-flight `refreshSession` (`authApi.ts:115-129`) means a sign-out during a 401 recovery
   shares one refresh, so no `refresh_reused` race. The new access token from the swap lives only in a local and is
   never stored or logged. **But** see P1-1: a non-refusal refresh failure is treated as "cookie dead".
3. **5xx/429 keep-alive.** After a 503 on the scheduled refresh, `recoveringFor` is reset; the token expires; the
   next data call gets a 401 → `recover` → one refresh (single-flight) → success, or 401 → one `signOut`, or 5xx →
   kept again. Each step is driven by a request or the timer; no loop. The refresh endpoint never answers 429 (only
   `otp/request` is rate-limited), so that branch is moot.
4. **`recover` change.** Marking `recoveringFor` before `signOut` is right: concurrent 401s for the same token now
   return early while the async logout runs, so one logout. Navigation happens once, through `store(null)` →
   `RequireAuth`. See P3-1 for the failure leg.
5. **Snackbar in AuthProvider.** Acceptable: `AuthProvider` sits inside `ThemeProvider` (`AppProviders.tsx:33-35`),
   the repo has no Snackbar or toast pattern to reuse, and MUI `Alert` renders `role="alert"` (the test finds it by
   that role). No `autoHideDuration`, so the error stays until closed: right for a security message.
6. **Tests.** All three fail on main's code (run above). The MSW logout change (`401` unless `authed`) is honest and
   matches the server's `get_current_user`. Only the auth test files click "Sign out"; no other test depends on the
   old always-204 mock.
7. **Docs and tracking.** File headers updated, `verifyOtp` and `revoke` documented, CHANGELOG line present, TODO
   P1 ticked with findings 4 and 5 noted. `signOut` itself has no JSDoc block (P3-3).

## Findings

### Must fix

1. **P1-1 Sign-out shows the sign-in page while the refresh cookie still works** (`apps/portal/src/auth/AuthProvider.tsx:L100`)
   - **What this is:** when logout answers 401 (dead access token), `revoke` trades the refresh cookie for a live
     token and logs out with it. If that refresh fails, it assumes the cookie is dead and the local state is cleared.
   - **Problem:** `refreshSession().catch(() => null)` treats *every* failure as "cookie dead": a network error, a 502
     from the proxy during a deploy, a 503. Case: staff A's scheduled refresh got a 503 (now kept alive by
     finding 5), the token expires, A clicks "Sign out" during a rolling restart. Logout → 401, refresh → 502 →
     `null` → sign-in page. A walks away. B opens the portal on the shared PC; the mount refresh uses A's live cookie
     and B works as A, with A's role. Reproduced in a scratch copy: sign-in page shown, mock cookie still signed in.
     The JSDoc ("when the cookie is dead too") and the worker report claim the narrower behaviour.
   - **Fix:** swallow only a refusal; rethrow the rest so the existing error branch keeps the session and shows
     "Could not sign out. …":
     ```ts
     const next = await refreshSession().catch((refused: unknown) => {
       if (refused instanceof ApiError && refused.status === 401) return null;
       throw refused;
     });
     ```
     Update the `revoke` JSDoc `@throws` to "a refresh that fails other than with a 401". Add one test in
     `auth.test.tsx` (verified passing with the fix, failing without):
     ```ts
     it('keeps the session when logout gets a 401 and the refresh then fails with a 503', async () => {
       const user = userEvent.setup();
       renderApp('/', true);
       await screen.findByRole('heading', { name: 'Dashboard' });
       server.use(
         http.post('/v1/auth/logout', () => fail(401, 'unauthorized'), { once: true }),
         http.post('/v1/auth/refresh', () => fail(503, 'internal_error'), { once: true }),
       );
       await user.click(screen.getByRole('button', { name: 'Sign out' }));
       expect(await screen.findByRole('alert')).toHaveTextContent('Could not sign out.');
       expect(screen.getByRole('heading', { name: 'Dashboard' })).toBeInTheDocument();
       expect(mockState.signedIn).toBe(true);
     });
     ```
   - **If we skip it:** on a flaky office link or during a deploy, "Sign out" can still leave the next person signed
     in as the previous one — the exact shared-PC risk this WP closes.

### Nice to have

2. **P3-1 After a failed loop-branch sign-out, later 401s for that token are ignored** (`AuthProvider.tsx:L144`)
   - **What this is:** the loop branch sets `recoveringFor = token` and calls `signOut`.
   - **Problem:** if that sign-out fails on the network, `recoveringFor` stays set, so every later 401 for the token
     returns early. Screens show errors until the scheduled refresh timer fires or the user clicks "Sign out" again
     (the banner tells them to). No security impact: the server already refuses the token.
   - **Fix:** none needed now; if it shows up, reset `recoveringFor.current = null` in `signOut`'s rejection handler.
   - **If we skip it:** a rare stuck screen until the next timer or click.
3. **P3-2 `403` in `endIfRejected` is a branch the server never takes** (`AuthProvider.tsx:L124`)
   - **What this is:** the refresh signs out on 401 or 403.
   - **Problem:** `identity.service.refresh` only raises `UnauthorizedError` and `RefreshReusedError` (both 401); an
     inactive account also gets a 401. The audit fix named only 401.
   - **Fix:** optional: drop `|| error.status === 403`. Harmless as a fail-safe; accept either way.
   - **If we skip it:** nothing breaks.
4. **P3-3 `signOut` callback has no JSDoc of its own** (`AuthProvider.tsx:L85`)
   - **What this is:** CLAUDE.md §5.2 asks for a doc block on every function; the interface member is documented, the
     `useCallback` is not (pre-existing gap, now a longer function).
   - **Fix:** add a three-line JSDoc: what it does, "Side effects: logout/refresh calls; clears the session and the
     query cache on success, or sets the sign-out error".
   - **If we skip it:** a reviewer nit next round.
