### P2

**P2-1 History lets the next user on a shared phone undo the previous user's entry, and the undo is sent under
the previous user's identity** (`apps/mobile/lib/features/history/history_screen.dart:35-49`, `:136-155`)
- What it does: `historyProvider` lists every standing farm-event entry in the database. It has no owner filter.
- What goes wrong: Farmer A logs a harvest at 09:00 and signs out (D-029 keeps A's entries). Farmer B signs in on
  the same family phone at 15:00. B opens History, sees A's "Harvest", and taps Undo. The window is still open.
  `EntriesDao.undo` copies `enteredByUserId` from the original, so the undo row and its outbox row belong to A. B's
  sync skips the row (D-029 owner filter). When A signs in again, the undo is pushed with A's token. A's harvest is
  withdrawn although A never did it. D-029 promises "no entry is ever sent under the wrong identity". B also sees
  A's history, but within one family that matters less.
- Fix: filter by the signed-in user, the same way `OutboxDao._signedInUser()` does. In `historyProvider`'s `where`,
  add
  `& e.enteredByUserId.isInQuery(db.selectOnly(db.sessionTable)..addColumns([db.sessionTable.userId]))`
  Add one test to `m08_screens_test.dart`: save an entry with `enteredByUserId: 'user-2'` and expect it to be
  missing from History. Pulled events never become Entries rows (`pull_service.dart:108-115`), so every row on the
  phone was entered here, and this filter loses nothing. M10's farmer filter under assist stays a TODO.
- If skipped: a rare but real wrong-identity undo of a farm event, which the farmer cannot see or reverse after
  24 h.

**P2-2 Sell and Money show the previous farmer's lots on a shared phone, so Sell can show a QR naming another
farmer in one tap** (`apps/mobile/lib/features/money/money_screen.dart:35-52`; root cause in
`apps/mobile/lib/core/sync/sync_service.dart:200-211`). **Hand-off, does not block M08.**
- What it does: `farmerLotsProvider` reads every `Lots` row when not in assist mode. On a user switch, the D-029
  block in `SyncService._run` clears the pull cursor and the reference bundles. It does not clear the pulled
  `lots`, `plots`, `farmers` or `tasks` rows.
- What goes wrong: A's lot is `ready_for_sale`. A signs out and B signs in. B taps Sell and immediately sees A's
  QR, with A's `farmerId` and A's packed kg, because a single ready lot skips the picker. The brief's rule
  "never a wrong lot" breaks. The same stale rows already affect M07: `activeLots()` in Log, and
  `nextTaskProvider`, which reads `farmers ..limit(1)`.
- Fix (M02 owns it): at a user switch, delete the pulled per-farmer rows that the fresh pull refills: lots, tasks,
  flags, and farmers/plots that have no unsent outbox row. M09's offline-registered farmers on an officer phone
  must survive. Alternatively, store the signed-in farmer's id in `Session` and filter by it. Neither is a few
  lines inside M08's paths without deciding D-029 semantics, so the Orchestrator should file it against M02/M06.
  M08 should add a TODO line naming this.
- If skipped: on shared phones, a farmer can present another family member's lot at the collection centre. M11
  shows the owner's name from `Farmers`, so an alert QC officer catches it.

### P3

**P3-1 The voice prompt does not change when the screen state changes** (`sell_screen.dart:69,71,96`;
`money_screen.dart:101-104`; `history_screen.dart:81-84`)
- `VoicePromptBar` autoplays only in `initState`. These screens swap one bar for another bar at the same list
  index with no key, so Flutter reuses the state. After the farmer picks a field, "Show this code at the collection
  centre." never plays. On an empty Money or History screen, the loading-state prompt (`moneyPrompt` /
  `historyPrompt`) plays instead of `noLot` / `historyEmpty`.
- Fix: add `key: ValueKey(promptId)` to each of these bars. M11 does the same in `scan_screen.dart`.

**P3-2 "Lot ABC123" is not a code that exists anywhere** (`sell_screen.dart:24-29,113`)
- The server's lot code is `LOT` plus 8 random hex characters (`apps/api/agritrace/core/ids.py:37`). B10's bag-tag
  QR (`GET /v1/lots/{id}/qr`) encodes that code. The phone shows the last 6 characters of the UUID instead.
  Staff who type it into the portal find nothing. M11 has no typed-code fallback.
- Fix: delete the line, `lotCode()` and `lotCodeLabel` until `code` is mirrored (the TODO already exists). Field
  and kg identify the lot for the farmer.

**P3-3 An entry the server marked undone still shows as "Not sent" with an Undo that does nothing**
(`history_screen.dart:39-45`)
- `pull_service.dart:111-114` sets a confirmed original to `undone` without writing an undo row. The `notExists`
  filter therefore keeps it, `entryBadge` falls through to "Not sent", and Undo throws `StateError`, which
  `_undo` swallows.
- Fix: add `& e.status.equalsValue(EntryStatus.undone).not()` to the same `where`.

**P3-4 Undoing a packing from History sets the lot to `open`** (`history_screen.dart:144-148`)
- The lot is usually `drying` before packing, so Money shows "Growing" until the next pull. With two standing
  packing entries on the lot, undoing one still reopens the lot. The worker records this as a risk, and the pull
  corrects it.
- Accept as documented, or reset only when `_localPackedKg` of the other standing packings is 0.

**P3-5 The file header names a test file that does not exist** (`sell_qr.dart:6`)
- `test/features/sell_money_test.dart` should be `test/features/m08_screens_test.dart`.

**P3-6 `SellQr.decode` returns a packed kg that the `sig` did not cover** (`sell_qr.dart:53-58`)
- `{"packedKg":300.04, "sig": sig(…|300.0)}` verifies and decodes to 300.04.
- Fix: `packedKg: double.parse((m['packedKg'] as num).toStringAsFixed(1))`.

**P3-7 D-035 wording** (`docs/adr/D-035.md`)

  - A keyed or server-signed QR would still not stop someone showing a screenshot of another farmer's genuine QR.

  - B10's `GET /v1/lots/{id}/qr` encodes only the unsigned lot code, so it is not a signed alternative today.

## SEC: D-035 and the QR

- **Payload:** `{"lotId","farmerId","packedKg","sig"}`, two server UUIDs, kilograms and an 11-character checksum.
  It has no phone number, name, village, survey number or location. The `encode` and `decode` tests check that the
  keys are exactly these four, in this order. CLAUDE.md §6 holds.
- **Honesty:** the ADR's Compromises section, the `DECISION D-035` comment (ADV/COMPROMISE) in `sell_qr.dart:30-34`,
  the report's Risks section and the TODO line all say plainly that `sig` is an unkeyed checksum and that anyone
  can forge a QR for a real lot. The ADR also admits the misleading field name. Honest enough. P3-7 adds wording.
- **Enough for the pilot?** Yes. The QR only selects a lot. Every consequence (the intake, received kg, the price)
  is entered by an authenticated QC user, and B09 checks it on the server: FPO scope, lot status, reconciliation
  of weight against packed kg. Forging needs the target's two UUIDs. A signature would not stop screenshot replay
  anyway. A server-issued signed QR (B07 pull of a signed `qr_payload` into the existing `Lots.qrPayload`, with an
  FPO public key on QC phones) belongs at P3/TODO level. It already appears as the ADR's "Revisit when". It is not
  a P2 hand-off. "Show the server's QR when synced" gains nothing today, because B10's lot QR is the unsigned lot
  code.
- **Weakness that matters more:** M11 r1 does not check the checksum and trusts QR fields for unknown lots (H-1).

step the app asks for, and the card does that in 3 (+1). The Log button opens a browse view for unplanned events.

  Verifier stops counting it;

  up.
