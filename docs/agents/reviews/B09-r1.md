## Findings

### P1 (blocks merge)

**P1-1. Acceptance test 4 fails when run** (`apps/api/tests/integration/test_lots_batches.py:401-411`).
The test writes `gi_eligible=False, gi_hold_reason="flags: yield_over_ceiling"` directly. That is B08's own
`HOLD_PREFIX` (`rules_flags/service.py:79`), and no hold flag backs it. `create_batch` calls
`run_gate_checks(batch_id=…)` (`service.py:877`), which calls `_check_lot` → `_sync_lot_hold` → `apply_hold(lot, [])`.
`apply_hold` sees a reason it owns and no active hold, so it restores `gi_eligible=True, gi_hold_reason=None` on
the same identity-map object. `_gi_check` (`service.py:879`) then finds no `lot_on_hold`. The only reason left
is `plot_location_needs_review`, because the seeded plot keeps the default `location_status=needs_review`. The
assertion `(lot, "lot_on_hold") in reasons` fails, so the line has no passing evidence.
**Fix (test only):** give the lot a real hold that the rules keep. Post a live harvest event of 2,000 kg on the
1.5-acre plot before the intake. The profile ceiling is 1,000 kg/acre and the hold margin is 30 %, so the hold
starts at 1,950 kg, and B08 raises `yield_over_ceiling` (hold) and sets `gi_eligible=false` itself. Seed the plot
with `location_status=LocationStatus.CONFIRMED`, so the plot is not what blocks GI. Then assert
`gi_verified is False`, `(lot, "lot_on_hold") in reasons` and `("hold_flag")` present. Drop the direct
`gi_hold_reason` write: B09 code must never set that field, and the test should not either.

### P2

**P2-1. Concurrent batch or intake requests can put a lot in two batches** (`service.py:803`, `service.py:667`/`303`).
`create_batch` reads the lots, checks `status == received`, then writes shares, with no row lock.
`create_intake` does the same check-then-write on `ready_for_sale`. Two admins, or a double click in the portal
(`BatchIn` has no `client_id`), committing at the same time both pass the check. The lot then gets shares in two
batches, and its kilograms show on two public pages. Migration 0004 makes those shares append-only, so the
mistake cannot be undone. (Load assumed: pilot, one FPO, a few admins on the portal.)
**Fix:** lock the lots you check. Use `select(Lot).where(...).with_for_update()` at `service.py:803`, and
`session.get(Lot, data.lot_id, with_for_update=True)` in the intake path (add a `lock: bool = False` argument to
`_lot_in_scope`, or load it directly in `create_intake`). Two lines; the second request then waits and gets
`lot_not_received` / `lot_not_ready`.

**P2-2. A wrong intake can never be corrected** (`alembic/versions/0004_lots_append_only.py`, `service.py:675-681`).
`lot_intakes` and `batch_shares` are now append-only, and the lot moves to `received` after one intake (the
`shortcut:` comment allows only one per lot). A typo such as 1000 kg for 100 kg is therefore permanent: it feeds
`total_received_kg`, the shares and the public page. Even a DBA has to disable the trigger to fix it. CLAUDE.md
§6 says "corrections add versions", and that half has no path yet. D-033 lists this as a compromise. TODO.md
mentions it as a risk, with no owner or interim procedure.
**Fix (pick one):**
(a) Before pilot data entry, replace the TODO risk line with a scheduled item that has an owner: a
`lot_intake` correction row (`supersedes_intake_id`, reason), with shares recomputed into a new batch version.
Also add a one-paragraph ops runbook in D-033 for the interim: an audited manual fix with
`ALTER TABLE … DISABLE TRIGGER` in one transaction, logged to `audit_log`.
(b) Leave `lot_intakes` out of 0004 until (a) exists. Keep `batch_approvals` and `batch_shares` append-only.

### P3

**P3-1. Strict `in_order` snapshot vs B08's ±5 % flag** (`service.py:125-159`). No code change. Extend the TODO
risk line to cover both directions (over 1–5 % → `in_order=false` with no flag; short by more than 5 % after
packing → `in_order=true` with a flag). Tell B10 to render the `quantity_mismatch` flag, not `in_order`.
Optionally add to the `IntakeOut.reconciliation` description: "strict chain; the tolerant verdict is the
`quantity_mismatch` flag".

**P3-2. A refused publish commits the GI re-check** (`service.py:1098` before `_refuse` at `:1108`). `_refuse`'s
docstring says "the gate's own changes have not been made yet", but publish has already rewritten
`gi_verified`/`gi_block_reasons`. The written state is correct, so only the docs are wrong. Fix the docstring at
`service.py:251-253` and D-033 §2 to read "flags and the GI re-check".

**P3-3. An intake resend does not check the body** (`service.py:662-666`). A `client_id` reused for a different
lot in the same FPO returns the other intake with 200. Fix:
`if existing.fpo_id != user.fpo_id or existing.lot_id != data.lot_id: raise ClientIdConflictError(...)`. This
matches the lot resend's plot check.

**P3-4. A lot resend skips the farmer ownership check** (`service.py:471-475`). A farmer who sends another
farmer's lot `client_id` together with that farmer's `plot_id` gets the stored lot back. The risk is low
(UUIDv7 ids, same FPO). Fix: call `_lot_in_scope(session, user, existing.id)` before returning.

**P3-5. `approve_grading` accepts any graded kg** (`service.py:1013`). Graded 2,000 kg on a 320 kg batch is
accepted and becomes the packing ceiling. D-030 makes ">5 % above received" a B15 warn, so blocking here would
contradict the ruling. Fix: add a TODO for B15 to confirm the warn covers this, or ask Architect-Gate whether a
`graded_above_received` gate reason is wanted.

**P3-6. `list_batches` runs two queries per batch** (`service.py:906` → `batch_out` → shares query and
`_needs_second_signoff` → `fpo_code`). That is about 400 queries for a 200-row page. Fine for the pilot. Fix
later: read `features_for` once per page and load the shares with one `IN` query.

**P3-7. The intake moisture reading is checked only for its lot** (`service.py:671-674`). It is not checked to be
`parameter_code == "moisture"` and `stage == "intake"`. Fix: add both to the condition and return `not_found`.

**P3-8. Wrong caller in the header** (`shares.py:5`). It names `tests/unit/test_lots_shares.py`, but the tests are
in `tests/unit/test_lots_batches.py`.
