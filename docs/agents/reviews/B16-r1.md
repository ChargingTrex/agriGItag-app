## Security review (SEC lens)

**D-040, `lot_intake` push.**
- Role: `create_intake` checks `user.role in INTAKE_ROLES` first (`lots_batches/service.py:725`), before any
  lookup, so the push route (any role) cannot bypass it. Farmer, field officer and viewer get `forbidden`
  (unit + integration). A correction by anyone but an FPO admin gets `forbidden` (`:727`). The REST route's
  `Receiver` dependency is a second layer. Opening REST to QC officers does not open corrections to them,
  because the service refuses them.
- Scope: lot through `_lot_in_scope(lock=True)` (FPO; the farmer branch is unreachable). Named processor:
  `fpo_id in (None, caller's FPO)`, else `not_found`. Default: `Processor.fpo_id == caller's FPO` with `LIMIT 2`,
  exactly one, never a shared processor. Intake reading: must be `(lot.id, moisture, intake)`, which implies the
  FPO. `_push_lot_intake` builds `{**entry.data, "client_id": entry.client_id}`, so the entry id wins over any id
  in `data`.
- Idempotency: a stored id in the same FPO and lot → `duplicate`. Another FPO, or another lot →
  `client_id_conflict`. Sequential resends are correct (line 1).
- **The race (P2-1).** The resend lookup (`:731`) runs before the lot lock (`:736`). Two pushes of the same
  entry: the loser reads "no intake", waits on the lock, then sees the lot `received` and refuses with
  `lot_not_ready`. The TODO says "the phone's retry then gets `duplicate`". That is wrong: the phone retries
  only `stale_version` (`apps/mobile/lib/core/sync/outbox_processor.dart:221–236`), and marks every other
  code `rejected` for good. Its own D-005 comment says foreground and background isolates do overlap on one
  client id. See P2-1.
- Moisture gate: it runs only in the first-intake branch for `open`/`drying` (`:771–776`), after every other
  check, and its `_refuse` commits nothing but releases the lock. `mark_ready` re-reads the locked lot through
  the identity map and sets `ready_for_sale` + `ready_at`. The rest of the function then writes `received`.
  If anything later fails, both roll back. Nothing sets `ready_for_sale` except `mark_ready`
  (`grep READY_FOR_SALE`), so a `ready_for_sale` lot has always passed the same gate. It is never skipped, and
  a correction never re-runs it, as ruled.
- `IntakePayload` (event type `intake`) is a documentation change only. No behaviour change.

**D-041.** `GI_ONLY_HOLD_CODES` holds exactly the two ruled codes. `_blocks` = hold AND (GI requested OR code not
in the set). That fails closed for every other hold and every future code. All three callers
(`approve_grading`, `final_packing`, `publish`) pass `batch.gi_label_requested`. No other caller exists, on the
branch or on main. `_approval` records `not _blocks(...)`, so a non-GI approval lists the GI-only holds and a
GI approval is unchanged. Flags are never resolved by the gates. `_gi_check` is untouched: it is skipped for a
non-GI batch, and in a GI batch it still lists every hold.

**D-042.**
- `NO_ASSIST_KINDS` returns the caller with both assist fields cleared, before any lookup
  (`events/service.py:931`). This also drops a request-level `X-Assist-Session` inside a push for these kinds.
  The ruling says "ignore: no session lookup, no assist fields". The ADR's only exception is REST
  `POST /v1/flags/{id}/resolve` with the header (D-042.md:37), which is unchanged. Same behaviour as D-031 for
  `farmer`. The worker's risk note matches the ruling.
- `create_reading` (`quality/service.py:779/784`): another farmer's lot → `forbidden`; any batch → `forbidden`
  before `_load_batch`. It is shared code, so `POST /v1/quality-readings` with `X-Assist-Session` gets the same
  check (no integration test on that path, P3-5).
- `_check_subject` batch branch (`events/service.py:304`): assist → `forbidden`. It covers push, REST
  corrections and undo, because `write_version` calls it.
- The B15 checks for consent, plot and lot events are unchanged: the lot branch of `_check_subject` is
  untouched, and the B15 unit tests still pass.

## Findings

### P2-1: a concurrent duplicate `lot_intake` ends `rejected` on the phone while the server has the intake
- **Where:** `apps/api/agritrace/modules/lots_batches/service.py:731–736`; `TODO.md:248` (the wrong claim).
- **What happens:** The phone's foreground and background isolates push the same `lot_intake` at the same time
  (outbox_processor.dart D-005 comment). Push A locks the lot, writes the intake and commits. Push B already read
  "no intake" before the lock. After the lock it sees the lot `received` and answers `gate_not_met` /
  `lot_not_ready`. The phone marks the entry `rejected` (only `stale_version` is retried). If B's result is
  written last, the QC officer sees "lot not ready" for an intake the server recorded, and any re-entry is
  refused too. The REST path has the same race: a client retry after a timeout gets a 409. The house pattern
  resolves such races to `duplicate` (B15 `_push_farmer`, B15-r1 P2-2).
- **Fix (5 lines moved, nothing added):** move the resend block below the lock:
  ```python
  lot = await _lot_in_scope(session, user, data.lot_id, lock=True)
  # after the lock, so a concurrent push of the same id that just committed is seen as a resend (D-005)
  existing = await session.get(LotIntake, data.client_id)
  if existing is not None:
      if existing.fpo_id != user.fpo_id or existing.lot_id != data.lot_id:
          raise ClientIdConflictError(details={"client_id": str(data.client_id)})
      return existing, [], False
  ```
  The `get` is the first load of that id in the session, so it queries the database. Under READ COMMITTED it
  sees the row the winner committed. The one visible change: a resend that names another FPO's lot now gets
  `not_found` instead of `client_id_conflict`, which is fine. Add one test: either an integration test that runs
  two identical pushes with `asyncio.gather` and asserts `{accepted, duplicate}` and one row, or a unit test
  whose session stub returns the stored row on `get(LotIntake)`, with the lot `received`, and asserts
  `(stored, [], False)`. Replace TODO.md:248 with nothing (fixed), and update the unit stub tests if their
  order matters (`test_intake_resend_is_a_duplicate_for_a_qc_officer` passes no `Lot`; give it one).
- **If skipped:** rare, but when it happens the QC phone shows a false rejection for a lot that was received.
  The officer cannot fix it from the phone, so it costs an admin ticket.
