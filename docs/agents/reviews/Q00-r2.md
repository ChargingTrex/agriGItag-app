## 4. Findings

### P1 (blocks the merge)

**P1-A Survey and patta numbers in plain text pass the linter. This is a regression from the W01-1 fix.**
- *What the code does:* A label word now counts only in four contexts:
  - a JSON key;
  - inside `<th>`, `<dt>` or `<label>`;
  - followed within 40 characters by **four or more** digits;
  - one of the "number" abbreviations `S.F. No`, `Sy. No`, `Survey No`, `சர்வே எண்`, `புல எண்`, followed by a digit.
- *What goes wrong:* Survey and patta numbers are short, usually 1–3 digits plus a subdivision (`123/4A`, `452`), so the 4-digit rule never fires on them. The abbreviation list leaves out the spelled-out and patta forms. As a result, `Survey Number 123/4A` (X03), `Patta No. 452` (X04) and `பட்டா எண் 45` (X05) all pass with exit 0. The round-1 linter caught X03 and X04. A survey number has no digit pattern of its own, so the label rule is its only guard.
- *Why it matters:* The Data Flow doc captures "land-record reference (survey number, patta/chitta)", FR65 records it, and the architecture doc names "survey number" as something the public page never shows. CLAUDE.md §6 and BM-09 ("0 hits for … survey no.") depend on this rule.
- *How to fix (also fixes P2-1):* Replace the "4 digits within 40 characters" rule with a "number right after the label" rule. One shape that works:
  `(?P<w>\b(?:survey|patta|chitta|S\.?\s?F\.?|Sy\.?)(?:\s*(?:no\b\.?|number|num\b\.?))?|(?:சர்வே|பட்டா|சிட்டா|புல)(?:\s*எண்)?|\b(?:phone|mobile|aadhaa?r)(?:\s*(?:no\b\.?|number))?|தொலைபேசி|அலைபேசி|கைபேசி|ஆதார்)(?=\s*[:#.-]?\s*\+?\d)`
  Keep the JSON-key and `<th>`/`<dt>`/`<label>` rules as they are.
  Add X03, X04 and X05 to `LEAKS`. Add `Pest survey · 14 Feb 2026` and `mobile app … 2026-10-29` to the negative list.
- *If skipped:* B10 or W03 can print a farmer's land-record number on a public page while BM-09 stays green.

**P1-B Phone numbers in `http(s)` URL paths are not checked. This is a regression from round 1.**
- *What the code does:* `NEUTRAL` masks every character of an `https?://` URL up to `?` or `#` before the digit rules run. This was added so hashed evidence filenames and the FP5 lot code pass.
- *What goes wrong:* `https://wa.me/919876543210`, the standard WhatsApp click-to-chat link (X01), passes with exit 0. So does any number in a URL path (X17). The round-1 linter caught both. WhatsApp is one of the platform's message channels (Architecture §Messages), so a "contact on WhatsApp" link is a realistic thing for a template to add.
- *How to fix:* Hex hashes of 16+ characters and UUIDs are already neutralised by their own patterns, so the path mask is only needed for the purely numeric lot-code case. The smallest change is to stop masking `wa.me/…` and `whatsapp.com/…` URLs: `https?://(?!(?:www\.)?wa\.me/|(?:api\.)?whatsapp\.com/)[^\s"'<>?#]+`. A stricter alternative is to stop masking URL paths at all and accept FP5 as a false positive; batch codes are alphanumeric (`FGP8T4033HM7`), so a 10-digit numeric lot code is unlikely in this product. Add `wa.me/919876543210` to `LEAKS` either way.
- *If skipped:* a farmer's or FPO officer's number published as a WhatsApp link passes BM-09.

### P2 (fix in this round or file in TODO with an owner)

**P2-1 A label word followed by a year is a false positive.** The same 40-character rule fires on any 4-digit year: `Pest survey · 14 Feb 2026`, `mobile app. Batch packed 2026-10-29` and `verified by phone OTP on 2026-10-12` each give one `sensitive_label` hit. Event names on the public page are date-ordered (FR63), so a "survey" event next to its date is likely. The P1-A fix removes this.

**P2-2 Some separators are missing.** An en dash (U+2013), a narrow NBSP (U+202F) or a thin space (U+2009) between the digit groups, and the HTML entity `&nbsp;`, all let a phone number through (X07–X09). Jinja does not produce `&nbsp;`. An en dash does come from desktop autocorrect when an FPO admin pastes notes from a document. *Fix:* add `‐-―  ` to `SEPARATORS`. Run `html.unescape` on `.html`, `.htm`, `.svg` and `.xml` text before scanning; keeping offsets means unescaping per entity and recording the length change. Add one test per character.

**P2-3 Coordinates written with degree signs or as DMS pass.** `9.5598061° N, 78.1335214° E` (X10), `9°33'35.3"N 78°08'00.7"E` (X11) and a space-separated pair outside WKT (X12) slip. The builder emits a 3-dp map link, so these need a template choice or free text, which is why this is P2 and not P1. *Fix:* allow an optional `°\s*[NS]?` in `SEP`, and add a DMS rule that matches `\d{1,3}°\s*\d{1,2}['′]\s*\d{1,2}(?:\.\d+)?["″]`. One test each.

**P2-4 The scanner skips any text file not in its suffix list.** It still uses a suffix allow-list, so `.csv`, `.ndjson`, `.md`, `.map` and files with no suffix are counted as "non-text skipped" and the run exits 0 (X13, X14). Calling a CSV "non-text" also misleads the reader of the summary. The partner API is 501 in the pilot (B11), so the risk is not immediate; BM-09 does cover "partner stub output". *Fix:* round 1's option. Treat a file as text when its first 8 KB has no NUL byte and decodes as UTF-8, and only skip images and fonts by suffix.
