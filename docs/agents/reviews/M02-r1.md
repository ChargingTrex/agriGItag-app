The engine is well built. Phases are small functions, the retry rules match PLAN §13 A6, and the per-user
outbox is clean. Every API call carries `extra['secure']`. Tokens never leave M06's keystore, and the

Three bugs block the merge. Each fix is small:
1. After about 54 failed attempts, the backoff overflows and the entry sleeps for about 73,000 years.
2. A plots bundle fetch overwrites real local plot values with placeholders, in the same run that pushed
   the plot.
3. On a shared phone, the second user inherits the first user's pull cursor and plots bundle. That user
   misses their own changes and sees the first user's plots.

## Findings

### P1 (blocks merge)

**P1-1. The backoff overflows, and a long-failing entry stops syncing for good** (`apps/mobile/lib/core/sync/retry.dart:47`)
- `pow(2, attempts - 1)` with int arguments returns an int, which wraps above 2^63. At 54 attempts the
  delay is negative, so the row is due at once. From 55 attempts the delay is about 73,000 years.
- The row stays `waiting`, so it counts as pending. It is never marked `needs_attention`, and no officer
  action exists to retry it.
- How a phone gets there: the background task runs `runOnce` every 15 min without the probe. WorkManager's
  "connected" constraint is met by Wi-Fi with no uplink (a router whose internet is down, or a captive
  portal). 54 failures take about 13.5 h, so one bad night is enough. A long server outage does the same.
- Fix: clamp the exponent. `final base = 2000 * pow(2, min(max(attempts, 1) - 1, 8));` (2 s × 2^8 = 512 s,
  already above the 5-min cap.)
- Test: `expect(backoff(60, Random(0)), lessThanOrEqualTo(maxBackoff))` and `greaterThan(Duration.zero)`.

**P1-2. The plots bundle overwrites real local plot values with placeholders** (`apps/mobile/lib/core/sync/bundle_fetcher.dart:68-83`)
- `insertOnConflictUpdate(PlotsCompanion.insert(...))` writes every column on conflict, including
  `pinAccuracyM: 0`, `pinMethod: 'live_gps'`, `giStatus: 'unknown'`, `locked: false` and `version: 1`.
  B07's `plot_json` sends none of these fields (`bundle_service.py:72-91`), so the placeholders always win.
- When it happens: M09's wizard saves a plot with real values. The push in the same run sends it, and the
  bundles phase in that run gets it back in the `plots` part. The real accuracy, pin method, GI status,
  lock and version are then replaced. `Plots.version` is documented as "for stale-write detection", so the
  next plot correction sends version 2 against the server's N, gets `stale_version` twice, and is rejected.
  A locked plot also shows as editable.
- Fix: insert the placeholders only for a new row. On conflict, update only the fields the part carries:
  `into(plots).insert(companion, onConflict: DoUpdate((_) => PlotsCompanion(farmerId: …, pinLat: …,
  pinLng: …, declaredArea: …, areaUnit: …)))`. Update the D-016 COMPROMISE text to match.
- Test: seed a plot with `locked: true, version: 3, giStatus: 'inside', pinAccuracyM: 4.2`, fetch a part
  that lists it, and check that those four values are unchanged and that the pin and area changed.

**P1-3. A user switch on a shared phone (D-029) keeps the previous user's pull cursor and plots bundle** (`apps/mobile/lib/core/sync/sync_service.dart:179-181`, `pull_service.dart:36`, `bundle_fetcher.dart:27-31`)
- `pull_cursor` and the RefBundles versions are global on the phone. The server cursor is
  `(updated_at, id)` and is not bound to a user (`events/pull_service.py:47-78`). So user B pulls from
  user A's position and never receives B's lots and flags older than it.
- The `plots` part version is a per-FPO sum (`bundle_service._db_versions`), the same number for every
  farmer of the FPO. B's `since=plots:41` therefore gets nothing back. B keeps A's plots body (A's plot
  codes and pins) in RefBundles, and M03's BundleRepository shows those plots to B. B's own plots arrive
  only after the FPO's plots version next changes.
- This is the D-029 scenario this WP introduces. TODO.md (B07 r1 P3 hand-off) already gives "wipe
  reference data on sign-out when the phone switches user" to M02/M06.
- Fix (about 6 lines in `_run`, after reading the session): read SyncState `sync_user_id`. If it differs
  from `session.userId`, delete `pull_cursor` and every RefBundles row in one transaction, then store the
  new id. The next fetch has no `since` and gets every part.
- Test: user A pulls (cursor `c2`) and fetches plots (A's body). Sign in B. One run then sends no
  `cursor`, sends no `since`, and stores B's plots body.

### P2

**P2-1. A row killed mid-send stays stuck when the app reopens within 5 min** (`apps/mobile/lib/core/sync/sync_service.dart:105-106, 179`)
- `resetAfterKill` runs only in `start()` and in the background task, and it only resets rows older than
  5 min. If the farmer kills the app during a push and reopens it at once, the row stays `sending`.
  `nextBatch` and `nextDue` both skip it, so it waits for the next start more than 5 min later, or for
  the 15-min Android task. On iOS it can wait indefinitely (see P2-2). The cloud icon stays on.
- Fix: call `await db.outboxDao.resetStaleSending(now: now());` at the top of `_run`. The 5-min age guard
  already protects a live request, because dio's timeouts are 30 s. Keep the media `uploading` reset in
  `start()` only.

**P2-2. The iOS background task cannot run: no plugins are registered in the headless engine** (`apps/mobile/ios/Runner/AppDelegate.swift:10`; `docs/LIBRARIES.md` workmanager row)
- workmanager_apple 0.9.11 starts the periodic task in a new FlutterEngine. It registers plugins only
  through `WorkmanagerPlugin.setPluginRegistrantCallback` (`BackgroundWorker.swift:173`).
- Without that call, `sessionProvider.notifier.restore()` (secure storage) and the drift_flutter open
  (path_provider) throw `MissingPluginException`, and the task returns false every time. The ledger row
  says "no AppDelegate code needed on iOS", which is wrong.
- Fix: in `AppDelegate.application(_:didFinishLaunchingWithOptions:)`, before
  `GeneratedPluginRegistrant.register(with: self)`:
  `WorkmanagerPlugin.setPluginRegistrantCallback { registry in GeneratedPluginRegistrant.register(with: registry) }`
  (`import workmanager_apple`). Correct the ledger row.
- Only a device run can prove it (Q01).

**P2-3. A failed reachability probe schedules no retry, so "network back ≤ 30 s" can be missed** (`apps/mobile/lib/core/sync/sync_service.dart:224-226`)
- When the signal returns, `connectivity_plus` fires once. The link is often up before DNS and the route
  are, so the 3 s probe fails. Nothing tries again until a resume, a save, another connectivity event or
  the 15-min task. `_scheduleRetry` cannot help: a never-tried row is already due, and `nextDue` only
  returns future rows.
- Fix: when the probe fails and the engine is started (`_lifecycle != null`), set
  `_retry ??= Timer(const Duration(seconds: 10), () => unawaited(_probeThenRun()))`.
- Test: `reachable = false`, emit a connectivity change, set `reachable = true`, wait 10 s (fake async),
  and check that one push happened.

**P2-4. One refused envelope blocks every later push, because its metrics are sent again** (`apps/mobile/lib/core/sync/outbox_processor.dart:245-253`, `metrics.dart:33`)
- `metrics[]` is validated as part of the envelope (`SyncMetricIn`: `failures ge=0`,
  `network_type ≤ 16`, UUID `entry_client_id`). Entry `data` is validated per entry instead.
- On a 4xx that is not 401, 403 or 429, `_failed` marks the whole batch `needs_attention` but leaves the
  metrics unshipped. They go into the next envelope, so every later batch is refused and marked
  `needs_attention`, and no officer retry exists yet.
- `recordPhotoTime` writes `failures: u.row.attempts - 1` on its update path without the `max(0, …)` that
  its insert path has. A media row moved to `sent` by `_storeUploads` (no `markSending`, attempts 0) can
  therefore produce `-1`.
- Fix:
  - In the attention branch of `_failed`, mark the batch's metrics shipped. Telemetry can be lost; entries
    cannot. Pass `metrics` into `_failed`.
  - Use `Value(max(0, failures))` on the update path too.
- Test: a server that answers 422 to the first push. The next push carries `metrics: []`.

**P2-5. Signing in does not start a sync** (`apps/mobile/lib/core/sync/sync_service.dart:105-116`)
- The triggers are app open, resume, the outbox insert, connectivity and the backoff timer. Sign-in writes
  only the Session row (`SessionDao.write`, `insertOnConflictUpdate`). On a fresh phone the first
  reference download (crops, rules, plots) and the first pull wait for a resume or the 15-min task. A
  farmer who signs in at the FPO office and then walks to the field offline has no bundles.
- Fix: in `start()`, add
  `db.tableUpdates(TableUpdateQuery.onTable(db.sessionTable)).listen((_) => afterSave())`. This reuses the
  debounce, and a locale or Wi-Fi-only toggle only adds a harmless run.
- Test: `start()` with no session, `signIn(db, 'user-1')`, then one `GET /v1/sync/reference` within
  600 ms.

**P2-6. Foreground and background runs do not exclude each other, and can mark a photo that is already on the server as `file_missing`** (`apps/mobile/lib/core/sync/photo_uploader.dart:100-126`)
- The mutex is per isolate. The Android WorkManager task runs every 15 min, also while the app is in the
  foreground.
- Concrete case: the background run confirms photo X and deletes its full-size file. The foreground run
  had already listed X in `ready`, and its `readAsBytes` then throws `FileSystemException`. `_failed`
  writes media `failed` over `done` and outbox `needs_attention file_missing`. An officer sees a false
  missing photo.
- The report covers duplicate pushes (the server deduplicates them) but not this case.
- Fix, either way:
  - Smallest: in `_failed`, when the error is a `FileSystemException`, re-read the media and return when it
    is `done` or `purgedAt != null`.
  - Better: a cross-isolate lease in SyncState (`run_lease` = start time, taken in a transaction at the
    start of `_run`, skipped if younger than 2 min, cleared at the end).
  - Add one test for the chosen guard.

### P3

1. **Lost "one more run" in a narrow window** (`sync_service.dart:146-152`): `_running` is cleared in
   `whenComplete`, one microtask after `_loop` returns. A `runOnce` that lands in between (for example the
   continuation of a probe) sets `_again` on a loop that has already ended, so the request is dropped
   until the next trigger. Fix: clear `_running` in a `finally` at the end of `_loop` and drop
   `whenComplete`.
2. **`refreshUploadUrls` skips the 256 KB trim** (`outbox_processor.dart:46-51`): up to 50 entries are
   re-pushed without a size check, and a 413 marks every stale photo `needs_attention`. Reuse the trim loop
   from `_pushBatch`.
3. **Metrics are not filtered by user** (`sync_metrics_dao.dart:23`, used at `outbox_processor.dart:120`):
   user A's telemetry (entry ids, timings) goes out under user B's token. Join `entries.enteredByUserId =
   c.userId` (D-029 consistency; no PII).
4. **The presigned URL stays in `Media.uploadUrl` after `done`** (`photo_uploader.dart:180-183`): storing
   the URL until confirm is in the spec (mobile-design §2/§3, needed for kill safety), but it is never
   cleared afterwards. Set `uploadUrl: Value(null)` in `_received`. While there, reuse
   `mediaDao.markUploaded` instead of a second "done + objectKey" write. The media_dao.dart:4 header
   already names it as an M02 caller.
5. **The D-003 comment is stale** (`outbox_processor.dart:157-161`): "/sync/pull and /sync/reference are
   not in main's spec yet" is no longer true after B07. Rewrite the ADV (JSON payload stays JSON; the
   contract test pins keys) or move to the typed client. TODO "M02 decisions to ratify" already asks for a
   D-003 amendment.
6. **Wrong caller in a header** (`enum_wire_names.dart:4`): it names `test/sync/enum_wire_names_test.dart`,
   which does not exist. The checks are in `test/sync/contract_test.dart`.
7. **The backoff is not visible "in logs" on a device** (`outbox_processor.dart:257`): `developer.log`
   goes to the VM service only, not to `flutter logs` or logcat. The Verifier's "2/4/8 s in logs" check
   needs DevTools, or a `debugPrint` mirror in debug builds.
8. **`recordPhotoTime` overwrites the ack row's `failures`** (`metrics.dart:32-33`): the push-attempt
   count is replaced by the PUT-failure count. Add the two instead, or keep the push value.
9. **The background task keeps a stale `apiBaseUrl`** (`background_scheduler.dart:32`):
   `ExistingPeriodicWorkPolicy.keep` keeps the first `inputData` across app updates. Use `.update`, which
   keeps the timing and refreshes the input.
10. **No test for the real-body 256 KB trim** (`outbox_processor.dart:123-126`): this is new loop logic.
    Add one test: two 200 KB entries go out as two pushes, and one 300 KB entry still goes alone.
11. **No test pins `extra['secure']`** on the push, confirm, pull and reference calls. Add one harness
    assertion that every `/v1/sync/*` request carries the marker. M06's interceptor depends on it, and the
    worker checked it only by reading the source.
