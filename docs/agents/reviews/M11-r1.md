`moistureVerdict` and `declaredVsComputed`, M09's `FieldRules.parse`, `NumberPad`, `FarmerButton`,

## D-034 split: **accepted** (must be renumbered, P3-1)

Receiving a lot offline and grading a batch from an online list is the smallest honest reading of the contract.
Grading readings must carry `batch_id` (a UUID). The grade engine reads only readings tagged with that batch
(`compute_grade_for_batch`), and `QualityReadingIn` has no batch-code field.

The alternative was to save offline against a scanned batch QR. It does not work today. B10's batch QR encodes
`{PUBLIC_BASE_URL}/b/<code>`: a code, not the id (B10 report row 17). The phone has no batch table to map a code to
an id. A typed code would hit the same problem, and typing is banned. So offline grading needs a `batch` pull entity
(schema v3) or a server that accepts `batch_code`. Both are outside M11, and the ADR's "Revisit" section names
them. After B10 merges, scanning the batch QR to pick from the cached list is a cheap follow-up (P3-7). It is not a
P2.

## Findings

### P1

**P1-1: the Instruments table is never filled, so no meter reading can be saved on a real phone**
(`apps/mobile/lib/features/qc_home/qc_common.dart:411-415` `qcInstrumentsProvider`. It only reads Drift.)

- Nothing writes `Instruments` on main. The server has no `instruments` bundle part (`events/schemas.py:386-399` `BundlePart` has none). The pull has no instrument entity (`pull_service.py` `Entity`). M02 mirrors only `plots`.
- So on a real device: intake moisture is blocked with "No meter on this phone". Grading moisture cannot be entered as an instrument reading. Visual is refused for moisture (`source_not_allowed`), so the grade preview stays grey for every batch. Two of the five acceptance lines can only pass in the test harness.
- M11's declared paths are `apps/mobile/**`. The worker's claim that `core/db` and `core/sync` are "outside M11" is wrong for this WP.
- **Fix (M11, about 20 lines + 1 test):**
  - Make `qcInstrumentsProvider` first try `ref.read(apiClientProvider).api.getQualityApi().listInstrumentsV1InstrumentsGet(active: true)`. The endpoint already exists in the generated client (`quality_api.dart:789`), and the route is `AnyRole` (`quality/router.py:171-183`).
  - Upsert the rows into `db.instruments` with `InsertMode.insertOrReplace`, inside one `db.batch`. Skip rows with a null `calibration_due_on`: the server refuses them anyway.
  - On `DioException` with no response, fall back to the cached rows. That is the same online-list pattern D-034 already accepts for batches, and it keeps working offline after one online visit.
  - Add a `DECISION D-036` line, or extend the ADR (the instrument mirror lives in M11 until B07/M02 serve it).
  - Add one `qc_screens_test` case: the fake API returns one meter, then the row appears and stays after going offline.
- **Hand-off stays:** a B07 bundle part `instruments` plus an M02 mirror, for refresh without opening QC screens online. Keep the TODO line, but reword it. Correct main's `38cc686` TODO line too: it says "the `instruments` bundle part exists server-side", which is false. No such part exists, so the hand-off is B07 (add the part, with `calibration_due_on`) + M02 (mirror it).

### P2

**P2-1: one source and instrument choice is stamped on every grading reading**
(`apps/mobile/lib/features/qc_grading/grading_screen.dart:52`, `:81`, `:158-164`, `:259-260`)

- `_source` is one value for the whole form.
- Pilot case: the officer picks the Delmhorst moisture meter, because moisture needs an instrument. Then extraneous matter, unripe and broken pods are saved as `source: instrument`, `instrument_id: <moisture meter>`. The flow test asserts exactly this (`qc_flow_test.dart:180-182`).
- If the officer picks "Visual" instead, moisture is refused. So the officer cannot record the true provenance of every reading. FR42 requires instrument ID and source per reading, and FR51 shows the source on the public page.
- **Fix:**
  - Store the source per parameter: `final _sources = <String, String>{}`. The picker edits `_sources[_selected]`, and `Reading(... source: _sources[p.code] ?? 'instrument')`.
  - In `_save`, use `_sources[r.parameterCode]`. The blocker "Pick the instrument…" applies when any typed parameter has no source.
  - Optionally filter meters to `moisture_meter` when the selected parameter is `moisture`.
  - Update the flow test: meter for moisture, visual for the other three. Assert both.
  - Remove "one source for all readings" from the TODO deferred line. It is fixed, not deferred.

**P2-2: a phone intake does not receive the lot on the server, and the code says it does**
(`apps/mobile/lib/features/qc_intake/intake_screen.dart:272-273`, the report "Save path", `docs/adr/D-034.md` §Consequences)

- On the server a lot is received only by `POST /v1/intakes`. That route is FPO-admin only and requires `processor_id` and `sale_date` (`lots_batches/router.py:210`, `schemas.IntakeIn`). It writes `lot_intakes` and moves the lot to `received`. Batch creation and farmer shares read `lot_intakes` (`service.py:866-868`).
- The phone pushes an `intake` **event version**. `events/service.py` stores it on the lot timeline and does nothing else: there is no `create_intake` call.
- Case: QC officer receives a 230 kg lot. The portal's "Ready lots" (received) never lists it, and `POST /v1/batches` cannot include it, until an admin re-enters the intake on the portal. The two records can then disagree.
- The shortcut comment "the server knows the FPO's processor from the intake route" is false: the phone never calls that route.
- **Fix (M11 part):**
  - Correct the comment to: `// shortcut: this is the lot-timeline intake event; the lot is received (lot_intakes, status received) only by POST /v1/intakes (FPO admin). Until B09 links them, the admin also records the intake on the portal.`
  - Add a Risks line to the report and a TODO line.
- **Escalate to Architect-Gate** with the B09 follow-up options:
  - (a) the sync handler for an `intake` event from a QC officer calls `lots_batches.create_intake` with the FPO's processor, or
  - (b) open `POST /v1/intakes` to `QC_OFFICER` and add an `intake` push kind that M11 sends instead of the event.
  - Either way the phone payload may need `processor_id` and `sale_date`.
- M11 is not blocked on the ruling. It is blocked on the honest comment, report and TODO.
