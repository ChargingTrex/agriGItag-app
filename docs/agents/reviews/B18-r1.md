## Answers to the focus questions

1. **Does the signature bind the length, and do phones still upload?** Yes and yes (see the verdict). `presign_put`
   passes `ContentLength` as a Param; botocore serialises it as the `Content-Length` header and SigV4 query auth
   signs it (it is not on botocore's unsigned-header list). The ID-document caller passes no size and keeps the
   old behaviour. Old URLs issued before deploy stay unsigned until they expire (15 min); harmless.
2. **`verify` size + 1 read.** Exact size: reads all, `len == size`, hash decides. Bigger: reads size + 1, length
   differs → `checksum_mismatch`, at most 2 MiB + 1 in memory. Shorter or empty object: `len < size` (size is
   `> 0` by schema) → `checksum_mismatch`. A short read from the stream cannot happen before EOF (urllib3 /
   `BufferedReader.read(n)` block for `n`); if it did, the result is a fail-safe flag, not acceptance.
   `make_variants` runs only after `verified`, where `len == size`, so its bounded read is the whole file.
   Reusing `checksum_mismatch` is honest: it is a `PhotoStatus`, not an `AppError`, and the officer's flag
   `photo_checksum_mismatch` says "the stored file is not the one the phone hashed", which is true of a wrong
   length too. Since the PUT now signs the length, only a writer that bypasses the URL can reach this branch. No new
   registered code is needed; the oversize declaration is refused by the existing per-entry `validation_error`.
3. **2 MiB constant vs D-017.** D-017 governs which fields are mandatory and which features are on. A byte ceiling
   at a trust boundary is not a field rule; it was a constant before and stays one. 2 MiB is about 6x the M04
   photo (≤ 350 KB, q40 floor at 1600 px) and 4x a 30 s voice note at any bit rate the recorder uses. No
   `shortcut:` needed. `openapi.json` `maximum` follows; neither generated client embeds the number.
4. **Builder lint on failure.** The details are `{loc: [file, line], msg, type: rule}`; the matched text is never
   stored (integration test asserts `"112/3"` is absent). Nothing is written to S3, so the previous built page
   stays live (the integration test proves zero objects for a first build). `PublicRecordInvalidError` is not in
   the task's `autoretry_for`, so it fails once, like the existing schema branch. The lint runs inside the same
   `publishing.build_page` task, under the batch row lock, with the same (unchanged) Celery limits; the regexes are
   bounded (`{0,40}`, `{0,80}`), so no runaway time on a ~100 KB page. `publish` still answers 202 and still marks
   the batch published before the build (the Verifier's earlier P3); this change adds one more way to land in a
   failed build, but only on a real leak or a false positive, so it does not make that P3 materially worse.
5. **Move + symlink.** `infra/scripts/privacy-lint.py` is a git symlink (mode `120000`) to
   `apps/public-page/agritrace_page/privacy_lint.py`; the only content change is two header lines. CI
   (`ci.yml` interrogate over `infra/scripts`, the QA self-tests), `qa/tests/test_privacy_lint.py` (`LINT = ...
   infra/scripts/privacy-lint.py`), `page.robot` and `tools/check_output.sh` all reach the same file.
   `interrogate` covers it from both places (both 100 %). Acceptable on macOS/Linux CI; the Windows note is P3-2.
6. **Is audit finding 3 closed?** Yes. The audit's fix was "scan `page.html` and `page.data_json` before `_write`";
   the `schema.py` pattern change was explicitly the stopgap "if that waits". Both checks fail the build the same
   way (row `failed`, `public_record_invalid`, nothing written), so adding the patterns to `schema.py` would be a
   second copy of the same rule. Not required.
7. **Docs, ledgers, Ponytail.** Touched functions keep full Google docstrings (`presign_put`, `upload_instruction`,
   `_read_object`, `verify`, `privacy_hits`, `build_page`); the builder header names `privacy_hits`. CHANGELOG line

## Findings

What this change does: the photo upload link now also locks the file length, so storage refuses a file of
another size; the ceiling drops to 2 MiB and the verify task reads at most one byte past the declared size. Every
public page is now run through the privacy linter before it is written; a hit fails the build and writes nothing.

### Should fix

1. **The officer cannot tell what to fix when the linter fails a build** (`apps/api/agritrace/modules/publishing/builder.py:641`)
   - **What this is:** `privacy_hits` returns `{"loc": [file, line], "msg": "privacy lint hit", "type": rule}`.
     The portal (`apps/portal/src/features/batches/PublishSection.tsx:134`) prints `loc.join(' › ') + ': ' + msg`
     and does not show `type`.
   - **Problem:** The officer sees `index.html › 212: privacy lint hit` and `data.json › 1: privacy lint hit`
     (`data.json` is one line). Neither the kind of leak nor the record is named, and the registry's how-to-fix
     says "read `details` (field path and reason)". The batch stays on a failed build until someone reads the
     server row.
   - **Fix:** name the rule and where free text comes from in `msg`, one line:
     `"msg": f"the page shows what looks like a {rule.replace('_', ' ')}; check the free-text fields (village, processor address, seed variety, farmer name)"`.
     Keep `type` as is. Optionally assert `"phone" in h["msg"]` in `test_privacy_hits_refuse_free_text_leaks`.
   - **If we skip it:** the first real hit (or false positive) becomes a support ticket instead of a two-minute fix
     by the officer.
