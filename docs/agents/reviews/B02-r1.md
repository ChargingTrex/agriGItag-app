**Verdict: FAIL.** There is 1 P1: the office PIN hash is written into the append-only `audit_log`. There
are also 7 P2s (6 for r2 to fix, 1 for the Architect-Gate to decide) and 13 P3s. The core design is
sound and the P00 contract is honoured:
- the `pin_token` is single-purpose, and nothing (refresh token, role, FPO) is released before the PIN;
- tokens are typed, HS256 is pinned and the claims are required;
- refresh rotation runs under a row lock;
- tenant scoping answers 404;

## Findings

### P1

**P1-1: Office PIN hashes go into the append-only `audit_log`, forever.** Locations: `identity/models.py`
`User(Audited, …)` with `pin_hash`, and `core/audit.py` `_diff`.
- *What happens:* `verify_pin`'s first-PIN path and `set_pin` update `users.pin_hash`. The flush listener
  writes `{"pin_hash": [old, new]}` into `audit_log.diff`. `audit_log` has a trigger that forbids UPDATE and
  DELETE. Reporting's audit export (B10) and any compliance view read it.
- *Why it is P1:* a 4-digit PIN has 10⁴ values, so its Argon2id hash falls to a laptop in minutes. The hash
  is effectively the PIN.
  - Every PIN an office user has ever had becomes permanent and cannot be redacted. That includes every
    backup and every future export.
  - The set of people who read `audit_log` is wider than the set who read `users`.
  - This is credential material in a log (CWE-532; ASVS V7.1.1).
  - D-024 lists it as a compromise, but nothing is gained by it. Once production rows exist it cannot be
    undone, while today it costs a few lines.
- *Fix:* redact in `_diff`. Either keep a module constant `_REDACTED = {"pin_hash"}`, or read column
  `info={"audit": "redact"}`, which keeps the knowledge in the model. Write `"[redacted]"` in place of the
  values. The `pin_attempts` and `pin_locked_until` diffs stay, because they are useful security events.
  Add one unit test (`audit_rows` on a `User` with a changed `pin_hash` contains no `$argon2`). Update the
  D-024 compromise bullet and the `models.py` DECISION comment.

### P2

**P2-1: A cookie-sourced refresh token can come back in the JSON body.** Location: `router.refresh`
(`token = body.refresh_token or request.cookies.get(...)`), then `_deliver`, which keys only on
`X-Client: web`.
- *Attack:* a script on the portal origin (XSS) calls `fetch('/v1/auth/refresh', {method: 'POST', body: '{}',
  headers: {'Content-Type': 'application/json'}})` without `X-Client`. It receives a fresh, never-expiring
  refresh token in the body and can use it from anywhere. That defeats the purpose of the httpOnly cookie
  (D-022's ADV). The same request also leaves the browser holding a rotated-out cookie, so the next normal
  refresh is treated as reuse and signs the user out.
- *Fix:* remember where the token came from. When it came from the cookie, always deliver through the
  cookie and null the body field:
  `from_cookie = body.refresh_token is None`, then `_deliver(..., web=_is_web(request) or from_cookie)`.
  Add one test: cookie present, no `X-Client` → body `refresh_token` is null and `Set-Cookie` is present.

**P2-2: Revoked access tokens come back to life when the device signs in again** (ASVS V3.3.1).
Location: `core/auth._device_active` checks only `revoked_at IS NULL`, and `_open_session` clears
`revoked_at`.
- *Scenario:* a thief's access token, or the user's own before logout, is killed by logout or by reuse
  detection. When the owner signs in again on the same device within 15 minutes, `revoked_at` is cleared
  and the old token passes again until its `exp`.
- *Bound:* at most 15 minutes. Still, it breaks the guarantee D-024 states ("logout and reuse detection
  take effect on the next request").
- *Fix:*
  - add `devices.signed_in_at` (timestamptz, nullable) to 0002, which is still unmerged;
  - set it in `_open_session` only for OTP/PIN sign-ins, not for refresh;
  - add it to the core `DEVICES` handle;
  - refuse tokens with `iat < floor(signed_in_at)`.

  The same check also stops the P3-4 `pin_token` replay, if `_bind_device` stamps it. Add a unit test on
  the comparison and one integration test (logout, sign in again, the old token → 401).

**P2-3: Anyone who knows a device id can sign that device out.** Device ids are not secret:
- `ConsentOut.device_id` shows the officer's device to the assisted farmer and to every role of the FPO,
  viewers included;
- `DeviceOut` shows it in `/me`;
- it is the prefix of every refresh token.

There are two ways in:
- (a) `refresh_outcome` classes any token that does not match as `reused`, so
  `POST /v1/auth/refresh {"refresh_token": "<victim device id>.x"}` revokes the victim's device.
- (b) `_bind_device` rebinds any `device_id` to whoever passes their own OTP, which signs the owner out.

A farmer can keep their field officer signed out, and each sign-in costs the officer an SMS plus the PIN.
- *Fix:*
  - (a) Keep `devices.prev_refresh_token_hash` (column in 0002) and set it at rotation. Only a match on the
    previous hash is `reused`; any other token is a plain 401 and changes nothing. This is the standard
    refresh-token family check, and it still catches the stolen-token race D-024 describes.
  - (b) In `_bind_device`, refuse with 401 or 409 a device that is currently active (`revoked_at IS NULL`)
    for a different `user_id`. The shared family phone signs out first, which the app does anyway.
  - Add tests for both.

**P2-4: There is no ceiling on OTP guesses or SMS per phone** (ASVS V2.2.1, L1). Location:
`request_otp`. The only limits are 5 guesses per challenge and 1 challenge per 60 s.
- *Guessing:* 7,200 guesses a day at one phone is about 0.7 %/day of the 10⁶ space, or about 20 % over a
  month. For farmers the OTP is the whole credential.
- *SMS:* the same loop makes the platform send about 1,440 SMS a day to each registered number. That costs
  money and harasses the farmer. There is no per-IP limit in front.
- *Fix:* in the same query, count the phone's challenges in the last 24 h and answer 429 `rate_limited`
  with `details.retry_after_s` above a cap (10 is generous for a real user). Add one test. The per-IP limit
  stays a D-024 "Revisit" item.

**P2-5: The PIN can be changed without the current PIN** (ASVS V2.1.6, L1). Location: `POST /v1/auth/pin`
→ `set_pin`.
- *Scenario:* the session lives on the phone for the whole season, with no PIN prompt on app open (D-024).
  Anyone holding the unlocked phone, or a 15-minute access token, can choose a new PIN. That locks the
  real owner out of sign-in on any other device.
- *Fix:* `PinChangeIn {current_pin, pin}`. When `pin_hash` is set, verify `current_pin` through the same
  `pin_outcome` lockout (`pin_invalid` / `pin_locked`). This is an additive request body; P01 has not
  built the screen yet.

**P2-6 (Architect-Gate decision): The first PIN is chosen by whoever passes the first OTP.** Location:
`verify_pin` when `pin_hash IS NULL`.
- *Gap:* the PIN exists to stop the SIM-swap / shared-phone attacker (Arch §Security). Until the real user
  signs in for the first time, it gives no such protection. Worst case: an `fpo_admin` whose account was
  provisioned but not yet used.
- *Options:*
  - (a) accept for the pilot, because officers are provisioned in person and sign in the same day. Record
    a TODO and a D-024 "Revisit" line;
  - (b) B03's user creation sets an admin-issued one-time initial PIN, with a `must_change` flag, at least
    for `fpo_admin` and super-admins;
  - (c) allow the first-PIN path only within N days of the user's `created_at`.
- *My recommendation:* (a) now and (b) in B03.

**P2-7: A super-admin can sign in without a PIN.** Location: `verify_otp`:
`if membership.role == Role.FARMER: return await _open_session(...)`.
- *What happens:* `_account` picks the oldest membership. When that is `farmer` and `is_super_admin` is
  true, the session carries `sa=true` and `roles` includes `super_admin`, with no PIN.
- *Status:* no route lists `super_admin` yet, and it depends on how B03/B12 provision users. But it is the
  most privileged flag, and the fix is one line.
- *Fix:* `if membership.role == Role.FARMER and not user.is_super_admin:`. Add a test.

### P3

- **P3-1: One key for two purposes.** The OTP HMAC uses `JWT_SECRET` directly. Derive a separate key once
  (`hmac.new(secret, b"agritrace-otp-v1", sha256).digest()`), or add an `OTP_HMAC_KEY` setting. This is
  one line and also lets the two secrets rotate separately.
- **P3-2: `otp/request` timing oracle.** Only known phones pay `to_thread(send_task)`, a broker round trip.
  Enqueue through `BackgroundTasks` after the 204, or do an equivalent no-op for unknown numbers.
- **P3-3: No clock-skew leeway.** PyJWT rejects `iat` in the future with no leeway, so API containers whose
  clocks differ by a second give spurious 401s. Pass `leeway=timedelta(seconds=30)` to `jwt.decode`.
- **P3-4: The `pin_token` is not single-use.** It can be replayed within its 5 minutes, even after logout,
  to open another session (the PIN is still needed). The P2-2 `signed_in_at` check closes it if
  `_bind_device` stamps it. Otherwise store the `jti`.
- **P3-5: Assist sessions never expire.** A session the officer forgets to end keeps `on_behalf_of` on
  later entries indefinitely. Consider `started_at > now − 12 h` in `_assist_farmer` (a product choice).
  The farmer's FPO is checked only at start, which is fine while a token carries one FPO. Re-check when
  the FPO switch lands.
- **P3-6: The super-admin scope is undefined.** `assert_same_fpo` does not let `sa` cross FPOs, and
  `_account` needs a membership to sign in at all. This is correct and fails closed. Note it for B03 (GI
  region versions) and B10 (compliance export), and add a D-024 "Revisit" line.
- **P3-7: No security event log.** OTP failures and locks, PIN locks and refresh reuse leave no log line or
  audit row (`devices` and `otp_challenges` are not audited). This is ASVS V7.2.1 (L2). Add structured
  log lines, with no codes or tokens, when observability lands. Add a TODO entry.
- **P3-8: Refresh tokens never expire.** D-024 lists this under "Revisit". An idle expiry is one comparison
  in `refresh` (e.g. `last_seen_at > now − 90 d`). This review recommends doing it before the pilot.
  Leave it to the Orchestrator.
- **P3-9: The prod guard depends on `ENV=prod`.** `ENV` defaults to `dev`, so the guard against a weak
  `JWT_SECRET` and against `OTP_DEV_CODE` only works if the deployment sets `ENV=prod`. This is B00 / infra
  scope. Assert it in the ECS task definition, or flip the default.
- **P3-10 (required, R8): DECISION comments.** The report says `core/errors.py` has `DECISION D-024`
  comments, but it has none: only a plain `# Identity (B02, FR1, D-024)` line. `core/auth.py` makes two
  non-obvious choices without a DECISION comment: a DB read per request for revocation, and the typed
  pin token. Add both and correct the report.
- **P3-11: The OTP code reaches the worker in Celery kwargs.** It travels as `payload.code` through
  Valkey. The B11 TODO already says "never log `payload.code`". Add "no `result_extended`, and no kwargs in
  failure logs".
- **P3-12 (B00-wide, informational): docstrings in OpenAPI.** The operation descriptions in OpenAPI
  include the docstrings' `Args:`/`Raises:` blocks, `/v1/healthz` too. A `\f` before `Args:` cuts them
  (FastAPI convention). This is for the Orchestrator, not B02.
- **P3-13: Optional hardening of the PIN lock.** The lock window resets the counter. An escalating lock
  (e.g. after 3 windows in 24 h, a lock that needs an FPO admin) would make an OTP-capable attacker's 60
  guesses an hour harmless.

## Cuts (Ponytail)

The code is lean for what it covers. Service ~900 lines (about half docstrings), router ~380, auth ~350.
The pure helpers are split from the DB code, which makes the security logic unit-testable without a DB.
There are no wrappers or speculative options.
- **Optional:** `_consent_out` is a one-line wrapper around `ConsentOut.model_validate`. Inline it or keep it.
- **Optional:** the `assert user.device_id is not None` in `get_current_user` exists only for mypy. Making
  `CurrentUser.device_id` non-optional would remove it, but that touches B01's signature, so leave it.
- **Do not cut:** the device check on every request. It is what makes logout and reuse detection real.
  The read is one PK lookup.
- The skipped items in the report (FPO switch, idle expiry, `X-Device-Id`, consent paging,
  `Retry-After`, a race-proof rate limit, user creation) are reasonable to skip. Idle expiry (P3-8) and
  the daily OTP cap (P2-4, required) are the only ones this review pushes back on.
