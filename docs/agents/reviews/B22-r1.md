## What this change does

`event_order.run` now gives `order_gaps` only the earliest live event of each type, not every event of the lot.
`_lot_context` selects four plain columns per event (id, type, date, `payload->>'input_id'`) and gets the harvest
and packing kg from one SQL `sum(...) FILTER (...)`, so it no longer builds 1,500 ORM rows and decodes 1,500 JSON
payloads. The three rules Celery tasks retry a `DBAPIError` up to 3 times, with jittered backoff.

## Equivalence (the whole review)

### 1. `event_order`: earliest event per type

`order_gaps(tracks, recorded, new_type, on)` asks one thing per earlier step: "is there any event of type
`step` dated on or before `on`?" It reads nothing else from `recorded` (not the id, not the count). "Some event of
type T is on or before D" is true exactly when "the earliest event of type T is on or before D". So passing the
earliest event of each type gives the same answer for every (event, step) pair, and `run` still loops over every
event, so every subject that was flagged before is flagged now, with the same `missing` list in track order.

The `firsts` line keeps the earliest: it sorts newest first and the dict comprehension lets the last write win.
For equal dates any of the tied events works, because only the date is compared.

The semantics the old code implemented, and the new code keeps, is "a step counts as started once any event of
it exists on or before this date": stage A must not start before stage B has started once. That matches the
`order_gaps` docstring ("no event on or before `on`") and the B08 acceptance. The cases asked for:

| Case | Old all-pairs | New earliest-per-type |
|---|---|---|
| Nursery 5 Sep, ploughing 30 Sep, sowing 20 Oct (B08: no flag) | none (separate tracks) | none (unit test passes) |
| Sowing 20 Oct before nursery 25 Oct (B08: flag) | flag on sowing, missing nursery | same (unit test passes) |
| Re-sowing after harvest | no flag: a ploughing and a nursery exist before it | same |
| Two harvests 14 Feb / 4 Mar, drying 15 Feb (seed lot, demo.py:229–233) | no flag | no flag (e2e passes) |
| Equal dates (nursery and sowing on one day) | `<=`, so no flag | same |
| Earliest sowing undone | dropped by `DEAD_EVENTS` before the rule runs; next sowing is used | same: `firsts` is rebuilt from the live list on every run, so "earliest" moves and the flag re-evaluates |
| Correction moves an event's date | `events.service` sets `Event.occurred_on` from the new version (service.py:494); both read `Event.occurred_on` | same |
| Events of two lots | the query is scoped to `Event.lot_id == lot.id` in both | same |

Brute-force check: 20,000 random lots (0–25 events, 8 types incl. untracked ones, dates packed into 13 days so
ties are frequent) with the crop's real tracks. The old all-pairs loop and the new `run` gave identical
(subject, missing) lists in every case.

### 2. `_lot_context` projection

`LotContext` and `LotEvent` are unchanged, and every lot rule (`event_order`, `practice_tags`, `yield_ceiling`,
`quantity_reconciliation`, `moisture_trail_override`) reads only `LotContext`. `photo_evidence` is an event rule and
does not use this path. So I compared field by field:

| Field | Old | New | Same? |
|---|---|---|---|
| rows filter | `JOIN event_versions ON id = events.current_version_id WHERE lot_id = :lot AND status NOT IN (undone, superseded)` | the same `current` join and `live` tuple, used by both new queries | yes |
| `events` | `(e.id, str(e.event_type), e.occurred_on)` | `(Event.id, str(event_type), Event.occurred_on)` | yes |
| `input_ids` | `p.get("input_id")` truthy, `uuid.UUID(str(...))`, input_application only | `payload->>'input_id'` (JSON null → SQL NULL → skipped), same type filter | yes |
| `has_pest_event` | any `problem` | any `problem` | yes |
| `harvested_kg` / `packed_kg` | Python sum of `Decimal(str(value))` where `unit == "kg"`, None when no such row, then `or lots.*_kg` | `sum((payload->'quantity'->>'value')::numeric) FILTER (event_type = X AND unit = 'kg')`, NULL when no row, then `or lots.*_kg` | yes |

Versions: both read only the current version (`current_version_id` join) of live events. Undone and superseded
events are excluded by the same `DEAD_EVENTS` tuple. A correction replaces the quantity because the join follows the
moved `current_version_id`. The existing correction tests (`test_rules.py:443`, `:611`, 1,350 → 1,150 kg) pass.
`Quantity.value` is a `Decimal` (`core/schemas.py:73`), stored as a JSON string or number. Both `Decimal(str(x))`
and `x::numeric` give the same value and scale, so `details.harvested_kg` strings are unchanged (`"1350"` asserted).
A zero sum is falsy in both, so it falls back to the lot column the same way. D-030 grading loss and D-041 come from
batch/intake sums (`received_kg`, `used_kg`), which this change does not touch.

No new N+1: the old single join became two queries over the same index path (`events.lot_id`, versions pk).

### 4. Retries

- `run_db_task` lets exceptions through (worker/__init__.py), so `autoretry_for` really fires.
- On SQLAlchemy 2 + asyncpg, a deadlock (40P01) or serialization failure (40001) arrives as a generic `DBAPIError`,
  and a connection lost mid-session arrives as `InterfaceError`. All are retried. A deadlock victim now re-runs
  instead of losing the check, which is what B19 needed.
- `IntegrityError` is a `DBAPIError`, so it is retried too. The expected race (two runs inserting one
  `dedupe_key`) is already caught inside `store_flags`' savepoint and never reaches the task. Any other
  integrity, data or programming error now runs 4 times in about 1–8 s and then fails and is logged as before.
  That adds noise but does no harm, because each run rolls back as a whole. Accepted, no change asked.
- `acks_late`: Celery's retry publishes a new message with a countdown and then acks the original. A crash between
  the two gives one extra run, which D-009 already tolerates. Countdowns are seconds, far below the Redis
  `visibility_timeout` (1 h), so the visibility TODO does not apply.
- Gap: see P2-1.

## Findings

### Must fix

None.

### Should fix

1. **P2-1: Postgres restart still loses the check** (`apps/api/agritrace/modules/rules_flags/tasks.py:35-39`)
   - **What this is:** `RETRY` is meant to stop a database error from losing a rules check (audit wave-7 #3).
   - **Problem:** When Postgres is down, restarting or failing over as a task starts, `run_db_task` fails while
     opening its connection with `ConnectionRefusedError` (or `TimeoutError`), both `OSError`. SQLAlchemy does not
     wrap connect errors into `DBAPIError`. I checked this: `run_db_task` against `127.0.0.1:1` raises
     `ConnectionRefusedError`, and `isinstance(e, DBAPIError)` is False. So every check that runs during a database
     restart is dropped without a retry, and the comment says "dropped connection" is covered.
   - **Fix:** `RETRY = {"autoretry_for": (DBAPIError, OSError), ...}` and add "connection refused or timed out at
     connect" to the comment. Rules tasks do no file or S3 I/O, so `OSError` can only come from the connection.
     In `test_check_event_task_retries_a_database_error`, parametrize the first-call error over
     `OperationalError("SELECT 1", {}, Exception("deadlock detected"))` and `ConnectionRefusedError()`.
   - **If we skip it:** a database restart during the BM-07 backlog or a deploy loses flags until that lot is
     checked again. That is the exact failure the add-on was written to close.

### Nice to have

2. **P3-1: only the slow e2e pins "earliest", not "latest"** (`apps/api/tests/unit/test_rules_lot.py`)
   - **What this is:** the whole equivalence rests on `reverse=True` in the `firsts` line.
   - **Problem:** with `reverse=True` dropped (latest event per type), all 632 unit tests and the new integration
     test still pass. Only `tests/e2e/test_reference_batch.py` fails, through the seed lot with two pickings. A
     later "cleanup" would raise false `event_out_of_order` flags on drying between two pickings.
   - **Fix:** one unit test next to `test_sowing_before_nursery_is_flagged_on_the_sowing`: land_preparation 30 Sep,
     nursery 5 Sep, sowing 20 Oct, harvest 14 Feb, drying 15 Feb, harvest 4 Mar →
     `event_order.run(LotContext(LOT, SCHEMA, events)) == []`.
   - **If we skip it:** the regression is caught only by the e2e run, minutes later instead of in under a second.

3. **P3-2: "before" range differs between files** (`CHANGELOG.md` B22 line, `TODO.md` B21 tick)
   - **What this is:** both say the 1,500-event check went from "169–525 ms".
   - **Problem:** the B22 report table and the worker's claim say 163–525 ms (the lowest pre-B22 run is 163).
   - **Fix:** write `163–525` in both lines.
   - **If we skip it:** the numbers disagree when the verifier compares them.
