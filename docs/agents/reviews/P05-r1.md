## What this change does

- **Batch page:** adds a "Labels and exports" section with three buttons, each greyed with its reason:
  - Download labels: the B10 PDF, saved as `labels-<code>.pdf`. Admin or QC officer, after final packing. The section says
    "8 labels per A4 sheet" and "print at 100 %".
  - Download audit CSV: the B11 file, saved as-is. Admin or viewer.
  - Download lots CSV: lot code, farmer, received, packed share and share %, each with a unit column. Built in the browser.
- **`/exports` page (sidebar "Labels & exports"):** downloads the farmers CSV. It reads every cursor page of the dashboard farmer table
  with `?fields=` set to the dashboard's visible columns, through an allow-list.
- **Shared code:** the CSV writer (`exportModel.ts`) does RFC 4180 quoting, CRLF line ends, a UTF-8 BOM and the
  `= + - @ \t \r` formula guard. P04's labels download, with its 40 s revoke, moved here as `saveBlob`, and the duplicate button
  left `PublishSection`.

Load assumed: one FPO admin at a time. The pilot FPO has hundreds to a few thousand farmers and a few dozen lots per batch, so holding
the whole farmer table in memory and making one farmer read per share is fine.

## Findings

### P2

**P2-1. The derived packed share is not labelled as derived, and D-051 misstates what is stored**
(`apps/portal/src/features/exports/exportModel.ts:97`, `BatchExports.tsx:117`, `docs/adr/D-051.md:13,21,42`)
- **What this is:** each lots CSV row has `packed_share` = batch packed kg × share % ÷ 100.
- **Problem:**
  - The header `packed_share,packed_share_unit` reads like a recorded figure.
  - `LotOut.packed` ("On-farm packed quantity in kg, filled at intake", `lots.packed_kg`, Stage 6) is a real per-lot packed figure, and
    the page has already loaded it. An auditor checking FR60's chain (harvested ≥ packed ≥ received) will compare `received` with
    `packed_share` and get it wrong. For example, a lot packed 69 kg on the farm and received 100 kg shows `packed_share` 93.75.
  - The ADR's context (line 13) says the API stores packing "not per lot", which is half true: final packing is per batch, but
    on-farm packing is per lot.
  - Line 42 says "the plan asks for it", but the PLAN P05 row asks only for a unit on every quantity. The request came from the
    Orchestrator's brief.
- **Fix (micro-patch):**
  - Rename the two header cells to `final_packed_share_derived` and `final_packed_share_derived_unit` (exportModel.ts:97).
  - Update the expected rows in `exports.test.tsx:152-153` and `:274`.
  - Change BatchExports.tsx:117 to "…, received kg, the share of the final packed kg (derived: packed kg × share %) and share %".
  - In D-051, write "final packing is recorded per batch (`BatchOut.packed`); `LotOut.packed` is on-farm packing" (line 13), and use
    the new column name (line 21). Replace line 42 with "the Orchestrator's P05 brief asks for it".
  - Optional, same size: add the recorded `farm_packed`/`farm_packed_unit` from `lots.get(s.lot_id)?.packed` (see P3-1).
- **If we skip it:** an audit file shows a computed number as if it were recorded, in a product whose purpose is a trustworthy record.

### P3

**P3-1. The lots CSV leaves out the recorded per-lot quantities** (`exportModel.ts:95-117`)
`LotOut.harvested` and `LotOut.packed` are already loaded, and the batch page shows them for FR60 reconciliation. Two `...qty()` calls
would add them. This is optional; record it in TODO if skipped.

**P3-2. The lots CSV can save placeholder farmer names** (`BatchExports.tsx:121`)
The button is enabled once the lots load, but the farmer name reads (`useFarmerNames`) can still be pending. A quick click on a slow
link saves `Farmer 00000000` instead of the names. The page test passes only because it waits for the "Muthu Kumar" cell (:264).
- Fix: also grey the button while any share's name is still the fallback, for example
  `batch.shares.some((s) => farmerName(s.farmer_id).startsWith('Farmer '))` → reason "Loading farmer names…".
- Alternative: return a `pending` flag from `useFarmerNames` (P03 helper, one caller more).

**P3-3. The audit CSV has no BOM** (`BatchExports.tsx:61`)
B11 writes `csv.writer` text with no BOM, so `entered_by_name` and `reason_text` in Tamil show as garbage when the file is
double-clicked in Excel. That is the very problem D-051's BOM solves for the other two files. Prepending the BOM is not double
escaping:
`saveBlob(new Blob(['﻿', blob], { type: blob.type }), …)`.
Alternatively, add a TODO for B11 to write `utf-8-sig`.

**P3-4. The privacy regexes miss spaced phone numbers** (`exports.test.tsx:24`, fixture `:192`, `:332`)
`/(?:\+91)?[6-9]\d{9}/` does not match `+91 98765 43210` or `98765-43210`, and no fixture uses those forms. The allow-list is the real
guard, so this only weakens the backstop.
- Fix: `const PHONE = /(?:\+?91[\s-]?)?[6-9](?:[\s-]?\d){9}/;` and set the `/exports` mock row's `phone` to `'+91 98765 43210'`.
- The coordinate regex (`COORDS`) already covers both `9.58, 77.96` and `POINT(77.96 9.58)`.

**P3-5. No file-level test of a Tamil name** (`exports.test.tsx:126`, `:327-335`)
Tamil is tested only in `csvCell`. The `/exports` test does not check the BOM bytes and uses English names only.
- Fix: set `name: 'முத்து குமார்'` on one mock row and assert `head` is `EF BB BF` and the decoded text contains the name.

**P3-6. A header misses an FR** (`BatchExports.tsx:5`)
The labels file is named by the batch ID shown under FR9, but the header does not cite FR9. Add "FR9 (batch ID in the file name)".

**P3-7. Comment lines are too long** (`BatchPage.tsx:10` 162 chars, `mocks/handlers.ts:9` 134 chars)
Prettier does not wrap comments, and every other header line is ≤ 120. Re-wrap both.
