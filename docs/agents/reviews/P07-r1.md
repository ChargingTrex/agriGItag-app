## What this change does

It adds the P07 Playwright suite: `e2e/chain.spec.ts` drives the FPO admin chain twice (OTP sign-in → import and
approve a farmer → clear a flag → Ready lots → create batch → approve grading → final packing → publish → labels
download), `e2e/axe.spec.ts` runs axe-core on the login page and all 14 routes, and `e2e/support.ts` holds the shared
sign-in, navigation and axe helpers. In mock mode the QC phone is simulated by swapping the MSW `grades` map through
a `agritraceMock` global (dev mock bundle only, D-052); `E2E_LIVE=1` runs the same chain on the B12 seed. It also
fixes three real colour-contrast failures, loosens two Vitest waits, and adds the e2e step to the CI `portal` job.

## Focus questions answered

1. **Vitest fixes are test-only and justified.** `checking_holds` ("Checking hold flags…") is P04's deliberate
   fail-closed reason (`BatchPage.tsx:473`, already on main): Publish stays greyed until holds load. Wrapping the
   final-name assertion in `waitFor` matches the page's intended behaviour; it hides nothing. The 15 s
   `asyncUtilTimeout` only lengthens how long a query may wait; every assertion must still become true, and jsdom
   timing is not a performance check. Cost: a real failure now takes 15 s instead of 5 s to report.
2. **Contrast:** there are **three** changes, not four (warning `contrastText`, info `main`, greyed Ready-lots
   rows; HANDOVER.md's "four" is from the WIP note). All are ≥ 4.5:1. Every warning/info use in `src` is a filled
   Chip (`SeverityChip`, `FarmerStatusChip`, PlotPage chip, GI chip) or a standard Alert (MUI darkens the colour for
   its text); nothing uses `warning.main`/`info.main` as text on white, so nothing got worse. Greyed rows keep their
   meaning: disabled checkbox, visible caption with the reason, reason in the accessible name, tooltip, and text still
   lighter than normal rows (5.7:1 vs ~15.8:1). P03 "out-of-GI greyed with tooltip" still holds.
3. **Timeouts / retries:** `retries: CI ? 1 : 0` was already on main. `expect` 15 s and `actionTimeout` 20 s are
   reasonable for cold Vite compiles. They mask no product bug: every gate step asserts its result text, and the
   gated buttons are matched by exact name, so a greyed button fails the step instead of being skipped. See finding 1
   for the one flake these caps cause.
4. **Chain:** it really exercises the UI against MSW: the farmer row leaves "Waiting for approval", the lot then
   shows "No hold flag on this lot.", a `Batch FGP…` heading appears, then "Grading approved", "Packed N", the
   `/b/<code>` link and a `labels-<code>.pdf` download. 320 kg is below the 5000 kg second-sign-off threshold, so no
   second admin is needed. "Twice without reseed" in mock mode only shows the spec repeats: each test gets a new page,
   so MSW starts from its seed. The worker says so plainly. The claim that matters (run 1 leaves data that run 2
   copes with) is the live mode's, and that is the Verifier's job (TODO line present).
5. **Live mode assumptions** are in TODO.md and look realistic against the code: `verify_pin` sets the PIN on the
   first sign-in (`identity/service.py:662`); no platform-by-role check exists in OTP verify; `farmer.yaml` requires
   only `name`; the seed leaves the batch `created` with 20 kg `graded_kg`; the seeded flags are all `warn`, so no
   `open_hold_flag` should block publish; staff phones and `OTP_DEV_CODE` match the seed and compose file.
6. **Privacy:** clean. The only phone numbers are the fake MSW number and the B12 demo staff numbers, typed into the
   login form or the OTP API; the CSV holds a name only; no ID documents, survey numbers or boundaries; CI uploads no
   traces or screenshots.
7. **Documentation:** headers on all three new files and the changed config; JSDoc with `@param/@returns/@throws`
   and side effects on every function in `chain.spec.ts` and `support.ts`; eslint-jsdoc passes; CHANGELOG line
   present; README updated. One stale header (finding 4).
8. **Ponytail:** small overall; reuses axe-core with no wrapper; nits in findings 3–5.

## Should fix

1. **The plot-page flake comes from P07's own 20 s caps** (`apps/portal/e2e/axe.spec.ts:45`, `apps/portal/playwright.config.ts:29`)
   - **What this is:** In the full run, `axe.spec` failed at the `plot` step and `members.spec` "plot page" failed;
     both passed on rerun. The report and TODO call it a P01 screen that "P07 did not change".
   - **Problem:** Both timeouts are P07's. The `plot` step waits only 20 s for the 1 MB MapLibre chunk's progress bar
     to go (`toHaveCount(0, { timeout: 20_000 })`), and the members failure was a `Sign in` click hitting the new
     global `actionTimeout: 20_000` (before P07 a click had the whole 60 s test budget). So P07 ships a known flake
     with a one-number fix available, and the TODO line blames the wrong change.
   - **Fix (micro-patch):** in `e2e/axe.spec.ts` change `{ timeout: 20_000 }` to `{ timeout: 60_000 }` (the map
     chunk, as the TODO already proposes), and in `playwright.config.ts` change `actionTimeout: 20_000` to
     `actionTimeout: 30_000` (the chain still fails fast against its 10-minute budget). Reword TODO.md line
     "P07 P2 flake" to: "the 20 s caps were P07's; raised to 60 s (axe plot step) and 30 s (actions); if it still
     shows in CI, preload the map chunk."
   - **If we skip it:** CI goes green only through `retries: 1` on slow runners, and a second unrelated slow step on
     the same run turns the job red.

3. **The final budget assertion can never fail** (`apps/portal/e2e/chain.spec.ts:308`)
   - **What this is:** Each run calls `test.setTimeout(BUDGET_MS)` and ends with
     `expect(Date.now() - started).toBeLessThan(BUDGET_MS)`.
   - **Problem:** If the run took 10 minutes, Playwright would already have killed it at the timeout, so the last
     line is dead.
   - **Fix:** delete the `expect(...)` line; the timeout is the check, and the logged duration is the evidence.
   - **If we skip it:** one harmless redundant line.

4. **Stale `PORTAL_URL` in a header, and a duplicate sign-in helper** (`apps/portal/e2e/smoke.spec.ts:4`, `apps/portal/e2e/members.spec.ts:17-24`)
   - **What this is:** `smoke.spec.ts` still says it needs "the portal running at PORTAL_URL"; `members.spec.ts` keeps
     its own `signIn` with the same steps as `support.ts` `signIn`.
   - **Problem:** The env var was renamed `E2E_BASE_URL` by this WP, so the header is wrong; two sign-in copies must
     change together when the login form changes.
   - **Fix:** header line → "(mock mode by default; `E2E_BASE_URL` for a running portal)"; in `members.spec.ts`
     replace the local `signIn` with `import { signIn } from './support.ts'` and call `signIn(page)` (the MSW
     number and PIN are the same).
   - **If we skip it:** a misleading header and a second place to fix on a login change.

5. **Two moderate axe items on login** (`landmark-one-main`, `region` on the sign-in page)
   - **What this is:** The login screen has no `<main>` landmark, so axe reports content outside landmarks.
   - **Problem:** Not serious (acceptance holds), but screen-reader users cannot jump to the form by landmark.
   - **Fix:** render the login page's outer container as `component="main"`.
   - **If we skip it:** two moderate findings stay in every axe log.
