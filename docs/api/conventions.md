## Base path and versioning (D-020)

- Every route is under `/v1`. The contract is `packages/openapi/openapi.json` (OpenAPI 3.1, generated by
  `make openapi`); the Dart and TypeScript clients are generated from it and never edited by hand.
- Changes inside `/v1` are **additive only**: new endpoints, new optional request fields, new response
  fields. Removing or renaming a field, tightening validation or changing a type is a breaking change.
  Deprecated fields stay for one season and get a dated entry in `TODO.md`. The previous season's spec is
  kept in `packages/openapi/previous/` and `oasdiff` fails CI on a breaking change.
- Clients must ignore response fields they do not know.

## Authentication (D-024, D-022)

- **Sign-in.** `POST /v1/auth/otp/request {phone}` (E.164) → 204, the same for unknown numbers. A second
  request for the phone within 60 s, or more than `OTP_DAILY_CAP` (default 10) in 24 hours, → 429
  `rate_limited` with `details.retry_after_s`. `POST /v1/auth/otp/verify {phone, code,
  device_id, platform, app_version?}` → `oneOf` discriminated by `kind`:
  - farmers: `{kind: "session", access_token, refresh_token, expires_in: 900, roles, fpo_id}`;
  - office roles (field_officer, qc_officer, fpo_admin, viewer) and every super-admin:
    `{kind: "pin_required", pin_token, expires_in: 300, pin_set}`. No refresh token, role or FPO id before
    the PIN.
  Wrong code `otp_invalid` (422), expired `otp_expired` (422), the 5th wrong code and after `otp_locked`
  (409). Never a bare 401 for a wrong code. The right code for a known account that has no FPO membership left or is suspended (e.g. a farmer the FPO rejected, B14) → 403 `account_inactive`; this answer comes only after the code check, so a phone number alone reveals nothing. A `device_id` that is signed in for another user → 409
  `device_in_use` (sign out on that device first).
- **PIN.** `POST /v1/auth/pin/verify {pin}` with `Authorization: Bearer <pin_token>` → session. When
  `pin_set` was false this first PIN becomes the user's PIN. Wrong PIN `pin_invalid` (422, with
  `details.attempts_left`); the 5th wrong PIN and the next 5 minutes `pin_locked` (409, with
  `details.locked_until`). `POST /v1/auth/pin {pin, current_pin}` (session, office roles) changes it;
  `current_pin` is required once a PIN is set and shares the same lockout. A pin token is spent once its
  sign-in succeeds.
- **Calls.** Send `Authorization: Bearer <access_token>` (15 minutes). A `pin_token` is never accepted as
  an access token. The token's device must still be signed in, and the token must be issued after the
  device's latest sign-in, otherwise 401 `unauthorized`. Optional
  headers: `X-Assist-Session: <assist session id>` (field officer entering data for a farmer; an unknown,
  foreign or ended session → 403 `assist_session_invalid`) and `X-Request-Id` (≤ 64 chars, copied to audit
  rows). The device comes from the token; `X-Device-Id` is not read.
- **Refresh.** `POST /v1/auth/refresh {refresh_token}` → a new session; the presented token is rotated
  out. Presenting the token rotated out last signs the device out: 401 `refresh_reused`. Any other unknown
  token is a plain 401 `unauthorized`. Clients must never
  run two refreshes at once. `POST /v1/auth/logout` signs the device out (its refresh token → 401).
- **Web (portal).** Send `X-Client: web` on verify, PIN verify and refresh. The refresh token then arrives
  only as the httpOnly, Secure, SameSite=Strict cookie `agritrace_refresh` (path `/v1/auth`,
  browser-session lifetime) and `refresh_token` in the body is null; call refresh with an empty body. A
  refresh token read from the cookie is always answered through the cookie, whatever `X-Client` says.
  Mobile keeps the body token.
- **Differences from the P00 portal skeleton** (P01 adapts the portal): verify also needs `device_id`
  (a UUID kept in `localStorage`) and `platform: "web"`; the PIN step uses `pin_token`, not
  `access_token`; office responses carry `pin_set`; the session body has a null `refresh_token` on web;
  `POST /v1/auth/otp/request` answers 204 with no body (P00's mock returned `expires_in_s`).
- `GET /v1/me` returns the user, every membership `{fpo_id, role}` and the session's device. Device ids
  appear in no other response (consent records do not carry them). Assist
  sessions: `POST /v1/assist/start {client_id, farmer_id, started_at?, started_gps?}` (field officer,
  idempotent by `client_id`) and `POST /v1/assist/end {assist_session_id}`.

## Error envelope

Every error response, whatever the status, has this body:

```json
{"error": {"code": "gate_not_met", "message": "The conditions for this step are not met yet.", "details": {"open_flags": 2}}}
```

- `code` is a registered snake_case code; the full list with HTTP status, meaning and fix is generated in
  [error-codes.md](error-codes.md). Raise a subclass of `AppError` (`apps/api/agritrace/core/errors.py`);
  raising an unregistered error fails `make error-codes` and CI.
- `message` is English for logs and developers. Apps show their own English/Tamil text for `code`
  (message key `error.<code>`).
- `details` is optional context (failing fields, ids, limits). For `validation_error` it is a list of
  `{loc, msg, type}`.
- Status use: 401 no or bad token, 403 role or FPO scope, 404 not found (also for other FPOs' data),
  405 wrong method (with an `Allow` header), 409 state conflicts and gate violations, 413 body too large,
  422 validation and plausibility, 429 rate limit, 501 pilot stubs.

## Lists: cursor pagination and `?fields=`

- Every list endpoint is cursor-paginated and returns `Page[T]`: `{"items": [...], "next_cursor": "...",
  "has_more": true}`. Pass `?cursor=<next_cursor>&limit=<n>` for the next page; the cursor is opaque.
  No offset pagination.
- List endpoints accept `?fields=a,b,c` to return only those item fields (lean lists for 2G/3G
  screens, plan §13 C4). Unknown field names are a `validation_error`.
  Allowed names are the item model's fields (computed ones included) minus fields the tenant's
  `fields/<entity>.yaml` disables (D-017); a disabled field is also "unknown". With `?fields=` the items
  carry only the named keys, although the OpenAPI schema shows the full item, so clients that trim must
  type the items as partial. Wired today on `GET /v1/farmers` (B14); other lists add it when a screen needs it.
- Filters and search run on the server as query parameters, never by fetching every page. Exact-match
  filters use the field name (`?status=`, `?village_id=`); `?q=` is a case-insensitive "contains" search
  over the fields the endpoint documents. `GET /v1/farmers?q=` searches name, local name and code, and
  1–4 digits also match the end of the phone: only the suffix `phone_masked` already shows, so a search
  cannot probe the hidden digits.
- Internal fields (D-017 visibility `internal`, e.g. the farmer's phone) never appear in lists: lists
  carry a masked form (`phone_masked`, last 4 digits) and the full value is a separate, role-limited,
  audited read (`GET /v1/farmers/{id}/phone`, FPO admin, `audit_log` action `farmer.phone_reveal`).
- Keep responses flat: return ids and codes of related objects rather than nesting them.

## Quantities carry units (FR58)

- Never send a bare number for an amount. Use `{"value": "12.5", "unit": "kg"}` (`Quantity`).
- `value` is a decimal (string or number) and is non-negative; `SignedQuantity` allows negatives and is used
  only for adjustments and differences.
- Units are short codes: `kg`, `g`, `t`, `acre`, `ha`, `l`, `ml`, `count`, `%`.

## Times

- All API timestamps are ISO 8601 with an offset, e.g. `2026-02-14T09:30:00+05:30`; the server stores and
  returns UTC (`...Z`). Naive timestamps are rejected. Dates without time are `YYYY-MM-DD`.
  (The farmer UI shows dates as "14 Feb"; that is a client concern.)
- **Three clocks** (`ThreeClocks`): every offline capture carries `device_time` (phone clock),
  `gps_time` (from the GPS fix, when there is one) and `server_received_at` (set by the server, clients
  leave it empty). The server compares device time with GPS time, else server time, and raises a
  `clock_skew` flag beyond the configured limit; the entry is still stored.

## Idempotency by client UUID (D-005)

- Entries created offline carry a client-generated UUIDv7 `client_id` that is both the primary key and
  the idempotency key. Sending the same `client_id` again is a no-op that returns the stored result
  (`duplicate`); a `client_id` owned by someone else is rejected.
- Retries are therefore always safe for sync pushes; clients retry only on network errors, 5xx and 429.

## Request limits

- `POST /v1/sync/push` accepts at most **50 entries or 256 KB** per request, whichever comes first. More
  than 50 entries is a 422 `validation_error`; a body over 256 KB is a 413 `payload_too_large`. Photos never travel in the push: each photo is a single presigned PUT
  (D-011) with its SHA-256 checked by object storage.
- Other JSON bodies should stay well under 256 KB.

## Sync (offline-first, backend-design.md §3)

- `POST /v1/sync/push` takes `{device_id, app_version, device_time, metrics[], entries[]}`. Each entry is
  `{client_id, kind, data, assist_session_id?}` with kind `event_version`, `quality_reading`, `plot`,
  `consent`, `flag_resolution`, `farmer` or `assist_session`; the entry's `client_id` becomes the record's id.
  `farmer` (D-031): `data` = `FarmerIn`, field officer or FPO admin only, stored `pending`; a farmer id this
  FPO already has → `duplicate`, another FPO's → `client_id_conflict`; assist context never applies to it.
  `POST /v1/farmers` takes the same optional `client_id` (a resend answers 201 with the stored farmer).
  `assist_session` (D-032): `data` = `{farmer_id, started_at?, started_gps?}`, field officer only, same
  rules as `POST /v1/assist/start` (an id of another officer or farmer → `conflict`). An entry's
  `assist_session_id` (on the entry, never inside `data`) records assist mode for that entry only: it must
  be one of your sessions, open or ended (else `assist_session_invalid`), and the entry's farmer must be the
  session's (consent, plot, event; else `forbidden`). Without it, `X-Assist-Session` applies as before
  (open sessions only). Order: `farmer` → `assist_session` → the entries that use them. Entries are processed in order, each
  in its own transaction, and the response is 200 whenever the envelope parses, with one result per entry:
  `accepted` (stored now), `duplicate` (already stored by you: same `server_id`, upload URLs only for photos
  not yet uploaded) or `rejected` with an error body (`validation_error`, `client_id_conflict`,
  `stale_version`, `forbidden`, `not_found`, `reason_required`, `undo_window_closed`,
  `assist_session_invalid`, `farmer_phone_taken`, `conflict`, `not_implemented_pilot` for
  `flag_resolution` in the pilot, ...). A rejected entry never blocks the
  others; fix it or drop it and send the rest again.
- `event_version` data is `EventVersionIn` (`oneOf` discriminated by `event_type`; one payload schema per
  type, every quantity a `Quantity`). `version_no` 1 is `change_kind=create`; later versions are
  `correct` (field officer or FPO admin, `reason_code` required) or `undo` (the farmer who entered it,
  within 24 hours of its device time). `version_no` must be the current max + 1, else `stale_version`:
  pull, re-apply, resend. Who entered it, the assist session and `server_received_at` come from the
  server, never the body. The REST routes `POST /v1/events/{id}/versions` and `POST /v1/events/{id}/undo`
  use the same rules.
- `plot_id` on a lot event must be the lot's own plot (or omitted); batch events carry none
  (`validation_error` otherwise).
- Photos and voice notes: announce them in `data.photos[]` (`client_id`, lower-case hex `sha256`,
  `size_bytes`, `content_type` `image/jpeg`, or `audio/ogg` / `audio/mp4` for voice notes, optional EXIF
  time and GPS, kept as declared in the audit trail). The result carries one presigned PUT per photo
  (15 minutes); send exactly the returned `Content-Type` and `x-amz-checksum-sha256` headers, then
  `POST /v1/sync/photos/confirm {photos: [{client_id}]}` → `[{client_id, status: received | missing}]`
  (only the user who pushed the entry can confirm its media; anyone else gets `missing`).
  The server then checks SHA-256 (voice notes: only that) and EXIF time (±30 min) and GPS (±250 m)
  against the entry and builds the WebP variants; a mismatch is flagged, never rejected. An expired URL is re-issued by resending the entry.
- `metrics[]` rows (`entry_client_id`, `saved_at`, `acked_at`, `photo_upload_ms`, `failures`,
  `network_type`) are stored for the sync-health dashboard against the token's device.
- **Pull** `GET /v1/sync/pull?cursor=&limit=200` → `{changes: [{entity, op: "upsert", data}], next_cursor,
  has_more}`. Entities: `flag`, `lot`, `event` (the event with its current version and photos, e.g. after an
  officer correction), `intake`, `notification` (your own) and `photo_pending`. Farmers get their own lots,
  plots, events and flags on them; other roles the whole FPO. Apply each change as an upsert by `data.id`;
  duplicates are harmless. Order is (change time, id); the cursor is opaque — store `next_cursor` (it equals
  the sent cursor when nothing changed) and call again while `has_more`. A change is served about 30 s after
  it is written (rows are ordered by transaction start, so very fresh rows wait one pull). `photo_pending`
  (`{id, event_id, event_version_id, status}`) lists, on the last page, your photos still `pending_upload`
  24 h after their entry arrived: resend that entry to get fresh upload URLs. The server records the
  device's last cursor (`sync_cursors`). A cursor this endpoint did not issue → 422 `validation_error`.
- **Photo URLs.** `variants.thumb_url` and `variants.medium_url` in the lot timeline and in pulled events are
  presigned GETs of the WebP variants in the private `evidence` bucket, valid 1 hour
  (`core.storage.presign_get`). The original JPEG (`jpeg_url`) is never listed: it keeps the phone's exact
  EXIF GPS. Do not store the links; load the image, or re-read the timeline for fresh links (a pull does
  not resend an event when only its photos change).

## Reference bundles (B07, plan §13 C2/C3, D-006, D-016, D-017)

- `GET /v1/sync/bundle` → `{parts: {<part>: {version, etag}}}` for the caller. `GET /v1/sync/bundle/{part}`
  → the part body with a strong `ETag` (SHA-256 of the body); send it in `If-None-Match` for a 304 with no
  body. An unknown part → 422. Responses are `Cache-Control: private, no-cache`.
- `version` is an integer. For parts fed by database tables (`plots`, `crops`, `inputs`, `standards`,
  `gi_region`, `villages`) it comes from `reference_versions`, bumped by triggers: the global row plus your
  FPO's row, summed, so it grows with every change. The other parts carry a content fingerprint (first 48
  bits of the ETag hash), which has no order.
- **Delta:** `GET /v1/sync/reference?since=<part>:<version>,<part>:<version>,...`, e.g.
  `since=plots:41,crops:7,fields:90210`. Each part is compared on its own (never one global number: the
  shared sequence orders transaction starts, not commits). A part is returned when its version differs
  from yours or you did not list it; unknown names are ignored; a bare number or a malformed item → 422
  `validation_error`. Answer: `{parts: {<part>: {version, etag, body}}}`, or 304 when nothing changed.
- **Bodies** (the shapes `apps/mobile/lib/core/refdata` parses; docs/agents/reports/M03.md):
  - `plots` `{plots: [{id, farmer_id, code, pin: {lat, lon}, declared_area, area_unit: "acre", gi_tag_id}]}` —
    your plots, or the FPO's for officer roles. Never boundaries or land records.
  - `crops` `{crops: [{id, code, name_en, name_local, gi_tag_id, event_schema: {mandatory: [type], tracks:
    {name: [type in date order]}}}]}` (active crops).
  - `inputs` `{inputs: [{id, name_en, name_local, manufacturer, category, unit}]}` — global list + your FPO's.
  - `standards` `{profiles: {<crop_id>: <full rules JSON>}}` — the published `standards_profile_versions.rules`
    the server grades with (D-006), including `grades`, `fail_grade`, `parameters`, `trail_rules`,
    `lot_gates`, `yield`, `lab_certified_requires`.
  - `gi_region` `{geometry: <GeoJSON Polygon|MultiPolygon>, tolerance_buffer_m, version_no,
    region_version_id, gi_tag_id, simplified_tolerance_m, source_ref, licence, confidence, effective_from}`
    — the region in effect for the active crops' GI tag, simplified (50 m, coarser until ≤ 50 KB). Absent
    from the manifest, and 404 `gi_region_missing` on download, while no region is in effect.
  - `farmer_profile` `{farmers: [{id, code, name, name_local, village_id, status, no_smartphone}]}` — you, or
    the FPO's farmers (assist mode). No phone numbers, addresses or ID numbers.
  - `villages` `{villages: [{id, lgd_code, name_en, name_local, block, taluk, district, pincode}]}` — the
    FPO's district (from the FPO address); empty when the FPO has no district.
  - `fields` `{version, entities, features}` = `fieldconfig.bundle_part(fpo_code)` (D-017).
  - `prompts` `{prompts: []}` — downloadable voice packs beyond the bundled ta/en clips; items will be
    `{lang, prompt_id, key, url}` (none exist yet, D-016).
  - `images` `{images: [{id, kind: "input", key, url}]}` — product pictures of the inputs; `url` is a plain
    link into the anonymous-read `public-pages` bucket (stable, so the ETag is stable; D-016). Only
    non-sensitive assets live there.
  - `calendar` `{calendar: []}` — crop-calendar reminders `{event_type, due_on: "YYYY-MM-DD", prompt_id,
    lot_id?}`; empty until lots carry sowing dates.

## Config: fields, features, imports (D-017)

- **Where.** `apps/api/config/fields/<entity>.yaml` (farmer, plot, lot, quality_reading, village, input,
  `event_<type>` for the 11 event types), `features.yaml`, `tenants/<FPO_CODE>.yaml`. Schema and loader:
  `apps/api/agritrace/core/fieldconfig.py` (Pydantic, unknown keys are errors); routes:
  `agritrace/modules/config/router.py`. The API refuses to start when any file fails the schema; the
  message names the file and key. Edit the YAML in git and redeploy; tenant files are reviewed like code.
- **Field keys.** `name`, `type`, `required`, `enabled`, `visibility` (`public` | `partner` | `internal`),
  `label.en` / `label.ta`, `stage`, `core`. A disabled field is never required and is dropped from
  payloads. `core: true` fields (database NOT NULL) cannot be disabled or made optional by a tenant.
  `extra: forbid` (farmer, plot, village, input) refuses payload keys not listed (`field_unknown`);
  `extra: allow` keeps them. Tenant overrides may change `enabled`, `required`, `visibility`, `label`.
- **Reads.** `GET /v1/config/fields?entity=<name>` → `{entity: [field, ...]}` for the caller's FPO
  (from the token), disabled fields absent; omit `entity` for all. `GET /v1/config/features` → the flags.
  Both send a strong `ETag`; send it back in `If-None-Match` to get 304. The sync bundle part `fields`
  (B07) is `fieldconfig.bundle_part(fpo_code)`: `{version, entities, features}`.
- **Enforced today** on `POST /v1/farmers`, `POST /v1/plots` (also sync-pushed plots through the same
  service) and the imports: missing required → 422 `field_required` with `details.field`. Event, lot and
  reading payloads are served for the forms but enforced only once their modules call
  `fieldconfig.validate_payload`. Public pages may show only `fieldconfig.public_fields(entity, fpo_code)`; a tenant
  may narrow visibility (public > partner > internal) or disable a field, never widen it (refused at
  start-up), and village fields take no tenant overrides.
- **Feature-gated routes** answer 404 `feature_disabled` while the FPO's flag is off:
  `POST /v1/farmers/{id}/id-documents` (`id_document_capture`; needs the farmer's unrevoked
  `data_collection` consent; returns one presigned PUT into the private `id-docs` bucket with the same
  SHA-256 headers as evidence photos) and `GET/POST /v1/producer-groups` (`producer_groups`).
- **Imports.** `POST /v1/imports/{farmers,inputs}` (FPO admin) and `POST /v1/imports/villages`
  (super-admin), multipart field `file`, UTF-8 CSV (BOM allowed), header first, at most 2 MB and 5,000
  rows (413 `import_too_large`). `?dry_run=true` runs every check, including database ones, then rolls
  back. The answer is always 200 `{dry_run, accepted, rejected: [{row, code, field}]}`; `row` is the file
  line (header = 1); `code` is a registered code (`field_required`, `field_unknown`,
  `import_row_invalid`, `import_row_exists`, `farmer_phone_taken`, `validation_error`). A commit writes
  the valid rows in one transaction; a rejected row writes nothing. Keys: villages `lgd_code`, inputs
  name + manufacturer (ignoring case), farmers phone. Farmers without a phone have no key, so after fixing
  rejected rows **re-upload only those rows**. Farmers pick their village with `village_lgd_code`.
  Templates: `GET /v1/imports/{kind}/template.csv` = the tenant's enabled CSV-capable fields.

## Compression and transport

- Responses of 400 bytes or more are compressed with Brotli when the client sends
  `Accept-Encoding: br`, else gzip (`brotli-asgi` middleware). Clients should always send
  `Accept-Encoding: br, gzip`.
- HTTP/2, TLS and CDN caching are terminated at the load balancer / CloudFront in production, not in the
  app (see infra/README.md).
