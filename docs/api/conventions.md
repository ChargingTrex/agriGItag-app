## Base path and versioning (D-020)

- Every route is under `/v1`. The contract is `packages/openapi/openapi.json` (OpenAPI 3.1, generated by
  `make openapi`); the Dart and TypeScript clients are generated from it and never edited by hand.
- Changes inside `/v1` are **additive only**: new endpoints, new optional request fields, new response
  fields. Removing or renaming a field, tightening validation or changing a type is a breaking change.
  Deprecated fields stay for one season and get a dated entry in `TODO.md`. The previous season's spec is
  kept in `packages/openapi/previous/` and `oasdiff` fails CI on a breaking change.
- Clients must ignore response fields they do not know.

## Authentication (D-024, D-022)

- **Sign-in.** `POST /v1/auth/otp/request {phone}` (E.164) → 204, the same for unknown numbers; a second
  request for the phone within 60 s → 429 `rate_limited`. `POST /v1/auth/otp/verify {phone, code,
  device_id, platform, app_version?}` → `oneOf` discriminated by `kind`:
  - farmers: `{kind: "session", access_token, refresh_token, expires_in: 900, roles, fpo_id}`;
  - office roles (field_officer, qc_officer, fpo_admin, viewer): `{kind: "pin_required", pin_token,
    expires_in: 300, pin_set}`. No refresh token, role or FPO id before the PIN.
  Wrong code `otp_invalid` (422), expired `otp_expired` (422), the 5th wrong code and after `otp_locked`
  (409). Never a bare 401 for a wrong code.
- **PIN.** `POST /v1/auth/pin/verify {pin}` with `Authorization: Bearer <pin_token>` → session. When
  `pin_set` was false this first PIN becomes the user's PIN. Wrong PIN `pin_invalid` (422, with
  `details.attempts_left`); the 5th wrong PIN and the next 5 minutes `pin_locked` (409, with
  `details.locked_until`). `POST /v1/auth/pin {pin}` (session, office roles) changes it.
- **Calls.** Send `Authorization: Bearer <access_token>` (15 minutes). A `pin_token` is never accepted as
  an access token. The token's device must still be signed in, otherwise 401 `unauthorized`. Optional
  headers: `X-Assist-Session: <assist session id>` (field officer entering data for a farmer; an unknown,
  foreign or ended session → 403 `assist_session_invalid`) and `X-Request-Id` (≤ 64 chars, copied to audit
  rows). The device comes from the token; `X-Device-Id` is not read.
- **Refresh.** `POST /v1/auth/refresh {refresh_token}` → a new session; the presented token is rotated
  out. Presenting an already-rotated token signs the device out: 401 `refresh_reused`. Clients must never
  run two refreshes at once. `POST /v1/auth/logout` signs the device out (its refresh token → 401).
- **Web (portal).** Send `X-Client: web` on verify, PIN verify and refresh. The refresh token then arrives
  only as the httpOnly, Secure, SameSite=Strict cookie `agritrace_refresh` (path `/v1/auth`,
  browser-session lifetime) and `refresh_token` in the body is null; call refresh with an empty body.
  Mobile keeps the body token.
- **Differences from the P00 portal skeleton** (P01 adapts the portal): verify also needs `device_id`
  (a UUID kept in `localStorage`) and `platform: "web"`; the PIN step uses `pin_token`, not
  `access_token`; office responses carry `pin_set`; the session body has a null `refresh_token` on web;
  `POST /v1/auth/otp/request` answers 204 with no body (P00's mock returned `expires_in_s`).
- `GET /v1/me` returns the user, every membership `{fpo_id, role}` and the session's device. Assist
  sessions: `POST /v1/assist/start {client_id, farmer_id, started_at?, started_gps?}` (field officer,
  idempotent by `client_id`) and `POST /v1/assist/end {assist_session_id}`.

## Error envelope

Every error response, whatever the status, has this body:

```json
{"error": {"code": "gate_not_met", "message": "The conditions for this step are not met yet.", "details": {"open_flags": 2}}}
```

- `code` is a registered snake_case code; the full list with HTTP status, meaning and fix is generated in
  [error-codes.md](error-codes.md). Raise a subclass of `AppError` (`apps/api/agritrace/core/errors.py`);
  raising an unregistered error fails `make error-codes` and CI.
- `message` is English for logs and developers. Apps show their own English/Tamil text for `code`
  (message key `error.<code>`).
- `details` is optional context (failing fields, ids, limits). For `validation_error` it is a list of
  `{loc, msg, type}`.
- Status use: 401 no or bad token, 403 role or FPO scope, 404 not found (also for other FPOs' data),
  405 wrong method (with an `Allow` header), 409 state conflicts and gate violations, 413 body too large,
  422 validation and plausibility, 429 rate limit, 501 pilot stubs.

## Lists: cursor pagination and `?fields=`

- Every list endpoint is cursor-paginated and returns `Page[T]`: `{"items": [...], "next_cursor": "...",
  "has_more": true}`. Pass `?cursor=<next_cursor>&limit=<n>` for the next page; the cursor is opaque.
  No offset pagination.
- List endpoints accept `?fields=a,b,c` to return only those item fields (lean lists for 2G/3G
  screens, plan §13 C4). Unknown field names are a `validation_error`.
- Keep responses flat: return ids and codes of related objects rather than nesting them.

## Quantities carry units (FR58)

- Never send a bare number for an amount. Use `{"value": "12.5", "unit": "kg"}` (`Quantity`).
- `value` is a decimal (string or number) and is non-negative; `SignedQuantity` allows negatives and is used
  only for adjustments and differences.
- Units are short codes: `kg`, `g`, `t`, `acre`, `ha`, `l`, `ml`, `count`, `%`.

## Times

- All API timestamps are ISO 8601 with an offset, e.g. `2026-02-14T09:30:00+05:30`; the server stores and
  returns UTC (`...Z`). Naive timestamps are rejected. Dates without time are `YYYY-MM-DD`.
  (The farmer UI shows dates as "14 Feb"; that is a client concern.)
- **Three clocks** (`ThreeClocks`): every offline capture carries `device_time` (phone clock),
  `gps_time` (from the GPS fix, when there is one) and `server_received_at` (set by the server, clients
  leave it empty). The server compares device time with GPS time, else server time, and raises a
  `clock_skew` flag beyond the configured limit; the entry is still stored.

## Idempotency by client UUID (D-005)

- Entries created offline carry a client-generated UUIDv7 `client_id` that is both the primary key and
  the idempotency key. Sending the same `client_id` again is a no-op that returns the stored result
  (`duplicate`); a `client_id` owned by someone else is rejected.
- Retries are therefore always safe for sync pushes; clients retry only on network errors, 5xx and 429.

## Request limits

- `POST /v1/sync/push` accepts at most **50 entries or 256 KB** per request, whichever comes first. More
  than 50 entries is a 422 `validation_error`; a body over 256 KB is a 413 `payload_too_large`. Photos never travel in the push: each photo is a single presigned PUT
  (D-011) with its SHA-256 checked by object storage.
- Other JSON bodies should stay well under 256 KB.

## Compression and transport

- Responses of 400 bytes or more are compressed with Brotli when the client sends
  `Accept-Encoding: br`, else gzip (`brotli-asgi` middleware). Clients should always send
  `Accept-Encoding: br, gzip`.
- HTTP/2, TLS and CDN caching are terminated at the load balancer / CloudFront in production, not in the
  app (see infra/README.md).
